# Static analysis and code quality

Three tools watch the quality of the code rather than its behaviour. SonarCloud measures duplication and maintainability issues (code smells, bugs, vulnerabilities) of the `master` branch; Codecov measures its coverage. Clang-Tidy gates include hygiene on every pull request and runs an advisory performance audit on request. The [roadmap](./roadmap.md#quality-of-implementation) turns their reports into cleaning work: SonarCloud's duplication ranking orders item 3.4, and item 3.5 widens Clang-Tidy beyond includes. The shared kernels that duplicated code should move to are described in [shared geometry and FEM kernels](./geometry_kernels.md).

## SonarCloud

The analysis runs in its own workflow, `.github/workflows/sonarcloud.yml`, on every push to `master` and on demand (**Actions → sonarcloud → Run workflow**). It never runs on a pull request or a release tag: it is a baseline for the branch, not a gate on a review. It builds nothing and runs no tests, so a scan takes minutes rather than waiting on the hours-long instrumented `coverage` job of `ci.yml`, which a newer push to `master` used to cancel before its scan step was reached. A newer push waits for a running scan instead of cancelling it. The quality gate and the duplication density appear on [sonarcloud.io](https://sonarcloud.io/summary/new_code?id=loumalouomega_meshioplusplus) and as badges in the README.

### One-time setup

The scan is skipped, with a warning in the job log, until the repository is set up on SonarCloud:

1. Sign in to [sonarcloud.io](https://sonarcloud.io) with GitHub, import the `loumalouomega` organization and analyse the `meshioplusplus` repository.
2. In the project's **Administration → Analysis Method**, turn **Automatic Analysis** off. C and C++ are analysed only from CI, with the build's compilation database; automatic analysis would conflict with the CI scan.
3. Create a token (**My Account → Security**) and add it as the `SONAR_TOKEN` repository secret on GitHub.
4. Check that the organization and project key SonarCloud assigned match `sonar.organization` and `sonar.projectKey` in `sonar-project.properties` (`loumalouomega` and `loumalouomega_meshioplusplus`, SonarCloud's defaults for this repository); change the file if they differ.

The next push to `master` then runs the scan. A failed scan (a SonarCloud outage, an expired token) does not fail the workflow.

### What is analysed

`sonar-project.properties` at the repository root holds the configuration. Sources are `src/cpp`, `src/python/meshioplusplus` and `bindings`; tests are `tests`. Excluded from analysis:

- vendored third-party code (`src/cpp/third_party`);
- the amalgamated single header (`src/single_include`), a generated copy of `src/cpp` that would otherwise double every duplication count;
- tables generated by `tools/gen_*.py` (the hex dual schemes, the colormaps, `_format_table.py`, the Nastran HDF5 schema);
- `bindings/wasm` and `bindings/fortran`, which Codecov also ignores;
- test fixtures (`tests/python/meshes`, `tests/python/input`, `tests/fuzz`).

Duplication is measured on library code only (`sonar.cpd.exclusions` lists `tests/**`): tests repeat their setup on purpose. The same property also lists the files that are literal tables alone (`src/cpp/src/detail/node_order.cpp`, the per-format node permutations): the detector normalises literals, so two tables of the same shape match although no entry agrees.

### The compilation database

The C/C++ analyzer needs the exact compile command of every translation unit. The workflow gets it from CMake's configure step alone (`-DCMAKE_EXPORT_COMPILE_COMMANDS=ON`), which is enough because no analysed source includes a header generated at build time. It configures two trees with HDF5, netCDF, zlib and OpenCASCADE on, mirroring the `coverage` job's two builds: the GoogleTest and C API tree, and the Python extension's tree, the only one that compiles `bindings/python/_core.cpp`. A step merges them into `compile_commands.json` and keeps one command per source. Sources neither tree compiles (the other mesh backends' headers) are not analysed.

```sh
# The same database locally, without building:
cmake -S . -B build-sonar -G Ninja -DCMAKE_EXPORT_COMPILE_COMMANDS=ON -DMESHIOPLUSPLUS_BUILD_TESTS=ON -DMESHIOPLUSPLUS_BUILD_C_API=ON -DMESHIOPLUSPLUS_BUILD_PYTHON=OFF
```

SonarCloud reports no coverage: nothing runs under instrumentation in this workflow. Coverage is Codecov's, uploaded by the `coverage` job.

## Local duplication report

SonarCloud reports on `master` only, so `tools/dup_report.py` gives the same kind of number on any checkout, before a change lands. It works like Sonar's copy-paste detector: every C++ and Python source is tokenised, identifiers, numbers and strings are normalised so a renamed copy still matches, and every window of 100 consecutive tokens is hashed; a window found in two places marks its lines as duplicated. A window made of literals and table punctuation (`{`, `}`, `[`, `]`, `(`, `)`, `,`, `:`, `;`, signs and dots), with at most one token in ten anything else, is skipped: it is a run of table rows, and two tables of one shape would otherwise match entry for entry although no entry agrees ([roadmap 8.1](./roadmap.md#code-duplication)). It excludes what `sonar-project.properties` excludes, including the table-only files of `sonar.cpd.exclusions`, and it scans the R binding's C sources (`bindings/r/meshioplusplus/src/*.c`) beside the C++ ones, as SonarCloud does, so the two measures agree on what counts.

```sh
tools/dup_report.py                      # density, top files and largest shared regions, C++ and Python
tools/dup_report.py --lang cpp --top 60  # one language, longer lists
tools/dup_report.py --json report.json   # the full result, for a before/after comparison
```

The density is a guide, not a target. Some repetition is structure: a table of node orders, a list of `py::arg` defaults that is the Python signature, or the typed signature of each MCP tool, which the SDK reads to build its schema. The largest regions shared by two files are the useful part of the report, because each names two line ranges that could call one helper.

The November 2026 measurements, by pass of [roadmap 3.4](./roadmap.md#quality-of-implementation):

| Language | Before the second pass | After the second | After the third |
| --- | ---: | ---: | ---: |
| C++ | 10.6% (26,097 of 245,231 lines) | 9.3% (22,739 of 243,556) | 9.1% (22,041 of 243,222) |
| Python | 11.0% (15,038 of 137,250 lines) | 9.9% (13,481 of 136,357) | 9.2% (12,467 of 135,765) |

What remains at the top is mostly structure the report cannot tell apart from copying: the explicit `py::arg` signatures of `bindings/python/_core.cpp`, the `extern "C"` entry points of `bindings/c/c_api.cpp`, the argument tables of the native CLI and the typed MCP tool signatures. The rest is listed in roadmap 3.4.8 to 3.4.12.

## Clang-Tidy

Two Clang-Tidy runs exist today:

- **Include hygiene, on every pull request.** The `include-cleanup` CI job runs `tools/include-cleanup.sh --check` with the repository's `.clang-tidy`, which enables `misc-include-cleaner` only. Unused includes fail the job; missing-include suggestions are advisory.
- **Performance audit, on request.** `tools/performance-tidy.sh` runs the `performance-*` checks over a separate Clang tree and writes a JSON report; see [the audit](./benchmarks.md#clang-tidy-performance-audit) for its commands and the triage of its first inventory.

Widening Clang-Tidy to the bug-finding and modernisation check families, first as advisory reports and then as a gate on new findings, is [roadmap item 3.5](./roadmap.md#quality-of-implementation).

## Acting on a report

A finding is a candidate, not a mandate. Before removing a duplicate:

- check whether a comment marks the copy as deliberate (a flat-buffer variant of a hot loop, a better-conditioned formula); those stay, and the reason stays with them;
- move the shared code to [the existing kernels](./geometry_kernels.md) (`detail/geometry.hpp`, `src/cpp/src/detail/fem_kernels.hpp`, the topology tables) rather than adding a third copy;
- prove the output did not move: the [determinism check](./benchmarks.md#determinism-check) with a baseline must report identical digests, and the [instruction-count gate](./benchmarks.md#instruction-count-gate) must pass.
