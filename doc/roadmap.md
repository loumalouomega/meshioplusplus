# meshio++ roadmap

Status at time of writing: **v16.30.0** — 79 core formats plus five Python-only physics-ML ones, forty-five mesh operations + six data operations, six language surfaces (Python / C / Fortran / Julia / R / WASM), two viewers plus a browser dataset manager, a Blender add-on, a ParaView plugin, an MCP server, a settings-driven pipeline engine, a dataset-manifest layer with a PhysicsNeMo adapter, and a versioned ABI (`MESHIOPLUSPLUS_ABI_VERSION` 22), sanitizer and fuzzing gates, and a format conformance matrix.

This document lists what is *not* built. Nothing here duplicates shipped functionality; where a feature partially exists, the shipped half is named and the gap is stated explicitly. Release history lives in [`CHANGELOG.md`](https://github.com/loumalouomega/meshioplusplus/blob/main/CHANGELOG.md), not here.

Effort key: **S** = days, **M** = a couple of weeks, **L** = a month or more, **XL** = a project in its own right. An item names a **probe** — the failing test that proves the gap — wherever one is cheap.

## How this file works

- **Sections are ordered, and the order is the recommendation.** Each section states what belongs in it; an item that sounds exciting does not move up for that reason. An empty section is removed, not kept as a placeholder.
- **A closed item is removed, not struck through.** Its history is the `CHANGELOG.md` entry and the feature's own `doc/` page; a partly closed item is narrowed to what remains (the `AGENTS.md` change checklist rule).
- **Every level of the outline is numbered**, so a gap can be cited in an issue, a commit or a release note: a group of work is `section.item` (a `###`/`####` heading, or a bold label line), the work under it `section.item.subitem`, and a bullet under that `section.item.subitem.subsub`. Lists that record a decision rather than open work — *Considered, not queued*, a section's *Landing an item* steps and the [non-goals](#non-goals-and-decisions-taken) — stay unnumbered, because a number here means work to do. The numbering follows the sections, so a new section inserted at the top renumbers the rest, as the rule above says, and so does a section removed once its last item closes (Performance, October 2026: what was §4 onward moved up one).
- **Defect-shaped items go in a *Correctness debts* section at the top, regardless of size** — behaviour that loses data, mis-orients cells, does not terminate on valid input or fails silently is not a feature request, even when the fix and the feature are the same work. None is open today, so there is no such section; the first defect found opens one as §1 and renumbers the rest.
- **An item estimated from a doc, a `.d.ts` or a changelog alone says so** ("verify first") and names its probe; the code has repeatedly been more or less capable than its description.
- **[Non-goals](#non-goals-and-decisions-taken) record decisions already taken**, with their reasons, so they are not re-proposed as gaps.

## 1. Format reach

*Admission: a format a simulation or physics-ML workflow actually exchanges; the missing half of a shipped one is [§3](#_3-reader-and-writer-parity)'s. "Exchanges" means a file that crosses a tool boundary in a real pipeline (mesher → solver, solver → post-processor, solver → training set), not a format that merely exists. Every item names the consumer on the other side of the file.*

Sizes: **S** ≈ days, **M** ≈ two weeks, **L** ≈ a month or more, including tests, docs page and CLI wiring. They assume a new format reuses the shared components rather than growing its own: the card tokenizer (`detail/keyword_card.hpp`), the [node-ordering registry](./node_ordering.md), the Fortran record reader (`detail/fortran_records.hpp`) and the directory sniffing that sequence globs share.

Link legend: unmarked links were opened or returned by a search while this section was written (September 2026); links marked † are quoted from memory and must be checked before relying on them. Vendor documentation portals move often — when a link is dead, search the document title.

Every format this section queued is now read: the native FEM interchange, solver input and result-file readers of v16.5.0 to v16.12.0 (Tecplot, Femap, MFEM, Patran, Abaqus `.fil`, Radioss, Z88, libMesh, Marc, Ansys `.rst`, LS-DYNA and OP2), DOLFINx's ADIOS2 `.bp` ([`vtx`](./formats/vtx.md)) and Tecplot SZL through TecIO ([`szplt`](./formats/szplt.md)) of v16.13.0, and the [vendor-runtime routes](./vendor_routes.md) for the files only a vendor's software reads (Abaqus `.odb`, Marc `.t16`, Femap `.modfem`, Ansys results beyond the native reader). Since v16.17.0 the shared components are used wherever a format's layout fits them, the input decks are written too (Radioss's starter deck, checked with the OpenRadioss starter, and Marc's), Femap writes a series as one output set per step, and every format read but not written names its reason on the [conformance page](./conformance.md#read-only-formats), which a test keeps in step with the registry; [§3](#_3-reader-and-writer-parity) now queues every one of those missing halves. What they still lack is a check against a run of the vendor tool, listed under [Awaiting a licensed run](#_1-2-awaiting-a-licensed-run): take each as soon as a licence, or a file the tool wrote, is in hand.

### Considered, not queued

- **Graphics, CAD, VFX or lab-specific rather than simulation interchange:** 3MF, X3D, DXF, Alembic, OpenVDB, Silo, LAS/LAZ, E57, OBJ materials (`.mtl`).
- **Closed FEM databases with no route worth shipping:** Altair `.h3d` (undisclosed format, SDK not redistributable — Altair's own advice for OpenRadioss is ANIM → VTK, see the [OpenRadioss discussion](https://github.com/orgs/OpenRadioss/discussions/552)); HyperMesh `.hm`; Abaqus `.sim`.
- **No native format to implement:** deal.II (reads and writes UCD, VTK, Gmsh, Abaqus, Exodus — all reachable today); MOOSE (Exodus).
- **Nastran OP4 matrices and punch `.pch`:** matrix and card dumps, not mesh/field exchange; pyNastran serves them.
- **Non-MSC Nastran HDF5 dialects:** incompatible schemas; revisit with a file in hand.
- **Partitioning niche:** gmsh `$PartitionedEntities` (Kratos partitions through MDPA).
- **Operators and tooling, not formats** (listed only because they came up in the same review): ICP registration; mesh duals; cylindrical/spherical coordinate transforms; shell completions.

Revisit any of them when a consumer asks with a file in hand — a real deck or result file, the tool version that wrote it, and the tool that needs the converted output.

## 3. Reader and writer parity

*Admission: a format that reads without writing, writes without reading, or whose one side keeps less than the other returns — and, as in the core-parity section this one replaces, a construct one engine handles and the other cannot. A Python-only path is not "slower from C", it is unreadable from C, Fortran, Julia, R, WASM and the native CLI, none of which has a fallback; a core-only path has no twin to check it against and nothing to run when the core is absent.*

What changed since parity last had a section. The reader/writer triage of September 2026 (then §1.2 of this file) recorded every result file as read-only by design and closed with the Radioss and Marc deck writers (v16.17.0), Femap's output set per step, and the `READ_ONLY` guard (`tests/python/conformance_spec.py`, checked by `read_only_drift` and `test_conformance.py`); the core-parity section closed with the Exodus sets and series writers and pipeline v2. The decision is now the reverse of the first: **every registered format both reads and writes**, which removes the *Result-file writers* and *Readers for the export-only surfaces* non-goals. The rule:

- **Both directions, both engines.** A format reads and writes in the C++ core and in its Python twin, so it reaches every surface: C, Fortran, Julia, R, WASM, both CLIs and the MCP server's format capabilities.
- **What one side keeps, the other keeps.** `read(write(m))` equals `m` within the limits the format itself imposes (single precision, a cell type it has no slot for, a concept it cannot express). A loss that is a fact of the format is stated on its page and in the [conformance](./conformance.md) notes; a loss that is only an unwritten feature is a gap, and belongs below.
- **The one exception: pure 2-D drawings.** `svg` and `tikz` draw a mesh rather than store it. Their readers parse only the structure meshio++'s own writers emit, return the geometry as planar (`z = 0`), and warn once per read that depth, and whatever else the drawing could not hold, is lost. Anything else in the file — another tool's drawing, or a hand edit — is a `ReadError` naming the construct, never a guess.
- **Exempt:** `ansys_rst_cyclic`, which is not a file but the full rotor a cyclic `.rst` expands to; its write side is `ansys_rst`'s cyclic option (3.2.6).

**Landing an item.** Each item names only what is particular to it. All of them:

1. A native writer (or reader) in `src/cpp/src/formats/`, registered in `registry.cpp`, with its parameters through `WriteOptions`/`registry_write_ex`; the Python twin behind a shim that asks `core_declined`. Where the format is deterministic the twins are byte-identical (the `svg`, `tikz` and `gltf` writers already are); otherwise value-equal.
2. **Promote the scratch writer that already exists.** Every read-only format has one, written to build its reader's fixtures: the items name them. It becomes the oracle the library writer is checked against, then the tests switch to the library writer and the scratch copy is deleted.
3. The format's `READ_ONLY` (or `write-only`) entry becomes a `SPEC` declaration in `conformance_spec.py`, and `python tools/gen_conformance_table.py` regenerates [conformance](./conformance.md) and the [format table](./formats.md)'s columns.
4. The validator the item names reads the written file, and the format page records the tool and its version. A file only a vendor's tool reads adds a line under [Awaiting a licensed run](#_1-2-awaiting-a-licensed-run).
5. Files the new writer produces join the reader's fuzz seeds ([fuzzing](./fuzzing.md)).
6. A result file is a series: it is written through the same machinery as the Exodus and XDMF series writers (a stateful writer for steps over one mesh, and `write_sequence`), and a plain `write` of one `Mesh` writes one step.
7. Solver naming is the reader's inverse. The arrays a reader returns — `<fmt>:id`, `abaqus:layout:*`, `marc:layout`, `lsdyna:alive`, the `@corner` and `@ply` suffixes, point-major integration-point arrays — are written back under the same names; without them, ids are 1-based and sequential and results go where the format puts unlayered data. Element types go through the inverse tables of the [node-ordering registry](./node_ordering.md), which exist in both directions.
8. The format page gains a *Writing* (or *Reading*) section; the [C](./c_api.md), [WASM](./wasm.md), [Fortran](./fortran.md), [Julia](./julia.md) and [R](./r.md) docs list the new direction; `mcp/_tools.py`, `_server.py`, `tests/python/test_mcp.py` and [MCP](./mcp.md) report it; and a notebook shows it wherever a user would reach for it.

**3.1 Readers for the export-only formats.**

- **3.1.1 `svg`, as a 2-D drawing.** The writer (`svg/_svg.py`, byte-identical to the core's) emits one `<svg viewBox>` with one `<style>`, then one `<path d="M x y L … Z">` per line, triangle or quad — never a `<polygon>` and never a shared vertex table — with y flipped (`max_y + min_y - y`) and the drawing scaled to `image_width`; a 3-D mesh is first skinned and projected (azimuth 45°, elevation 35.26° by default) and sorted back to front; `color_by` adds a `fill` per path and a colour bar of 32 `<rect>` and 2 `<text>`. The reader inverts exactly that, through the vendored pugixml: a closed path of 3 vertices is a triangle, of 4 a quad, of more a polygon, and an open 2-vertex path a line; points are welded on their exact coordinate text in order of first appearance, so shared corners come back shared; the y-flip is undone from the `viewBox`; the colour bar is skipped; a fill can come back as an RGB `svg:fill` cell array, never as the data it was coloured from (a colour map does not invert). A `<polygon>`, a `transform`, a curve (`C`, `Q`, `A`) or a relative command is a `ReadError`. What cannot come back without 3.1.3: the original scale and offset. **S**
- **3.1.2 `tikz`, as a 2-D drawing.** The writer emits an optional `standalone` wrapper, `\begin{tikzpicture}[scale=…]`, one `\draw[fill=…, draw=…] (x,y) -- … -- cycle;` per cell and `\draw[draw=…] (x,y) -- (x,y);` per line, with coordinates verbatim (or projected) and no y-flip, so planar input comes back exactly in x and y. The reader tokenizes with `detail/text_cursor.hpp`, skips the colour bar (`\fill … rectangle` and `\node`), reads `fill={rgb,255:red,R;green,G;blue,B}` into `tikz:fill`, and refuses `\path`, `plot`, `circle`, `.. controls ..`, named, polar and relative (`++`) coordinates and `\foreach` by name. **S**
- **3.1.3 A marker, so the warning can say what was lost.** Neither drawing says today whether it was planar input or a projection, nor that meshio++ wrote it. Both writers gain a provenance comment (`<!-- … -->`, `% …`) carrying the version, the projection (`none`, or azimuth and elevation) and, for `svg`, the scale and offset — a change to both byte-identical twins together. The reader then warns "planar drawing, z = 0 assumed" or "projected from 3-D, depth lost", restores model units in `svg`, and refuses a file without the marker unless the caller passes `strict=False`. **S**
- **3.1.4 `gltf`, as a real reader.** glTF is not a 2-D drawing — the writer keeps 3-D positions — so it gets a general glTF 2.0 reader, not one limited to meshio++'s output. Containers: `.gltf` with external or `data:` URI buffers and `.glb` with its JSON and BIN chunks, through the vendored nlohmann/json and the base64 decoder the VTK XML readers already use. Primitives: `POINTS` → `vertex`, `LINES`/`LINE_STRIP`/`LINE_LOOP` → `line`, `TRIANGLES`/`TRIANGLE_STRIP`/`TRIANGLE_FAN` → `triangle`, indexed or not. Accessors: every `componentType`, `normalized`, `byteStride`, sparse accessors, and `KHR_mesh_quantization`. Node transforms (TRS or `matrix`) are applied down the hierarchy into world space. The writer's choices are inverted: a node name becomes a cell region (`unassigned` and `mesh` give none); the `_NAME` custom attributes become `point_data` under the accessor's `name`; `COLOR_0` becomes `gltf:color`; the root `meshio++` node's up axis, recentring and scale are undone from `asset.extras`; and the vertices the writer split per smooth fan can be welded back (`weld=True`). Draco and meshopt compression are refused by name; morph targets, skins, animations, materials and textures are skipped with a warning. Volume cells came out as their skin, so the conformance row reads `→ tri`. It replaces the test-local `read_glb`, `accessor` and `world_positions` in `tests/python/test_gltf.py`. Probe: read back every glTF the writer tests produce, and the Khronos glTF-Sample-Assets, each one's licence checked and attributed in `CITATION.cff`. **M**

**3.2 Result-file writers.** The consumer the old non-goal waited for is the physics-ML loop this project already serves: a surrogate's prediction (the [PhysicsNeMo adapter](./physicsnemo.md)'s output) handed to the solver's own post-processor beside the real run, which needs the solver's own result file. Close behind: regression tests for post-processing scripts, which today need a solver run per fixture, and results converted or anonymised before they are shared. Ordered by how cheaply the output can be checked: tier A has an open tool that reads it, pip-installable or buildable in CI; tier B only the vendor's.

*Tier A — an open tool reads the result.*

- **3.2.1 `frd` (CalculiX).** ASCII first, in the short and long forms: the `1C` header, `2C` nodes, `3C` elements with `frd:group` and `frd:material`, then a `100C` block per result and step with its `-4` component headers; the binary variant (ASCII headers, raw little-endian blocks) second. `.frd` is nodal, so cell data is dropped with a warning; it holds no sets, so losing regions is a fact of the format. Start from `tools/gen_frd_fixtures.py` (`cgx_short`, `_binary_variant`) and `tests/cpp/test_frd.cpp` (`FrdText`, `FrdBinaryText`, `write_frd`). Validators: `ccx2paraview` (pip, so it runs in CI) and `cgx -b`. The cheapest writer of the section. **S–M**
- **3.2.2 `nastran_op2`.** MSC dialect, 32-bit little-endian, SORT1 and real tables first — GEOM1/GEOM2 (or BGPDT) for the mesh, OUGV1 for displacements, OES1 for stresses — over `detail/nastran_model.hpp`; complex, random and SORT2 tables and the 64-bit and big-endian variants are sub-items once the first passes. `detail/fortran_records.hpp` gains the writing half of its record framer (4- and 8-byte markers, both byte orders), which 3.2.7 and 3.2.10 reuse. Start from `tests/cpp/test_nastran_op2.cpp` (`Op2`, `write_file`). Validator: pyNastran, which reads and writes OP2. **M**
- **3.2.3 `lsdyna_d3plot`.** The control block, geometry with part numbers, user ids, part titles, and states (time, globals, nodal displacement, velocity and acceleration, solid/shell/beam element variables point-major as the reader returns them, and deletion from `lsdyna:alive`), split into a family (`d3plot01`, …) by size; 4-byte words first. Sub-items: SPH, airbag particles, rigid roads, `d3part`, 8-byte words. Start from `tests/cpp/test_lsdyna_d3plot.cpp` (`Words`, `write_family`); `tools/gen_d3plot_reference.py` already drives lasso-python's `write_d3plot`, the oracle. Validators: lasso-python and LS-PrePost. **L**
- **3.2.4 `lsdyna_binout`.** The LSDA container — its 8-byte header, the `CD`/`VARIABLE` symbol table, `DATA` records and the `%001` continuation files — with `nodout` from point data per step and every `binout:<db>:<var>` field-data array written back to its directory. Start from `tests/cpp/test_lsdyna_binout.cpp` (`Lsda`, `write_file`); lasso-python's LSDA writer is already the oracle of `tools/gen_binout_reference.py`. Validators: lasso-python's `Binout` and LS-PrePost. **M**
- **3.2.5 `nastran_h5`.** The MSC compound tables under `/NASTRAN/INPUT` (grids, elements, properties) and `/NASTRAN/RESULT` (nodal and elemental), their `/INDEX` twins (domain, position, length) and the domain table, over `detail/hdf5_util.hpp` and h5py; HDF5 builds only, like every HDF5 format. Start from `write_msc` in `tests/python/test_nastran_h5.py` and `write_table`/`write_grids` in `tests/cpp/test_nastran_h5.cpp`. Validators: pyNastran's HDF5 reader and h5py; MSC's own post-processors join [§1.2](#_1-2-awaiting-a-licensed-run). **M**
- **3.2.6 `ansys_rst`.** Pointer-linked records in the `fdresu.inc` layout (64-bit word pointers, little-endian, uncompressed): the standard header, the result-set table, the geometry over `detail/ansys_model.hpp`'s element-type and real-constant tables, the DOF solution and element-nodal stress. A `cyclic=` option writes a cyclic sector with its sector count and harmonic index, which is `ansys_rst_cyclic`'s write side. Both test suites already hold a full scratch writer: `RstWriter` in `tests/cpp/test_ansys_rst.cpp` and `_Writer`/`_write_element_solution` in `tests/python/test_ansys_rst.py`. Validators: pymapdl-reader (pip, the reader's frozen oracle); DPF joins [§1.2](#_1-2-awaiting-a-licensed-run). **L**
- **3.2.7 `abaqus_fil`.** ASCII (the `*` + `I`/`D`/`A` item encoding) and binary (512-word blocks, both byte orders): element and node definitions, sets, increments, and results under their location codes (integration point, centroid, element node) from the `abaqus:layout:*` arrays. Start from `tools/gen_abaqus_fil_fixtures.py` (`ascii_bytes`, `binary_bytes`) and `tests/cpp/test_abaqus_fil.cpp`. Validator: pybaqus (MIT) † — verify first that it reads binary files; Abaqus itself joins [§1.2](#_1-2-awaiting-a-licensed-run). **M**
- **3.2.8 `xplt` (FEBio).** The magic word, the chunk tree (header with the node, element and surface dictionaries, materials, geometry with node, domain and surface sections) and one state chunk per step. `detail/zlib_inflate` only inflates, so the writer writes states uncompressed unless the build has zlib. Material-point variables are not read, so they are not written. Paired with the `febio` `.feb` writer it gives a model and its results. Start from `tests/cpp/test_xplt.cpp` (`Plt`, `plot_chunks`, `write_plot`). Validator: FEBio Studio (and febio-python †). **M**

## 4. Operations

*Admission: a new operation, or a public face for machinery that already exists privately inside one.*

**4.1 Generation.** Almost every operation transforms a mesh you already have. The exceptions all start from something else — `grid` from a lattice (`detail/grid_lattice.hpp`), `voxelize`/`compute_sdf` from a surface's bounding box, `remesh_volume` from a closed surface — and nothing builds a shape from parameters, sweeps one, or fills a skin with an adaptive lattice. Triangulating a domain is not this library's work; it reaches meshio++ only through the optional MMG backend (4.3).

- **4.1.1 Primitive constructors** — parametric generators in their own `operations/primitives.hpp` beside `grid` (today in `voxelize.hpp`, see [`grid` as a primitive constructor](./voxelize.md#grid-as-a-primitive-constructor)). Dependency-free, and it removes the fixture-file dependency from tests, docs, notebooks, the browser demo and the MCP server; and it could replace the test-local canonical mesh of the [format conformance matrix](./conformance.md). Highest leverage per line of code in this document. The demand is already in the tree: the Python tests hand-roll `_quad_grid` and `_hex_grid` six times each, `_unit_cube` four times, and `_tet_cube`, `_hex_cube`, `_tri_grid`, `_sphere` and `cube_quads` besides; the C++ tests `hex_grid` (seven times), `quad_grid` (six), `uv_sphere`, `two_tets` and `two_hexes`; the notebooks `hex_grid` (03, 09), `hex_block` (25), `plate` (09) and a squircle `disk` (27). The catalogue follows [meshzoo](https://github.com/meshpro/meshzoo)'s where the two overlap, taking names and parameterisations from its README only: check its licence before reading its code, since later releases are not MIT. **S per tier, M for the family**
  - **4.1.1.1 The contract every generator shares**, as `grid` already keeps it: a Python twin of the C++ core, coordinates computed from indices and never accumulated (an angle is `2πk/n`, not the previous point rotated), points and cells in a documented order, a `max_cells` budget, and a zero count yielding an empty mesh. Surfaces are oriented outward and volumes positively; boundaries come back as named side `Region`s (`xmin` … `zmax` on a box, `inner`/`outer` on an annulus, `side`/`top`/`bottom` on a cylinder), which is what notebook 26's `wall_facets` rebuilds by hand. Wherever the geometry allows, a `cell_type` choice (triangle or quad; tetra, hexahedron or wedge) and an `order=2` that places mid-edge and mid-face nodes on the exact geometry, so quadratic cells on a sphere or a cylinder are genuinely curved — the input the `curved()` helper of notebooks 16 to 24 exists to draw. One entry point per surface: Python, C, Fortran, Julia, R, WASM, both CLIs (a `generate <shape>` verb), an MCP tool and a pipeline source step.
  - **4.1.1.2 Tier 1: the replacements.** `rectangle` (the 2-D `grid`: quads, or triangles split `zigzag`, `up`, `down` or `center`); `box` (hexahedra, tetrahedra by the six-tet Kuhn split, which conforms across cells without the five-tet split's alternating parity, or wedges; six side regions); `disk` (quads by the squircle map notebook 27 uses, or triangles by an inflated polygon); `uv_sphere` and `icosa_sphere` surfaces; `cylinder` (hexahedra by an O-grid, or wedges by sweeping a triangle disk; three side regions). Enough to retire every helper listed above. **S**
  - **4.1.1.3 Planar domains**, at `z = 0`: `triangle` (a refined reference triangle, in barycentric order); `ngon` (a regular polygon fanned from its centre); `annulus` (two named rims, and a seam that [`periodic`](./periodic.md) can link); `lshape` (`[-1, 1]²` minus a quadrant, with the re-entrant corner at the origin: a singular solution for `refine`, [`error`](./error.md) and the gradient recovery operators); `plate_with_hole` (a square plate around a circular hole in quad blocks, the stress-concentration benchmark); `honeycomb` (a hexagonal tiling as a `polygon` block, so the ragged polygon paths have a parametric fixture). **S**
  - **4.1.1.4 Surfaces**: spheres from the other platonic seeds (`tetra_sphere`, `octa_sphere`, and `cube_sphere` in quads); `geo_sphere` (a UV sphere closed with triangle caps rather than degenerate quads); `torus` (genus one, negative Gaussian curvature on the inner rim and periodic both ways — the [curvature](./curvature.md) and Euler-characteristic probe a sphere cannot give); `moebius` (non-orientable, with `num_twists`: no consistent orientation exists, which probes [`compute_normals`](./normals.md)' `inconsistent_pairs` report and `repair(fix_orientation=True)`); `tube`, `cone` and `capsule` (open and closed surfaces of revolution, with sharp rims for [`feature_edges`](./feature_edges.md)); `box_surface` (today's `cube_quads`, a region per face); and the five platonic solids with one cell per face, the dodecahedron's pentagons as a `polygon` block. **S**
  - **4.1.1.5 Solids**: `ball` (tetrahedra, or hexahedra by a seven-block butterfly so no cell degenerates at the centre); `spherical_shell` and `pipe` (thick shells between two radii in hexahedra, `inner`/`outer` regions, with a radial grading ratio for wall-resolved spacing); `fichera` (the cube minus one octant, the 3-D L-shape and its corner singularity); `solid_torus`. **S**
  - **4.1.1.6 Lines and points**: `line` (a subdivided segment), `circle` (a closed polyline) and `helix` (a spring), as `line` cells for beam and 1-D format fixtures; point clouds on a sphere (a Fibonacci lattice) or in a box (seeded sampling) for the point-cloud formats and [point budgets](./point_budgets.md). Seeded sampling needs its own small generator (splitmix64 or PCG) in both twins: `std::uniform_real_distribution` is implementation-defined, and numpy's `default_rng` has no C++ counterpart. **S**
  - **4.1.1.7 Reference cells**: `reference_cells(types=…)`, one cell of each requested type in its reference coordinates — linear and higher-order (`tetra10`, `hexahedron20`/`27`, `pyramid13`, the quadratic wedges and the VTK Lagrange types) and a `polyhedron` — laid out side by side without touching, with a `pairs=True` variant of two cells sharing a facet. It is the conformance matrix's canonical mesh, `two_tets`/`two_hexes` and the [node-ordering](./node_ordering.md) fixtures in one, and the cheapest way for a notebook to show a format's cell coverage. **S**
  - **4.1.1.8 Watch.** Byte identity between the twins holds for `grid` because it is index arithmetic; `std::sin`/`std::cos` are not correctly rounded and differ between glibc, MSVC, Emscripten's libc and numpy's own SIMD kernels. Pin byte identity only for the polynomial generators (`rectangle`, `box`, `triangle`, `lshape`, `reference_cells`) and compare the trigonometric ones within a few ulps, or have the Python twin take its angle table from the core. Seams and poles are welded points, never duplicates, or `periodic`, `clean` and the Euler-characteristic checks see a boundary that is not there.
- **Deliberately not**, so not re-proposed: generators driven by a user callback (no callback crosses the flat ABI; numpy users build `Mesh(points, cells)` directly, and [`isosurface`](./isosurface.md) on a `grid` covers implicit shapes); scanned or modelled assets (the bunny, the teapot, the bracket fixture — data rather than parameters, each under its own licence); and CSG combinations (a [non-goal](#non-goals-and-decisions-taken)) — two-body interface and contact fixtures are primitives placed with `transform` and joined with `merge`.
- **4.1.2 `extrude`** — 2-D → 3-D sweep (triangle → wedge, quad → hexahedron) with `nlayers` and per-layer offsets, carrying regions to side and cap regions. The most-requested generation primitive. **M**
- **4.1.3 `revolve`** — `extrude`'s rotational sibling around an axis, sharing its layer machinery; degenerate cells on the axis are the only new work. **M**
- **4.1.4 Voxel and octree meshes from a skin, and their 2-D counterparts.** What exists: [`voxelize`](./voxelize.md) fills a closed surface's bounding box with uniform hexahedra (`fill="all"`, `"surface"` by exact triangle–box separating-axis overlap, `"inside"` by the [signed distance](./sdf.md)'s sign), under a `max_cells` budget and with byte-identical twins; `refine(closure="balanced")` already keeps hanging nodes and reports them in `refine:hanging`; and `voxelize.md` already turned down `custom` cells "for a future adaptive octree" because they would make the result invisible to every operation and most writers. What is missing is a lattice that is fine only where the surface is, and any of it in 2-D. It is in scope where Delaunay meshing is not for the reason [`remesh_volume`](./remesh_volume.md) is: a lattice is index arithmetic plus the overlap and sign tests that already exist, with no robust predicate anywhere. **M for the family**
  - **4.1.4.1 2-D `voxelize` (pixels).** The input is a closed planar polyline skin (`line` cells at constant `z`, or in a plane chosen by `plane=`), or the boundary of a 2-D surface mesh, taken with the boundary-edge extraction `feature_edges` already does; a two-entry `resolution` or `cell_size` selects 2-D. The output is a `quad` lattice with `voxelize`'s numbering (x fastest), the same lattice the `rectangle` primitive builds (4.1.1.2), so the two share one implementation. `fill="surface"` uses exact segment–box overlap (the separating-axis test in 2-D); `fill="inside"` uses the winding number of the closed polyline, with even-odd offered for self-overlapping input; a polyline that does not close is refused for `inside` by naming its open ends. **S–M**
  - **4.1.4.2 Octree and quadtree from a skin.** The root is the padded bounding box, made cubic, or a coarse `root_cells` lattice with one tree per cell (a forest, for elongated parts). A cell is split while the surface cuts it (the same overlap test) and its level is below `max_level`; every cell is split down to `min_level`. Optional criteria refine further: a distance band around the surface (`sample_distance`), surface curvature above a threshold ([curvature](./curvature.md)), cells crossed by [`feature_edges`](./feature_edges.md), and a size field sampled at the cell centre. A 2:1 balance pass follows, by faces or by faces, edges and corners (`balance="face"`/`"full"`), as a ripple to a fixed point. `fill` keeps `voxelize`'s meaning. The result carries `octree:level` and `octree:cut` cell data and, on request, `sdf:distance`. **M**
  - **4.1.4.3 Transitions — the decision this item records.** Where a fine cell meets a coarse one, three outputs, chosen by `transition=`: (a) **`"hanging"`, the v1 default**: plain hexahedra (quads in 2-D) with hanging nodes, flagged in `octree:hanging` point data — what adaptive-mesh-refinement, lattice-Boltzmann, immersed-boundary and cut-cell solvers and octree learning models consume, and what `check_conformity` (4.2.1) is built to report; (b) **`"polyhedra"`**: each coarse cell next to a finer one becomes a `polyhedron` (a `polygon` in 2-D) whose faces are split into the fine faces, the split-hex representation snappyHexMesh produces — conforming with no new points, through the [polyhedron kernel](./polyhedra.md), and readable by every format and finite-volume solver that takes polyhedra (OpenFOAM, Fluent, CGNS `NGON_n`, EnSight `nfaced`, VTU) (**M**); (c) **`"templates"`**: conforming transition templates (pyramids, tetrahedra and wedges in 3-D, triangles in 2-D) for a hex-dominant mesh a finite-element code takes — the most work, because every 2:1 configuration needs a template that tiles its cell with positive volume, checked exhaustively, and it is implemented from published descriptions only, as `remesh_volume` was (**L**).
  - **4.1.4.4 Optional snapping.** `snap=True` moves the outer nodes of the kept cells onto the skin with `shrinkwrap`'s projection, for a body-fitted rather than stair-stepped boundary, and never moves a node that would invert a cell: it reports the nodes it refused rather than leaving a bad cell. Boundary-layer inflation stays a [non-goal](#non-goals-and-decisions-taken). **M**
  - **4.1.4.5 Determinism.** Leaves come out in Morton order. Every point is an integer coordinate on the finest level's lattice (`2^max_level` per root cell), so shared corners are deduplicated arithmetically, with no hash and no tolerance, as `voxelize`'s are, and coordinates are `origin + spacing * index`, never accumulated. Refinement and balance run in parallel per level with a prefix-sum compaction, so the output is byte-identical across backends, thread counts and the C++/numpy twins.
  - **4.1.4.6 Surfaces and probes.** Python, C, Fortran, Julia, R, WASM, both CLIs (an `octree` verb beside `voxelize`), an MCP tool and an `Octree` pipeline step that, like `Voxelize`, replaces its input's geometry; documented in `voxelize.md` or a new `octree.md`, and shown in a notebook. Probes on a sphere skin: leaves at `max_level` occur only in the band the surface cuts; the `inside` volume converges to 4/3·πr³ as `max_level` grows; the inside cells of the 2-D quadtree of a circle converge to πr²; `check_conformity` reports zero hanging nodes under `"polyhedra"` and `"templates"` and exactly `octree:hanging` under `"hanging"`; and every cell has a positive volume.

**4.2 Checks, selection and measurement.**

- **4.2.1 `check_conformity`** — hanging nodes, T-junctions and interface facets that only partly overlap, so a user knows which `find_interface` mode to choose. It also gives `refine` and `undo_green`, which discuss conformity only in comments, a checker. A report plus a flagging `point_data` array. **S–M**
- **4.2.2 `find_intersections`** — self-intersection of a surface and mutual interpenetration of two parts, by triangle–triangle tests over the bucket grid. Returns the pairs, the intersection segments as a line mesh and a flagging `cell_data` array, with exact and "possible" hits reported separately because there are no robust predicates; booleans stay a [non-goal](#non-goals-and-decisions-taken). Also the precondition check for `repair`, `shrinkwrap` and `remesh_volume`. Probe: two overlapping spheres. **M**
- **4.2.3 `select`** — write `Region`s (cell, point or side) from a box, plane or sphere, a `cell_data` or quality threshold, a component label, or normal-angle patch growing bounded by `feature_edges`, so boundary-condition and contact patches are reproducible and feed `find_interface`. Reuses `crop(where=)`'s predicate parser, `feature_edges` and `split(by="component")`. **M**
- **4.2.4 `thickness`** — wall thickness and inter-part clearance per facet, from a ray along the inward normal to the opposite surface. Needs a ray–triangle kernel that `find_intersections` also needs: write it once in `detail/`. **M**
- **4.2.5 `mirror`** — reflect across a plane, flipping the winding so the orientation stays valid, optionally welding on the plane: a full model from a half, and the demi-sphere fixture from one hemisphere. **Verify first:** a reflecting `transform` matrix may already flip orientation correctly; probe by mirroring a tetrahedral mesh and asserting positive volumes, and if it does this item shrinks to documentation. **S**

**4.3 Optional MMG backend.** [MMG](https://www.mmgtools.org/) — `mmg2d` (planar triangles), `mmgs` (surface triangles in 3-D) and `mmg3d` (tetrahedra) — adapts an existing simplicial mesh to a size or an anisotropic metric, embeds a level set in it conformally, and moves it in a Lagrangian way; `mmg2d` also triangulates a planar domain from its boundary. Everything here was read in the source of MMG 5.8.0 (October 2024), not taken from its documentation. It is LGPL-3.0, so it follows the KaHIP, ADIOS2 and TecIO pattern exactly: **`MESHIOPLUSPLUS_WITH_MMG`**, off by default, bring-your-own (`find_package(mmg CONFIG)` over the package MMG installs, with its `Mmg::` targets; `mmg_DIR` or `CMAKE_PREFIX_PATH` point at it), never vendored, never downloaded, never probed under Emscripten, linked dynamically only, and absent from the release wheels and the native CLI binaries; the page states the licence's implications for anyone who redistributes a build with it. Without it, every operation below throws `Unsupported` naming the flag, as `partition(method="kahip")` does, and reports it in the configured capabilities. There is no numpy twin — MMG's result cannot be reproduced by a second implementation, the [`remesh_volume`](./remesh_volume.md) precedent — so Python raises `NotImplementedError` naming the flag when the core lacks it.

- **4.3.1 `adapt`** — remesh to a size field or a metric. A tetrahedral mesh goes to `MMG3D_mmg3dlib`, a triangle surface in 3-D to `MMGS_mmgslib`, a planar triangle mesh to `MMG2D_mmg2dlib`. **M**
  - **4.3.1.1 Size and metric.** A constant `hsiz`; a scalar size as one-component `point_data`; or an anisotropic metric as a symmetric tensor `point_data` (six components in 3-D, three in 2-D, in the upper-triangular order MMG expects — verify first against `MMG3D_Set_tensorSol`). The producers are already in the tree: [`hessian`](./hessian.md) (with a small metric-from-Hessian helper — absolute eigenvalues, scaled by a target error and clamped to `hmin`/`hmax`), [`error`](./error.md) for an isotropic size, and [curvature](./curvature.md) for a surface.
  - **4.3.1.2 Parameters.** `hmin`, `hmax`, `hausd` (the Hausdorff distance the boundary may move), `hgrad` and `hgradreq` (gradation), `angle_detection` (ridge angle, or off), `optim`, `noinsert`/`noswap`/`nomove`/`nosurf`, `nreg` (normal regularisation), `opnbdy` (keep internal open surfaces), `mem` and `verbose` (default −1, since MMG prints to stdout), and per-region `hmin`/`hmax`/`hausd` through `Set_localParameter` (`local={"inlet": {"hmax": 0.01}}`).
  - **4.3.1.3 Entities.** Cell and side regions map to MMG references through a reference ↔ name table and come back under their names; `frozen` points and named `required` regions become required vertices, edges, triangles and tetrahedra; [`feature_edges`](./feature_edges.md) become ridges, and their corners MMG corners. `wedge` blocks pass as MMG prisms, which `mmg3d` keeps unchanged (verify first), and boundary quads as MMG quadrilaterals (verify). Hexahedra, pyramids, higher-order cells and ragged blocks are refused with a pointer to [`convert_cells`](./convert_cells.md).
  - **4.3.1.4 What does not survive**, as for `remesh`: point and cell data on the new points are dropped with a warning — compose with [`interpolate`](./interpolate.md) — and `field_data` carries through.
  - **4.3.1.5 Report.** MMG's return code: `MMG5_SUCCESS`; `MMG5_LOWFAILURE`, where MMG returns a valid mesh it could not finish adapting, is a warning in the report, not an error; `MMG5_STRONGFAILURE` throws. Also points and cells in and out, and the quality histogram of the result.
- **4.3.2 `discretize_levelset`** — `MMG3D_mmg3dls`, `MMGS_mmgsls` and `MMG2D_mmg2dls` cut a mesh along the zero (or a chosen) isovalue of a `point_data` field and remesh both sides, so the interface is a conforming side region between an `inside` and an `outside` cell region; several materials through `Set_multiMat`, and small parasitic components removed through `rmc`. Where [`isosurface`](./isosurface.md) extracts a level set and [`crop`](./crop.md) cuts along cells, this embeds it in a mesh fit for a solver. Chained with `compute_sdf` on a `grid` and `convert_cells(simplexify)`, it is the backend's route from a skin to a tetrahedral mesh of its interior. **S–M**
- **4.3.3 `mesh_domain`** — `MMG2D_mmg2dmesh` triangulates a planar domain from its boundary `line` cells, with `hsiz`, `hmax` or a size field, boundary references kept as side regions. How MMG tells holes and subdomains apart is not yet read in its source: verify first, probing with an annulus. This is the only domain mesher meshio++ offers, and only through the backend (the [non-goal](#non-goals-and-decisions-taken) stands for native meshing). MMG has no 3-D counterpart that meshes from a surface; the 3-D routes are 4.3.2, [`remesh_volume`](./remesh_volume.md) and the octree of 4.1.4. **S**
- **4.3.4 `move`** — `MMG3D_mmg3dmov` and `MMG2D_mmg2dmov` move a mesh by a displacement `point_data` vector and remesh as it deforms. They need MMG built with the ELAS linear-elasticity library, so the operation is gated on that capability too, and comes last. **S**
- **4.3.5 Embedding hazards**, read in the 4.8.0 source:
  - **4.3.5.1 Signal handlers.** `MMG3D_mmg3dlib` calls `signal()` for `SIGABRT`, `SIGFPE`, `SIGILL`, `SIGSEGV`, `SIGTERM` and `SIGINT` on every call (`libmmg3d.c`), which replaces Python's Ctrl-C handler and any crash handler of the host. The wrapper saves every handler with `sigaction` before the call and restores it after, on every path including errors, and the page says a call cannot be interrupted. Check the other entry points and libraries for the same.
  - **4.3.5.2 Index width.** `MMG5_int` is `int32_t` unless MMG was configured with `-DMMG5_INT=int64_t`: detect it at configure time, and refuse a mesh beyond its range by name rather than truncate.
  - **4.3.5.3 Threads.** Whether two meshes can be adapted at once in one process is not established; serialise the calls behind one mutex until it is. ParMmg, MMG's MPI layer, falls under the MPI [non-goal](#non-goals-and-decisions-taken).
- **4.3.6 The file route, and Medit's half of it.** MMG's native files are Medit `.mesh` and `.sol`. meshio++'s `medit` reader discards `Corners`, `Ridges` and the `Required*` keywords and has no `.sol` support. Reading and writing `.sol` (and `.solb`) — scalar, vector and symmetric-tensor solutions at vertices and cells, as `point_data` and `cell_data` — and keeping those keywords as regions (3.3.11) make the `mmg3d_O3`/`mmgs_O3`/`mmg2d_O3` executables usable through files with no link at all, which also serves anyone driving MMG themselves. Independent of the rest, so it can land first. **S**
- **4.3.7 Surfaces and probes.** `operations/mmg.hpp` in the core; Python; C entry points with append-only, reserved-tail option structs and reports (`mio_adapt_ex`, the `mio_remesh_ex` pattern); Fortran, Julia and R mirrors; both CLIs (`adapt`, `discretize-levelset`, `mesh-2d`); MCP tools that report the capability; an `Adapt` pipeline step; no WASM. A `doc/mmg.md` page with the licence section, and a notebook adapting a `rectangle` to the metric of an analytic field's [`hessian`](./hessian.md). CI: one Linux leg that builds MMG 5.8 from source (cached) and runs with the flag on, beside the KaHIP and ADIOS2 legs; a conda-forge `mmg` package may serve instead †. Probes: a constant `hsiz` gives a mean edge length within a stated tolerance of it; region names and frozen points survive bit for bit; the level set of a sphere's signed distance gives an interface of area ≈ 4πr²; an anisotropic metric along a boundary layer gives elongated triangles aligned with it.

## 6. Long run (spike first)

*Admission: work whose shape is unknown until an investigation writes it down. Findings before code.*

**6.1 Scale.** Memory-mapped reads ([mmap](./mmap.md), via `ReadOptions` and the C ABI but not Python's `read()`) roughly halve the peak footprint of a large read, and the XDMF series appender and Python's chunked `write_dataset` write a series or a dataset without holding it — but nothing writes one mesh larger than memory, and no operation streams. Run the benchmark harness's `--tier XL` (about 10M cells) first; it decides whether either item below matters.

- **6.1.1 Streaming / chunked writes of one mesh**, the counterpart to selective and memory-mapped reads. **L**
- **6.1.2 Out-of-core operations** for the ops that are already block-local. **XL**

**6.2 NURBS and higher-order geometry.** The data model is strictly linear/Lagrange polytopes: a `CellBlock` is a cell-type string plus a node-index array. NURBS is a genuinely different object — control points, weights, knot vectors, and a parametric mapping — and CAD/IGA formats (STEP, IGES, Rhino 3dm, `.iga`) express geometry that no current cell type can hold. This is the most architecturally invasive item on the list and should be approached as a research spike, not a feature.

- **6.2.1 Spike: how far can the current model stretch?** Higher-order Lagrange cells already exist (`hexahedron27`, VTK-Lagrange types); a rational Bézier/NURBS patch needs *weights* and a *knot vector*, which have nowhere to live. Determine whether a side-channel struct (the `MedInfo`/`GmshInfo` precedent) suffices, or whether the `Mesh` needs a genuine second entity kind. Write the finding up before committing. **M**
- **6.2.2 Read-only CAD ingestion first**: a NURBS surface tessellated to a triangle mesh at a requested tolerance, with the parametric data carried out-of-band. This delivers most of the practical value (getting CAD into the mesh world) without touching the data model, and is the natural first release. **L**
- **6.2.3 A real IGA data model** — patches, control nets, weights, knots, trimming curves — plus formats and evaluation. This is XL, likely a separate library or a major version, and should only be attempted if the spike shows real demand.
- **6.2.4 Dependency reality**: robust STEP/IGES parsing effectively means OpenCASCADE, which is a heavyweight LGPL dependency. If ingestion goes ahead, it must follow the KaHIP/Polyscope pattern — strictly optional, off by default, never in the core, licence implications documented. **Findings before code.**
- **6.2.5 No C++ tessellator exists yet** — `tessellate` is Python-only — so read-only CAD ingestion reaching every surface also carries that port.

*Recommended posture: spike and document; do not schedule implementation until the spike says what shape it takes.*

**6.3 Skin mesh to CAD (reverse engineering).** 6.2 is the CAD → mesh direction; this is its inverse, and the two share the dependency question (6.2.4) and the data-model question (6.2.1). A triangle skin of a part (an STL, a scan, a 3-D-printing download, the output of `extract_skin` or [`isosurface`](./isosurface.md)) goes to a B-rep solid whose faces are real surfaces — planes, cylinders, cones, spheres, tori, then freeform patches — so it can be dimensioned and edited in a CAD tool, where a plain triangle-per-face STEP export gives thousands of flat facets nobody can select. The reference is [stl2curves](https://github.com/Duvdivan/stl2curves) (MIT, a beta CLI and FreeCAD add-on: STL and 3MF in, STEP out), whose pipeline is the shape of the work: repair the mesh; group triangles into flat facets and fit exact cylinders, cones, spheres and tori; detect fillets between planar faces, constant-radius swept fillets along curved edges and screw threads; fall back to B-spline surfaces or blend patches within a stated tolerance of the mesh for what no primitive fits, and leave the rest faceted; sew the patches into a closed solid, fuse overlapping bodies, validate the solid and its volume against the mesh, read the STEP file back, and drop any feature that fails the check so the result always matches the skin. Its stated limits carry over as design constraints: freeform fits are height fields over a plane or cylinder, so an area that curls in two directions is split into several pieces; lettering and shapes extruded from free-form curves stay faceted; a mesh that is not a clean solid warns; large meshes take minutes. Its algorithms are read from its README only so far — verify first, and check its licence and its dependencies' before reading or porting any code, as 4.1.1 does for meshzoo. **Findings before code, and the dependency decision (6.3.5) before either.**

- **6.3.1 Segmentation into smooth patches — the part meshio++ can own.** Everything up to the fit is mesh-side machinery the library already has most of: [`repair`](./repair.md), [`feature_edges`](./feature_edges.md) for the sharp-edge graph, [`curvature`](./curvature.md) for principal curvatures and directions, [`compute_normals`](./normals.md), [`split`](./split.md) by component and [`region_adjacency`](./region_adjacency.md) for the patch graph. What is missing is the operation that joins them: region growing over the facet graph, bounded by feature edges and a normal-angle and curvature tolerance, returning each patch as a `Region` and a patch-adjacency table (4.2.3 `select` is the manual cousin and shares the growing code). Standalone value: a segmented skin is an input for [`decimate`](./decimate.md), [`remesh`](./remesh.md) and boundary-condition patches, whether or not a CAD writer ever exists. **M**
- **6.3.2 Primitive fitting, with a residual report.** Per patch, a least-squares fit of a plane, sphere, cylinder, cone and torus (RANSAC or a Hough-style vote to propose, a Gauss–Newton or algebraic fit to refine, the principal-curvature ratios of 6.3.1 to choose the type), each returning its parameters, the RMS and maximum distance of the patch's vertices, and the fraction of the patch it explains. Reported as `field_data` and per-patch `cell_data` (`fit:type`, `fit:rms`), so it is useful without a CAD back end: a recovered radius, axis or plane normal is a measurement. No fit that fails the stated tolerance is accepted, and the report says so rather than rounding a bad fit to a neat primitive. Probes on analytic parts: a tessellated cylinder, cone, sphere and torus recover their parameters to the tessellation error; a box recovers six planes and twelve edges; the same parts with seeded noise degrade the residual, not the type. **M–L**
- **6.3.3 Fillets, blends and threads.** Rolling-ball fillets (a constant-radius band tangent to two fitted faces), swept fillets along a curved edge and helical threads are the features that make a recovered model editable rather than merely smooth; each is a second pass over the 6.3.2 patches and the hardest to get robust. Out of v1. **L**
- **6.3.4 Freeform fallback and fit quality.** A B-spline surface fit within a stated tolerance for what no primitive explains, over a plane or cylinder parametrisation, with its limit (a doubly-curled area splits into several pieces) documented, using the tolerance machinery [`hausdorff`](./hausdorff.md) and [`shrinkwrap`](./shrinkwrap.md) already provide to *check* the fit against the skin. It needs the NURBS representation of 6.2.1/6.2.3, so it comes after that spike. **L**
- **6.3.5 The CAD back end — the decision this item records.** Two routes, chosen before anything else is built:
  - **6.3.5.1 A native faceted STEP writer.** STEP Part 21 is ASCII, and a `faceted_brep` (AP203/AP214 `MANIFOLD_SOLID_BREP` over `ADVANCED_FACE`s with plane surfaces and polyloop bounds) needs no CAD kernel. It gives the registry a `step` writer for a closed skin today, and a CAD tool opens it as a solid made of flat facets: the baseline stl2curves is trying to improve on, and the format half of this item. **Verify first:** that FreeCAD and OpenCASCADE both accept it as a solid, that the format is registered as write-only with its reason on the [conformance page](./conformance.md#read-only-formats), and that a reader (the inverse, for faceted files only) is not promised. **M**
  - **6.3.5.2 Analytic and freeform faces through an optional OpenCASCADE backend.** Fitted cylinders, cones, spheres, tori and B-spline faces, sewn into a solid, checked for validity and volume and read back, are OpenCASCADE's job (`BRepBuilderAPI_Sewing`, `ShapeFix`, `BRepCheck`, `STEPControl_Writer`), the same dependency 6.2.4 names for ingestion and under the same rule: strictly optional, off by default, bring-your-own and never vendored, linked dynamically, absent from the wheels, the WASM build and the native CLI binaries, licence implications documented (OpenCASCADE is LGPL-2.1 with an exception; verify the version), and the operation throws `Unsupported` naming the flag where it is absent, as the MMG and KaHIP operations do. One backend serves 6.2.2 (read) and this (write), so decide them together. There is no numpy twin — a second implementation could not reproduce a CAD kernel's output — so Python raises `NotImplementedError` naming the flag. The `cadquery-ocp` wheels that stl2curves uses are the Python-side route to prototype against (about 750 MB installed, which is why this must never be a hard dependency). **L**
- **6.3.6 Surfaces and probes.** If it goes ahead: `operations/` kernels for 6.3.1 and 6.3.2 in the core (dependency-free, deterministic, byte-identical across backends and thread counts, with a numpy twin for the segmentation and the fits); a `fit_cad` operation gated on 6.3.5.2 that returns the solid's validity, volume ratio against the skin, the maximum deviation, the number of faces by type and the features that were dropped; Python, C, Fortran, Julia, R, both CLIs (`segment`, `fit-primitives`, `to-cad`), an MCP tool that reports the capability and a pipeline step; no WASM for 6.3.5.2. A `doc/cad_fit.md` page, a notebook fitting a noisy tessellated bracket and drawing each patch in its fitted type's colour, and CI of one Linux leg that builds with OpenCASCADE beside the KaHIP, ADIOS2 and MMG legs. Probes: the volume of the recovered solid is within a stated tolerance of the skin's; every output face lies within the stated tolerance of the skin; re-meshing the STEP output and running [`hausdorff`](./hausdorff.md) against the input stays under it; an input that is not a closed solid is refused with the open edges named, or repaired with a report; and a part with a feature the fitter cannot explain comes back faceted there, never silently wrong.

*Recommended posture: land 6.3.1 and 6.3.2 first — they are useful as measurements and as patch selection with no CAD kernel in sight — and the faceted writer 6.3.5.1 beside them; do not schedule 6.3.3 to 6.3.5.2 until the OpenCASCADE decision shared with 6.2.4 is taken.*

## Non-goals and decisions taken

Recorded so they are not re-proposed as gaps.

- **MPI in the library** — none planned ([C++ API](./cpp_api.md)); `partition`'s ghost layers produce the halo an MPI assembly in the owning application needs. ParMmg, MMG's MPI layer, is excluded with it.
- **Solver-coupled physics-ML** — assembled solver residuals, adjoints and Sobolev training, co-simulation, active-learning *labeling*, adaptive remeshing driven by a surrogate, and MPI model-part gathering. Every one needs a live solver (an assembly routine, its tangent, its communicator) and meshio++ has no notion of a discrete system; they belong in the application that owns the solver, the division [Symbolic and physics](physicsnemo/symbolic_and_physics.md) describes.
- **The Python-only layers stay Python** — `pmsh`, `zarr`, `cae` and `usd`, and the physics-ML surface (`tessellate`, grids, point budgets, proximity graphs, datasets, training) are export targets and tooling for a training pipeline, registered in Python rather than the shared C++ registry. A core kernel they call (the neighbour search) does not change that.
- **Polyscope in the release CLI binaries** — excluded deliberately, so `view`/`screenshot` there report the build flag rather than opening a window ([viewer](./viewer.md)).
- **General meshing algorithms as operations** — Delaunay and constrained triangulation or tetrahedralization of a domain, hex and hex-dominant meshing from a CAD-like boundary, boolean/CSG, boundary-layer inflation, quadrangulation and geodesic distance are each a library in their own right, and the triangulators need robust geometric predicates, which is where dependency-free stops paying (the reason the queued Delaunay item was dropped). The answer is an optional backend (the KaHIP pattern), not a native implementation: domain meshing and adaptation reach meshio++ only through the MMG backend (§4.3). Lattice generation is the exception, and in scope: [`voxelize`](./voxelize.md), the octree of §4.1.4 and [`remesh_volume`](./remesh_volume.md)'s isosurface stuffing are index arithmetic over a signed distance, with no predicate to make robust.
- **Contact mechanics itself** — penalty or mortar assembly, friction and contact search in time need a live solver. meshio++ detects and exports the interface of one snapshot ([§4](#_4-operations)); the contact algorithm belongs in the application that owns the solver.
- **MMG in the WASM build, the release wheels and the native CLI binaries** — it is LGPL-3.0 and an external install, so it is linked dynamically into builds that opt in and nowhere else; the operations throw by name where it is absent.
- **KaHIP in the WASM build** — no Emscripten port, and a graph partitioner would bloat every consumer's bundle; `"auto"` resolving to the SFC method is the answer, and `"kahip"` throwing by name is the contract.
- **zstd/lz4 codecs, memory mapping and the Kokkos backend under Emscripten** — the codecs have no Emscripten port and are compiled out, CMake refuses the Kokkos backend under Emscripten, and there is nothing to map inside MEMFS.
- **Single-file output for DOLFIN, TetGen and EnSight from WASM**, or lifting DOLFIN's simplicial restriction — both are facts of the formats; `writeMesh`'s written-paths return value (v11.2.0) is the fix for the bookkeeping they cause.
- **Polyhedron blocks as a WASM gap** — `vtu`, `ensight`, `cgns`, `med` and `openfoam` all write them from WASM; a consumer that cannot is constrained by its own data model.
- **Performance work measured or decided against** — recorded when the roadmap's performance section closed (October 2026); a new performance change passes the gates of [landing a performance change](./benchmarks.md#landing-a-performance-change):
  - **The serial phases kept for determinism**: the keep-first weld loop (chains make it order-dependent), the union sweeps of `split` and `compute_normals` (cheap, and their partitions are order-independent anyway), and `remesh`'s energy sweep (every accepted move changes what the next test reads; it has no numpy twin because a near-tie decided differently yields a different clustering).
  - **A facet table cached across pipeline steps** — measured ([benchmarks](./benchmarks.md#pipeline-row-what-a-shared-facet-table-could-save)): in a `Smooth` then `ExtractSurface` chain a cache saves at most one table build, about 3.6% of the chain on SEQ at tier L with the default ten iterations, at most 10% on four OpenMP threads and about 20% with one iteration. `smooth` and `extract_surface` do not share a record structure, so it would also need a refactor, and a cache on the `Mesh` is a Tier A layout change. Reopen it for a workload that chains several facet readers after cheap topology-preserving steps; the `pipeline_smooth_surface` row measures it.
  - **Explicit SIMD intrinsics or `-march` flags** — portability across wheels, WASM and the release binaries is worth more than the scalar kernels cost; revisit only if the harness shows a kernel dominating.
  - **Kokkos device execution** — every `parallel_for` body captures host pointers (`parallel.hpp`); the GPU route is the DLPack/CuPy handoff ([GPU handoff](./gpu.md)).
  - **A BVH in place of the distance query's uniform grid** — `detail/surface_distance.hpp` rejects one because its visit order would make the equidistant-triangle tiebreak observable.
  - **Tuning the pure-Python fallback readers** — the fix is making the C++ path accept the file, not a faster fallback; `_decimate.py`'s heap-based twin is deleted once `decimate` accepts its inputs, not optimised.
  - **Dropping the copy in `transform`** — `transform` copies the connectivity and data it does not change (through `transform_owned_copy`, as 17 operation files copy through `clone_mesh`, `clone_geometry` or `quality_clone_mesh`), and the Python twin copies too; that copy is what makes the result a new mesh that aliases nothing, so removing it is an API change, not an optimisation.
  - **Caching between the browser viewer's applies** — every apply re-reads the staged file and replays the whole pipeline, which is what makes undo exact. Measured with the typed-array channel ([benchmarks](./benchmarks.md#a-typed-array-channel-for-the-browser-viewer)), the read is at most 2 to 25% of an apply that smooths and up to 69% of a quality-only apply on a large surface; a cached mesh or pipeline prefix would hold a second copy of the mesh in the 32-bit heap MEMFS already shares, and make undo depend on invalidation.

- **Terminal rendering stays software, dependency-free and core-only** — no GPU, no windowing stack, no new dependency and no audio library; it is a *preview*, not a replacement for Polyscope or vtk.js, and does not try to match their fidelity, lighting or picking. Python calls the core or raises by name (the [`remesh_volume`](./remesh_volume.md) precedent: a NumPy edge-function rasterizer would be slow and double the surface that has to stay byte-identical). Vector output is unchanged: SVG, TikZ and glTF keep the painter's algorithm and their byte-pinned twins, and their colormap tables are only ever extended. The interactive loop is not a library feature (raw mode, signals and the event loop live in the CLI layer; the library exposes frames and encoders, never a tty, and WASM and the C API carry frames and text only). `--follow` polls modification times and does not use inotify or kqueue. The soundtrack is generated, played by an external player and silent unless asked for, in CI and over SSH. See [terminal rendering](./tui.md#design-decisions).
