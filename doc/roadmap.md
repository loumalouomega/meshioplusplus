# meshio++ roadmap

Status at time of writing: **v19.0.0**, ABI 44. What ships is listed where it is documented rather than counted here, where counts went stale: the formats in [supported formats](./formats.md) and the [conformance matrix](./conformance.md), the operations in [architecture](./architecture.md#the-operations-layer), the language surfaces in the [C API](./c_api.md), [Fortran](./fortran.md), [Julia](./julia.md), [R](./r.md), [Octave / MATLAB](./octave.md) and [WebAssembly](./wasm.md) pages.

This document lists what is *not* built. Nothing here duplicates shipped functionality; where a feature partially exists, the shipped half is named and the gap is stated explicitly. Release history lives in [`CHANGELOG.md`](https://github.com/loumalouomega/meshioplusplus/blob/main/CHANGELOG.md), not here.

Effort key: **S** = days, **M** = a couple of weeks, **L** = a month or more, **XL** = a project in its own right. An item names a **probe** — the failing test that proves the gap — wherever one is cheap.

## How this file works

- **Sections are ordered, and the order is the recommendation.** Each section states what belongs in it; an item that sounds exciting does not move up for that reason. An empty section is removed, not kept as a placeholder.
- **A closed item is removed, not struck through.** Its history is the `CHANGELOG.md` entry and the feature's own `doc/` page; a partly closed item is narrowed to what remains (the `AGENTS.md` change checklist rule).
- **Every level of the outline is numbered**, so a gap can be cited in an issue, a commit or a release note: a group of work is `section.item` (a `###`/`####` heading, or a bold label line), the work under it `section.item.subitem`, and a bullet under that `section.item.subitem.subsub`. Lists that record a decision rather than open work — *Considered, not queued*, a section's *Landing an item* steps and the [non-goals](#non-goals-and-decisions-taken) — stay unnumbered, because a number here means work to do. The numbering follows the sections, so a new section inserted at the top renumbers the rest, as the rule above says, and so does a section removed once its last item closes (Performance, October 2026: what was §4 onward moved up one; and again when reader and writer parity closed, the same month: operations, ecosystem reach and the full WebAssembly build became §3 to §5). - **Defect-shaped items go in a *Correctness debts* section at the top, regardless of size** — behaviour that loses data, mis-orients cells, does not terminate on valid input or fails silently is not a feature request, even when the fix and the feature are the same work. The section is removed when its last item closes, which renumbers the rest, and the next defect found opens it again as §1.
- **An item estimated from a doc, a `.d.ts` or a changelog alone says so** ("verify first") and names its probe; the code has repeatedly been more or less capable than its description.
- **[Non-goals](#non-goals-and-decisions-taken) record decisions already taken**, with their reasons, so they are not re-proposed as gaps.
- **Every open item is written to be picked up without a planning pass** (November 2026). It states what exists today with the place in the code that proves the gap, what to reuse, ordered steps numbered so one can be closed alone, tests and fixtures, and a *done when* probe; a design-pass item lists the decisions to take and the option the code favours. Line numbers are those of `master` in November 2026 and drift: each is given beside a function, option or message name, which is what to search for. A claim an item could not check in the code says *verify first*.
- **A priority is optional and only for sections that need to be ordered against each other** (§10 to §12 do not use one; their order is the sequencing's). Where an item carries one: **P0** blocks correctness or a release, **P1** the next release, **P2** planned, **P3** opportunistic or a spike. It never replaces the effort letter.
- **GPL and AGPL implementations (Gmsh's sources, ScanRuler) inform an item only through their documented behaviour**; no code is read from them or ported ([non-goals](#non-goals-and-decisions-taken)).

## 1. Correctness debts {#correctness-debts}

*Admission: behaviour that loses data, mis-orients cells, does not terminate on valid input or fails silently ([how this file works](#how-this-file-works)). Reopened in November 2026 by the pass that put code anchors on every item, which found the first item below while checking what was then 1.1.2.*

### 1.1 Ansys `.rst` records flagged both bit-sparse and windowed-sparse are refused, not yet decoded

Three files of Ansys' DPF example data hold records with both flags set; their layout is neither form's. Both engines refuse such a record by name (`ReadError` naming the record pointer and the flags; [Ansys `.rst`](./formats/ansys_rst.md#not-read)); decoding it is what remains. **M**

- **State today.** `src/cpp/src/formats/ansys_rst.cpp`: `RstFile::Record` refuses the both-flags case right after the zlib check, and `src/python/meshioplusplus/ansys_rst/_ansys_rst.py` (`_Reader.record`) does the same; `test_both_sparse_flags_refused` and `TEST(AnsysRst, RefusesBothSparseFlags)` pin it, with a fuzz seed in `tests/fuzz/regressions/ansys_rst/both-sparse-flags`. pymapdl-reader misreads these records too.
- **Steps.**
  - **1.1.2 Decode it.** Find the layout: locate the three DPF example files (`ansys-dpf-core`'s `examples` module downloads them; record their names and hashes), dump each both-flag record's header and length beside the dense values DPF returns for the same result set, and test the two candidate layouts (a windowed run inside each set bit, or a bit mask over windows). Needs a DPF Server (2.2.3's installation). When one layout reproduces DPF's values on all three, implement it in both engines .
- **Done when.** A file with such a record reads to DPF's values in both engines; `pytest tests/python/test_ansys_rst.py -k both_sparse` then asserts values rather than the refusal (`MESHIOPLUSPLUS_STRICT_CORE=1` for the core).

## 2. Format reach {#format-reach}

*Admission: a format a simulation or physics-ML workflow actually exchanges; a shipped format's missing half is not a roadmap item, because every registered format reads and writes ([decisions](#non-goals-and-decisions-taken)). "Exchanges" means a file that crosses a tool boundary in a real pipeline (mesher → solver, solver → post-processor, solver → training set), not a format that merely exists. Every item names the consumer on the other side of the file.*

Sizes: **S** ≈ days, **M** ≈ two weeks, **L** ≈ a month or more, including tests, docs page and CLI wiring. They assume a new format reuses the shared components rather than growing its own: the card tokenizer (`detail/keyword_card.hpp`), the [node-ordering registry](./node_ordering.md), the Fortran record reader (`detail/fortran_records.hpp`) and the directory sniffing that sequence globs share.

Link legend: unmarked links were opened or returned by a search while this section was written (September 2026); links marked † are quoted from memory and must be checked before relying on them. Vendor documentation portals move often — when a link is dead, search the document title.

Every format this section queued is now read: the native FEM interchange, solver input and result-file readers of v16.5.0 to v16.12.0 (Tecplot, Femap, MFEM, Patran, Abaqus `.fil`, Radioss, Z88, libMesh, Marc, Ansys `.rst`, LS-DYNA and OP2), DOLFINx's ADIOS2 `.bp` ([`vtx`](./formats/vtx.md)) and Tecplot SZL through TecIO ([`szplt`](./formats/szplt.md)) of v16.13.0, and the [vendor-runtime routes](./vendor_routes.md) for the files only a vendor's software reads (Abaqus `.odb`, Marc `.t16`, Femap `.modfem`, Ansys results beyond the native reader). Since v16.17.0 the shared components are used wherever a format's layout fits them, the input decks are written too (Radioss's starter deck, checked with the OpenRadioss starter, and Marc's), Femap writes a series as one output set per step, and every format read but not written names its reason on the [conformance page](./conformance.md#formats-missing-a-direction), which a test keeps in step with the registry; the missing half of each has since been written, so every registered format reads and writes. What they still lack is a check against a run of the vendor tool, listed under [Awaiting a licensed run](#awaiting-a-licensed-run): take each as soon as a licence, or a file the tool wrote, is in hand.

### Considered, not queued

- **Graphics, CAD, VFX or lab-specific rather than simulation interchange:** X3D, VRML, Alembic, Silo, FBX, COLLADA, AMF, BYU, Rhino `.3dm`, Parasolid, OpenCASCADE `.brep`. DXF, once listed here, was reopened for sketches and outlines measured from a scan and ships as a drawing format ([DXF](./formats/dxf.md)); 3MF, E57, LAS/LAZ, OpenVDB and OBJ materials, listed here until November 2026, were reopened the same way, because the operations that produce or consume them have shipped since (2.4.5 to 2.4.8).
- **Building and city models, and GIS vector layers:** IFC, CityGML and CityJSON, GeoJSON, Shapefile, GeoPackage. Their consumers want semantics (storeys, attributes, layers) a `Mesh` does not carry, and GDAL and IfcOpenShell serve them; [WKT](./formats/wkt.md) stays the one geometry exchange. Revisit with 9.10.2 if georeferenced meshes become a workflow.
- **Medical image volumes:** NIfTI, NRRD and DICOM are voxel images, not meshes; an array from nibabel or SimpleITK reaches [`isosurface`](./isosurface.md) through `grid` today. The surface formats of the same pipelines are 2.4.4.
- **Closed CFD databases:** STAR-CCM+ `.ccm` (libccmio is not redistributable) and `.sim`; FUN3D and FAST grids beyond what [UGRID](./formats/ugrid.md) already reads.
- **Closed FEM databases with no route worth shipping:** Altair `.h3d` (undisclosed format, SDK not redistributable — Altair's own advice for OpenRadioss is ANIM → VTK, see the [OpenRadioss discussion](https://github.com/orgs/OpenRadioss/discussions/552)); HyperMesh `.hm`; Abaqus `.sim`.
- **No native format to implement:** deal.II (reads and writes UCD, VTK, Gmsh, Abaqus, Exodus — all reachable today); MOOSE (Exodus).
- **Nastran OP4 matrices and punch `.pch`:** matrix and card dumps, not mesh/field exchange; pyNastran serves them.
- **Non-MSC Nastran HDF5 dialects:** incompatible schemas; revisit with a file in hand.
- **Partitioning niche:** gmsh `$PartitionedEntities` (Kratos partitions through MDPA).
- **CalculiX `.dat` print files:** `frd.read_dat` stays a Python helper that returns a list of table dictionaries; it is not a `Mesh`, it has no writer, and `.dat` already belongs to Tecplot and Marc ([CalculiX results](./formats/frd.md)).
- **Operators, not formats** (listed only because they came up in the same review): mesh duals other than the tetrahedral median dual (now [`tet_to_poly`](./tet_poly.md)). ICP registration, the cylindrical and spherical transforms and the shell completions, listed here with them, shipped as [`register_rigid`](./registration.md), [`convert_coordinates`](./coordinates.md) and `meshioplusplus completion`.

Revisit any of them when a consumer asks with a file in hand — a real deck or result file, the tool version that wrote it, and the tool that needs the converted output.

### 2.2 Awaiting a licensed run {#awaiting-a-licensed-run}

Checks that need the vendor tool itself, or a file it wrote that no public source has. Each reader works from the vendor's documentation and every public file found (September 2026); what remains is one probe per line. The procedure is the same for all of them, so it is stated once.

**Recording a run.**

1. Run the probe the item names, on the vendor version it names or a later one.
2. If the run produces a file worth keeping and its licence allows redistribution: put it under `tests/python/meshes/<format>/` with a `README.md` in the form of `tests/python/meshes/szplt/README.md` (a `<!--pytest-codeblocks:skipfile-->` first line, who wrote the file with which tool and version, a table of files, the licence), add the directory's rule to `.gitattributes` (`filter=lfs` for large binaries as for `nastran_op2/*.op2`, or `binary -filter` to keep small ones out of LFS as for `frd` and `szplt`), and add a paragraph to the comment block at the top of `CITATION.cff` (source, copyright, licence, "redistributed unmodified") and a line to `CHANGELOG.md`. A file that cannot be redistributed is described on the page, with its hash, and a reference `.npz` of what the vendor tool reads from it is frozen by a `tools/gen_<format>_reference.py` in the pattern of `tools/gen_vtx_reference.py`.
3. Turn the stand-in test into a real one beside it (the table names both), skipped when the fixture is absent, never deleted: the stand-in still guards the script's calls.
4. Write the vendor version and the date into the page section the table names; where the table says *add*, create a `## Checked against` section as [Abaqus `.odb`](./routes/abaqus_odb.md) has.
5. Fix what the run finds in both engines, with the minimized input as a fuzz regression if it was a crash, then remove the item here and its clause in the [non-goals](#non-goals-and-decisions-taken)' *facts of the format* if the run turned a fact into a feature.

### 4.2 Rust bindings

Over the C API: the next language by scientific adoption after Julia and R. **M**

- **State today.** No `bindings/rust`. The header `bindings/c/include/meshioplusplus/meshioplusplus.h` (9,181 lines; 639 functions, about 163 structs, about 30 enums) is C99, includes only `stddef.h` and `stdint.h`, and CI compiles a `-std=c99` consumer. Conventions (header lines 25–40): a status or `NULL`/`-1` return with the thread-local `mio_last_error()`; setters copy; getters borrow until the next mutation; row-major, 0-based; string getters follow `snprintf`. Discovery: `meshioplusplus.pc` and `find_package(meshioplusplus)`.
- **Design.**
  - `meshioplusplus-sys`: `bindgen` at build time from the installed header (`pkg-config` crate; `MESHIOPLUSPLUS_DIR` override), with care for: `MIO_API` needing `MIO_SHARED` on Windows, which the `.pc` does not set; the `MIO_CELL_TYPES(X)` X-macro behind `enum mio_cell_type` (lines 178–208), which bindgen expands; the function-like `MIO_VERSION_AT_LEAST`, which it skips (re-express as a `const fn`); enums as `newtype` constants, since the C side may add values. A `vendored` feature that builds the C library with the `cmake` crate.
  - `meshioplusplus`: safe wrappers. `Mesh` owns a `*mut mio_mesh` and frees it in `Drop`; the borrow window is the lifetime system's job: getters return `&[T]` or `ndarray::ArrayView` tied to `&self`, and every mutating method takes `&mut self`, so "borrows expire on mutation" is checked at compile time. Option structs are built by `*_opts_init` then field assignment behind builder types, never by literal (the reserved tails must stay zero). Errors: a `Result<T, Error>` carrying the status and `mio_last_error()`.
- **Steps.** (1) `bindings/rust/{meshioplusplus-sys,meshioplusplus}` as a workspace, version in step with the others (a row in `AGENTS.md`'s version table). (2) Tests ported from the Julia suite's sections (`bindings/julia/MeshioPlusPlus/test/runtests.jl`: introspection, shape identity, the borrow window, file round trip, regions, each operation, errors carrying `mio_last_error()`, the XDMF series). (3) A parity guard, which no binding but Octave has today: `tests/python/test_binding_parity.py` parses the C header's function names and checks each is wrapped or listed as exempt, for Julia (`ccall(_sym(:mio_…))` in `src/*.jl`), R and Rust alike. (4) A `rust` CI job in the pattern of `julia` (`ci.yml` lines 2488–2584: build the C API, run the tests against it, run the doc example, check that a missing library fails by name). (5) `doc/rust.md` on the template of `doc/julia.md` (building, array layout, the borrow window, memory, errors, documented gaps, tests), in the *Language surfaces* sidebar group (`doc/.vitepress/config.mts` line 253), and the binding lists in `AGENTS.md`. (6) crates.io publication from the release workflow.
- **Done when.** `cargo test` passes against an installed C library on the three platforms, and the parity test covers every `mio_` function.

### 4.9 An MCP server for programs that embed meshio++

The [MCP server](./mcp.md) is a Python process. A program that links meshio++ as a C++ library, through the C API or the single header, or that loads the WebAssembly package, has the operations but no way to offer them to an agent, and the Python-free native CLI has no `mcp` verb. **L, design pass first**

- **State today.** Native pieces that exist: `detail/json_value.hpp` (core-private: `JsonValue`, `parse_json`, `write_json`, non-finite numbers written as `null`), which the single header and WASM can carry, unlike the pipeline's JSON front end and `pipeline_report_json`, which need the optional nlohmann; `src/cpp/cli/json_out.hpp` (`JsonOut`, a streaming writer with no truncation and no non-finite count); the registry; `apply_pipeline_step` and `run_pipeline_steps` (`include/meshioplusplus/operations/pipeline.hpp` lines 191 and 198) over `PipelineStep {mOp, mParams}`, with the step table generated from `tools/pipeline_steps.json` (111 steps with each key's kind and default). The Python side: sandbox, read cache (`_CACHE`, `_cache_limit`, `_cache_key`; `_tools.py` lines 450–477), sanitizer (`_MAX_ARRAY = 1000`), 203 tools of which about 100 are named after a pipeline step and about 104 are not (generators, inspection, multi-mesh operations, datasets, training, rendering). No native MCP code exists.
- **4.9.1 Design pass.** Decide and write down in a `doc/mcp_native_plan.md`:
  - *The native tool set*: `read`/`info`/`convert`/`formats`/`sniff` through the registry; one tool per pipeline step type, dispatched through `apply_pipeline_step` and described from `pipeline_steps.json` (never a second dispatch); the generators and the two-mesh operations (`merge`, `interpolate`, `diff`, `hausdorff`), which the pipeline's v2 steps partly cover. Python-only tools (training, datasets, Arrow and Parquet export, the viewers) are recorded exemptions.
  - *One source of truth for schemas*: 4.4.2's generated schema file, committed, with the Python registration and the native server both checked against it; `pipeline_steps.json` gains the per-key descriptions it lacks.
  - *The JSON layer*: promote `detail/json_value.hpp` to what the server uses for parsing and writing, with the truncation wrapper and the non-finite count added there; the pipeline's JSON front end moves onto it too, which removes the nlohmann requirement from `pipeline_report_json` (a prerequisite, and a gain on its own for the single header and WASM).
  - *Whether the Python server delegates* its sandbox and sanitizer to the core once they exist there, or keeps a twin held equal by tests. Recommended: keep the twin for one release, then delegate.
- **4.9.2 The core server.** An installed header `meshioplusplus/mcp.hpp`: `McpServer` with `HandleMessage(std::string_view json) -> std::string` (JSON-RPC 2.0: `initialize`, `tools/list`, `tools/call`, `ping`), so the host owns its transport; `ServeStdio()` for the common case; `McpOptions` (sandbox root, read-cache budget, tool allow-list, host name and version); `AddTool(name, schema, callback)` for host tools. ## 8. Data model {#data-model}

*Admission: something files hold and users ask for that `Mesh` has no place for, so that every format carrying it drops it, splits it or hides it in a naming convention. Each item may change `NDArray` or `Mesh`, and then it reaches every mesh backend (MESHIO, NATIVE, KRATOS), every binding and the [ABI](./abi.md): each starts with a design pass in the manner of the [long-run spikes](./spikes.md), which decided the last two questions of this kind (NURBS as a side channel; the isogeometric layer beside `Mesh`), and the outcome may again be "a convention, documented and tested" rather than a new type. Each item lists the questions its pass must answer and the option recommended from what the code shows today. The order is by how many shipped formats lose data for want of each.*

**What a new dtype touches**, for 8.1 and 8.2: `enum class DType` and `dtype_size`/`dtype_numpy_str` (`src/cpp/include/meshioplusplus/ndarray.hpp` lines 225–270); `detail::DTypeUtils` (`src/cpp/src/detail/dtype_table.hpp`, `kNumDTypes = 10`) and `dispatch_dtype` (`detail/value_io.hpp` line 180); `dtype_from_numpy` (`bindings/python/np_conversions.hpp` line 103, which today throws on kinds `b` and `c`, sending the call to the Python twin); `mio_dtype` (`meshioplusplus.h` line 156, values 0 to 9); Fortran's four constants (`meshioplusplus.f90` near line 2281); Julia's `_DTYPES` (`libmio.jl` line 93); R's `mio_r_fill_real`, which widens everything to double; Octave's `dtype_of_class` (`util.c` lines 421–433); WASM's `js_typed_array_ctor` and `dtype_of_js_array` (`js_bindings.cpp` lines 303 and 559); every writer's dtype switch. A new enumerator appended is ABI Tier C for C++ and additive for C, but every `switch` over `DType` in the 86 format sources must handle it, which is the real cost.

### 8.1 Complex values

- **State today.** No complex dtype. The readers that meet complex data already agree on one convention: `<name>_real` and `<name>_imag` in UNV (`formats/unv.cpp` lines 1572 and 1639), OP2 (which converts magnitude and phase to real and imaginary first, `op2_complex`, `formats/nastran_op2.cpp` line 1905) and Nastran HDF5 (`formats/nastran_h5.cpp` line 522). EnSight's complex variables are skipped (2.3.3.5); Ansys `.rst` harmonic sets are neither read nor written (2.2.12).
- **Decisions to take first.** (1) Convention or dtype. Recommended: the convention, since three formats already share it: document `_real`/`_imag` in [mesh data model](./mesh_data_model.md) as *the* form, add helpers `complex_pairs(mesh)` (names that form a pair), `to_complex`/`from_complex` in Python (numpy has the dtype, so a Python user gets `complex128` arrays on request) and a C++ `detail/complex_pairs.hpp`, and have every writer that can store complex data (UNV 2414, OP2, Nastran HDF5, EnSight, VTK through two arrays) recognise a pair and write it as one complex field. (2) Which operations must treat a pair together: `transform` with `rotate_vector_data` (rotate both), `interpolate` (both), `data_calc` (expose `abs` and `phase`). (3) A real dtype only if a consumer needs complex arrays through the C API; then `MIO_COMPLEX64`/`128` as interleaved pairs, by the list above.
- **Steps (the convention).** The page section; the helpers with tests; EnSight complex read and write under it; a conformance property `complex` in `conformance_spec.py` for the formats that hold it; `data_info` reporting pairs as one field.
- **Done when.** One complex OP2 table and one complex UNV dataset read to arrays of the same names and shapes, round-trip through each other's writers, and `to_complex` returns `complex128`. **S** (convention); **L** (dtype)

### 8.2 Strings and booleans

- **State today.** `field_data` is numeric arrays only in the core (`unordered_map<string, NDArray>` in MESHIO, `NamedArrays` in NATIVE, `native_mesh.hpp` line 450); Python's `Mesh.field_data` accepts any dict (`_mesh.py` line 200), and the conversion throws on a non-numeric entry unless `lenient_field_data` skips it (`np_conversions.hpp` lines 487–575), so a string in `field_data` silently selects the Python twin or is dropped. Strings a format holds live in side structs (`ExodusInfo::mInfoRecords`, `MedInfo::mMedNom`). Booleans widen to `uint8` (Octave maps logical to `MIO_UINT8`) and come back as integers.
- **Decisions to take first.** (1) Strings in `field_data`: recommended, a documented encoding rather than a dtype: a `uint8` array of UTF-8 bytes with a companion `<name>:offsets` `int64` array for a list of strings (the ragged layout `NDArray` already carries for polyhedra), written by `np_conversions` from a Python `str` or list of `str` and decoded back, so the core carries them opaquely and every format writer that has a string slot (Exodus info and QA records, CGNS `Descriptor_t`, MED descriptions, VTK `vtkStringArray`) can use it. (2) Booleans: recommended, a `meshio:bool:<array>` marker in `field_data` naming `uint8` arrays that are masks, honoured by the numpy conversion (returns `bool`) and by the formats with a boolean type; no dtype.
- **Steps.** The encoding in `detail/string_field.hpp` with tests; `np_conversions.hpp` both ways; the C API needs nothing new (arrays of bytes) but gets `mio_mesh_get_field_string` as a convenience; the four formats above; drop the silent fallback (a `str` in `field_data` no longer declines the core).
- **Done when.** `Mesh(..., field_data={"title": "wing"})` writes through the core (`MESHIOPLUSPLUS_STRICT_CORE=1`) to Exodus and reads back equal. **M, design pass first**

### 8.3 Integration-point data

Gauss-point results are the primary output of a structural solver, and no operation knows an array is per integration point.

- **State today.** Three per-format conventions, each a cell array of shape `(cells, points × width)` with its layout in `field_data`: Abaqus `.fil` (`abaqus:layout:<name>` = `[points, width]`, point-major, NaN-padded; names with `@sp<k>` section points; `formats/abaqus_fil.cpp` lines 1060–1148); d3plot (`lsdyna_d3plot:layout:<name>`, `formats/lsdyna_d3plot.cpp` lines 1426 and 1992); GiD (`gid:gauss_points:<name>` and `gid:gauss_coords:<name>`, `formats/gid.hpp` lines 275 and 303, the only one that records where the points are). MED's ELGA fields are read by the Python twin as a 3-D `(cells, NGA, components)` array, not written, and declined by the core (`med/_med.py` lines 695–719 and 1104). `.rst` element results and Gmsh's `$ElementNodeData` (2.3.6.1) have the same shape. `interpolate`, `data_average` and `tessellate` treat the columns as components.
- **Decisions to take first.** (1) Recommended: one convention replacing the three, not a third data location: `field_data["meshio:ip:<name>"] = [points, width, rule_id]` on a 2-D cell array, with `rule_id` naming a rule of 3.4.3's quadrature table (point positions and weights in the reference element), or 0 for "nodes of the cell" (element-nodal data) and -1 for "unknown rule" (the order is the file's); the readers write both their old key and the new one for one release. A third location (`ip_data`) would cost every backend, binding and writer for no operation the convention cannot serve. (2) Each format's rule and point order mapped to the table: Abaqus and Ansys element libraries, LS-DYNA's through-thickness points, MED's `GAUSS` localisations (read from the file: MED stores coordinates and weights), GiD's internal and given rules. Where a format's order is undocumented, -1. (3) The operations: `ip_to_points` (extrapolate with the element's shape functions, then average at nodes: the least-squares form for rules with fewer points than nodes), `ip_to_cells` (weighted average), and the reverse `points_to_ip` for writing.
- **Steps.** `detail/integration_points.hpp` (layout read and write, rule lookup); the readers and writers of the five formats on it, with MED ELGA written and read in the core; the two operations by [checklist O](#landing-checklists); `data_info` reporting integration-point arrays as such; conversion MED to GiD and `.fil` to MED as the round-trip tests.
- **Done when.** A `.fil` stress field converts to MED ELGA and to a nodal field whose values match Abaqus's own extrapolation (`.dat` printout) on the truss and a C3D8 run. **L, design pass first**

### 8.4 Data on facets and edges

- **State today.** A `Region` holds a name, kind, dimension, tag and entries (`include/meshioplusplus/region.hpp` lines 123–148; `Side` entries are `(global cell, local facet)` rows, numbered by `detail/cell_faces.hpp` and `cell_edges.hpp`) and no values; `Region` is 120 bytes in `test_abi_layout.cpp`. A value per boundary face today means a duplicated block of surface cells with cell data, which is what the VTK family and OpenFOAM's boundary fields use (the writer maps boundary-block rows to `boundaryField`).
- **Decisions to take first.** (1) Recommended: no change to `Region`; side data is cell data on the lower-dimensional block, and a side region can be turned into such a block and back: `sides_to_cells(mesh, region)` (the facets as a new block with a `meshio:side_of` `(cell, local facet)` cell array) and its inverse, so the formats that store values on sides (CGNS `FaceCenter` solutions and BC data, Exodus side-set variables, UGRID `location = "face"` on volumes, MED face families) read into that form and write from it. This makes the convention explicit and testable instead of per format. (2) Edge data likewise on `line` blocks with `meshio:edge_of`. (3) A data member on `Region` only if a format needs values on sides with no cells to hang them on.
- **Steps.** The two helpers by checklist O (they are `extract_skin`'s neighbours and reuse its facet table); the readers of 2.3.1.4, 2.3.2.3 and 2.4.3.2; a section in [regions](./regions.md).
- **Done when.** An Exodus side-set variable reads as cell data on a quad block that `sides_to_cells` would have produced, and writes back. **M, design pass first**

### 8.5 Hierarchy

- **State today.** Regions are flat; nesting is `/` in the name ([regions](./regions.md), lines 286–298), and the KRATOS backend is the one consumer that interprets it (`BuildSubModelPartsFromRegions`, `kratos_mesh.hpp` line 610; `RestoreRegions`, 995), losing only names that contain `.` and the `mDim`/`mTag` members. VTKHDF assemblies and `.vtm` flatten to it on read.
- **Decisions to take first.** Whether `/` names plus one `field_data` entry are enough to round-trip the trees files hold. Recommended: yes, with `field_data["meshio:tree"]` as a string list (8.2) of the internal nodes that own no entity (an assembly that only groups), since leaves are regions already. Check against: Abaqus parts and instances (instances repeat a part with a transform: the tree names them, the transform goes to `field_data`), VTKHDF `Assembly`, `.vtm` nesting, CGNS families of families, Exodus assemblies (2.3.2.4), USD prims.
- **Steps.** `detail/region_tree.hpp` (parse, build, parent and children queries) with the KRATOS interpreter moved onto it; the five formats' writers rebuild their nesting from it; `regions` reports print the tree.
- **Done when.** A nested `.vtm` and a VTKHDF file with an `Assembly` round-trip with the same nesting. **M, design pass first; after 8.2**

### 8.6 Structured grids that stay structured

- **State today.** `vti`, `vtr`, `vts` and legacy structured VTK are expanded to explicit cells by `detail::vtk_structured_cells` (`src/cpp/src/detail/vtk_xml_pieces.cpp` line 315): eight indices per cell for what three integers describe. Their writers accept only a mesh that `detail::lattice_from_mesh` (`detail/grid_lattice.hpp` line 205) recognises as a lattice, which is why they fail [conformance](./conformance.md) on the canonical mesh. CGNS structured zones are refused (2.3.1.3) and PLOT3D is not read (2.4.2). The physics-ML [grids](./grids.md) are the opposite case: `GridSpec`/`GridArray` in Python with no `Mesh`.
- **Decisions to take first.** (1) Recommended first step: an annotation, not a block kind: `field_data["meshio:structured:<block>"] = [ni, nj, nk]` (point counts) set by every structured reader on the block it expands, checked by `lattice_from_mesh` instead of re-deriving, honoured by the structured writers (which then also accept curvilinear lattices for `vts`, CGNS and PLOT3D without geometric detection), and removed by any operation that changes the block's points or cells (the pipeline clears it unless the step is data-only or a rigid transform; an explicit list, tested). This closes the three conformance failures by declaring what the formats hold, and costs no ABI. (2) An implicit-connectivity block (`CellView` generating corners from indices) only for 10⁸-cell voxel data: every operation's hot loop reads connectivity through `CellView`, and the measured cost of changing it is what kept the backends' `CellView`s apart ([§6](#code-duplication)). XL, and only with a workload.
- **Steps (annotation).** The key and its invalidation rule in [mesh data model](./mesh_data_model.md); readers (`vti`, `vtr`, `vts`, legacy VTK, VTKHDF image data, CGNS, PLOT3D, EnSight `block`) set it; writers use it; `conformance_spec.py`'s three `error` declarations become lattice round-trips; `to_grid(mesh)`/`from_grid` join `Mesh` and the Python `GridArray`.
- **Done when.** `read("a.vts")` then `write("b.vts")` is exact, and the same mesh after `smooth` is refused by name. **M** (annotation); **XL** (block kind), design pass first

### 9.2 Smooth subdivision

- **State today.** [`refine`](./refine.md) splits at midpoints (`RefineOptions`, `operations/refine.hpp` line 356; `refine_once`, `refine.cpp` line 292) and [`subdivide`](./subdivide.md) is polyhedral; neither moves a point. No Loop or Catmull–Clark code exists anywhere (`fit_cad`'s patch network fits B-spline patches by other constructions). Crease and boundary classification exists: `crease_edges`, `crease_edges_triangles` and `CreaseEdge {IsBoundary, IsNonManifold, IsCrease}` (`src/cpp/src/detail/crease_edges.hpp`), already behind `feature_edges`, `decimate` and `smooth`.
- **Design.** A new operation `subdivide_surface(mesh, SubdivideSurfaceOptions {mScheme: Loop|CatmullClark, mLevels, mFeatureAngleDeg, mPreserveBoundary, mRecordParentIds})`, not an option of `refine`: `refine`'s contract (points of the input are points of the output, bit for bit; green closure; hierarchy arrays) does not hold when points move. Loop for triangle blocks (Warren's weights; boundary and crease edges by the cubic B-spline curve rule; corners fixed), Catmull–Clark for quads and polygons (output all quads); creases from `crease_edges` at the feature angle, semi-sharp not offered. Point data is subdivided with the same masks, cell data inherited by children, regions remapped through `detail/region_remap` with `FirstChild`. Topology by one pass over an edge table (`detail/edge_table` as `refine` uses), `parallel_for` over points for the masks, serial numbering for determinism. A numpy twin with the same arithmetic order.
- **Tests.** Limit positions on a regular patch against the closed form; a cube converging to its Catmull–Clark limit volume; a creased cube staying a cube at feature angle 30; determinism across backends (`thread_sweep.hpp`).
- **Done when.** `meshioplusplus subdivide-surface coarse.obj out.obj --scheme loop --levels 2` on every surface. **M**

### 9.3 Ray and nearest-point queries

- **State today.** Two private-or-installed kernels and no public operation. (2) Only if a caller needs many batches on one mesh: a `SurfaceQuery` handle owning the soup and both trees, following the existing handle conventions: C `mio_surface_query_create`/`_free` like `mio_sequence` (`meshioplusplus.h` lines 6177–6229), Julia a mutable struct with a finalizer, R an external pointer, WASM an integer handle in the module table (`js_bindings.cpp` lines 10441–10462), pybind a `py::class_`.
- **Surfaces.** Checklist O; arrays in, arrays out, so the flat bindings need no new conventions for (1). MCP tools write the hits as a point-cloud file.
- **Tests.** Rays against an analytic sphere and a box; grazing rays (edge and vertex hits counted once); `locate_points` on every volume cell type with points on faces; agreement with `interpolate` on a field (`f(locate(p))` equals `interpolate`'s value bit for bit).
- **Done when.** `cast_rays` and `locate_points` on every surface; the handle only on request. **M**

### 9.4 Mass properties

- **State today.** `compute_stats` (`operations/stats.hpp` line 47: `StatsReport`) gives `mTotalArea`, `mSignedVolume`, `mUnsignedVolume` and an `mCentroid` that is the mean of the points, not the centre of mass; [`measure`](./measure.md) is GD&T, not mass. `data_integrate` integrates a field per region with `detail::cell_measure` (`detail/data_ops.hpp` line 243). `poly_measure` (`detail/polyhedron.hpp` line 198) returns a true centroid per polyhedral cell; `closed_surface_volume` is private to the boolean spike.

For a closed triangle surface: the divergence-theorem polynomials (Eberly's formulation; exact for a polyhedron), sharing 3.4.2's `ClosedSurfaceVolume`; for volume cells: tetrahedra exactly, other types by simplexification (`convert_cells`' tables) so curved cells are approximated as elsewhere and the page says so; an open surface is refused by name unless treated as a shell.

### 9.5 Elevation beyond order 2

- **State today.** `ccells_elevate` (`src/cpp/src/operations/convert_cells.cpp` line 835) refuses the full-Lagrange targets `quad9`, `hexahedron27`, `wedge18` and `pyramid14` (lines 845–849, `ccells_is_full_lagrange`, 191–194) and has no entry above order 2 (`ccells_elevate_table`, 168; twin `_ELEVATE`, `_convert_cells.py` line 99). - **Design.** `convert_cells(mesh, "elevate", order=q)` and `"reduce", order=q` for any supported shape: the new nodes are the geometry interpolated at the target lattice's nodes with `interpolation_matrix` (order p to q), deduplicated across cells by their owning edge, face or interior (an edge table and a face table keyed by sorted corner ids, as the order-2 path does for mid-edge nodes); point data interpolated by the same matrix; fixed types up to the registry's limit, VTK Lagrange ragged cells above. - **Tests.** Elevate then reduce is the identity on points and data; a polynomial field of degree q is reproduced exactly at the new nodes; node counts against the closed form per shape; VTK reads a written order-4 mesh with positive Jacobians (the `pyvista` gated test).
- **Done when.** `convert_cells(elevate, order=3)` on a tetrahedral mesh gives `tetra20` on every surface, and `order=2, full=True` gives `hexahedron27`. **M**

### 9.6 Repeated and mixed green refinement

- **State today.** [`refine`](./refine.md#what-is-not-implemented) names two limits. A later selective pass refines the green (transitional) cells directly, so repeated passes over one region degrade quality without bound. And mixed-type green (a quadrilateral closed into triangles, a hexahedron into pyramids) is not offered, because one input block would emit several output blocks, which the `FirstChild` cell-map contract cannot express (`RefineResult::mCellMaps`, `operations/refine.hpp` line 427; `CellMapKind {Direct, FirstChild, Global}`, `include/meshioplusplus/detail/region_remap.hpp` line 100). `undo_green(coarse, fine)` exists (`operations/undo_green.hpp` line 134) but needs the coarse mesh and undoes a single-pass hierarchy only; the hierarchy reader is `detail/refine_hierarchy.hpp`.
- **Steps.**
  - **9.6.1 Undo before refining.** A `RefineOptions` flag `mUndoGreenFirst` (from the reserved space: `mio_refine_opts` has `reserved[5]` free; the C++ struct is pinned at 120 bytes, so a new member is Tier A): before a selective pass, cells whose `refine:entity` marks them green are merged back to their parent using `refine:parent_id` and `refine:cell_id` alone (no coarse mesh: rebuild the parent's corners from the children's, which the templates of `detail/refine_templates.cpp` make possible), the parent is marked for red refinement if any child was selected, and closure runs again. Requires `record_hierarchy`, and raises by name without it. Extends `undo_green` to multi-level hierarchies as a by-product. **M**
  - **9.6.2 Mixed-type green.** Decide the map shape first: `CellMapKind::Global` (one global child-range per input cell) exists internally; expose it for `refine` when `mClosure = MixedGreen`, with every binding's map accessor returning the global form. Then the templates: quad with one or three marked edges into triangles, hexahedron into pyramids and tetrahedra around a refined face. **M–L, design pass first**
- **Done when.** Ten selective passes over the same region keep the minimum scaled Jacobian above a stated bound (a test that fails today), driven by `error_size` in a notebook.

### 9.7 Partitioning

## Non-goals and decisions taken

Recorded so they are not re-proposed as gaps. A decision is reopened when what it rested on has changed, and then it is narrowed here, with the date and the number of the item that took it up; the November 2026 review read each against what has shipped since. It reopened five (surface booleans through a backend, 9.1; decomposed files read without MPI, 2.3.8; the `zarr` and `pmsh` stores in the core, 4.15; an in-place `transform`, 5.14; vector kernels behind runtime dispatch, 5.15) and four formats of *Considered, not queued* (2.4.5 to 2.4.8), and left the rest as they stand: the reasons recorded for the native constrained tetrahedralisation, NURBS as an entity kind in `Mesh`, Kokkos device execution, link-time optimisation by default (though a profile was never tried: 5.12), solver-coupled learning, contact mechanics, the copyleft codes and the CAD modeller have not moved.

- **Every registered format reads and writes, in both engines** — decided in October 2026, when the parity tier closed; it reversed the earlier non-goals that kept result files and the export-only formats read-only. A format reads and writes in the C++ core and in its Python twin, so it reaches every surface (C, Fortran, Julia, R, WASM, both CLIs and the MCP server's format capabilities); a core-only path is unreadable from the surfaces that have no fallback, a Python-only one has no twin to check it against. `read(write(m))` equals `m` within the limits the format itself imposes (single precision, a cell type it has no slot for, a concept it cannot express): a loss that is a fact of the format is stated on its page and in the [conformance](./conformance.md) notes, and one that is only an unwritten feature is a gap that reopens a *Reader and writer parity* section here. A new format or direction lands as `AGENTS.md` says (native writer registered in `registry.cpp`, parameters through `WriteOptions`, the Python twin behind `core_declined`, the arrays a reader returns written back under the same names, a `SPEC` declaration and a *Writing* section). The exemptions are recorded in `tests/python/conformance_spec.py` (`READ_ONLY`, `ENGINE_EXEMPT`, `PARTIAL_ENGINE_EXEMPT`) and checked by `test_conformance.py`:
  - **Pure 2-D drawings.** `svg` and `tikz` draw a mesh rather than store it: their readers parse only the structure meshio++'s own writers emit, return the geometry as planar (`z = 0`) and warn once per read that depth, and whatever else the drawing could not hold, is lost; anything else in the file is a `ReadError` naming the construct, never a guess.
  - **`ansys_rst_cyclic`**, which is not a file but the full rotor a cyclic `.rst` expands to; its write side is `ansys_rst`'s cyclic option. **`step` and `iges`** outside a build with OpenCASCADE: reading a CAD model means a CAD kernel, which the `meshioplusplus-occt` add-on wheel (since v18.0.0) and the release binaries carry and a source build finds when it can ([skin to CAD](./cad_fit.md), [STEP](./formats/step.md#reading)); on WASM the lean build is the exempt one, and the [full build](./wasm.md#lean-and-full-builds) carries the kernel.
  - **One engine only, by decision**: GiD (gidpost and its Gauss points are implemented once, in the core), the OpenFOAM case writer and its zone, field and multi-region reading, CGNS's face-based polyhedra (the writer's winding repair is a discrete branch two implementations could resolve differently), the CAD readers, and the `step` writer's merged and fitted faces (`faces="planar"`/`"fitted"`, with `segment`'s primitive method that feeds them: loop walking, vertex snapping and the primitive growth are discrete branches too, so the twin writes `faces="facet"` byte for byte and nothing else); the Python entry points raise naming the missing core rather than guess.
- **What the parity tier left as facts of the format**, each stated on the format's page and in the conformance notes, none an unwritten feature:
  - **`nastran_op2`** writes the MSC dialect only (32-bit little-endian words, SORT1 tables). 64-bit words, big-endian files, NX/Simcenter's interlaced table names and double-precision GRIDs are read and detected, not written: a post-processor reads the MSC dialect with no flags, and whether NX accepts it is a vendor check ([2.2.14](#awaiting-a-licensed-run)). The random PSD, CRM and ATO tables are written as SORT1 magnitudes, as the reader reads them (MSC writes them SORT2, and pyNastran reads only the RMS and NO ones in SORT1); no SORT2 pivot is written. Elements on scalar points (`CELAS3`/`CELAS4`, `CDAMP3`/`CDAMP4`, `CMASS3`/`CMASS4`) and `CBUSH1D` and `CBEND` have no cell type — `Mesh` has no scalar-point entity to hang them on — and are skipped with a warning.
  - **`nastran_h5`** writes a table only where an MSC sample fixes its layout: `CBUSH`, `CGAP`, `CMASS` and `CONM1` elements, and `MAT5`, `MAT8`, `MAT9`, `PBARL`, `PBEAML` and `PCOMPG` values, have no table in the six MSC Nastran 2020 files at hand, so the elements are left out and the values go on the plain cards, each with one warning; the OP2 file holds them.
  - **`lsdyna_d3plot`** leaves the rigid roads' full rigid-body velocities (`NDIM = 9`) out of the state, and writes an airbag variable under a title-case name, since the names of a real file are in no manual available.
  - **`radioss_anim`** writes the nodal normals as zeros: `anim_to_vtk` ignores them and their 16-bit encoding is undocumented.
  - **`abaqus_fil`** writes 8-byte words only, the reader's width; a single-precision build's 4-byte layout has no description or sample.
  - **`ansys_rst`** has no complex (harmonic) results, read or written (8.1 gives them a form once a sample exists): no public sample or open reader covers them, and DPF alone reads them. The nodal coordinate systems are written as `ansys:node_angles` and agree with pymapdl-reader only for single-axis angles, since it applies the three turns in the opposite order.
  - **`xplt`** writes a per-surface-node variable as `FMT_NODE` in surface order, where the reader averages the values a node on two surfaces has into one point value, which both surfaces then write.
  - **`marc` and `marc_t19`**: edge and face sets stay `(cell, number)` field data and side regions are dropped, since mapping them to facets needs Volume A's numbering ([2.2.11](#awaiting-a-licensed-run)); the Herrmann, bubble and generalized-plane-strain types come back as the default type of their shape, and a deck holds no data arrays.
  - **`szplt`** does not write polygon and polyhedral zones: TecIO 2018.3, the newest source available, refuses them in an SZL file, so the reader refuses them by name too and the face-based zones stay with the `.plt` and ASCII readers. Partitioned output is for tetrahedron and brick zones of a static file only (TecIO's own limit), and a series is written whole.
  - **`vtx`**: DOLFINx and ParaView read one cell type per file, so a file of several cell types or parts is meshio++'s own extension of the layout.
- **Generators the primitives leave out** — recorded when roadmap §3.1 closed (October 2026), with the [parametric primitives](./primitives.md#not-generated): generators driven by a user callback (no callback crosses the flat ABI; numpy users build `Mesh(points, cells)` directly, and [`isosurface`](./isosurface.md) on a `grid` covers implicit shapes); scanned or modelled assets (the bunny, the teapot, the bracket fixture — data rather than parameters, each under its own licence); and CSG combinations, under the volume-meshing non-goal below (surface booleans were reopened as a spike and kept out on its measurements, [findings](./spikes.md#surface-booleans-formerly-roadmap-7-8)) — two-body interface and contact fixtures are primitives placed with `transform` and joined with `merge`.
- **MPI in the library** — none planned ([C++ API](./cpp_api.md)); `partition`'s ghost layers produce the halo an MPI assembly in the owning application needs. ParMmg, MMG's MPI layer, is excluded with it. Narrowed in November 2026: reading the files a parallel run left, one per rank, into one mesh needs no MPI, as the OpenFOAM and `pvtu` readers show, and is queued for the formats that lack it as 2.3.8. Added November 2026: this also excludes MPI-parallel writers (parallel HDF5, collective `cgp_*`) from [§10](#in-situ-interchange), whose adapters take the data a rank holds and never talk to a communicator; reopen only with an application that needs a shared file and cannot gather.
- **Solver-coupled physics-ML** — assembled solver residuals, adjoints and Sobolev training, co-simulation, active-learning *labeling*, adaptive remeshing driven by a surrogate, and MPI model-part gathering. Every one needs a live solver (an assembly routine, its tangent, its communicator) and meshio++ has no notion of a discrete system; they belong in the application that owns the solver, the division [Symbolic and physics](physicsnemo/symbolic_and_physics.md) describes.
- **The Python-only layers stay Python** — `pmsh`, `zarr`, `cae` and `usd`, and the physics-ML surface (grids, point budgets, proximity graphs, datasets, training) are export targets and tooling for a training pipeline, registered in Python rather than the shared C++ registry. A core kernel they call (the neighbour search) does not change that; `tessellate` moved to the core ([tessellation](./tessellation.md)) because the native CLI and the flat bindings needed it, and its `Tessellation` helpers stay Python. Narrowed in November 2026 for the two stores a dataset is written to: reading `zarr` and `pmsh` in the core, so the browser, the flat bindings and the native CLI open what Python wrote, is queued as 4.15 behind a design pass; `usd`, `cae` and the physics-ML surface stay as decided.
- **Polyscope in the release CLI executables** — excluded deliberately, so `view`/`screenshot` there report the build flag rather than opening a window ([viewer](./viewer.md)): the executable stays free of OpenGL, GLFW and X11. Narrowed in November 2026, once v18.0.0's plugins made it possible: a Polyscope plugin loaded beside the executable is queued as 4.8.2.
- **General volume meshing algorithms as native operations** — constrained tetrahedralization of a domain, hex-dominant meshing and general hex meshing from a CAD-like boundary, boolean/CSG, boundary-layer inflation and quadrangulation are each a library in their own right. (Narrowed in November 2026: geodesic distance, once listed here, is not one, since the heat method needs only the P1 operators and the sparse solver the core has, and shipped as [`geodesic_distance`](./geodesic.md); surface booleans were measured by a spike in November 2026 (exact in topology, but rounding its output to doubles left most curved results self-intersecting and coplanar contact unhandled, so no native operation is queued: [findings](./spikes.md#surface-booleans-formerly-roadmap-7-8), though the backend route this non-goal names was not measured for them and is, since the same month, 9.1); and v18.0.0's provider registry is the optional-backend route below, which external meshers and field-aligned quads now take as installed programs: [`tetrahedralize`](./tetrahedralize.md#external-meshers-tetgen-and-gmsh)'s TetGen and Gmsh and [`remesh_quads`](./remesh_quads.md)'s QuadriFlow and Instant Meshes.) The answer is an optional backend (the KaHIP pattern), not a native implementation: volume domain meshing reaches meshio++ through [`tetrahedralize`](./tetrahedralize.md) (v17.23.0: natively by its octree backend, the skin fitted by isosurface stuffing, and exactly by Netgen, the skin kept) and adaptation through MMG ([MMG backend](./mmg.md)); boundary-layer inflation reopened through a design pass for layers grown from a surface ([`boundary_layer`](./boundary_layer.md), v17.23.0), the volume behind them filled by `tetrahedralize`; and quadrangulation reopened for CAD surfaces only (recombination of `mesh_cad_surface`'s own triangles by a matching, v17.23.0), field-aligned remeshing through installed programs ([`remesh_quads`](./remesh_quads.md)). A native constrained tetrahedralisation stays out: `orient3d` and `insphere` exist and the Delaunay kernel is short (Bowyer 1981, Watson 1981), but boundary recovery with Steiner points is where TetGen and the exact constructions spend their complexity (George, Hecht and Saltel 1991; Si and Gärtner 2005; Shewchuk 2008; Si 2015; Diazzi et al. 2023). Reopen it when a design pass shows a native recovery on the core's predicates within a stated size, measured against `tetrahedralize`'s probes and its Thingi10K sample. Two exceptions are in scope. Surface triangulation of a CAD model is native since v17.13.0 ([`mesh_cad_surface`](./mesh_cad.md)): the robust predicates it needs are Shewchuk's, public domain and a few hundred lines, and a planar constrained Delaunay triangulation per face is small enough to own; this reverses the earlier decision that dropped the queued Delaunay item, for surfaces and the plane only. Lattice generation is the other: [`voxelize`](./voxelize.md), [`octree`](./octree.md), [`remesh_volume`](./remesh_volume.md)'s isosurface stuffing and the octree volume mesher [`octree_mesh`](./octree_mesh.md) (stuffed tetrahedra and the all-hexahedral octree dual, uniform or graded, [plan](./octree_mesh_3d_plan.md)) are index arithmetic over a signed distance on a lattice, followed by projection and untangling, with no predicate to make robust.
- **A declared tolerance deciding degeneracy in `mesh_cad_surface`** — `model_tolerances` widens where uses start, how far corners and uses may lie apart and which trims pair, but whether an edge is degenerate (a pole) stays on the global tolerance: an edge shorter than a generous declared tolerance is real geometry, and collapsing it would change the model rather than accept its gaps ([item 21](./mesh_cad.md#how-it-works)).
- **What mesh generation leaves, by decision** — recorded when roadmap §6 closed (October 2026); [mesh generation](./mesh_cad.md) and its [measured-and-parked notes](./mesh_cad.md#measured-and-parked) hold the numbers:
  - **No small-angle bound stated on a curved face.** Corner lopping's bound (Pav and Walkington 2005) is the plane's; on a curved face `lop_corners` reports the angles it reaches and termination stays `max_points` and the insertion-radius declines. Stating one would need the paper's argument redone in the surface's metric.
  - **A pinched boundary stays declined** by the flattening of 6.4.4: splitting the pinch into one vertex per wedge makes the coarse mesh manifold, but the face's loops pair the pinch's edges otherwise than the wedges do, so each loop would have to be re-stitched through both copies.
  - **Field-aligned quads stay with backends.** Recombination of the mesher's own triangles leaves its worst quads at poles (0.12 on the sphere at `h = 0.1`); field-aligned remeshing is Instant Meshes (BSD-3), QuadriFlow (MIT) or QuadWild (GPL, excluded), each a library of its own. Since v18.0.0 that pattern is the provider registry, and [`remesh_quads`](./remesh_quads.md) runs an installed QuadriFlow or Instant Meshes as a separate process (0.25 to 0.58 on the same sphere, by seed); a linked add-on wheel extracting their solvers stays unqueued until a user needs them in the wheels or the browser. The core's cross field and quad layout (`detail/cross_field`, `detail/quad_layout`) stay `fit_cad`'s.
  - **Curved boundary layers: linearize first.** `boundary_layer` takes linear triangles and quads; a `triangle6` or `quad9` surface is linearized first. Growing curved layers needs a Bernstein bound on a prism's and a hexahedron's Jacobian (the tensor bound `detail/curved_quad` has for quads, raised a dimension) to keep "no cell is written folded" true, and its mid-edge nodes' directions; no model has asked.
  - **Mesh-generation corpora with non-commercial terms stay out.** The Fusion 360 Gallery (Willis et al. 2021) permits use for non-commercial research only and asks its users to indemnify Autodesk, which an MIT project's published measurements cannot accept.
  - **No numpy twin** of `mesh_cad_surface`, `triangulate_polygon_2d` or `tetrahedralize`: a second implementation of the predicates and the triangulation could not stay byte-identical, the precedent of [`remesh_volume`](./remesh_volume.md).
  - **Healing the model.** Sewing gaps, removing sliver faces or rebuilding pcurves changes the CAD model, which is the CAD kernel's work; `mesh_cad_surface` meshes around defects without writing them back. Narrowed in November 2026: the CAD kernel is reachable through the provider registry, so healing at read time, before the B-rep reaches the mesher, is the STEP and IGES readers' `heal` option ([STEP reading](./formats/step.md#reading)); `mesh_cad_surface` itself still never heals.
  - **Code from Triangle, TetGen, Gmsh, CGAL's GPL packages or Blossom V**, under any route other than a separate process: their licences ([THIRD_PARTY_NOTICES](https://github.com/loumalouomega/meshioplusplus/blob/main/THIRD_PARTY_NOTICES.md)). Geogram's constrained tetrahedralisation is in that list too: it creates TetGen's AGPL Delaunay kernel. The separate-process route is `tetrahedralize(backend="tetgen")` and `backend="gmsh"` ([external meshers](./tetrahedralize.md#external-meshers-tetgen-and-gmsh): installed executables behind named tet-mesher providers, never linked), and the rule keeps the gmsh Python API, which runs in-process, out of the interop bridges (4.10).
  - **A native parallel Delaunay kernel** in the style of HXT (Marot, Pellerin and Remacle 2019): it is the fast path of a 3-D mesher the core does not have, and the 2-D triangulation of one face is small enough that faces in parallel already use every thread on a real model.
  - **Advancing-front surface meshing as a second native mesher** (Lo 1985, Peraire et al. 1987, Löhner and Parikh 1988, Schöberl 1997): smoother gradation, but its robustness rests on the front's intersection tests that the Delaunay route avoids, and two native meshers would double what must stay byte-identical. Frontal point placement inside the Delaunay mesher (Rebay 1993, Tristano, Owen and Canann 1998) is the alternative if the varying metric's circumcentres leave triangles poorly aligned on strongly stretched faces.
- **Contact mechanics itself** — penalty or mortar assembly, friction and contact search in time need a live solver. meshio++ detects and exports the interface of one snapshot ([interfaces and contact](./region_adjacency.md)); the contact algorithm belongs in the application that owns the solver.
- **MMG in the base wheel and in the native CLI executables** — it is LGPL-3.0 (GPL-3.0 with the ELAS that `move` needs) and an external install, so the native backend is linked dynamically into builds that opt in, and its operations throw by name where it is absent ([MMG backend](./mmg.md#licence)). v18.0.0 narrowed this for Python: the `meshioplusplus-mmg` add-on wheel ships it, built without ELAS, beside the MIT base wheel ([installation](./installation.md#what-the-pypi-wheels-contain)); the same split for the native CLI, a plugin beside the executable, is queued as 4.8.1. Its WebAssembly half was lifted for the full artifact when roadmap 3.1.8 closed (October 2026): MMG is linked there statically, without ELAS, under the LGPL-3.0 relinking terms the artifact's notices state ([WebAssembly](./wasm.md#mmg-in-the-full-artifact)); the lean artifact keeps none.
- **What the full WebAssembly build leaves, by decision** — recorded when roadmap §5 closed (October 2026); [fit CAD's measured and parked notes](./fit_cad.md#measured-and-parked) hold the numbers and the reopening conditions:
  - **Constraints beyond the coaxial, right-angle and equal-radius ones.** Parallel but offset axes are different surfaces, and a bolt circle or a plane at another angle needs the pattern known to the pass, so `constrain_primitives` stays exact only where it is exact.
  - **G1 at valence 5 and 6 beyond the sweeps' reach.** The refine-before-discard step of the patch network brings the largest G1 angle down on the Catmull-Clark fixtures ([limitations](./fit_cad.md#limitations)); a construction that holds G1 exactly there (Loop and Schaefer's full scheme, or G-splines) is not implemented.
  - **Genus-one-and-more homology cuts.** The layout's pieces are triangle groups, so a cut along both sides of a loop has no representation; that is a change to the layout's partition, not a bounded experiment.
  - **THB stays experimental**, behind its knot-line fallback: a rung whose hierarchical fit misses its target falls back to knot lines, so `"thb"` never leaves as facets a patch `"knots"` fits.
- **KaHIP in the lean WASM build, ADIOS2 and TecIO in either WASM build** — KaHIP ships only in the full artifact (serial kaffpa, built by `build-wasm-deps.sh --full`; a graph partitioner would bloat every consumer's bundle, so the lean pair keeps the SFC method with `"kahip"` throwing by name as the contract); no one has made a wasm build of ADIOS2 (`vtx`); TecIO's redistribution terms keep `szplt` out. Each reports by name in the lean and the full artifact alike ([what stays out](./wasm.md#what-stays-out)).
- **zstd/lz4 codecs in the lean WASM build** — the lean artifact keeps zlib as its only block codec; the full one (v17.2.0) links zstd, lz4 and bzip2. A zstd-compressed VTK XML file is a meshio++ extension VTK itself has no compressor for, so vtk.js does not read it; the second reader of a zstd file is meshio++'s native and Python ones. **Memory mapping and the Kokkos backend under Emscripten** — CMake refuses the Kokkos backend under Emscripten, and there is nothing to map inside MEMFS.
- **Single-file output for DOLFIN, TetGen and EnSight from WASM**, or lifting DOLFIN's simplicial restriction — both are facts of the formats; `writeMesh`'s written-paths return value (v11.2.0) is the fix for the bookkeeping they cause.
- **NURBS patches and trims as a second entity kind inside `Mesh`** — decided with the [isogeometric layer](./iga.md) (v16.43.0, [findings](./spikes.md#the-isogeometric-layer)): a model (`NurbsInfo`, `BrepInfo`) stays a side channel beside the mesh, with its own evaluate, refine and sample operations, because a first-class entity kind needs patches, control nets, weights, knots and trimming curves in `Mesh`, every mesh backend (MESHIO, NATIVE, KRATOS), every binding and the C++ ABI: a major version for a gain the three operations already give. Reopen it when an operation must act on patches and trims as mesh entities (mixed IGA and FEM assembly in one model, for instance, or a patch-aware `partition`), and start from the spike's list of what the side channel cannot do: no `Mesh` operation sees a patch, the model does not travel through the pipeline, and an MFEM model refines every direction alike.
- **Polyhedron blocks as a WASM gap** — `vtu`, `ensight`, `cgns`, `med` and `openfoam` all write them from WASM; a consumer that cannot is constrained by its own data model.
- **Performance work measured or decided against** — recorded when the roadmap's performance section closed (October 2026), and not re-proposed when it reopened as [§5](#performance) in November 2026; a new performance change passes the gates of [landing a performance change](./benchmarks.md#landing-a-performance-change):
  - **The serial phases kept for determinism**: the keep-first weld loop (chains make it order-dependent), the union sweeps of `split` and `compute_normals` (cheap, and their partitions are order-independent anyway), and `remesh`'s energy sweep (every accepted move changes what the next test reads; it has no numpy twin because a near-tie decided differently yields a different clustering).
  - **A facet table cached across pipeline steps** — measured ([benchmarks](./benchmarks.md#pipeline-row-what-a-shared-facet-table-could-save)): in a `Smooth` then `ExtractSurface` chain a cache saves at most one table build, about 3.6% of the chain on SEQ at tier L with the default ten iterations, at most 10% on four OpenMP threads and about 20% with one iteration. `smooth` and `extract_surface` do not share a record structure, so it would also need a refactor, and a cache on the `Mesh` is a Tier A layout change. Reopen it for a workload that chains several facet readers after cheap topology-preserving steps; the `pipeline_smooth_surface` row measures it.
  - **Link-time optimisation by default** — measured ([benchmarks](./benchmarks.md#link-time-optimisation)), November 2026: identical output and binaries a third smaller, but the instruction counts move both ways (`read_vtk_ascii` +40%, `gradient` +14%, `decimate` −6%), so it is the opt-in `MESHIOPLUSPLUS_ENABLE_LTO` rather than the default.
  - **Explicit SIMD intrinsics or `-march` flags** — portability across wheels, WASM and the release binaries is worth more than the scalar kernels cost; revisit only if the harness shows a kernel dominating. Narrowed in November 2026: the decision stands for flags and for intrinsics compiled unconditionally; variants selected at run time inside one portable binary, for kernels whose vector form is bit-identical, are to be measured as 5.15.
  - **Kokkos device execution** — every `parallel_for` body captures host pointers (`parallel.hpp`); the GPU route is the DLPack/CuPy handoff ([GPU handoff](./gpu.md)).
  - **An occupancy pyramid over the distance query's bucket grid** (formerly roadmap 5.3.1) — measured in November 2026 and not taken: descending the grid's occupancy at coarser block sizes, best first with Euclidean bounds, was 2 to 3 times faster than the Chebyshev-shell search at tier L, but a bounding-volume hierarchy of the triangles (formerly 5.3.2, which had been decided against because its visit order was thought to make the equidistant-triangle tiebreak observable, a reason the total order on (distance², triangle id) answers) was a further 2 to 4 times faster with its build included, on uniform and graded targets alike, and replaced the grid in ABI 40 ([benchmarks](./benchmarks.md#a-bounding-volume-hierarchy-for-the-distance-query-and-a-grid-for-find_interface)). A cell's bound is the cell's, so a point far from the surface still opens every bucket of a patch around its nearest one; a box is as tight as its triangles.
  - **Tuning the pure-Python fallback readers** — the fix is making the C++ path accept the file, not a faster fallback; `_decimate.py`'s heap-based twin is deleted once `decimate` accepts its inputs, not optimised.
  - **Dropping the copy in `transform`** — `transform` copies the connectivity and data it does not change (through `transform_owned_copy`, as 17 operation files copy through `clone_mesh`, `clone_geometry` or `quality_clone_mesh`), and the Python twin copies too; that copy is what makes the result a new mesh that aliases nothing, so removing it is an API change, not an optimisation. Narrowed in November 2026: that holds for `transform`; a second, explicitly in-place entry point changes no existing contract and is to be measured as 5.14.
  - **Caching between the browser viewer's applies** — every apply re-reads the staged file and replays the whole pipeline, which is what makes undo exact. Measured with the typed-array channel ([benchmarks](./benchmarks.md#a-typed-array-channel-for-the-browser-viewer)), the read is at most 2 to 25% of an apply that smooths and up to 69% of a quality-only apply on a large surface; a cached mesh or pipeline prefix would hold a second copy of the mesh in the 32-bit heap MEMFS already shares, and make undo depend on invalidation. The heap's size is the half of this a higher ceiling or a 64-bit build would change (5.13); measure again there before reopening.

- **Code from AGPL-3.0 scan tools** — [ScanRuler](https://github.com/CNCKitchen/ScanRuler) and its STEP importer meshStep are AGPL-3.0, which this MIT library cannot take in any form: no copying, porting, translating or paraphrasing of their code, tests, shaders, guides or data. The scan metrology section (then §7, closed November 2026) was listed from their published feature descriptions only; an agent implementing an item of that kind (9.9 is one) works from the literature it cites and from meshio++'s own kernels, does not open their source, and does not use their output files as fixtures. The same rule as for Triangle, TetGen and Gmsh above, without the separate-process exception, since nothing there needs to run them.
- **Booleans of a scan with fitted solids** — subtracting a measured cylinder from a scan, or adding a modelled body to it (roadmap 7.8.7, closed November 2026), waits on surface booleans, which a spike measured and kept out: exact in topology, but rounding its output to doubles left most curved results self-intersecting and coplanar contact unhandled ([findings](./spikes.md#surface-booleans-formerly-roadmap-7-8)). A fitted solid reaches a CAD kernel as STEP ([`write_step_elements`](./formats/step.md#elements)), where the boolean is the kernel's. If a boolean backend passes the spike's criteria (9.1), this is its first use and the entry is removed.
- **An interactive parametric CAD modeller** — a sketch constraint solver, a feature history with rebuilds and rollback, face fingerprints that survive upstream edits, thread and insert catalogues: a CAD application, not a mesh library. meshio++ fits and writes geometry ([`fit_cad`](./fit_cad.md), 7.6.5) and may build a solid from a scripted list of profile features through the CAD provider (7.7.4); editing that solid belongs to the CAD tool that opens the STEP file.
- **Terminal rendering stays software, dependency-free and core-only** — no GPU, no windowing stack, no new dependency and no audio library; it is a *preview*, not a replacement for Polyscope or vtk.js, and does not try to match their fidelity, lighting or picking. Python calls the core or raises by name (the [`remesh_volume`](./remesh_volume.md) precedent: a NumPy edge-function rasterizer would be slow and double the surface that has to stay byte-identical). Vector output is unchanged: SVG, TikZ and glTF keep the painter's algorithm and their byte-pinned twins, and their colormap tables are only ever extended. The interactive loop is not a library feature (raw mode, signals and the event loop live in the CLI layer; the library exposes frames and encoders, never a tty, and WASM and the C API carry frames and text only). `--follow` polls modification times and does not use inotify or kqueue. The soundtrack is generated, played by an external player and silent unless asked for, in CI and over SSH. See [terminal rendering](./tui.md#design-decisions).
