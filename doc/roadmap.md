# meshio++ roadmap

Status at time of writing: **v16.30.0** — 79 core formats plus five Python-only physics-ML ones, forty-five mesh operations + six data operations, six language surfaces (Python / C / Fortran / Julia / R / WASM), two viewers plus a browser dataset manager, a Blender add-on, a ParaView plugin, an MCP server, a settings-driven pipeline engine, a dataset-manifest layer with a PhysicsNeMo adapter, and a versioned ABI (`MESHIOPLUSPLUS_ABI_VERSION` 22), sanitizer and fuzzing gates, and a format conformance matrix.

This document lists what is *not* built. Nothing here duplicates shipped functionality; where a feature partially exists, the shipped half is named and the gap is stated explicitly. Release history lives in [`CHANGELOG.md`](https://github.com/loumalouomega/meshioplusplus/blob/main/CHANGELOG.md), not here.

Effort key: **S** = days, **M** = a couple of weeks, **L** = a month or more, **XL** = a project in its own right. An item names a **probe** — the failing test that proves the gap — wherever one is cheap.

## How this file works

- **Sections are ordered, and the order is the recommendation.** Each section states what belongs in it; an item that sounds exciting does not move up for that reason. An empty section is removed, not kept as a placeholder.
- **A closed item is removed, not struck through.** Its history is the `CHANGELOG.md` entry and the feature's own `doc/` page; a partly closed item is narrowed to what remains (the `AGENTS.md` change checklist rule).
- **Every level of the outline is numbered**, so a gap can be cited in an issue, a commit or a release note: a group of work is `section.item` (a `###`/`####` heading, or a bold label line), the work under it `section.item.subitem`, and a bullet under that `section.item.subitem.subsub`. Lists that record a decision rather than open work — *Considered, not queued*, *Deliberately not*, *Serial by design*, a section's *Landing an item* steps and the [non-goals](#non-goals-and-decisions-taken) — stay unnumbered, because a number here means work to do. The numbering follows the sections, so a new section inserted at the top renumbers the rest, as the rule above says.
- **Defect-shaped items go in a *Correctness debts* section at the top, regardless of size** — behaviour that loses data, mis-orients cells, does not terminate on valid input or fails silently is not a feature request, even when the fix and the feature are the same work. None is open today, so there is no such section; the first defect found opens one as §1 and renumbers the rest.
- **An item estimated from a doc, a `.d.ts` or a changelog alone says so** ("verify first") and names its probe; the code has repeatedly been more or less capable than its description.
- **[Non-goals](#non-goals-and-decisions-taken) record decisions already taken**, with their reasons, so they are not re-proposed as gaps.

## 1. Format reach

*Admission: a format a simulation or physics-ML workflow actually exchanges; the missing half of a shipped one is [§4](#_4-reader-and-writer-parity)'s. "Exchanges" means a file that crosses a tool boundary in a real pipeline (mesher → solver, solver → post-processor, solver → training set), not a format that merely exists. Every item names the consumer on the other side of the file.*

Sizes: **S** ≈ days, **M** ≈ two weeks, **L** ≈ a month or more, including tests, docs page and CLI wiring. They assume a new format reuses the shared components rather than growing its own: the card tokenizer (`detail/keyword_card.hpp`), the [node-ordering registry](./node_ordering.md), the Fortran record reader (`detail/fortran_records.hpp`) and the directory sniffing that sequence globs share.

Every format this section queued is now read: the native FEM interchange, solver input and result-file readers of v16.5.0 to v16.12.0 (Tecplot, Femap, MFEM, Patran, Abaqus `.fil`, Radioss, Z88, libMesh, Marc, Ansys `.rst`, LS-DYNA and OP2), DOLFINx's ADIOS2 `.bp` ([`vtx`](./formats/vtx.md)) and Tecplot SZL through TecIO ([`szplt`](./formats/szplt.md)) of v16.13.0, and the [vendor-runtime routes](./vendor_routes.md) for the files only a vendor's software reads (Abaqus `.odb`, Marc `.t16`, Femap `.modfem`, Ansys results beyond the native reader). Since v16.17.0 the shared components are used wherever a format's layout fits them, the input decks are written too (Radioss's starter deck, checked with the OpenRadioss starter, and Marc's), Femap writes a series as one output set per step, and every format read but not written names its reason on the [conformance page](./conformance.md#read-only-formats), which a test keeps in step with the registry; [§4](#_4-reader-and-writer-parity) now queues every one of those missing halves. What they still lack is a check against a run of the vendor tool, listed under [Awaiting a licensed run](#_1-2-awaiting-a-licensed-run): take each as soon as a licence, or a file the tool wrote, is in hand.

### Considered, not queued

- **Graphics, CAD, VFX or lab-specific rather than simulation interchange:** 3MF, X3D, DXF, Alembic, OpenVDB, Silo, LAS/LAZ, E57, OBJ materials (`.mtl`).
- **Closed FEM databases with no route worth shipping:** Altair `.h3d` (undisclosed format, SDK not redistributable — Altair's own advice for OpenRadioss is ANIM → VTK, see the [OpenRadioss discussion](https://github.com/orgs/OpenRadioss/discussions/552)); HyperMesh `.hm`; Abaqus `.sim`.
- **No native format to implement:** deal.II (reads and writes UCD, VTK, Gmsh, Abaqus, Exodus — all reachable today); MOOSE (Exodus).
- **Nastran OP4 matrices and punch `.pch`:** matrix and card dumps, not mesh/field exchange; pyNastran serves them.
- **Non-MSC Nastran HDF5 dialects:** incompatible schemas; revisit with a file in hand.
- **Partitioning niche:** gmsh `$PartitionedEntities` (Kratos partitions through MDPA).
- **Operators and tooling, not formats** (listed only because they came up in the same review): ICP registration; mesh duals; cylindrical/spherical coordinate transforms; shell completions.

Revisit any of them when a consumer asks with a file in hand — a real deck or result file, the tool version that wrote it, and the tool that needs the converted output.

## 3. Performance

*Admission: a measured or code-verified slowdown in a path a user hits, with the shape of the fix named. Every item shows its before/after on the benchmark harness (`benchmark/bench.py` for I/O, `tools/bench_ops.sh` for operations; [benchmarks](./benchmarks.md)).*

Use the [Clang-Tidy performance audit](./benchmarks.md#clang-tidy-performance-audit) to discover candidates; its findings are advisory and must satisfy the landing gates below.

Two findings frame the section. First, **the serial phases below are deliberate**: each is documented in the code as a determinism pin, not an oversight — output is byte-identical across parallel backends and thread counts, which repeated-run tests and the C++-versus-numpy byte comparisons enforce — so every fix must keep that guarantee and prove it with a SEQ-versus-OpenMP diff, not assert it. Second, **every parallel item is conditional on the backend**: a SEQ build (and the `stl` fallback without TBB) runs `parallel_for` sequentially, so each change must also show that SEQ does not get slower — a parallel sort is O(n log n) where the hash map it replaces is O(n). SEQ is not a corner case: the Linux wheels and the native CLI release binaries are built SEQ, and WASM ships a SEQ build beside the threaded one, so an algorithmic win reaches every user while a parallel one reaches source, conda and threaded-WASM builds.

**Landing an item.** Each item names only what is particular to it. All of them:

1. Record the before on SEQ, OpenMP and TBB at 1, 4 and 8 threads: `tools/bench_ops.sh before.csv "SEQ OPENMP TBB" "1 4 8" -- --hash --ops <op> --tier M --tier L`, or `benchmark/bench.py --sizes M,L --formats <format>`.
2. Show the output is byte-identical across backends and thread counts, and to the digests before the change: `meshioplusplus_bench_ops --hash`, with `BASELINE=before.csv` for the second sweep ([benchmarks](./benchmarks.md#determinism-check)). The rows each item needs exist since v16.15.0; an item whose operation has none adds one first.
3. Show SEQ is not slower.
4. Classify the change by the [ABI policy](./abi.md): the body of an exported, non-inline function is free; an inline or template body in an installed header is Tier B; a new function in an installed header is additive and goes in the [ABI review](./abi_reviews.md); a changed signature, or the layout of an installed type, is Tier A. Regenerate the single header.
5. Correct every code comment that describes the old algorithm (the items name the stale ones already found), and update the numbers in [benchmarks](./benchmarks.md).

**3.4 Boundaries and startup.**

- **3.4.2 Lazy submodules for `import meshioplusplus`.** `python -X importtime` bills ~260 ms to `_cli` only because it is the first name in the package's `from . import (_cli, …)`, so it pays for numpy and everything else the package imports anyway. With `_cli` stubbed (Python 3.14, September 2026): numpy ~90 ms, the `_core` extension ~58 ms, the ~320 other package modules ~79 ms, and `_cli` itself ~7 ms; `rich`, `xml.sax.saxutils` (with `urllib`, `http.client` and `ssl`) and `importlib.metadata` left the import path in v16.15.0, and `test_import_footprint.py` keeps them out. **M**
  - **3.4.2.1 Lazy `_cli`** saves only ~12 ms, and changes behaviour: format registration follows import order, and without `_cli` first, `.msh` resolves to ansys, freefem, gmsh instead of ansys, gmsh, freefem, so every Gmsh file would try FreeFEM first. Pin the order explicitly before making it lazy (`test_helpers.py` documents today's). `_cli` is in `__all__`, so `from meshioplusplus import *` would trigger a module `__getattr__`.
  - **3.4.2.2 The real lever** is loading operation and format submodules on first use through a module `__getattr__`, for which the registration-order pin is also the precondition. The CLI's entry point imports the whole package regardless, so these gains reach library and MCP users (the latter once per process), not a single CLI call.
  - **3.4.2.3 Gate.** Extend `test_import_footprint.py` with `meshioplusplus._cli` and the lazily loaded submodules. Measure with `SKBUILD_EDITABLE_SKIP` set in an editable install, whose `editable.rebuild` otherwise adds a build check to every import.
- **3.4.3 Clones at the Python boundary are semantics.** `transform` clones the connectivity and data it does not change — as 17 operation files do through `clone_mesh`, `clone_geometry` or `quality_clone_mesh` — but that clone is what makes the result a new mesh that aliases nothing, and the Python twin copies too. Dropping it is an API decision, not an optimisation. `transform`'s binding also refuses ragged meshes (`allow_ragged=false`), so those always run the Python twin. **S**
- **3.4.4 R copies the points twice.** `R_mio_points` (`mesh.c`) copies them through `mio_r_copy_as_real`, then `memcpy`s the result into a second matrix, and `conn_matrix` converts the connectivity into one allocation and shifts it to 1-based into another with a scalar loop; `shape_data` in the same file already copies once and sets the `dim` attribute. Fixable behind the same accessor names ([R](./r.md) documents R as copy-only). Julia needs nothing: `points` is one copy and `connectivity` one fused copy-and-shift loop, the minimum for an owning result. **S**
- **3.4.5 The browser viewer round-trips every operation result through a VTP file.** `renderPipeline` (`src/viewer/src/worker/worker.ts`) writes the result to `/out.vtp` in MEMFS as binary, zlib-compressed, base64 VTP; `take()` copies it out of MEMFS once with `FS.readFile`; and `Renderer.load` parses it on the main thread with vtk.js's `XMLPolyDataReader` — an XML parse, a base64 decode and an inflate. Every apply also re-reads the original file and replays the whole pipeline. **L**
  - **3.4.5.1 Skip the inflate (S).** The single copy out of MEMFS shipped, and so did an uncompressed write (`compressVtp: false`), but **the viewer cannot use that write yet**: vtk.js reads an uncompressed array as `new TYPED_ARRAY(buffer, headerBytes)` with no length, so the writer's 4-byte header (no `header_type`) puts an 8-byte type at offset 4 and throws a `RangeError`. What would work, to be checked against vtk.js before relying on it: an uncompressed VTP written with `header_type="UInt64"`, so the offset is 8 and `Float64Array(buffer, 8)` is aligned (its Int64 path already narrows through `integer64to32`). That needs a way to force the 8-byte header in `write_vtp` (today `vtk_xml_header_bytes` picks it from the array size), then the viewer requesting it. Probe: a Playwright load of the viewer on the written file. Measure `applyOps` first: the inflate may be too small a share of it to matter.
  - **3.4.5.2 The typed-array channel.** A variant of `convertSurfaceOps` that returns `mesh_to_val(surface)` instead of writing a file reuses the typed-array `Mesh` the npm library already returns (`points` as a `Float64Array`, `Int32Array` cells per block, `*_components` for multi-component data). The reason `worker/protocol.ts` and `js_bindings.cpp` give for VTP — that flat meshes cannot carry multi-component arrays — has been stale since `*_components` arrived in v9.9.0.
  - **3.4.5.3 Watch.** The offline embedded page and the dataset page still need a VTP; the picker needs `surface:parent_cell`; vtk.js wants its own cell layout (a count, then the ids), not per-block arrays; and `mesh_to_val` narrows connectivity to `Int32` and widens points to `Float64`.
  - **3.4.5.4 Gate.** `tests/viewer/*.spec.mjs` (Playwright: `npm run test:e2e` in `src/viewer`) and `tests/wasm/smoke.mjs`. There is no viewer benchmark: time `applyOps` in `ops.spec.mjs` until the viewer's status changes.

**Deliberately not**, and recorded so it is not re-proposed:

- **Explicit SIMD intrinsics or `-march` flags** — portability across wheels, WASM and the release binaries is worth more than the scalar kernels cost; revisit only if the harness shows a kernel dominating.
- **Kokkos device execution** — every `parallel_for` body captures host pointers (`parallel.hpp`); the GPU route is the DLPack/CuPy handoff ([GPU handoff](./gpu.md)).
- **A BVH in place of the uniform grid** — the tiebreak argument above.
- **Tuning the pure-Python fallback readers** — the fix is making the C++ path accept the file not a faster fallback; `_decimate.py`'s heap-based twin is deleted once `decimate` accepts its inputs, not optimised.

*Recommended posture:* the boundary items as their consumers ask, and the tokenizer's remaining readers alongside other work in them; the operations' layout-bound leftovers with the next ABI bump. Every item is judged by the determinism check (`--hash`, v16.15.0).

## 4. Reader and writer parity

*Admission: a format that reads without writing, writes without reading, or whose one side keeps less than the other returns — and, as in the core-parity section this one replaces, a construct one engine handles and the other cannot. A Python-only path is not "slower from C", it is unreadable from C, Fortran, Julia, R, WASM and the native CLI, none of which has a fallback; a core-only path has no twin to check it against and nothing to run when the core is absent.*

What changed since parity last had a section. The reader/writer triage of September 2026 (then §1.2 of this file) recorded every result file as read-only by design and closed with the Radioss and Marc deck writers (v16.17.0), Femap's output set per step, and the `READ_ONLY` guard (`tests/python/conformance_spec.py`, checked by `read_only_drift` and `test_conformance.py`); the core-parity section closed with the Exodus sets and series writers and pipeline v2. The decision is now the reverse of the first: **every registered format both reads and writes**, which removes the *Result-file writers* and *Readers for the export-only surfaces* non-goals. The rule:

- **Both directions, both engines.** A format reads and writes in the C++ core and in its Python twin, so it reaches every surface: C, Fortran, Julia, R, WASM, both CLIs and the MCP server's format capabilities.
- **What one side keeps, the other keeps.** `read(write(m))` equals `m` within the limits the format itself imposes (single precision, a cell type it has no slot for, a concept it cannot express). A loss that is a fact of the format is stated on its page and in the [conformance](./conformance.md) notes; a loss that is only an unwritten feature is a gap, and belongs below.
- **The one exception: pure 2-D drawings.** `svg` and `tikz` draw a mesh rather than store it. Their readers parse only the structure meshio++'s own writers emit, return the geometry as planar (`z = 0`), and warn once per read that depth, and whatever else the drawing could not hold, is lost. Anything else in the file — another tool's drawing, or a hand edit — is a `ReadError` naming the construct, never a guess.
- **Exempt:** `ansys_rst_cyclic`, which is not a file but the full rotor a cyclic `.rst` expands to; its write side is `ansys_rst`'s cyclic option (4.3.6).

**Landing an item.** Each item names only what is particular to it. All of them:

1. A native writer (or reader) in `src/cpp/src/formats/`, registered in `registry.cpp`, with its parameters through `WriteOptions`/`registry_write_ex`; the Python twin behind a shim that asks `core_declined`. Where the format is deterministic the twins are byte-identical (the `svg`, `tikz` and `gltf` writers already are); otherwise value-equal.
2. **Promote the scratch writer that already exists.** Every read-only format has one, written to build its reader's fixtures: the items name them. It becomes the oracle the library writer is checked against, then the tests switch to the library writer and the scratch copy is deleted.
3. The format's `READ_ONLY` (or `write-only`) entry becomes a `SPEC` declaration in `conformance_spec.py`, and `python tools/gen_conformance_table.py` regenerates [conformance](./conformance.md) and the [format table](./formats.md)'s columns.
4. The validator the item names reads the written file, and the format page records the tool and its version. A file only a vendor's tool reads adds a line under [Awaiting a licensed run](#_1-2-awaiting-a-licensed-run).
5. Files the new writer produces join the reader's fuzz seeds ([fuzzing](./fuzzing.md)).
6. A result file is a series: it is written through the same machinery as the Exodus and XDMF series writers (a stateful writer for steps over one mesh, and `write_sequence`), and a plain `write` of one `Mesh` writes one step.
7. Solver naming is the reader's inverse. The arrays a reader returns — `<fmt>:id`, `abaqus:layout:*`, `marc:layout`, `lsdyna:alive`, the `@corner` and `@ply` suffixes, point-major integration-point arrays — are written back under the same names; without them, ids are 1-based and sequential and results go where the format puts unlayered data. Element types go through the inverse tables of the [node-ordering registry](./node_ordering.md), which exist in both directions.
8. The format page gains a *Writing* (or *Reading*) section; the [C](./c_api.md), [WASM](./wasm.md), [Fortran](./fortran.md), [Julia](./julia.md) and [R](./r.md) docs list the new direction; `mcp/_tools.py`, `_server.py`, `tests/python/test_mcp.py` and [MCP](./mcp.md) report it; and a notebook shows it wherever a user would reach for it.

**4.1 Turn the guard around.** Today a missing direction is legal once it has a reason; it becomes a tracked gap. **S**

- **4.1.1** Every `READ_ONLY` reason and every `{"error": "write-only"}` declaration (`gltf`, `svg`, `tikz`) changes from a justification ("nothing to write back") to a pointer at its item here, and the conformance page's *Read-only formats* table becomes *Formats missing a direction*. The end state is an exemption list holding only `ansys_rst_cyclic`, and `svg`/`tikz` rows whose points are declared `2d`.
- **4.1.2** `test_the_native_registry_agrees` checks both directions in both registries, so a writer registered without a reader fails as a reader without a writer does today. Probe: register a writer with no reader and no exemption; the test must fail.
- **4.1.3** `doc/conformance.md` says glTF is read "only as the scene it wrote": no glTF reader exists, so the note (it comes from `conformance_spec.py`) is wrong until 4.2.4 lands.

**4.2 Readers for the export-only formats.**

- **4.2.1 `svg`, as a 2-D drawing.** The writer (`svg/_svg.py`, byte-identical to the core's) emits one `<svg viewBox>` with one `<style>`, then one `<path d="M x y L … Z">` per line, triangle or quad — never a `<polygon>` and never a shared vertex table — with y flipped (`max_y + min_y - y`) and the drawing scaled to `image_width`; a 3-D mesh is first skinned and projected (azimuth 45°, elevation 35.26° by default) and sorted back to front; `color_by` adds a `fill` per path and a colour bar of 32 `<rect>` and 2 `<text>`. The reader inverts exactly that, through the vendored pugixml: a closed path of 3 vertices is a triangle, of 4 a quad, of more a polygon, and an open 2-vertex path a line; points are welded on their exact coordinate text in order of first appearance, so shared corners come back shared; the y-flip is undone from the `viewBox`; the colour bar is skipped; a fill can come back as an RGB `svg:fill` cell array, never as the data it was coloured from (a colour map does not invert). A `<polygon>`, a `transform`, a curve (`C`, `Q`, `A`) or a relative command is a `ReadError`. What cannot come back without 4.2.3: the original scale and offset. **S**
- **4.2.2 `tikz`, as a 2-D drawing.** The writer emits an optional `standalone` wrapper, `\begin{tikzpicture}[scale=…]`, one `\draw[fill=…, draw=…] (x,y) -- … -- cycle;` per cell and `\draw[draw=…] (x,y) -- (x,y);` per line, with coordinates verbatim (or projected) and no y-flip, so planar input comes back exactly in x and y. The reader tokenizes with `detail/text_cursor.hpp`, skips the colour bar (`\fill … rectangle` and `\node`), reads `fill={rgb,255:red,R;green,G;blue,B}` into `tikz:fill`, and refuses `\path`, `plot`, `circle`, `.. controls ..`, named, polar and relative (`++`) coordinates and `\foreach` by name. **S**
- **4.2.3 A marker, so the warning can say what was lost.** Neither drawing says today whether it was planar input or a projection, nor that meshio++ wrote it. Both writers gain a provenance comment (`<!-- … -->`, `% …`) carrying the version, the projection (`none`, or azimuth and elevation) and, for `svg`, the scale and offset — a change to both byte-identical twins together. The reader then warns "planar drawing, z = 0 assumed" or "projected from 3-D, depth lost", restores model units in `svg`, and refuses a file without the marker unless the caller passes `strict=False`. **S**
- **4.2.4 `gltf`, as a real reader.** glTF is not a 2-D drawing — the writer keeps 3-D positions — so it gets a general glTF 2.0 reader, not one limited to meshio++'s output. Containers: `.gltf` with external or `data:` URI buffers and `.glb` with its JSON and BIN chunks, through the vendored nlohmann/json and the base64 decoder the VTK XML readers already use. Primitives: `POINTS` → `vertex`, `LINES`/`LINE_STRIP`/`LINE_LOOP` → `line`, `TRIANGLES`/`TRIANGLE_STRIP`/`TRIANGLE_FAN` → `triangle`, indexed or not. Accessors: every `componentType`, `normalized`, `byteStride`, sparse accessors, and `KHR_mesh_quantization`. Node transforms (TRS or `matrix`) are applied down the hierarchy into world space. The writer's choices are inverted: a node name becomes a cell region (`unassigned` and `mesh` give none); the `_NAME` custom attributes become `point_data` under the accessor's `name`; `COLOR_0` becomes `gltf:color`; the root `meshio++` node's up axis, recentring and scale are undone from `asset.extras`; and the vertices the writer split per smooth fan can be welded back (`weld=True`). Draco and meshopt compression are refused by name; morph targets, skins, animations, materials and textures are skipped with a warning. Volume cells came out as their skin, so the conformance row reads `→ tri`. It replaces the test-local `read_glb`, `accessor` and `world_positions` in `tests/python/test_gltf.py`. Probe: read back every glTF the writer tests produce, and the Khronos glTF-Sample-Assets, each one's licence checked and attributed in `CITATION.cff`. **M**

**4.3 Result-file writers.** The consumer the old non-goal waited for is the physics-ML loop this project already serves: a surrogate's prediction (the [PhysicsNeMo adapter](./physicsnemo.md)'s output) handed to the solver's own post-processor beside the real run, which needs the solver's own result file. Close behind: regression tests for post-processing scripts, which today need a solver run per fixture, and results converted or anonymised before they are shared. Ordered by how cheaply the output can be checked: tier A has an open tool that reads it, pip-installable or buildable in CI; tier B only the vendor's.

- **4.4.13 CalculiX `.dat`.** `frd.read_dat` is a Python-only table reader outside the registry; register it as a format with a writer, or document it as a helper.

**4.5 Engine parity per direction.** A format whose two engines differ in what they read or write. Each either gains the missing half, or records a core-only (or Python-only) exemption with its reason, as GiD's HDF5 flavour does through gidpost; the exemptions are what the probe checks against. **S–M each**

- **4.5.1 OpenFOAM**: the writer, and zone, field and multi-region reading, are C++ only.
- **4.5.2 GiD**: the writer is C++ only, through gidpost; the ASCII flavour's layout is documented and can have a Python twin, the HDF5 flavour stays core-only.
- **4.5.3 CGNS**: face-based polyhedra (`NGON_n`/`NFACE_n`) have no Python path.
- **4.5.4 Gmsh**: regions become `$PhysicalNames` only in the C++ writer.
- **4.5.5 EnSight**: `VARIABLE` reading and writing are C++ only.
- **4.5.6 PLY**: extra face properties are read only in Python.
- **4.5.7 VTU/VTP**: lzma is Python only; an optional liblzma in the core, as the other [codecs](./codecs.md).
- **4.5.8 libMesh**: bzip2 and compressed writing are listed as Python only, while the format table says the core compresses natively — verify first which is true.
- **4.5.9 XDMF**: high-order hexahedra are Python only.
- **4.5.10 Nastran**: `points_id`/`cells_id` are set only by the Python reader.
- **4.5.11 Neuroglancer**: Python only; port it, or add it to the *Python-only layers* [non-goal](#non-goals-and-decisions-taken) with its reason.
- **4.5.12 Probe.** One test over both registries asserting, for every format, read and write in both the core and Python, against the recorded exemptions — an extension of `test_the_native_registry_agrees`.

**4.6 Done when.** Every row of the [format table](./formats.md) has ✓ under both Read and Write (`svg` and `tikz` marked 2-D); `READ_ONLY` holds only `ansys_rst_cyclic`; the conformance matrix has no `write-only` row; every partial-writer note left is a fact of its format; and the binding docs and the MCP server list both directions.

## 5. Operations

*Admission: a new operation, or a public face for machinery that already exists privately inside one.*

**5.1 Generation.** Almost every operation transforms a mesh you already have. The exceptions all start from something else — `grid` from a lattice (`detail/grid_lattice.hpp`), `voxelize`/`compute_sdf` from a surface's bounding box, `remesh_volume` from a closed surface — and nothing builds a shape from parameters, sweeps one, or fills a skin with an adaptive lattice. Triangulating a domain is not this library's work; it reaches meshio++ only through the optional MMG backend (5.3).

- **5.1.1 Primitive constructors** — parametric generators in their own `operations/primitives.hpp` beside `grid` (today in `voxelize.hpp`, see [`grid` as a primitive constructor](./voxelize.md#grid-as-a-primitive-constructor)). Dependency-free, and it removes the fixture-file dependency from tests, docs, notebooks, the browser demo and the MCP server; and it could replace the test-local canonical mesh of the [format conformance matrix](./conformance.md). Highest leverage per line of code in this document. The demand is already in the tree: the Python tests hand-roll `_quad_grid` and `_hex_grid` six times each, `_unit_cube` four times, and `_tet_cube`, `_hex_cube`, `_tri_grid`, `_sphere` and `cube_quads` besides; the C++ tests `hex_grid` (seven times), `quad_grid` (six), `uv_sphere`, `two_tets` and `two_hexes`; the notebooks `hex_grid` (03, 09), `hex_block` (25), `plate` (09) and a squircle `disk` (27). The catalogue follows [meshzoo](https://github.com/meshpro/meshzoo)'s where the two overlap, taking names and parameterisations from its README only: check its licence before reading its code, since later releases are not MIT. **S per tier, M for the family**
  - **5.1.1.1 The contract every generator shares**, as `grid` already keeps it: a Python twin of the C++ core, coordinates computed from indices and never accumulated (an angle is `2πk/n`, not the previous point rotated), points and cells in a documented order, a `max_cells` budget, and a zero count yielding an empty mesh. Surfaces are oriented outward and volumes positively; boundaries come back as named side `Region`s (`xmin` … `zmax` on a box, `inner`/`outer` on an annulus, `side`/`top`/`bottom` on a cylinder), which is what notebook 26's `wall_facets` rebuilds by hand. Wherever the geometry allows, a `cell_type` choice (triangle or quad; tetra, hexahedron or wedge) and an `order=2` that places mid-edge and mid-face nodes on the exact geometry, so quadratic cells on a sphere or a cylinder are genuinely curved — the input the `curved()` helper of notebooks 16 to 24 exists to draw. One entry point per surface: Python, C, Fortran, Julia, R, WASM, both CLIs (a `generate <shape>` verb), an MCP tool and a pipeline source step.
  - **5.1.1.2 Tier 1: the replacements.** `rectangle` (the 2-D `grid`: quads, or triangles split `zigzag`, `up`, `down` or `center`); `box` (hexahedra, tetrahedra by the six-tet Kuhn split, which conforms across cells without the five-tet split's alternating parity, or wedges; six side regions); `disk` (quads by the squircle map notebook 27 uses, or triangles by an inflated polygon); `uv_sphere` and `icosa_sphere` surfaces; `cylinder` (hexahedra by an O-grid, or wedges by sweeping a triangle disk; three side regions). Enough to retire every helper listed above. **S**
  - **5.1.1.3 Planar domains**, at `z = 0`: `triangle` (a refined reference triangle, in barycentric order); `ngon` (a regular polygon fanned from its centre); `annulus` (two named rims, and a seam that [`periodic`](./periodic.md) can link); `lshape` (`[-1, 1]²` minus a quadrant, with the re-entrant corner at the origin: a singular solution for `refine`, [`error`](./error.md) and the gradient recovery operators); `plate_with_hole` (a square plate around a circular hole in quad blocks, the stress-concentration benchmark); `honeycomb` (a hexagonal tiling as a `polygon` block, so the ragged polygon paths have a parametric fixture). **S**
  - **5.1.1.4 Surfaces**: spheres from the other platonic seeds (`tetra_sphere`, `octa_sphere`, and `cube_sphere` in quads); `geo_sphere` (a UV sphere closed with triangle caps rather than degenerate quads); `torus` (genus one, negative Gaussian curvature on the inner rim and periodic both ways — the [curvature](./curvature.md) and Euler-characteristic probe a sphere cannot give); `moebius` (non-orientable, with `num_twists`: no consistent orientation exists, which probes [`compute_normals`](./normals.md)' `inconsistent_pairs` report and `repair(fix_orientation=True)`); `tube`, `cone` and `capsule` (open and closed surfaces of revolution, with sharp rims for [`feature_edges`](./feature_edges.md)); `box_surface` (today's `cube_quads`, a region per face); and the five platonic solids with one cell per face, the dodecahedron's pentagons as a `polygon` block. **S**
  - **5.1.1.5 Solids**: `ball` (tetrahedra, or hexahedra by a seven-block butterfly so no cell degenerates at the centre); `spherical_shell` and `pipe` (thick shells between two radii in hexahedra, `inner`/`outer` regions, with a radial grading ratio for wall-resolved spacing); `fichera` (the cube minus one octant, the 3-D L-shape and its corner singularity); `solid_torus`. **S**
  - **5.1.1.6 Lines and points**: `line` (a subdivided segment), `circle` (a closed polyline) and `helix` (a spring), as `line` cells for beam and 1-D format fixtures; point clouds on a sphere (a Fibonacci lattice) or in a box (seeded sampling) for the point-cloud formats and [point budgets](./point_budgets.md). Seeded sampling needs its own small generator (splitmix64 or PCG) in both twins: `std::uniform_real_distribution` is implementation-defined, and numpy's `default_rng` has no C++ counterpart. **S**
  - **5.1.1.7 Reference cells**: `reference_cells(types=…)`, one cell of each requested type in its reference coordinates — linear and higher-order (`tetra10`, `hexahedron20`/`27`, `pyramid13`, the quadratic wedges and the VTK Lagrange types) and a `polyhedron` — laid out side by side without touching, with a `pairs=True` variant of two cells sharing a facet. It is the conformance matrix's canonical mesh, `two_tets`/`two_hexes` and the [node-ordering](./node_ordering.md) fixtures in one, and the cheapest way for a notebook to show a format's cell coverage. **S**
  - **5.1.1.8 Watch.** Byte identity between the twins holds for `grid` because it is index arithmetic; `std::sin`/`std::cos` are not correctly rounded and differ between glibc, MSVC, Emscripten's libc and numpy's own SIMD kernels. Pin byte identity only for the polynomial generators (`rectangle`, `box`, `triangle`, `lshape`, `reference_cells`) and compare the trigonometric ones within a few ulps, or have the Python twin take its angle table from the core. Seams and poles are welded points, never duplicates, or `periodic`, `clean` and the Euler-characteristic checks see a boundary that is not there.
- **Deliberately not**, so not re-proposed: generators driven by a user callback (no callback crosses the flat ABI; numpy users build `Mesh(points, cells)` directly, and [`isosurface`](./isosurface.md) on a `grid` covers implicit shapes); scanned or modelled assets (the bunny, the teapot, the bracket fixture — data rather than parameters, each under its own licence); and CSG combinations (a [non-goal](#non-goals-and-decisions-taken)) — two-body interface and contact fixtures are primitives placed with `transform` and joined with `merge`.
- **5.1.2 `extrude`** — 2-D → 3-D sweep (triangle → wedge, quad → hexahedron) with `nlayers` and per-layer offsets, carrying regions to side and cap regions. The most-requested generation primitive. **M**
- **5.1.3 `revolve`** — `extrude`'s rotational sibling around an axis, sharing its layer machinery; degenerate cells on the axis are the only new work. **M**
- **5.1.4 Voxel and octree meshes from a skin, and their 2-D counterparts.** What exists: [`voxelize`](./voxelize.md) fills a closed surface's bounding box with uniform hexahedra (`fill="all"`, `"surface"` by exact triangle–box separating-axis overlap, `"inside"` by the [signed distance](./sdf.md)'s sign), under a `max_cells` budget and with byte-identical twins; `refine(closure="balanced")` already keeps hanging nodes and reports them in `refine:hanging`; and `voxelize.md` already turned down `custom` cells "for a future adaptive octree" because they would make the result invisible to every operation and most writers. What is missing is a lattice that is fine only where the surface is, and any of it in 2-D. It is in scope where Delaunay meshing is not for the reason [`remesh_volume`](./remesh_volume.md) is: a lattice is index arithmetic plus the overlap and sign tests that already exist, with no robust predicate anywhere. **M for the family**
  - **5.1.4.1 2-D `voxelize` (pixels).** The input is a closed planar polyline skin (`line` cells at constant `z`, or in a plane chosen by `plane=`), or the boundary of a 2-D surface mesh, taken with the boundary-edge extraction `feature_edges` already does; a two-entry `resolution` or `cell_size` selects 2-D. The output is a `quad` lattice with `voxelize`'s numbering (x fastest), the same lattice the `rectangle` primitive builds (5.1.1.2), so the two share one implementation. `fill="surface"` uses exact segment–box overlap (the separating-axis test in 2-D); `fill="inside"` uses the winding number of the closed polyline, with even-odd offered for self-overlapping input; a polyline that does not close is refused for `inside` by naming its open ends. **S–M**
  - **5.1.4.2 Octree and quadtree from a skin.** The root is the padded bounding box, made cubic, or a coarse `root_cells` lattice with one tree per cell (a forest, for elongated parts). A cell is split while the surface cuts it (the same overlap test) and its level is below `max_level`; every cell is split down to `min_level`. Optional criteria refine further: a distance band around the surface (`sample_distance`), surface curvature above a threshold ([curvature](./curvature.md)), cells crossed by [`feature_edges`](./feature_edges.md), and a size field sampled at the cell centre. A 2:1 balance pass follows, by faces or by faces, edges and corners (`balance="face"`/`"full"`), as a ripple to a fixed point. `fill` keeps `voxelize`'s meaning. The result carries `octree:level` and `octree:cut` cell data and, on request, `sdf:distance`. **M**
  - **5.1.4.3 Transitions — the decision this item records.** Where a fine cell meets a coarse one, three outputs, chosen by `transition=`: (a) **`"hanging"`, the v1 default**: plain hexahedra (quads in 2-D) with hanging nodes, flagged in `octree:hanging` point data — what adaptive-mesh-refinement, lattice-Boltzmann, immersed-boundary and cut-cell solvers and octree learning models consume, and what `check_conformity` (5.2.1) is built to report; (b) **`"polyhedra"`**: each coarse cell next to a finer one becomes a `polyhedron` (a `polygon` in 2-D) whose faces are split into the fine faces, the split-hex representation snappyHexMesh produces — conforming with no new points, through the [polyhedron kernel](./polyhedra.md), and readable by every format and finite-volume solver that takes polyhedra (OpenFOAM, Fluent, CGNS `NGON_n`, EnSight `nfaced`, VTU) (**M**); (c) **`"templates"`**: conforming transition templates (pyramids, tetrahedra and wedges in 3-D, triangles in 2-D) for a hex-dominant mesh a finite-element code takes — the most work, because every 2:1 configuration needs a template that tiles its cell with positive volume, checked exhaustively, and it is implemented from published descriptions only, as `remesh_volume` was (**L**).
  - **5.1.4.4 Optional snapping.** `snap=True` moves the outer nodes of the kept cells onto the skin with `shrinkwrap`'s projection, for a body-fitted rather than stair-stepped boundary, and never moves a node that would invert a cell: it reports the nodes it refused rather than leaving a bad cell. Boundary-layer inflation stays a [non-goal](#non-goals-and-decisions-taken). **M**
  - **5.1.4.5 Determinism.** Leaves come out in Morton order. Every point is an integer coordinate on the finest level's lattice (`2^max_level` per root cell), so shared corners are deduplicated arithmetically, with no hash and no tolerance, as `voxelize`'s are, and coordinates are `origin + spacing * index`, never accumulated. Refinement and balance run in parallel per level with a prefix-sum compaction, so the output is byte-identical across backends, thread counts and the C++/numpy twins.
  - **5.1.4.6 Surfaces and probes.** Python, C, Fortran, Julia, R, WASM, both CLIs (an `octree` verb beside `voxelize`), an MCP tool and an `Octree` pipeline step that, like `Voxelize`, replaces its input's geometry; documented in `voxelize.md` or a new `octree.md`, and shown in a notebook. Probes on a sphere skin: leaves at `max_level` occur only in the band the surface cuts; the `inside` volume converges to 4/3·πr³ as `max_level` grows; the inside cells of the 2-D quadtree of a circle converge to πr²; `check_conformity` reports zero hanging nodes under `"polyhedra"` and `"templates"` and exactly `octree:hanging` under `"hanging"`; and every cell has a positive volume.

**5.2 Checks, selection and measurement.**

- **5.2.1 `check_conformity`** — hanging nodes, T-junctions and interface facets that only partly overlap, so a user knows which `find_interface` mode to choose. It also gives `refine` and `undo_green`, which discuss conformity only in comments, a checker. A report plus a flagging `point_data` array. **S–M**
- **5.2.2 `find_intersections`** — self-intersection of a surface and mutual interpenetration of two parts, by triangle–triangle tests over the bucket grid. Returns the pairs, the intersection segments as a line mesh and a flagging `cell_data` array, with exact and "possible" hits reported separately because there are no robust predicates; booleans stay a [non-goal](#non-goals-and-decisions-taken). Also the precondition check for `repair`, `shrinkwrap` and `remesh_volume`. Probe: two overlapping spheres. **M**
- **5.2.3 `select`** — write `Region`s (cell, point or side) from a box, plane or sphere, a `cell_data` or quality threshold, a component label, or normal-angle patch growing bounded by `feature_edges`, so boundary-condition and contact patches are reproducible and feed `find_interface`. Reuses `crop(where=)`'s predicate parser, `feature_edges` and `split(by="component")`. **M**
- **5.2.4 `thickness`** — wall thickness and inter-part clearance per facet, from a ray along the inward normal to the opposite surface. Needs a ray–triangle kernel that `find_intersections` also needs: write it once in `detail/`. **M**
- **5.2.5 `mirror`** — reflect across a plane, flipping the winding so the orientation stays valid, optionally welding on the plane: a full model from a half, and the demi-sphere fixture from one hemisphere. **Verify first:** a reflecting `transform` matrix may already flip orientation correctly; probe by mirroring a tetrahedral mesh and asserting positive volumes, and if it does this item shrinks to documentation. **S**

**5.3 Optional MMG backend.** [MMG](https://www.mmgtools.org/) — `mmg2d` (planar triangles), `mmgs` (surface triangles in 3-D) and `mmg3d` (tetrahedra) — adapts an existing simplicial mesh to a size or an anisotropic metric, embeds a level set in it conformally, and moves it in a Lagrangian way; `mmg2d` also triangulates a planar domain from its boundary. Everything here was read in the source of MMG 5.8.0 (October 2024), not taken from its documentation. It is LGPL-3.0, so it follows the KaHIP, ADIOS2 and TecIO pattern exactly: **`MESHIOPLUSPLUS_WITH_MMG`**, off by default, bring-your-own (`find_package(mmg CONFIG)` over the package MMG installs, with its `Mmg::` targets; `mmg_DIR` or `CMAKE_PREFIX_PATH` point at it), never vendored, never downloaded, never probed under Emscripten, linked dynamically only, and absent from the release wheels and the native CLI binaries; the page states the licence's implications for anyone who redistributes a build with it. Without it, every operation below throws `Unsupported` naming the flag, as `partition(method="kahip")` does, and reports it in the configured capabilities. There is no numpy twin — MMG's result cannot be reproduced by a second implementation, the [`remesh_volume`](./remesh_volume.md) precedent — so Python raises `NotImplementedError` naming the flag when the core lacks it.

- **5.3.1 `adapt`** — remesh to a size field or a metric. A tetrahedral mesh goes to `MMG3D_mmg3dlib`, a triangle surface in 3-D to `MMGS_mmgslib`, a planar triangle mesh to `MMG2D_mmg2dlib`. **M**
  - **5.3.1.1 Size and metric.** A constant `hsiz`; a scalar size as one-component `point_data`; or an anisotropic metric as a symmetric tensor `point_data` (six components in 3-D, three in 2-D, in the upper-triangular order MMG expects — verify first against `MMG3D_Set_tensorSol`). The producers are already in the tree: [`hessian`](./hessian.md) (with a small metric-from-Hessian helper — absolute eigenvalues, scaled by a target error and clamped to `hmin`/`hmax`), [`error`](./error.md) for an isotropic size, and [curvature](./curvature.md) for a surface.
  - **5.3.1.2 Parameters.** `hmin`, `hmax`, `hausd` (the Hausdorff distance the boundary may move), `hgrad` and `hgradreq` (gradation), `angle_detection` (ridge angle, or off), `optim`, `noinsert`/`noswap`/`nomove`/`nosurf`, `nreg` (normal regularisation), `opnbdy` (keep internal open surfaces), `mem` and `verbose` (default −1, since MMG prints to stdout), and per-region `hmin`/`hmax`/`hausd` through `Set_localParameter` (`local={"inlet": {"hmax": 0.01}}`).
  - **5.3.1.3 Entities.** Cell and side regions map to MMG references through a reference ↔ name table and come back under their names; `frozen` points and named `required` regions become required vertices, edges, triangles and tetrahedra; [`feature_edges`](./feature_edges.md) become ridges, and their corners MMG corners. `wedge` blocks pass as MMG prisms, which `mmg3d` keeps unchanged (verify first), and boundary quads as MMG quadrilaterals (verify). Hexahedra, pyramids, higher-order cells and ragged blocks are refused with a pointer to [`convert_cells`](./convert_cells.md).
  - **5.3.1.4 What does not survive**, as for `remesh`: point and cell data on the new points are dropped with a warning — compose with [`interpolate`](./interpolate.md) — and `field_data` carries through.
  - **5.3.1.5 Report.** MMG's return code: `MMG5_SUCCESS`; `MMG5_LOWFAILURE`, where MMG returns a valid mesh it could not finish adapting, is a warning in the report, not an error; `MMG5_STRONGFAILURE` throws. Also points and cells in and out, and the quality histogram of the result.
- **5.3.2 `discretize_levelset`** — `MMG3D_mmg3dls`, `MMGS_mmgsls` and `MMG2D_mmg2dls` cut a mesh along the zero (or a chosen) isovalue of a `point_data` field and remesh both sides, so the interface is a conforming side region between an `inside` and an `outside` cell region; several materials through `Set_multiMat`, and small parasitic components removed through `rmc`. Where [`isosurface`](./isosurface.md) extracts a level set and [`crop`](./crop.md) cuts along cells, this embeds it in a mesh fit for a solver. Chained with `compute_sdf` on a `grid` and `convert_cells(simplexify)`, it is the backend's route from a skin to a tetrahedral mesh of its interior. **S–M**
- **5.3.3 `mesh_domain`** — `MMG2D_mmg2dmesh` triangulates a planar domain from its boundary `line` cells, with `hsiz`, `hmax` or a size field, boundary references kept as side regions. How MMG tells holes and subdomains apart is not yet read in its source: verify first, probing with an annulus. This is the only domain mesher meshio++ offers, and only through the backend (the [non-goal](#non-goals-and-decisions-taken) stands for native meshing). MMG has no 3-D counterpart that meshes from a surface; the 3-D routes are 5.3.2, [`remesh_volume`](./remesh_volume.md) and the octree of 5.1.4. **S**
- **5.3.4 `move`** — `MMG3D_mmg3dmov` and `MMG2D_mmg2dmov` move a mesh by a displacement `point_data` vector and remesh as it deforms. They need MMG built with the ELAS linear-elasticity library, so the operation is gated on that capability too, and comes last. **S**
- **5.3.5 Embedding hazards**, read in the 5.8.0 source:
  - **5.3.5.1 Signal handlers.** `MMG3D_mmg3dlib` calls `signal()` for `SIGABRT`, `SIGFPE`, `SIGILL`, `SIGSEGV`, `SIGTERM` and `SIGINT` on every call (`libmmg3d.c`), which replaces Python's Ctrl-C handler and any crash handler of the host. The wrapper saves every handler with `sigaction` before the call and restores it after, on every path including errors, and the page says a call cannot be interrupted. Check the other entry points and libraries for the same.
  - **5.3.5.2 Index width.** `MMG5_int` is `int32_t` unless MMG was configured with `-DMMG5_INT=int64_t`: detect it at configure time, and refuse a mesh beyond its range by name rather than truncate.
  - **5.3.5.3 Threads.** Whether two meshes can be adapted at once in one process is not established; serialise the calls behind one mutex until it is. ParMmg, MMG's MPI layer, falls under the MPI [non-goal](#non-goals-and-decisions-taken).
- **5.3.6 The file route, and Medit's half of it.** MMG's native files are Medit `.mesh` and `.sol`. meshio++'s `medit` reader discards `Corners`, `Ridges` and the `Required*` keywords and has no `.sol` support. Reading and writing `.sol` (and `.solb`) — scalar, vector and symmetric-tensor solutions at vertices and cells, as `point_data` and `cell_data` — and keeping those keywords as regions (4.4.11) make the `mmg3d_O3`/`mmgs_O3`/`mmg2d_O3` executables usable through files with no link at all, which also serves anyone driving MMG themselves. Independent of the rest, so it can land first. **S**
- **5.3.7 Surfaces and probes.** `operations/mmg.hpp` in the core; Python; C entry points with append-only, reserved-tail option structs and reports (`mio_adapt_ex`, the `mio_remesh_ex` pattern); Fortran, Julia and R mirrors; both CLIs (`adapt`, `discretize-levelset`, `mesh-2d`); MCP tools that report the capability; an `Adapt` pipeline step; no WASM. A `doc/mmg.md` page with the licence section, and a notebook adapting a `rectangle` to the metric of an analytic field's [`hessian`](./hessian.md). CI: one Linux leg that builds MMG 5.8 from source (cached) and runs with the flag on, beside the KaHIP and ADIOS2 legs; a conda-forge `mmg` package may serve instead †. Probes: a constant `hsiz` gives a mean edge length within a stated tolerance of it; region names and frozen points survive bit for bit; the level set of a sphere's signed distance gives an interface of area ≈ 4πr²; an anisotropic metric along a boundary layer gives elongated triangles aligned with it.

## 7. Long run (spike first)

*Admission: work whose shape is unknown until an investigation writes it down. Findings before code.*

**7.1 Scale.** Memory-mapped reads ([mmap](./mmap.md), via `ReadOptions` and the C ABI but not Python's `read()`) roughly halve the peak footprint of a large read, and the XDMF series appender and Python's chunked `write_dataset` write a series or a dataset without holding it — but nothing writes one mesh larger than memory, and no operation streams. Run the benchmark harness's `--tier XL` (about 10M cells) first; it decides whether either item below matters.

- **7.1.1 Streaming / chunked writes of one mesh**, the counterpart to selective and memory-mapped reads. **L**
- **7.1.2 Out-of-core operations** for the ops that are already block-local. **XL**

**7.2 NURBS and higher-order geometry.** The data model is strictly linear/Lagrange polytopes: a `CellBlock` is a cell-type string plus a node-index array. NURBS is a genuinely different object — control points, weights, knot vectors, and a parametric mapping — and CAD/IGA formats (STEP, IGES, Rhino 3dm, `.iga`) express geometry that no current cell type can hold. This is the most architecturally invasive item on the list and should be approached as a research spike, not a feature.

- **7.2.1 Spike: how far can the current model stretch?** Higher-order Lagrange cells already exist (`hexahedron27`, VTK-Lagrange types); a rational Bézier/NURBS patch needs *weights* and a *knot vector*, which have nowhere to live. Determine whether a side-channel struct (the `MedInfo`/`GmshInfo` precedent) suffices, or whether the `Mesh` needs a genuine second entity kind. Write the finding up before committing. **M**
- **7.2.2 Read-only CAD ingestion first**: a NURBS surface tessellated to a triangle mesh at a requested tolerance, with the parametric data carried out-of-band. This delivers most of the practical value (getting CAD into the mesh world) without touching the data model, and is the natural first release. **L**
- **7.2.3 A real IGA data model** — patches, control nets, weights, knots, trimming curves — plus formats and evaluation. This is XL, likely a separate library or a major version, and should only be attempted if the spike shows real demand.
- **7.2.4 Dependency reality**: robust STEP/IGES parsing effectively means OpenCASCADE, which is a heavyweight LGPL dependency. If ingestion goes ahead, it must follow the KaHIP/Polyscope pattern — strictly optional, off by default, never in the core, licence implications documented. **Findings before code.**
- **7.2.5 No C++ tessellator exists yet** — `tessellate` is Python-only — so read-only CAD ingestion reaching every surface also carries that port.

*Recommended posture: spike and document; do not schedule implementation until the spike says what shape it takes.*

## Non-goals and decisions taken

Recorded so they are not re-proposed as gaps.

- **MPI in the library** — none planned ([C++ API](./cpp_api.md)); `partition`'s ghost layers produce the halo an MPI assembly in the owning application needs. ParMmg, MMG's MPI layer, is excluded with it.
- **Solver-coupled physics-ML** — assembled solver residuals, adjoints and Sobolev training, co-simulation, active-learning *labeling*, adaptive remeshing driven by a surrogate, and MPI model-part gathering. Every one needs a live solver (an assembly routine, its tangent, its communicator) and meshio++ has no notion of a discrete system; they belong in the application that owns the solver, the division [Symbolic and physics](physicsnemo/symbolic_and_physics.md) describes.
- **The Python-only layers stay Python** — `pmsh`, `zarr`, `cae` and `usd`, and the physics-ML surface (`tessellate`, grids, point budgets, proximity graphs, datasets, training) are export targets and tooling for a training pipeline, registered in Python rather than the shared C++ registry. A core kernel they call (the neighbour search in [§3](#_3-performance)) does not change that.
- **Polyscope in the release CLI binaries** — excluded deliberately, so `view`/`screenshot` there report the build flag rather than opening a window ([viewer](./viewer.md)).
- **General meshing algorithms as operations** — Delaunay and constrained triangulation or tetrahedralization of a domain, hex and hex-dominant meshing from a CAD-like boundary, boolean/CSG, boundary-layer inflation, quadrangulation and geodesic distance are each a library in their own right, and the triangulators need robust geometric predicates, which is where dependency-free stops paying (the reason the queued Delaunay item was dropped). The answer is an optional backend (the KaHIP pattern), not a native implementation: domain meshing and adaptation reach meshio++ only through the MMG backend (§5.3). Lattice generation is the exception, and in scope: [`voxelize`](./voxelize.md), the octree of §5.1.4 and [`remesh_volume`](./remesh_volume.md)'s isosurface stuffing are index arithmetic over a signed distance, with no predicate to make robust.
- **Contact mechanics itself** — penalty or mortar assembly, friction and contact search in time need a live solver. meshio++ detects and exports the interface of one snapshot ([§5](#_5-operations)); the contact algorithm belongs in the application that owns the solver.
- **MMG in the WASM build, the release wheels and the native CLI binaries** — it is LGPL-3.0 and an external install, so it is linked dynamically into builds that opt in and nowhere else; the operations throw by name where it is absent.
- **KaHIP in the WASM build** — no Emscripten port, and a graph partitioner would bloat every consumer's bundle; `"auto"` resolving to the SFC method is the answer, and `"kahip"` throwing by name is the contract.
- **zstd/lz4 codecs, memory mapping and the Kokkos backend under Emscripten** — the codecs have no Emscripten port and are compiled out, CMake refuses the Kokkos backend under Emscripten, and there is nothing to map inside MEMFS.
- **Single-file output for DOLFIN, TetGen and EnSight from WASM**, or lifting DOLFIN's simplicial restriction — both are facts of the formats; `writeMesh`'s written-paths return value (v11.2.0) is the fix for the bookkeeping they cause.
- **Polyhedron blocks as a WASM gap** — `vtu`, `ensight`, `cgns`, `med` and `openfoam` all write them from WASM; a consumer that cannot is constrained by its own data model.

## Suggested sequencing

Open work only; what shipped is in `CHANGELOG.md`.

1. **Format reach ([§1](#_1-format-reach))** — the checks against the vendor tools, as licences or files the tools wrote appear.
2. **The OSS-Fuzz submission ([§2](#_2-quality-of-implementation))** — calendar-bound, so it runs alongside everything else.
3. **Performance ([§3](#_3-performance))** — the boundaries, and the tokenizer's remaining readers as they are touched; the operations' layout-bound leftovers with the next ABI bump.
4. **Reader and writer parity ([§4](#_4-reader-and-writer-parity))** — the guard first (4.1), so every gap is tracked; then the `svg`, `tikz` and `gltf` readers (4.2), a few days each but the glTF reader; then the tier-A result writers in their listed order, `frd` first as the cheapest with a pip-installable validator; the partial writers (4.4) and the engine gaps (4.5) as their formats are touched; `marc_t19` last, since nothing but Mentat can check it. A new Python-only construct still enters here, as it entered the core-parity section this replaces.
5. **Primitive constructors ([§5](#_5-operations))** — tier 1 and the reference cells first, a few days, and a prerequisite of the conformance matrix, every demo surface, `extrude`/`revolve`, the 2-D `voxelize` and the octree's fixtures; the other tiers as tests and notebooks ask for them.
6. **Voxel and octree meshes ([§5](#_5-operations))** — the 2-D `voxelize`, then the octree with hanging nodes and its quadtree, then the polyhedral transitions; the transition templates when a finite-element consumer asks.
7. **The MMG backend ([§5](#_5-operations))** — Medit `.sol` first, since it needs no link and opens the file route; then `adapt`, `discretize_levelset`, `mesh_domain` and, with ELAS, `move`.
8. **Registration ([§6](#_6-ecosystem-reach))** — calendar-bound, so start the submissions early and let them run alongside everything else.
9. **Long-run spikes ([§7](#_7-long-run-spike-first))** — the benchmark tier decides the scale items; the NURBS spike is scheduled independently of the rest.
