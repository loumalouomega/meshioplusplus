# meshio++ roadmap

Status at time of writing: **v17.15.0**, ABI 34. What ships is listed where it is documented rather than counted here, where counts went stale: the formats in [supported formats](./formats.md) and the [conformance matrix](./conformance.md), the operations in [architecture](./architecture.md#the-operations-layer), the language surfaces in the [C API](./c_api.md), [Fortran](./fortran.md), [Julia](./julia.md), [R](./r.md) and [WebAssembly](./wasm.md) pages.

This document lists what is *not* built. Nothing here duplicates shipped functionality; where a feature partially exists, the shipped half is named and the gap is stated explicitly. Release history lives in [`CHANGELOG.md`](https://github.com/loumalouomega/meshioplusplus/blob/main/CHANGELOG.md), not here.

Effort key: **S** = days, **M** = a couple of weeks, **L** = a month or more, **XL** = a project in its own right. An item names a **probe** — the failing test that proves the gap — wherever one is cheap.

## How this file works

- **Sections are ordered, and the order is the recommendation.** Each section states what belongs in it; an item that sounds exciting does not move up for that reason. An empty section is removed, not kept as a placeholder.
- **A closed item is removed, not struck through.** Its history is the `CHANGELOG.md` entry and the feature's own `doc/` page; a partly closed item is narrowed to what remains (the `AGENTS.md` change checklist rule).
- **Every level of the outline is numbered**, so a gap can be cited in an issue, a commit or a release note: a group of work is `section.item` (a `###`/`####` heading, or a bold label line), the work under it `section.item.subitem`, and a bullet under that `section.item.subitem.subsub`. Lists that record a decision rather than open work — *Considered, not queued*, a section's *Landing an item* steps and the [non-goals](#non-goals-and-decisions-taken) — stay unnumbered, because a number here means work to do. The numbering follows the sections, so a new section inserted at the top renumbers the rest, as the rule above says, and so does a section removed once its last item closes (Performance, October 2026: what was §4 onward moved up one; and again when reader and writer parity closed, the same month: operations, ecosystem reach and the full WebAssembly build became §3 to §5). The long-run section closed the same month as the last of its spikes landed ([findings](./spikes.md)); being last, it renumbered nothing.
- **Defect-shaped items go in a *Correctness debts* section at the top, regardless of size** — behaviour that loses data, mis-orients cells, does not terminate on valid input or fails silently is not a feature request, even when the fix and the feature are the same work. None is open today, so there is no such section; the first defect found opens one as §1 and renumbers the rest.
- **An item estimated from a doc, a `.d.ts` or a changelog alone says so** ("verify first") and names its probe; the code has repeatedly been more or less capable than its description.
- **[Non-goals](#non-goals-and-decisions-taken) record decisions already taken**, with their reasons, so they are not re-proposed as gaps.

## 1. Format reach

*Admission: a format a simulation or physics-ML workflow actually exchanges; a shipped format's missing half is not a roadmap item, because every registered format reads and writes ([decisions](#non-goals-and-decisions-taken)). "Exchanges" means a file that crosses a tool boundary in a real pipeline (mesher → solver, solver → post-processor, solver → training set), not a format that merely exists. Every item names the consumer on the other side of the file.*

Sizes: **S** ≈ days, **M** ≈ two weeks, **L** ≈ a month or more, including tests, docs page and CLI wiring. They assume a new format reuses the shared components rather than growing its own: the card tokenizer (`detail/keyword_card.hpp`), the [node-ordering registry](./node_ordering.md), the Fortran record reader (`detail/fortran_records.hpp`) and the directory sniffing that sequence globs share.

Link legend: unmarked links were opened or returned by a search while this section was written (September 2026); links marked † are quoted from memory and must be checked before relying on them. Vendor documentation portals move often — when a link is dead, search the document title.

---

Every format this section queued is now read: the native FEM interchange, solver input and result-file readers of v16.5.0 to v16.12.0 (Tecplot, Femap, MFEM, Patran, Abaqus `.fil`, Radioss, Z88, libMesh, Marc, Ansys `.rst`, LS-DYNA and OP2), DOLFINx's ADIOS2 `.bp` ([`vtx`](./formats/vtx.md)) and Tecplot SZL through TecIO ([`szplt`](./formats/szplt.md)) of v16.13.0, and the [vendor-runtime routes](./vendor_routes.md) for the files only a vendor's software reads (Abaqus `.odb`, Marc `.t16`, Femap `.modfem`, Ansys results beyond the native reader). Since v16.17.0 the shared components are used wherever a format's layout fits them, the input decks are written too (Radioss's starter deck, checked with the OpenRadioss starter, and Marc's), Femap writes a series as one output set per step, and every format read but not written names its reason on the [conformance page](./conformance.md#formats-missing-a-direction), which a test keeps in step with the registry; the missing half of each has since been written, so every registered format reads and writes. What they still lack is a check against a run of the vendor tool, listed under [Awaiting a licensed run](#_1-2-awaiting-a-licensed-run): take each as soon as a licence, or a file the tool wrote, is in hand.

### Considered, not queued

- **Graphics, CAD, VFX or lab-specific rather than simulation interchange:** 3MF, X3D, DXF, Alembic, OpenVDB, Silo, LAS/LAZ, E57, OBJ materials (`.mtl`).
- **Closed FEM databases with no route worth shipping:** Altair `.h3d` (undisclosed format, SDK not redistributable — Altair's own advice for OpenRadioss is ANIM → VTK, see the [OpenRadioss discussion](https://github.com/orgs/OpenRadioss/discussions/552)); HyperMesh `.hm`; Abaqus `.sim`.
- **No native format to implement:** deal.II (reads and writes UCD, VTK, Gmsh, Abaqus, Exodus — all reachable today); MOOSE (Exodus).
- **Nastran OP4 matrices and punch `.pch`:** matrix and card dumps, not mesh/field exchange; pyNastran serves them.
- **Non-MSC Nastran HDF5 dialects:** incompatible schemas; revisit with a file in hand.
- **Partitioning niche:** gmsh `$PartitionedEntities` (Kratos partitions through MDPA).
- **CalculiX `.dat` print files:** `frd.read_dat` stays a Python helper that returns a list of table dictionaries; it is not a `Mesh`, it has no writer, and `.dat` already belongs to Tecplot and Marc ([CalculiX results](./formats/frd.md)).
- **Operators and tooling, not formats** (listed only because they came up in the same review): ICP registration; mesh duals; cylindrical/spherical coordinate transforms; shell completions.

Revisit any of them when a consumer asks with a file in hand — a real deck or result file, the tool version that wrote it, and the tool that needs the converted output.

#### 1.2 Awaiting a licensed run

Checks that need the vendor tool itself, or a file it wrote that no public source has. Each reader works from the vendor's documentation and every public file found (September 2026); what remains is one probe per line.

The [vendor-runtime routes](./vendor_routes.md) of v16.13.0 are tested against stand-ins of the vendor APIs only. Each needs one recorded run, with the vendor version written into its page; what to install for it:

- **1.2.1 Abaqus `.odb`.** Abaqus 2020 or later (its `abaqus python`, whose bundled numpy the script needs; 2023 and before run Python 2.7, 2024 and later Python 3). Run `contrib/abaqus_odb/odb_to_vtu.py` on a job with shells, C3D20R and an assembly-level set, and compare its nodal `U` and centroidal `S` against the same job's `.fil` read natively ([route](./routes/abaqus_odb.md)).
- **1.2.2 Marc `.t16`.** Marc/Mentat 2020 or later with PyPost (`py_post`, run with Mentat's Python). Run `contrib/marc_t16/t16_to_vtu.py` on a job that writes both `.t16` and `.t19`, and compare against the `.t19` read natively; confirm that post file position 0 holds the model ([route](./routes/marc_t16.md)).
- **1.2.3 Ansys results via PyDPF.** A DPF Server (Ansys 2021 R1 or later, or the standalone DPF Server 2024 R2 or later) and `pip install ansys-dpf-core pyvista meshioplusplus[h5py]`. Run `contrib/ansys_dpf/rst_to_vtkhdf.py` on a structural `.rst` and compare against the native `.rst` reader; then on a `/FCOMP,RST,1` file, which the native reader refuses ([route](./routes/ansys_dpf.md)).
- **1.2.4 Femap `.modfem`.** Femap 2301 or later on Windows, and `pip install pywin32`. Run `contrib/femap/export_neutral.py`, check `feFileWriteNeutral`'s argument list against that version's API help, and read the neutral file back ([route](./routes/femap_modfem.md)).
- **1.2.5 Tecplot `.szplt`.** Tecplot 360 2023 or later, and `pip install pytecplot`. Save a data set as `.szplt` and as `.plt` from Tecplot itself and read both (the TecIO-backed reader against the native one); run `contrib/tecplot/szplt_to_plt.py` and the macro `contrib/tecplot/szplt_to_plt.mcr`; and point `MESHIOPLUSPLUS_TECIO_LIBRARY` at Tecplot's own shared `libtecio` for the ctypes reader ([route](./routes/tecplot_szplt.md)). Also open in Tecplot 360 a file meshio++ wrote with single-precision, 16-bit and byte variables and one with partitioned zones; and, with a TecIO newer than 2018.3 (which refuses to write polygon and polyhedral zones in an SZL file), write such a zone, read it back, and check the written face map against Tecplot's reading, which would turn the refusal of those zones into a reader and a writer.

The readers:

- **1.2.6 Tecplot.** A `.plt` written by `preplot` from the ASCII fixtures (`#!TDV112`), read identically to its `.dat`, and the `.plt` meshio++ now writes opened in Tecplot or checked by `preplot`; binary files of versions 100–105 and 109–111, of which no sample was found (the VisIt suite covers 71, 75, 106–108).
- **1.2.7 Femap.** Element (404) and group (408) records written by Femap 10 and by 12 or later (the public 2401 files hold none); the slot layout of the 13-node pyramid (topology 19); a file meshio++ writes, a multi-set series included, imported into Femap.
- **1.2.8 Patran.** A neutral file exported by ANSA or HyperMesh.
- **1.2.9 Abaqus `.fil`.** A binary run with shells and C3D20R, checked against its `.dat` printout (the truss run TenBarArea is checked); a binary file of a single-precision build (4-byte words), of which no layout description or sample was found, which decides whether the reader and the writer take that width; and a file meshio++ writes, opened in Abaqus.
- **1.2.10 Radioss.** Animation files of the layouts before OpenRadioss (magic numbers `0x5426` to `0x542B`): neither OpenRadioss's tools nor its readers document them. The 16-bit encoding of the nodal normals (the writer leaves them zero: `anim_to_vtk` ignores them and the encoding is undocumented), and a run of OpenRadioss's `anim_to_vtk` on a file meshio++ wrote, time-history lists included.
- **1.2.11 Marc.** A run of Marc itself, including on a deck or a `.t19` post file (a remeshing series included) meshio++ writes (`SIZING`'s fields, one type per `ELEMENTS` line, and the shell and plane-strain default types follow Volume C and Mentat's decks); post files before revision 9 (Marc K7 and earlier, Volume D 2000's PLDUMP layout); Volume A's edge and face numbering, to map edge and face sets (kept as `(cell, number)` field data) onto facets, which also decides whether side regions can be written to decks and post files; the binary `.t16`, read or written natively, which needs Volume D's PLDUMP description of it or a sample file (today it is read only through Marc's PyPost, by the [route](./routes/marc_t16.md)).
- **1.2.12 Ansys `.rst`.** A file written with `/FCOMP,RST,1` or higher (zlib records): `detail/zlib_inflate` is ready, the record framing needs a sample. A harmonic (complex) result file, which no public sample or open reader covers (pymapdl-reader takes cyclic mode pairs only and only DPF reads complex sets), so complex results are neither read nor written; and a file meshio++ writes with element rotations and nodal coordinate systems, read by DPF (pymapdl-reader applies the three nodal rotations in the opposite order, so it agrees only on single-axis angles).
- **1.2.13 LS-DYNA.** A family from LS-DYNA with adaptive remeshing (`NADAPT`), the `d3thdt` time-history database, the cubic and bubble solids (21P, 15T, 20T, 40P, 64), airbag particles and rigid roads (read and written from the manual and lasso-python only: the airbag variable names of a real file, and rigid roads with the full rigid-body velocities, `NDIM = 9`, which the writer leaves out), a real `d3part`, thick shells, and the whole reader against LS-PrePost, with the families and `binout` files (links included) meshio++ writes opened there; whether LS-DYNA writes a ten-node solid's extra nodes once or twice.
- **1.2.14 Nastran OP2.** Random element tables, complex SORT2 nodal tables, CBUSH and CGAP forces, CBUSH real stresses, and NX's solid types 300–303 (read from pyNastran's layouts; no sample). Files meshio++ writes, opened in Femap, Patran or an NX/Simcenter post-processor: the writer produces the MSC dialect only, and the element tables it writes beyond pyNastran's reach (the SORT1 PSD, CRM and ATO random tables, the complex layouts pyNastran does not read) follow the reader's layouts.
- **1.2.15 CalculiX `frd`.** `cgx -b` (CalculiX GraphiX) reading a binary file meshio++ writes; `ccx2paraview` parses the ASCII layout only, so no open tool checks the binary variant beyond meshio++'s own reader and the binary files `ccx` wrote.
- **1.2.16 FEBio `.xplt`.** FEBio Studio or `febio4` opening a file meshio++ wrote: the remeshed series (a mesh section per remeshed step), surfaces with per-surface-node variables, and the compressed states.
- **1.2.17 Nastran HDF5.** MSC's own post-processors (Patran, Simcenter) reading a file meshio++ wrote: its tables follow the column sets of the six MSC Nastran 2020 files, but the `CBUSH`, `CGAP`, `CMASS` and `CONM1` element tables and the `MAT5`, `MAT8`, `MAT9`, `PBARL`, `PBEAML` and `PCOMPG` tables have no sample, so they are not written; a file with them would add them.
- **1.2.18 DOLFINx VTX.** ParaView's `ADIOS2VTXReader` (`tools/gen_vtx_reference.py` drives it) and DOLFINx reading a file meshio++ wrote with several cell types or parts (one block per type and part, with `meshio.shared_points`): both read one cell type per file, so this is meshio++'s own extension of the layout; and a `VTXMeshPolicy.reuse` file (ParaView 6.1 aborts on every step after the first of DOLFINx's own).

## 3. Operations

*Admission: a new operation, or a public face for machinery that already exists privately inside one.*

**3.1 Generation.** Almost every operation transforms a mesh you already have. The exceptions all start from something else — `grid` from a lattice (`detail/grid_lattice.hpp`), the [primitives](./primitives.md) from parameters, `voxelize`/`compute_sdf` from a surface's bounding box, `remesh_volume` and [`octree_mesh`](./octree_mesh.md) from a closed surface, and [`mesh_cad_surface`](./mesh_cad.md) and `triangulate_polygon_2d` from a CAD model or a polygon — and nothing sweeps a shape yet. Triangulation with quality and size control continues in [§6](#_6-mesh-generation); volume meshing of a domain reaches meshio++ only through optional backends (3.3, 6.7), and the octree mesher (3.1.4) is the native lattice route.

- **3.1.1 Primitive constructors** — parametric generators in `operations/primitives.hpp` beside `grid`. Tier 1, the planar domains and the reference cells have shipped (`rectangle`, `box`, `disk`, `uv_sphere`, `icosa_sphere`, `cylinder`, `reference_triangle`, `ngon`, `annulus`, `lshape`, `plate_with_hole`, `honeycomb` and `reference_cells`, on every surface; see [parametric primitives](./primitives.md)); the catalogue below is what is left. They are dependency-free and remove the fixture-file dependency from tests, docs, notebooks, the browser demo and the MCP server, and `reference_cells` could replace the test-local canonical mesh of the [format conformance matrix](./conformance.md) (whose coordinates are exact in binary and keep a deliberately inexact `0.1` vertex, so the swap needs that vertex kept). **The hand-rolled helpers are mostly retired**: the x-fastest `_quad_grid`, `_hex_grid` and `_tri_grid` of ten Python test files, and `hex_grid`, `quad_grid` and `tri_grid` of nine C++ test files, call `rectangle` and `box`, whose coordinates are bit-identical (`origin + size * i / n` is exactly `i` for a size equal to the count). **What remains is a decision per helper, each recorded here so it is not re-litigated:** `_unit_cube` (three Python copies and `test_voxelize.py`) numbers its corners in VTK order, not `box`'s x-fastest order; `_hex_cube` and `_tet_cube` carry extra `point_data` and `cell_data`, and `np.linspace` differs from `size * i / n` in the last bit above three cells; the i-major helpers of `test_smooth` and `test_openfoam` pin a different numbering; `test_region_analysis.cpp`'s `quad_grid` is asserted against region counts the generators' side regions would change; and the jittered `ft_*` fixtures of `golden_fixtures.hpp` feed pinned digests. The notebook helpers (`hex_grid` in 03 and 09, `hex_block` in 25, `plate` in 09, the squircle `disk` of 27) are left to the next edit of each notebook, since a change re-executes it. The catalogue follows [meshzoo](https://github.com/meshpro/meshzoo)'s where the two overlap, taking names and parameterisations from its README only: check its licence before reading its code, since later releases are not MIT. **S per tier**
  - **3.1.1.1 What every further generator owes.** The contract is shipped (index-computed coordinates, a documented order, a `max_cells` budget, a zero count as an empty mesh, outward surfaces and positive volumes, named side `Region`s); a new generator adds the same surface list: Python and its numpy twin, C (`mio_gen_opts` has room in its reserved tail, so a shape that needs a field grows the struct append-only), Fortran, Julia, R, WASM, both CLIs' `generate` verb, an MCP tool and a pipeline `Generate` shape. **Remaining in the contract itself:** `order=2` serves the serendipity types only; the full-Lagrange types (`quad9`, `hexahedron27`, `wedge18`) and the VTK Lagrange family are not generated.
  - **3.1.1.4 Surfaces**: spheres from the other platonic seeds (`tetra_sphere`, `octa_sphere`, and `cube_sphere` in quads); `geo_sphere` (a UV sphere closed with triangle caps rather than degenerate quads); `torus` (genus one, negative Gaussian curvature on the inner rim and periodic both ways — the [curvature](./curvature.md) and Euler-characteristic probe a sphere cannot give); `moebius` (non-orientable, with `num_twists`: no consistent orientation exists, which probes [`compute_normals`](./normals.md)' `inconsistent_pairs` report and `repair(fix_orientation=True)`); `tube`, `cone` and `capsule` (open and closed surfaces of revolution, with sharp rims for [`feature_edges`](./feature_edges.md)); `box_surface` (today's `cube_quads`, a region per face); and the five platonic solids with one cell per face, the dodecahedron's pentagons as a `polygon` block. **S**
  - **3.1.1.5 Solids**: `ball` (tetrahedra, or hexahedra by a seven-block butterfly so no cell degenerates at the centre); `spherical_shell` and `pipe` (thick shells between two radii in hexahedra, `inner`/`outer` regions, with a radial grading ratio for wall-resolved spacing); `fichera` (the cube minus one octant, the 3-D L-shape and its corner singularity); `solid_torus`. **S**
  - **3.1.1.6 Lines and points**: `line` (a subdivided segment), `circle` (a closed polyline) and `helix` (a spring), as `line` cells for beam and 1-D format fixtures; point clouds on a sphere (a Fibonacci lattice) or in a box (seeded sampling) for the point-cloud formats and [point budgets](./point_budgets.md). Seeded sampling needs its own small generator (splitmix64 or PCG) in both twins: `std::uniform_real_distribution` is implementation-defined, and numpy's `default_rng` has no C++ counterpart. **S**
  - **3.1.1.8 Watch.** Byte identity between the twins holds for `grid` because it is index arithmetic; `std::sin`/`std::cos` are not correctly rounded and differ between glibc, MSVC, Emscripten's libc and numpy's own SIMD kernels. Pin byte identity only for the polynomial generators (`rectangle`, `box`, `reference_triangle`, `lshape`, `honeycomb`, `reference_cells`) and compare the trigonometric ones within a few ulps, or have the Python twin take its angle table from the core. Seams and poles are welded points, never duplicates, or `periodic`, `clean` and the Euler-characteristic checks see a boundary that is not there.
- **Deliberately not**, so not re-proposed: generators driven by a user callback (no callback crosses the flat ABI; numpy users build `Mesh(points, cells)` directly, and [`isosurface`](./isosurface.md) on a `grid` covers implicit shapes); scanned or modelled assets (the bunny, the teapot, the bracket fixture — data rather than parameters, each under its own licence); and CSG combinations (a [non-goal](#non-goals-and-decisions-taken)) — two-body interface and contact fixtures are primitives placed with `transform` and joined with `merge`.
- **3.1.2 `extrude`** — 2-D → 3-D sweep (triangle → wedge, quad → hexahedron) with `nlayers` and per-layer offsets, carrying regions to side and cap regions. The most-requested generation primitive. **M**
- **3.1.3 `revolve`** — `extrude`'s rotational sibling around an axis, sharing its layer machinery; degenerate cells on the axis are the only new work. **M**
- **3.1.4 Octree and quadtree: what is left.** [`octree`](./octree.md) (octrees and quadtrees from a skin with `hanging`, `polyhedra` and `templates` transitions, snapping, curvature / feature / size-field criteria and a choice of plane) and the 2-D [`voxelize`](./voxelize.md#2-d-pixels) have shipped; what remains is below. **S**
  - **3.1.4.1 `plane=` on `voxelize`.** The pixel variant picks the skin's plane automatically; an explicit `plane` option needs a field on `VoxelOptions`, which is a released type, so it waits for the next ABI bump. **S**
  - **3.1.4.2 Probes.** [`check_conformity`](#_3-2-checks-selection-and-measurement) (3.2.1) reporting zero hanging nodes under `"polyhedra"` and `"templates"` and exactly `octree:hanging` under `"hanging"`, once it exists; the tests already check face sharing and volumes with their own oracle.
  - **3.1.4.3 `octree_mesh`: what is left.** [`octree_mesh`](./octree_mesh.md) shipped in v17.12.0 with its castellated, tetrahedral and hexahedral outputs ([plan](./octree_mesh_3d_plan.md)). Three pieces remain. First, a *graded* all-hexahedral output: the hexahedra are a uniform grid at the skin size today, and the octree's grading needs the conforming dual templates of Livesu, Pitzalis and Cherchi (TOG 2022). Second, feature chains on thin features of fine graded skins: a cylinder's rims are reported missed at small `min_size`, where the snap guard refuses moves that would invert thin stuffed tetrahedra. Third, the inside test of lattice vertices away from the skin: their winding numbers dominate the time of a uniformly fine mesh, and a flood fill through the leaves the skin does not cut would save most of them for a closed skin. **M**

**3.2 Checks, selection and measurement.**

- **3.2.1 `check_conformity`** — hanging nodes, T-junctions and interface facets that only partly overlap, so a user knows which `find_interface` mode to choose. It also gives `refine` and `undo_green`, which discuss conformity only in comments, a checker. A report plus a flagging `point_data` array. **S–M**
- **3.2.2 `find_intersections`** — self-intersection of a surface and mutual interpenetration of two parts, by triangle–triangle tests over the bucket grid. Returns the pairs, the intersection segments as a line mesh and a flagging `cell_data` array, with exact and "possible" hits reported separately unless the triangle–triangle test is built on the core's exact `orient3d` (`detail/predicates`, v17.13.0), which would make every hit exact; booleans stay a [non-goal](#non-goals-and-decisions-taken). Also the precondition check for `repair`, `shrinkwrap` and `remesh_volume`. Probe: two overlapping spheres. **M**
- **3.2.3 `select`** — write `Region`s (cell, point or side) from a box, plane or sphere, a `cell_data` or quality threshold, a component label, or normal-angle patch growing bounded by `feature_edges`, so boundary-condition and contact patches are reproducible and feed `find_interface`. Reuses `crop(where=)`'s predicate parser, `feature_edges` and `split(by="component")`. **M**
- **3.2.4 `thickness`** — wall thickness and inter-part clearance per facet, from a ray along the inward normal to the opposite surface. Needs a ray–triangle kernel that `find_intersections` also needs: write it once in `detail/`. **M**
- **3.2.5 `mirror`** — reflect across a plane, flipping the winding so the orientation stays valid, optionally welding on the plane: a full model from a half, and the demi-sphere fixture from one hemisphere. **Verify first:** a reflecting `transform` matrix may already flip orientation correctly; probe by mirroring a tetrahedral mesh and asserting positive volumes, and if it does this item shrinks to documentation. **S**

**3.3 Optional MMG backend.** [MMG](https://www.mmgtools.org/) — `mmg2d` (planar triangles), `mmgs` (surface triangles in 3-D) and `mmg3d` (tetrahedra) — adapts an existing simplicial mesh to a size or an anisotropic metric, embeds a level set in it conformally, and moves it in a Lagrangian way; `mmg2d` also triangulates a planar domain from its boundary. Everything here was read in the source of MMG 5.8.0 (October 2024), not taken from its documentation. It is LGPL-3.0, so it follows the KaHIP, ADIOS2 and TecIO pattern exactly: **`MESHIOPLUSPLUS_WITH_MMG`**, off by default, bring-your-own (`find_package(mmg CONFIG)` over the package MMG installs, with its `Mmg::` targets; `mmg_DIR` or `CMAKE_PREFIX_PATH` point at it), never vendored, never downloaded, never probed under Emscripten, linked dynamically only, and absent from the release wheels and the native CLI binaries; the page states the licence's implications for anyone who redistributes a build with it. Without it, every operation below throws `Unsupported` naming the flag, as `partition(method="kahip")` does, and reports it in the configured capabilities. There is no numpy twin — MMG's result cannot be reproduced by a second implementation, the [`remesh_volume`](./remesh_volume.md) precedent — so Python raises `NotImplementedError` naming the flag when the core lacks it.

- **3.3.1 `adapt`** — remesh to a size field or a metric. A tetrahedral mesh goes to `MMG3D_mmg3dlib`, a triangle surface in 3-D to `MMGS_mmgslib`, a planar triangle mesh to `MMG2D_mmg2dlib`. **M**
  - **3.3.1.1 Size and metric.** A constant `hsiz`; a scalar size as one-component `point_data`; or an anisotropic metric as a symmetric tensor `point_data` (six components in 3-D, three in 2-D, in the upper-triangular order MMG expects — verify first against `MMG3D_Set_tensorSol`). The producers are already in the tree: [`hessian`](./hessian.md) (with a small metric-from-Hessian helper — absolute eigenvalues, scaled by a target error and clamped to `hmin`/`hmax`), [`error`](./error.md) for an isotropic size, and [curvature](./curvature.md) for a surface.
  - **3.3.1.2 Parameters.** `hmin`, `hmax`, `hausd` (the Hausdorff distance the boundary may move), `hgrad` and `hgradreq` (gradation), `angle_detection` (ridge angle, or off), `optim`, `noinsert`/`noswap`/`nomove`/`nosurf`, `nreg` (normal regularisation), `opnbdy` (keep internal open surfaces), `mem` and `verbose` (default −1, since MMG prints to stdout), and per-region `hmin`/`hmax`/`hausd` through `Set_localParameter` (`local={"inlet": {"hmax": 0.01}}`).
  - **3.3.1.3 Entities.** Cell and side regions map to MMG references through a reference ↔ name table and come back under their names; `frozen` points and named `required` regions become required vertices, edges, triangles and tetrahedra; [`feature_edges`](./feature_edges.md) become ridges, and their corners MMG corners. `wedge` blocks pass as MMG prisms, which `mmg3d` keeps unchanged (verify first), and boundary quads as MMG quadrilaterals (verify). Hexahedra, pyramids, higher-order cells and ragged blocks are refused with a pointer to [`convert_cells`](./convert_cells.md).
  - **3.3.1.4 What does not survive**, as for `remesh`: point and cell data on the new points are dropped with a warning — compose with [`interpolate`](./interpolate.md) — and `field_data` carries through.
  - **3.3.1.5 Report.** MMG's return code: `MMG5_SUCCESS`; `MMG5_LOWFAILURE`, where MMG returns a valid mesh it could not finish adapting, is a warning in the report, not an error; `MMG5_STRONGFAILURE` throws. Also points and cells in and out, and the quality histogram of the result.
- **3.3.2 `discretize_levelset`** — `MMG3D_mmg3dls`, `MMGS_mmgsls` and `MMG2D_mmg2dls` cut a mesh along the zero (or a chosen) isovalue of a `point_data` field and remesh both sides, so the interface is a conforming side region between an `inside` and an `outside` cell region; several materials through `Set_multiMat`, and small parasitic components removed through `rmc`. Where [`isosurface`](./isosurface.md) extracts a level set and [`crop`](./crop.md) cuts along cells, this embeds it in a mesh fit for a solver. Chained with `compute_sdf` on a `grid` and `convert_cells(simplexify)`, it is the backend's route from a skin to a tetrahedral mesh of its interior. **S–M**
- **3.3.3 `mesh_domain`** — `MMG2D_mmg2dmesh` triangulates a planar domain from its boundary `line` cells, with `hsiz`, `hmax` or a size field, boundary references kept as side regions. How MMG tells holes and subdomains apart is not yet read in its source: verify first, probing with an annulus. A planar domain with holes is also triangulated natively since v17.13.0 (`triangulate_polygon_2d`, uniform size, refined to a minimum angle since v17.15.0), so what this item adds is MMG's size fields until [§6.3](#_6-mesh-generation) gives the native triangulator its own; whichever lands second states the overlap on its page. MMG has no 3-D counterpart that meshes from a surface; the 3-D routes are 3.3.2, [`remesh_volume`](./remesh_volume.md) and the octree of 3.1.4. **S**
- **3.3.4 `move`** — `MMG3D_mmg3dmov` and `MMG2D_mmg2dmov` move a mesh by a displacement `point_data` vector and remesh as it deforms. They need MMG built with the ELAS linear-elasticity library, so the operation is gated on that capability too, and comes last. **S**
- **3.3.5 Embedding hazards**, read in the 4.8.0 source:
  - **3.3.5.1 Signal handlers.** `MMG3D_mmg3dlib` calls `signal()` for `SIGABRT`, `SIGFPE`, `SIGILL`, `SIGSEGV`, `SIGTERM` and `SIGINT` on every call (`libmmg3d.c`), which replaces Python's Ctrl-C handler and any crash handler of the host. The wrapper saves every handler with `sigaction` before the call and restores it after, on every path including errors, and the page says a call cannot be interrupted. Check the other entry points and libraries for the same.
  - **3.3.5.2 Index width.** `MMG5_int` is `int32_t` unless MMG was configured with `-DMMG5_INT=int64_t`: detect it at configure time, and refuse a mesh beyond its range by name rather than truncate.
  - **3.3.5.3 Threads.** Whether two meshes can be adapted at once in one process is not established; serialise the calls behind one mutex until it is. ParMmg, MMG's MPI layer, falls under the MPI [non-goal](#non-goals-and-decisions-taken).
- **3.3.6 The file route, and Medit's half of it.** MMG's native files are Medit `.mesh` and `.sol`. meshio++'s `medit` reader and writer keep `Corners`, `Ridges` and the `Required*` keywords as regions ([Medit](./formats/medit.md)); what is missing is `.sol`. Reading and writing `.sol` (and `.solb`) — scalar, vector and symmetric-tensor solutions at vertices and cells, as `point_data` and `cell_data` — makes the `mmg3d_O3`/`mmgs_O3`/`mmg2d_O3` executables usable through files with no link at all, which also serves anyone driving MMG themselves. Independent of the rest, so it can land first. **S**
- **3.3.7 Surfaces and probes.** `operations/mmg.hpp` in the core; Python; C entry points with append-only, reserved-tail option structs and reports (`mio_adapt_ex`, the `mio_remesh_ex` pattern); Fortran, Julia and R mirrors; both CLIs (`adapt`, `discretize-levelset`, `mesh-2d`); MCP tools that report the capability; an `Adapt` pipeline step; no WASM. A `doc/mmg.md` page with the licence section, and a notebook adapting a `rectangle` to the metric of an analytic field's [`hessian`](./hessian.md). CI: one Linux leg that builds MMG 5.8 from source (cached) and runs with the flag on, beside the KaHIP and ADIOS2 legs; a conda-forge `mmg` package may serve instead †. Probes: a constant `hsiz` gives a mean edge length within a stated tolerance of it; region names and frozen points survive bit for bit; the level set of a sphere's signed distance gives an interface of area ≈ 4πr²; an anisotropic metric along a boundary layer gives elongated triangles aligned with it.

## 6. Mesh generation

*Admission: generating a mesh from a CAD model or a boundary, rather than transforming a mesh that exists. The first milestone shipped in v17.13.0: [`mesh_cad_surface`](./mesh_cad.md) ([plan](./mesh_cad_plan.md)) triangulates a B-rep (`BrepInfo`: a Kratos CAD JSON read, or STEP and IGES through OpenCASCADE) into one conforming, watertight surface mesh at a single global size, with no CAD kernel. Each edge is sampled once by arc length and shared by the faces that use it. Each face is a constrained Delaunay triangulation of its parameters, mapped by the Cholesky factor of its mean first fundamental form, filled with an equilateral lattice and lifted onto the surface. Every decision is one of Shewchuk's exact predicates (`detail/predicates`), and a face that cannot be meshed is reported by status and reason. The planar triangulator is public as `triangulate_polygon_2d`. v17.14.0 closed most of what the milestone left: a face's embedded edges are constrained segments of its triangulation, a closed edge whose uses start at different points is rotated onto one corner, loops that cross only at a coarse size are split until they do not, and two fuzz targets cover the mesher and the planar triangulator. v17.15.0 added Delaunay refinement to a minimum angle measured on the surface, shared across faces, and guarded smoothing (6.2), and measures a mesh by its interpolation error (6.11). v17.16.0 added curved quadratic and cubic triangles whose nodes lie on the geometry, each proved valid everywhere inside by a Bézier bound on its Jacobian or kept straight-sided (6.6). What follows is ordered by what each item unlocks. Native work stops at surfaces, their quality and their sizing; volume meshing, quadrangulation and boundary layers stay with optional backends unless a design pass narrows the [non-goal](#non-goals-and-decisions-taken).*

The order follows the one production CAD meshers settled on, bottom-up from model vertices to edges, faces and volumes (Schöberl 1997, Geuzaine and Remacle 2009, the OpenCASCADE mesh guide), and the order in which the Delaunay literature builds its guarantees: a valid constrained triangulation first (shipped), then a bound on angles by refinement (6.2, shipped), then a size that varies (6.3), then a metric that varies inside a face (6.4), each needing the one before (Cheng, Dey and Shewchuk 2012, chapters 1 to 6; Frey and George 2008). Robustness on real models (6.5) is measured beside all of them, since it is where meshers lose most of their failures in practice. The citations are listed under [references](#references-for-mesh-generation) at the end of this section; an author and year in an item points there.

Landing an item:

- Keep the first milestone's contract. Add no new dependency to the core. Report a failed face rather than meshing it wrong. Keep the output byte-identical across parallel backends and thread counts, with a `meshioplusplus_bench_ops` row hashed by the determinism job. A face is serial inside and faces run in parallel, assembled in index order.
- New options reach every surface in one change: `MeshCadSurfaceOptions` (120 bytes since ABI 34, pinned in `test_abi_layout.cpp`), Python, the C struct `mio_mesh_cad_surface_opts`, Fortran, Julia, R, WASM in both artifacts, both CLIs' `mesh-cad-surface` and the MCP tool, with `doc/mesh_cad.md` and notebook 42 updated.
- Growing `MeshCadSurfaceOptions` is a layout change. ABI 34 (v17.15.0) laid out the fields of 6.2, 6.3, 6.4 and 6.6 in one bump (`mInsertion`, `mGrading`, `mCurvatureDeviation`, `mCellsAcrossGaps`, `mMetric`, `mPoleRings`, `mReparamConditionNumber`, `mOrder`), refused by name until their item lands, so landing one needs no further bump (`mOrder` landed in v17.16.0); a field none of them names takes the next. The C struct grows within its tail: `int64_t reserved[3]` (24 bytes) is left in the options and `reserved[3]` in the report, scalars only. Arrays (a size per face, a background field) need their own entry points, never the struct.
- Test the kernel in C++ (`tests/cpp/test_mesh_cad.cpp`, `test_cdt2d.cpp`) as well as through Python, on the hand-built solids of `tests/cpp/brep_solids.hpp` and the CAD JSON fixtures of `tools/gen_cad_json_fixtures.py`. Keep the OpenCASCADE oracle (`MeshCadOcct.*`) passing in both OCCT CI legs.
- Write an algorithm from its paper, never from another library's code, and name the paper in the implementing header and in `doc/mesh_cad.md#references` (the predicates precedent, [THIRD_PARTY_NOTICES](https://github.com/loumalouomega/meshioplusplus/blob/main/THIRD_PARTY_NOTICES.md)). An item that states a guarantee from a paper also states the paper's preconditions (input angles, a size function's Lipschitz constant) and tests both sides of them.

- **6.1 What the first milestone leaves.** Each of these is reported today, never meshed wrong ([limitations](./mesh_cad.md#limitations)). **S each**
  - **6.1.1 The model through the pipeline.** The pipeline carries a `Mesh`, not the `BrepInfo` a CAD read returns beside it, so `MeshCadSurface` (like the `iga_*` operations) is refused by name. Carrying the read's side channel from `Input` to the first step that asks for it, and dropping it at the first step that changes the mesh, would give both a pipeline step. Shared with the isogeometric layer. **S–M**
  - **6.1.2 One physical group per face in Gmsh output.** Every face is in one `triangle` block, so the Gmsh writer cannot give each face its own physical group, and the faces travel only as `cad:face` data ([output](./mesh_cad.md#output-and-report)). The `face:<k>` cell regions already name them. **Verify first** whether the Gmsh writer maps cell regions to physical groups; if it does, the gap is that `mesh_cad_surface`'s regions do not reach it, and if it does not, the writer gains that mapping, which any region-carrying mesh needs. Probe: a box meshed and written to Gmsh 4.1 opens with six named physical surfaces.

- **6.2 Quality: what refinement leaves.** v17.15.0 refines every face by Ruppert's algorithm with Chew's circumcentres, judged on the surface, with boundary splits shared across faces, concentric shells around small input angles, a deterministic worst-first order and guarded Laplacian or ODT smoothing (`min_angle`, `smooth_iterations`; [how it works](./mesh_cad.md#how-it-works)). One piece remains, and off-centres were measured and parked. **S–M**
  - **6.2.3 Small input angles on curved input: the stated bound.** Concentric shells and the terminator keep refinement finite on the plane, and each corner under 60 degrees is reported with the smallest angle it forces, measured. Pav and Walkington (2005) prove termination for curved input with small angles by lopping the corners off first, the case the curved trims of a CAD face are, and bound the angles they cannot fix; landing their corner lopping would let the report state that bound beside the measured one instead of leaving termination on curved faces to `max_points` and the insertion-radius declines. Probe: a face with a 5-degree corner between two circular trims ends under the stated bound with no budget warning.
  - **6.2.9 Off-centres: measured, parked.** Üngör's off-centre puts the new point on the bisector of a bad triangle's shortest edge, at the distance where the new triangle just meets `B`, or at the circumcentre when that is nearer the edge (Üngör 2009). Implemented and measured against circumcentres in October 2026 (plane in `cdt2d`, surface through the triangle's affine map), it changed nothing `mesh_cad_surface` makes: the plate, sphere, capped cylinder and box at `h` from 1.0 to 0.1 and 20, 25 and 30 degrees mesh byte for byte the same, except the sphere at 30 degrees and `h = 0.2`, a face that runs away, where it inserted 168 points against 26. A face starts from an equilateral lattice at spacing `h`, so refinement only meets triangles a little worse than the bound, whose off-centre lies at or beyond their circumcentre; it moves a point only for a triangle whose smallest angle is well under half of `min_angle`. On `cdt2d` refining from the boundary alone it was no better either: a 40-gon took 70 points against 71 at 25 degrees and 72 against 79 at 30, a square with a needle hole 126 against 91 at 25 and 319 against 270 at 30, the rest the same. `MeshCadSurfaceOptions::mInsertion` stays laid out and refused. Worth measuring again when a face is meshed from its boundary alone, or when size fields (6.3) leave coarse regions for refinement to fill.

- **6.3 Size fields and grading.** One global `h` over-refines flat regions and under-resolves curved ones. The chordal cap acts on boundary edges only. Needs 6.2, since refinement is what honours a size inside a face. **M**
  - **6.3.1 Sources.** A size per face and per edge (keyed by `BrepFace` and `BrepEdge` index), a background mesh with a size `point_data` array (sampled through `detail/surface_distance`'s closest-point query), and curvature (6.3.2), combined by taking the smallest. A callback is not a source: none crosses the flat bindings (the decision recorded under [3.1.1](#_3-operations)).
  - **6.3.2 Curvature sizing.** For a chordal error `d` on a surface of principal curvature `k`, the edge length is about `2 sqrt(2 d / k - d^2)`. The principal curvatures need the second fundamental form, hence second derivatives of the NURBS patch, which `detail/iga_kernels.hpp` does not evaluate yet (the isogeometric layer lists them under [not yet](./iga.md)). Add them there first, with their own tests against finite differences and analytic spheres and cylinders. The NURBS Book's algorithms A3.6 and A4.4 give the second derivatives of a rational surface from those of its homogeneous form (Piegl and Tiller 1997), the same algorithms whose first-derivative case the kernels already use. An edge's own curvature, from the trim's 3-D image, sizes the edge the same way, so a fillet's rim and its face agree.
  - **6.3.3 Gradation.** Limit the size's growth between neighbours to a factor (`grading`, about 1.2 to 1.5) by H-correction (Borouchaki, Hecht and Frey 1998) on a per-face background grid in the parameters plus the edge sizes, so a small feature does not leave a cliff of sizes. Deterministic: sweep in index order to a fixed point. The continuous form of the same limit is a bound on the size function's gradient, `|∇h| <= g`, solved as a Hamilton–Jacobi equation (Persson 2006); on a 3-D background (6.3.7) it gives one field for every face, which a per-face grid cannot, and is the route if neighbouring faces' fields disagree across their shared edges in practice.
  - **6.3.4 Edges under a size field.** Replace `ceil(L / h)` equal pieces with points at equal increments of `∫ ds / h(s)`, integrated with the Gauss–Legendre spans `edge_sampler` already uses, keeping the chordal cap and `min_points_per_edge`.
  - **6.3.5 Passing a field.** A size per face or a background field is an array, so it travels as a separate C++ struct (`MeshCadSizeField`) taken by a new overload, a Python dict of arrays, and C entry points that attach arrays to an opaque handle before the call. The fixed options struct gets only the scalars (`grading`, `curvature_deviation`).
  - **6.3.6 Probes.** A cylinder meshed with a curvature size keeps its chordal error below the cap on the faces as well as the edges, with fewer triangles than the uniform mesh of the same error. Neighbouring edge lengths never differ by more than the grading factor plus a stated tolerance. A face given its own size has its median edge length within 15% of it.
  - **6.3.7 Proximity sizing (local feature size).** A thin wall or a narrow slot needs a size below its width even where both faces are flat. Ruppert's local feature size, the distance from a point to the nearest boundary feature it is not incident to, is the measure his size-optimality argument uses (Ruppert 1995). Estimate it from the edge samples and the coarse first-milestone mesh with the closest-point query of `detail/surface_distance`, excluding the point's own face and its neighbours, and take `h = lfs / n_across` with `n_across` (about 2 to 3 elements across a gap) an option. The octree of [3.1.4](#_3-operations), whose leaves already refine by size and features, is a candidate background that holds this field and the curvature field for every face at once. Probe: two parallel plates a distance `t` apart get at least `n_across` elements across `t` on their side faces.
  - **6.3.8 Agreement on shared edges.** An edge sized from two faces' fields takes the smaller of the two at every point, so neither face sees a boundary coarser than its own field; record the face whose field decided each edge in the report. A per-face size that the edge then overrides is reported per face ("size limited by edge k"), so a user setting sizes per face can see why a face came out finer. Probe: two faces with sizes 1 and 0.25 share an edge sampled at 0.25, and the coarse face grades away from it within `grading`.

- **6.4 Metrics, poles and folds.** One affine map per face meshes a face by its average metric. A face whose parameterisation stretches differently from place to place (a cone near its apex, a trimmed corner of a large patch, a torus) gets stretched triangles. **M**
  - **6.4.1 A metric that varies over a face.** Use the first fundamental form `J^T J` at each point, scaled by the size field, as a Riemannian metric in the plane. Insertion and refinement use metric lengths and a metric Delaunay criterion evaluated in the local frame of each cavity, as parametric surface meshers do (Borouchaki, Laug and George 2000). Validity still goes through exact `orient2d` in the plane, so robustness does not depend on the metric. Probe: a cone and a torus patch whose parameter scales vary tenfold keep the 6.2 bound measured on the surface. The metric Delaunay kernel is Borouchaki, George, Hecht, Laug and Saltel (1997): the cavity of a new point is the set of triangles whose circumellipse, measured in the metric at the point, contains it, repaired to be star-shaped from the point with exact `orient2d`. A metric anisotropic in 3-D (an error estimate's, 6.10) composes with `J` as `J^T M J`, the same formula, so this item is also what lets 6.10.2 re-mesh to an anisotropic metric on the CAD. Tristano, Owen and Canann (1998) do the same with an advancing front, and Gmsh's frontal-Delaunay surface algorithm with frontal point placement (Rebay 1993, Geuzaine and Remacle 2009): recorded as the alternative if metric circumcentres leave triangles poorly aligned on strongly stretched faces, not planned.
  - **6.4.2 Graded poles.** A pole (a degenerate trim, one corner) is the apex of a fan of thin triangles today, and `mesh_cad_surface` drops the triangles it collapses. Seed one or two rings of points at 3-D distances `h` and `2h` around the pole, placed in the parameters by inverting the surface locally, so the apex has a valence near six and its angles meet the bound. Probe: the sphere's pole triangles meet `min_angle`.
  - **6.4.3 Folds.** On a small, strongly curved face a triangle that is valid in the plane can lift with its normal against `S_u × S_v`. Detect it (the dot product of the two normals) and split the triangle until it lifts the right way round, failing the face as `degenerate` past `max_points`. Probe: a narrow fillet strip with a radius below `h`.
  - **6.4.4 Reparametrising a face whose parameters are unusable.** Some patches have parameterisations no metric rescues: control points collapsed off a pole, a trim that covers a sliver of a large patch, a parameter speed that varies by orders of magnitude within one span. Gmsh meshes such faces in a discrete parameterisation of a coarse mesh of the face instead of the patch's own (Remacle et al. 2010). The core has the pieces: the first milestone's mesh of the face is the coarse mesh, and `detail/param_disc` (least-squares conformal maps and mean-value coordinates, used by `fit_cad`) maps a disc-shaped triangle patch onto the plane, bijectively for mean-value coordinates (Floater 2003). Mesh the face in that plane, map each new point back through its coarse triangle to `(u, v)` by barycentric interpolation, and lift it with `S`, so points stay on the exact surface. A face that is not a disc is split first, as `fit_cad` does. Trigger it per face when the metric's condition number over the face exceeds an option, and report which faces took the route. **Verify first** that `param_disc` accepts a patch whose boundary must stay fixed to the shared edge samples (mean-value coordinates put the boundary on a circle, which keeps the samples' order but not their spacing). Probe: a patch whose corner control points coincide meets the 6.2 bound, where the metric route of 6.4.1 does not. **M**

- **6.5 Real CAD input.** The fixtures are clean. Real STEP files have tolerances, tiny edges, sliver faces and gaps that the first milestone reports as failures. This item measures how often, and narrows it without altering the model. **M**
  - **6.5.1 Tolerances.** `BrepInfo` has no tolerance field. OpenCASCADE's per-edge and per-vertex tolerances are not carried, and Kratos keeps its own in `mExtra`. The mesher uses one global tolerance and reports `max_edge_gap`. Carrying per-entity tolerances changes pinned `Brep*` layouts (an ABI bump) or needs a side table. With them, corner joining and trim pairing can accept gaps the model itself declares.
  - **6.5.2 Small edges and sliver faces.** An edge much shorter than `h` forces tiny triangles around it, and a sliver face narrower than `h` gets triangles with no interior point. Mesh across them with a virtual topology (consecutive short edges merged into one discretisation, a sliver meshed with its boundary points only) recorded in the report, never written back to the model. The operators are those of Sheffer et al. (2000): merging edges that meet at a vertex of valence two, and merging a sliver into a neighbour along their shared edge, so the neighbour's triangulation spans both; the merged faces keep their own `cad:face` ids on the triangles whose centroids lie in each, so regions survive. A merge across faces of different surfaces needs a common parameterisation, which is 6.4.4's, so the face-merging half follows it.
  - **6.5.3 A corpus and a success rate.** A set of public STEP files with a licence that allows redistribution or at least download in CI (NIST's MBE PMI test models are a US-government work; the ABC dataset's terms need checking first), meshed in a scheduled CI job rather than every push. It publishes the share of faces meshed and the failures by status in [benchmarks](./benchmarks.md), so a change to the mesher shows its effect on real models. ABC is a million Onshape models with their B-reps (Koch et al. 2019) and the Fusion 360 Gallery a set of designs with construction sequences (Willis et al. 2021); both are the corpora published mesh and CAD-learning work measures on, and each states its own terms, so **verify first** whether either may be downloaded in CI, and store model ids and a checksum in the repository rather than the files (the LFS budget). Start with a fixed sample (a few hundred models, chosen by a seeded draw from the ids and recorded), so the published rate is comparable from release to release.
  - **6.5.4 Oracles.** OpenCASCADE's `BRepMesh` is the in-tree oracle (area, volume and watertightness, `MeshCadOcct.*`). Gmsh's executable could join it in a CI job, called through files across a process boundary, never linked (its licence is GPL). Compare area, volume, Hausdorff distance and quality per model.
  - **6.5.5 What a corpus run measures.** Per model: faces meshed and failed by status, `num_open_edges` on closed solids, `max_edge_gap`, the extreme angles and the [`compute_quality`](./quality.md) histograms (Knupp's algebraic metrics, the scaled Jacobian and aspect ratio; Knupp 2001), the Hausdorff distance to the model sampled densely, points, time and peak memory, beside the same for `BRepMesh` and Gmsh at a matched size. The first published run is the baseline: a change that lowers the success rate or raises a failure class states why in its `CHANGELOG.md` entry, the rule of [landing a performance change](./benchmarks.md#landing-a-performance-change). Probe: the job fails when a model that meshed in the baseline stops meshing, so a regression cannot hide in an average.
  - **6.5.6 A taxonomy of the failures.** Classify every failure of the corpus run by its geometric cause — a gap beyond tolerance, an edge used once, a trim outside its patch, a self-intersecting loop, a degenerate patch, an edge below tolerance that is not a pole — from the face reports and the measured gaps, and publish the counts. The CAD-repair literature has catalogued these classes for decades (Butlin and Stops 1996), and a count per class is what decides whether 6.5.1, 6.5.2 or 6.4.4 is the next item worth landing. It changes no output, so it can land with 6.5.3.

- **6.6 Curved surface meshes: what is left.** v17.16.0 writes `order` 2 and 3 as `triangle6` and `triangle10` (with `line3` and `line4`) whose nodes lie on the exact surfaces and edges, each element proved valid everywhere inside by a Bézier bound on its Jacobian (Johnen, Remacle and Geuzaine 2013) or kept straight-sided and counted ([curved elements](./mesh_cad.md#how-it-works)). Area and volume converge at order 4 for both, and interpolation at the optimal orders 3 and 4 on the Scordelis–Lo roof; what is left is where the nodes go and what becomes of an element that folds.
  - **6.6.2 Interior mid-edge nodes.** The parameter midpoint lifts to a point that is not the surface's midpoint of the edge where the metric varies, which skews the element. Place an interior mid-edge node at the point of the surface closest to the 3-D chord's midpoint, a Newton step from the parameter midpoint (Sherwin and Peiró 2002), and fall back to the parameter midpoint when the step leaves the triangle's parameter image. The cubic elements fall short today, plausibly from this placement: their area and volume converge at order 4, not 6, and their interpolation on the sphere at 3.7 away from the poles, not 4. Probe: on the Scordelis–Lo roof the mid-edge nodes' distances to both ends differ by less than a stated fraction of the edge, and the sphere's cubic orders rise.
  - **6.6.3 Untangling instead of straightening.** Keeping an invalid element straight-sided loses the geometric accuracy the order bought, at exactly the elements on highly curved boundaries. The follow-up moves interior high-order nodes to maximise the worst scaled Jacobian while boundary nodes stay on the CAD (Toulorge et al. 2013), or treats the mesh as an elastic solid deformed onto the curved boundary (Persson and Peraire 2009; Moxey et al. 2016 for a thermo-elastic variant). Both are optimisation over a mesh the core already holds, so they stay native; a design pass picks one before it starts. **M**

- **6.7 Volume meshes from the watertight surface.** A closed `mesh_cad_surface` result is the input a tetrahedral mesher needs. **L**
  - **6.7.1 The native route that already exists.** [`octree_mesh`](./octree_mesh.md) meshes the inside of any skin, so `octree_mesh(mesh_cad_surface(model, h))` gives conforming graded tetrahedra today, fitted to the skin by snapping rather than keeping its triangles. Document it in `doc/mesh_cad.md` and notebook 42 with a probe (the sphere's volume within the octree mesher's stated error) before any backend lands. Its stuffed tetrahedra follow isosurface stuffing, whose dihedral angles are bounded away from 0 and 180 degrees by construction (Labelle and Shewchuk 2007); the documentation states that bound beside the boundary error it trades for it.
  - **6.7.2 The backend contract.** A `tetrahedralize` operation (`operations/tetrahedralize.hpp`) takes a closed, manifold, consistently oriented triangle surface: it refuses an open, non-manifold or misoriented one by name, using `mesh_cad_surface`'s own counts. It returns tetrahedra with the surface's triangles kept exactly (`preserve_boundary=True`, where the backend can) or within a reported Hausdorff distance (an envelope mesher), plus `max_volume`, a quality target and `max_cells`. It follows the KaHIP pattern: off by default, one `MESHIOPLUSPLUS_WITH_*` flag per backend, bring-your-own, never vendored or downloaded, `Unsupported` naming the flag where absent, no numpy twin. Because it takes a mesh and returns one, it fits the pipeline as a `Tetrahedralize` step, unlike `mesh_cad_surface`.
  - **6.7.3 Candidates, by licence.** Geogram (BSD-3): its Delaunay kernel is permissive. Whether its constrained tetrahedralisation of a closed surface runs without its optional TetGen component, which is AGPL, must be verified first. fTetWild (MPL-2.0): robust to dirty input because it meshes within an envelope around the surface, so it does not keep the triangles exactly. It depends on Geogram and libigl, whose licences and size need checking first. Netgen (LGPL-2.1): advancing front with Delaunay, quality tetrahedra, and its own OpenCASCADE route. MPL and LGPL code is linked, never vendored. Excluded: TetGen (AGPL-3.0), CGAL's `Mesh_3` (GPL), and Gmsh (GPL) except as a file route through its executable, the [vendor routes](./vendor_routes.md) pattern. A fourth candidate since 2023 is the exact constrained Delaunay tetrahedralisation of Diazzi, Panozzo, Vaxman and Attene (2023), which recovers every input triangle without approximation using Attene's indirect predicates (Attene 2020) and meshed all 4408 valid models of Thingi10K in their tests: **verify first** the licence of its reference code (github.com/MarcoAttene/CDT †) and of the indirect-predicates library it builds on; if both are permissive it is the backend that keeps `preserve_boundary=True` on every valid input, which the envelope meshers cannot.
  - **6.7.4 Regions and data.** Side regions come from the surface's `cad:face` (one per CAD face), and cell regions from enclosed volumes: nested or touching shells are told apart by the fast winding number `octree_mesh` already uses, from a seed point per region. `BrepInfo` has no shells, so a multi-body model gets one region per enclosed component.
  - **6.7.5 After meshing.** [`optimize_volume`](./optimize_volume.md) (ODT relocation and flips) improves the result without a backend, and [3.3.1](#_3-operations)'s `adapt` remeshes it to a metric once MMG lands. The literature's strongest improvement schedules combine smoothing with topological moves beyond 2-3 and 3-2 flips (edge removal, multi-face removal, vertex insertion) and often reach minimum dihedral angles above 30 degrees (Klingner and Shewchuk 2007); ODT relocation is Alliez et al. (2005), and sliver exudation removes the near-flat tetrahedra Delaunay refinement leaves by weighting the vertices (Cheng et al. 2000). Measure what `optimize_volume` reaches on each backend's output first; the moves it lacks are an item of their own once a backend lands.
  - **6.7.6 Probes.** The sphere's tetrahedra enclose `4/3 π` to the surface's own chordal error. With `preserve_boundary`, the boundary triangles of the result equal the input's. A box inside a box gives two cell regions. Dihedral-angle extremes are reported, and the digests agree across runs for each backend.
  - **6.7.7 Not native.** `orient3d` and `insphere` exist, but a constrained 3-D Delaunay tetrahedralisation also needs boundary recovery with Steiner points, where the robust libraries spend their years. That is the line the non-goal draws. The difficulty is not the Delaunay kernel, which is short (Bowyer 1981, Watson 1981) and fast when points are inserted in a spatially sorted order (Marot, Pellerin and Remacle 2019 reach billions of tetrahedra a minute), but the recovery: some polyhedra have no tetrahedralisation without Steiner points, and placing them robustly is where TetGen, the boundary-recovery schemes and exact constructions spend their complexity (George, Hecht and Saltel 1991; Si and Gärtner 2005; Shewchuk 2008; Si 2015; Diazzi et al. 2023). **Reopen condition:** a backend of 6.7.3 shows the contract and the probes work, and a design pass shows a native recovery on the core's predicates within a stated size; until both, no native item is queued.
  - **6.7.8 A robustness corpus for the backends.** Thingi10K is ten thousand triangle meshes from a 3-D printing repository with every defect real surfaces have (Zhou and Jacobson 2016), and the corpus tetrahedral meshers report their success rates on (Hu et al. 2018, Hu et al. 2020, Diazzi et al. 2023). Each model carries its own licence, so store ids and checksums, not files (6.5.3's rule). Run each enabled backend on its closed, manifold subset in the scheduled job and publish, per backend, the share meshed, the share with `preserve_boundary` honoured, the Hausdorff distance for envelope meshers, the dihedral-angle extremes and the time, beside 6.5.5's surface measures. Probe: a backend that crashes or hangs on a model fails the job with the model id, rather than the run timing out silently.

- **6.8 Quadrilaterals.** Quad-dominant and all-quad surface meshes for shell solvers. A design pass comes first, because the [non-goal](#non-goals-and-decisions-taken) keeps quadrangulation with backends. **L**
  - **6.8.1 Routes.** Recombination of the triangulation into quads: Blossom-quad (Remacle et al. 2012) needs a minimum-cost perfect matching. Kolmogorov's Blossom V is licensed for research only and is excluded; LEMON (Boost licence) has a matching and needs checking first. Greedy recombination by quality (Lee and Lo 1994) needs no library. Field-aligned remeshing: Instant Meshes (BSD-3, verify first), QuadriFlow (verify its licence first); QuadWild is GPL and excluded. The core already has a cross field and a quad layout (`detail/cross_field`, `detail/quad_layout`) for `fit_cad`'s freeform network, a native candidate for per-face layouts. Recombination works best on triangles that already pair into good quads: Gmsh generates them with a frontal-Delaunay mesher in the `L∞` norm, which places points so that triangles come out right-angled and aligned with a cross field (Remacle et al. 2013), which is 6.4.1's metric machinery with a different norm. Q-Morph (Owen et al. 1999) is the advancing-front alternative that converts a triangulation front by front; Paving (Blacker and Stephenson 1991) is its direct precursor. The surveys of Bommes et al. (2013) and, for the field-aligned methods, Jakob et al. (2015) and Huang et al. (2018) set out the trade-offs; the design pass cites them rather than re-deriving them.
  - **6.8.2 Conformity across faces.** An all-quad mesh needs an even number of segments on every loop of every face. Choosing edge counts to satisfy that over the whole model is a small integer problem over the shared edges, native whichever route meshes the faces. Mitchell's interval assignment (Mitchell 1997) poses it as an integer programme that stays close to the edge counts the size field asks for; a greedy fix that adds one segment to the edge whose relative change is smallest on each odd loop solves the even-parity case alone, and is the first step.
  - **6.8.3 The decision.** The design pass records whether greedy recombination on the core's own kernels narrows the quadrangulation non-goal, or quads stay a backend. Probes either way: a box and a capped cylinder all-quad, their scaled Jacobians reported by `compute_quality`.

- **6.9 Boundary layers.** Prismatic layers grown from a surface along its normals (first height, growth ratio, number of layers), the rest of the volume tetrahedralised against the last layer by 6.7. A design pass comes first, because the non-goal keeps boundary-layer inflation with backends. **L**
  - **6.9.1 What it takes.** Normals at sharp edges and corners (`compute_normals`, with fans at convex corners and merging at concave ones). Layers that shrink or stop where they would collide, using a ray–triangle kernel [3.2.4](#_3-operations)'s `thickness` also needs. Prisms where layers stay whole, and pyramids or tetrahedra where they collapse. Side regions carried to the layer caps. The established schemes are the advancing-layer method (Pirzadeh 1996), the boundary-layer mesh generation of Garimella and Shephard (2000), which handles corners by blending normals and sweeping fans, and Aubry and Löhner (2009) for normals at ridges and corners specifically; the design pass picks the corner treatment from them and states which cases it leaves to the collision check.
  - **6.9.2 Machinery it shares.** [3.1.2](#_3-operations)'s `extrude` (per-layer offsets, side and cap regions) is the same sweep along a direction field, so it lands first.
  - **6.9.3 Candidates.** Netgen's boundary layers (LGPL-2.1). The well-known alternatives are GPL (cfMesh, snappyHexMesh, Gmsh) and excluded. The design pass decides between a native implementation on `extrude`'s machinery, which narrows the non-goal, and Netgen.

- **6.10 Adaptation that stays on the CAD.** Adapting a surface mesh to a metric moves boundary points off the exact surface. **M**
  - **6.10.1 Project back.** After 3.3.1's `adapt` (MMG, which knows no CAD), project every boundary point onto the face that `cad:face` names: Newton on `S(u, v)` warm-started from the source triangle's parameters. This needs closest-point projection on a `NurbsPatch`, which the isogeometric layer lists under [not yet](./iga.md). Points on shared edges project onto the edge. Point inversion on NURBS is Newton on the first-order condition `(S - p) · S_u = (S - p) · S_v = 0`, which needs the second derivatives of 6.3.2 and a starting point inside the right basin; Ma and Hewitt (2003) start from a subdivision of the patch into Bézier pieces, and the warm start from `cad:face` and the source triangle's parameters is what makes a single Newton run enough here. A projection that leaves the face's trimmed region is reported, not clamped. MMG's adaptation follows the metric framework of Frey and Alauzet (2005) and Dapogny, Dobrzynski and Frey (2014).
  - **6.10.2 Or re-mesh from the model.** With 6.3 a size field from an error estimate ([`error`](./error.md), [`hessian`](./hessian.md)) can drive `mesh_cad_surface` again, which keeps every point on the model by construction. Document both routes and when each applies. An anisotropic metric built from a Hessian (absolute eigenvalues, scaled to a target interpolation error, the construction of the continuous-mesh framework of Loseille and Alauzet 2011) reaches `mesh_cad_surface` once 6.4.1 meshes to a varying metric; before that, its smallest eigen-size is the isotropic field 6.3 takes.

- **6.11 Measuring a generated mesh by what it is for: what is left.** v17.15.0 measures the `L2` and maximum errors of linear interpolation of a smooth field on the sphere and the Scordelis–Lo roof under halving of `h`, with Dunavant's 7-point rule (the [`error`](./error.md) operation compares fields at nodes and has no quadrature), and pins their observed orders at 2 beside the angle histogram ([verification](./mesh_cad.md#verification)). v17.16.0 measures quadratic and cubic interpolation on the curved meshes of 6.6 the same way and pins their orders (3 and 4 on the roof; on the sphere 3 and 3.7 away from the poles, whose fans hold the whole mesh to 2.5 and 3.4 until graded poles, 6.4.2). What remains needs other items: the field with a sharp layer as the measure of size fields (6.3) and adaptation (6.10), where a mesh sized from its Hessian should reach the uniform mesh's error with fewer points; the uniform mesh's layer error is measured today (order 1.9 on the sphere) as their baseline. **S**

Deliberately not, so not re-proposed:

- **A numpy twin** of `mesh_cad_surface` or `triangulate_polygon_2d`: a second implementation of the predicates and the triangulation could not stay byte-identical, the precedent of [`remesh_volume`](./remesh_volume.md).
- **Healing the model.** Sewing gaps, removing sliver faces or rebuilding pcurves changes the CAD model, which is the CAD kernel's work. 6.5 meshes around defects without writing them back.
- **Code from Triangle, TetGen, Gmsh, CGAL's GPL packages or Blossom V**, under any route other than a separate process: their licences ([THIRD_PARTY_NOTICES](https://github.com/loumalouomega/meshioplusplus/blob/main/THIRD_PARTY_NOTICES.md)).
- **Hex-dominant and general hexahedral meshing from a CAD boundary**: the volume [non-goal](#non-goals-and-decisions-taken); the all-hexahedral octree dual of [`octree_mesh`](./octree_mesh.md) is the lattice exception.
- **A native parallel Delaunay kernel** in the style of HXT (Marot, Pellerin and Remacle 2019): it is the fast path of a 3-D mesher the core does not have (6.7.7), and the 2-D triangulation of one face is small enough that faces in parallel already use every thread on a real model.
- **Advancing-front surface meshing as a second native mesher** (Lo 1985, Peraire et al. 1987, Löhner and Parikh 1988, Schöberl 1997): it gives smoother size gradation, but its robustness rests on intersection tests of the front that the Delaunay route avoids, and two native meshers would double what must stay byte-identical. Its point placement is recorded under 6.4.1 as an option inside the Delaunay mesher, not a separate one.

## Non-goals and decisions taken

Recorded so they are not re-proposed as gaps.

- **Every registered format reads and writes, in both engines** — decided in October 2026, when the parity tier closed; it reversed the earlier non-goals that kept result files and the export-only formats read-only. A format reads and writes in the C++ core and in its Python twin, so it reaches every surface (C, Fortran, Julia, R, WASM, both CLIs and the MCP server's format capabilities); a core-only path is unreadable from the surfaces that have no fallback, a Python-only one has no twin to check it against. `read(write(m))` equals `m` within the limits the format itself imposes (single precision, a cell type it has no slot for, a concept it cannot express): a loss that is a fact of the format is stated on its page and in the [conformance](./conformance.md) notes, and one that is only an unwritten feature is a gap that reopens a *Reader and writer parity* section here. A new format or direction lands as `AGENTS.md` says (native writer registered in `registry.cpp`, parameters through `WriteOptions`, the Python twin behind `core_declined`, the arrays a reader returns written back under the same names, a `SPEC` declaration and a *Writing* section). The exemptions are recorded in `tests/python/conformance_spec.py` (`READ_ONLY`, `ENGINE_EXEMPT`, `PARTIAL_ENGINE_EXEMPT`) and checked by `test_conformance.py`:
  - **Pure 2-D drawings.** `svg` and `tikz` draw a mesh rather than store it: their readers parse only the structure meshio++'s own writers emit, return the geometry as planar (`z = 0`) and warn once per read that depth, and whatever else the drawing could not hold, is lost; anything else in the file is a `ReadError` naming the construct, never a guess.
  - **`ansys_rst_cyclic`**, which is not a file but the full rotor a cyclic `.rst` expands to; its write side is `ansys_rst`'s cyclic option. **`step` and `iges`** outside a build with OpenCASCADE: reading a CAD model means a CAD kernel, which the wheels and release binaries carry and a source build finds when it can ([skin to CAD](./cad_fit.md), [STEP](./formats/step.md#reading)); on WASM the lean build is the exempt one, and the [full build](./wasm.md#lean-and-full-builds) carries the kernel.
  - **One engine only, by decision**: GiD (gidpost and its Gauss points are implemented once, in the core), the OpenFOAM case writer and its zone, field and multi-region reading, CGNS's face-based polyhedra (the writer's winding repair is a discrete branch two implementations could resolve differently), the CAD readers, and the `step` writer's merged and fitted faces (`faces="planar"`/`"fitted"`, with `segment`'s primitive method that feeds them: loop walking, vertex snapping and the primitive growth are discrete branches too, so the twin writes `faces="facet"` byte for byte and nothing else); the Python entry points raise naming the missing core rather than guess.
- **What the parity tier left as facts of the format**, each stated on the format's page and in the conformance notes, none an unwritten feature:
  - **`nastran_op2`** writes the MSC dialect only (32-bit little-endian words, SORT1 tables). 64-bit words, big-endian files, NX/Simcenter's interlaced table names and double-precision GRIDs are read and detected, not written: a post-processor reads the MSC dialect with no flags, and whether NX accepts it is a vendor check ([§1.2.14](#_1-2-awaiting-a-licensed-run)). The random PSD, CRM and ATO tables are written as SORT1 magnitudes, as the reader reads them (MSC writes them SORT2, and pyNastran reads only the RMS and NO ones in SORT1); no SORT2 pivot is written. Elements on scalar points (`CELAS3`/`CELAS4`, `CDAMP3`/`CDAMP4`, `CMASS3`/`CMASS4`) and `CBUSH1D` and `CBEND` have no cell type — `Mesh` has no scalar-point entity to hang them on — and are skipped with a warning.
  - **`nastran_h5`** writes a table only where an MSC sample fixes its layout: `CBUSH`, `CGAP`, `CMASS` and `CONM1` elements, and `MAT5`, `MAT8`, `MAT9`, `PBARL`, `PBEAML` and `PCOMPG` values, have no table in the six MSC Nastran 2020 files at hand, so the elements are left out and the values go on the plain cards, each with one warning; the OP2 file holds them.
  - **`lsdyna_d3plot`** leaves the rigid roads' full rigid-body velocities (`NDIM = 9`) out of the state, and writes an airbag variable under a title-case name, since the names of a real file are in no manual available.
  - **`radioss_anim`** writes the nodal normals as zeros: `anim_to_vtk` ignores them and their 16-bit encoding is undocumented.
  - **`abaqus_fil`** writes 8-byte words only, the reader's width; a single-precision build's 4-byte layout has no description or sample.
  - **`ansys_rst`** has no complex (harmonic) results, read or written: no public sample or open reader covers them, and DPF alone reads them. The nodal coordinate systems are written as `ansys:node_angles` and agree with pymapdl-reader only for single-axis angles, since it applies the three turns in the opposite order.
  - **`xplt`** writes a per-surface-node variable as `FMT_NODE` in surface order, where the reader averages the values a node on two surfaces has into one point value, which both surfaces then write.
  - **`marc` and `marc_t19`**: edge and face sets stay `(cell, number)` field data and side regions are dropped, since mapping them to facets needs Volume A's numbering ([§1.2.11](#_1-2-awaiting-a-licensed-run)); the Herrmann, bubble and generalized-plane-strain types come back as the default type of their shape, and a deck holds no data arrays.
  - **`szplt`** does not write polygon and polyhedral zones: TecIO 2018.3, the newest source available, refuses them in an SZL file, so the reader refuses them by name too and the face-based zones stay with the `.plt` and ASCII readers. Partitioned output is for tetrahedron and brick zones of a static file only (TecIO's own limit), and a series is written whole.
  - **`vtx`**: DOLFINx and ParaView read one cell type per file, so a file of several cell types or parts is meshio++'s own extension of the layout.
- **MPI in the library** — none planned ([C++ API](./cpp_api.md)); `partition`'s ghost layers produce the halo an MPI assembly in the owning application needs. ParMmg, MMG's MPI layer, is excluded with it.
- **Solver-coupled physics-ML** — assembled solver residuals, adjoints and Sobolev training, co-simulation, active-learning *labeling*, adaptive remeshing driven by a surrogate, and MPI model-part gathering. Every one needs a live solver (an assembly routine, its tangent, its communicator) and meshio++ has no notion of a discrete system; they belong in the application that owns the solver, the division [Symbolic and physics](physicsnemo/symbolic_and_physics.md) describes.
- **The Python-only layers stay Python** — `pmsh`, `zarr`, `cae` and `usd`, and the physics-ML surface (grids, point budgets, proximity graphs, datasets, training) are export targets and tooling for a training pipeline, registered in Python rather than the shared C++ registry. A core kernel they call (the neighbour search) does not change that; `tessellate` moved to the core ([tessellation](./tessellation.md)) because the native CLI and the flat bindings needed it, and its `Tessellation` helpers stay Python.
- **Polyscope in the release CLI binaries** — excluded deliberately, so `view`/`screenshot` there report the build flag rather than opening a window ([viewer](./viewer.md)).
- **General volume meshing algorithms as native operations** — constrained tetrahedralization of a domain, hex-dominant meshing and general hex meshing from a CAD-like boundary, boolean/CSG, boundary-layer inflation, quadrangulation and geodesic distance are each a library in their own right. The answer is an optional backend (the KaHIP pattern), not a native implementation ([§6.7](#_6-mesh-generation)): volume domain meshing and adaptation reach meshio++ only through backends (§3.3, §6.7); quadrangulation and boundary-layer inflation reopen only through the design passes of §6.8 and §6.9. Two exceptions are in scope. Surface triangulation of a CAD model is native since v17.13.0 ([`mesh_cad_surface`](./mesh_cad.md)): the robust predicates it needs are Shewchuk's, public domain and a few hundred lines, and a planar constrained Delaunay triangulation per face is small enough to own; this reverses the earlier decision that dropped the queued Delaunay item, for surfaces and the plane only, and its refinement and sizing continue in [§6](#_6-mesh-generation). Lattice generation is the other: [`voxelize`](./voxelize.md), the octree of §3.1.4, [`remesh_volume`](./remesh_volume.md)'s isosurface stuffing and the octree volume mesher of §3.1.4.3 (stuffed tetrahedra and the all-hexahedral octree dual, [plan](./octree_mesh_3d_plan.md)) are index arithmetic over a signed distance on a lattice, followed by projection and untangling, with no predicate to make robust.
- **Contact mechanics itself** — penalty or mortar assembly, friction and contact search in time need a live solver. meshio++ detects and exports the interface of one snapshot ([§3](#_3-operations)); the contact algorithm belongs in the application that owns the solver.
- **MMG in the release wheels and the native CLI binaries** — it is LGPL-3.0 and an external install, so when the backend of §3.3 lands it is linked dynamically into builds that opt in and nowhere else, and its operations throw by name where it is absent. The WASM half of the old decision is [§5.2.3](#_5-the-full-webassembly-build)'s probe, not this non-goal.
- **KaHIP in the lean WASM build, ADIOS2 and TecIO in either WASM build** — KaHIP ships only in the full artifact (serial kaffpa, built by `build-wasm-deps.sh --full`; a graph partitioner would bloat every consumer's bundle, so the lean pair keeps the SFC method with `"kahip"` throwing by name as the contract); no one has made a wasm build of ADIOS2 (`vtx`); TecIO's redistribution terms keep `szplt` out. Each reports by name in the lean and the full artifact alike ([what stays out](./wasm.md#what-stays-out)).
- **zstd/lz4 codecs in the lean WASM build** — the lean artifact keeps zlib as its only block codec; the full one (v17.2.0) links zstd, lz4 and bzip2. A zstd-compressed VTK XML file is a meshio++ extension VTK itself has no compressor for, so vtk.js does not read it; the second reader of a zstd file is meshio++'s native and Python ones. **Memory mapping and the Kokkos backend under Emscripten** — CMake refuses the Kokkos backend under Emscripten, and there is nothing to map inside MEMFS.
- **Single-file output for DOLFIN, TetGen and EnSight from WASM**, or lifting DOLFIN's simplicial restriction — both are facts of the formats; `writeMesh`'s written-paths return value (v11.2.0) is the fix for the bookkeeping they cause.
- **NURBS patches and trims as a second entity kind inside `Mesh`** — decided with the [isogeometric layer](./iga.md) (v16.43.0, [findings](./spikes.md#the-isogeometric-layer)): a model (`NurbsInfo`, `BrepInfo`) stays a side channel beside the mesh, with its own evaluate, refine and sample operations, because a first-class entity kind needs patches, control nets, weights, knots and trimming curves in `Mesh`, every mesh backend (MESHIO, NATIVE, KRATOS), every binding and the C++ ABI: a major version for a gain the three operations already give. Reopen it when an operation must act on patches and trims as mesh entities (mixed IGA and FEM assembly in one model, for instance, or a patch-aware `partition`), and start from the spike's list of what the side channel cannot do: no `Mesh` operation sees a patch, the model does not travel through the pipeline, and an MFEM model refines every direction alike.
- **Polyhedron blocks as a WASM gap** — `vtu`, `ensight`, `cgns`, `med` and `openfoam` all write them from WASM; a consumer that cannot is constrained by its own data model.
- **Performance work measured or decided against** — recorded when the roadmap's performance section closed (October 2026); a new performance change passes the gates of [landing a performance change](./benchmarks.md#landing-a-performance-change):
  - **The serial phases kept for determinism**: the keep-first weld loop (chains make it order-dependent), the union sweeps of `split` and `compute_normals` (cheap, and their partitions are order-independent anyway), and `remesh`'s energy sweep (every accepted move changes what the next test reads; it has no numpy twin because a near-tie decided differently yields a different clustering).
  - **A facet table cached across pipeline steps** — measured ([benchmarks](./benchmarks.md#pipeline-row-what-a-shared-facet-table-could-save)): in a `Smooth` then `ExtractSurface` chain a cache saves at most one table build, about 3.6% of the chain on SEQ at tier L with the default ten iterations, at most 10% on four OpenMP threads and about 20% with one iteration. `smooth` and `extract_surface` do not share a record structure, so it would also need a refactor, and a cache on the `Mesh` is a Tier A layout change. Reopen it for a workload that chains several facet readers after cheap topology-preserving steps; the `pipeline_smooth_surface` row measures it.
  - **Explicit SIMD intrinsics or `-march` flags** — portability across wheels, WASM and the release binaries is worth more than the scalar kernels cost; revisit only if the harness shows a kernel dominating.
  - **Kokkos device execution** — every `parallel_for` body captures host pointers (`parallel.hpp`); the GPU route is the DLPack/CuPy handoff ([GPU handoff](./gpu.md)).
  - **A BVH in place of the distance query's uniform grid** — `detail/surface_distance.hpp` rejects one because its visit order would make the equidistant-triangle tiebreak observable.
  - **Tuning the pure-Python fallback readers** — the fix is making the C++ path accept the file, not a faster fallback; `_decimate.py`'s heap-based twin is deleted once `decimate` accepts its inputs, not optimised.
  - **Dropping the copy in `transform`** — `transform` copies the connectivity and data it does not change (through `transform_owned_copy`, as 17 operation files copy through `clone_mesh`, `clone_geometry` or `quality_clone_mesh`), and the Python twin copies too; that copy is what makes the result a new mesh that aliases nothing, so removing it is an API change, not an optimisation.
  - **Caching between the browser viewer's applies** — every apply re-reads the staged file and replays the whole pipeline, which is what makes undo exact. Measured with the typed-array channel ([benchmarks](./benchmarks.md#a-typed-array-channel-for-the-browser-viewer)), the read is at most 2 to 25% of an apply that smooths and up to 69% of a quality-only apply on a large surface; a cached mesh or pipeline prefix would hold a second copy of the mesh in the 32-bit heap MEMFS already shares, and make undo depend on invalidation.

- **Terminal rendering stays software, dependency-free and core-only** — no GPU, no windowing stack, no new dependency and no audio library; it is a *preview*, not a replacement for Polyscope or vtk.js, and does not try to match their fidelity, lighting or picking. Python calls the core or raises by name (the [`remesh_volume`](./remesh_volume.md) precedent: a NumPy edge-function rasterizer would be slow and double the surface that has to stay byte-identical). Vector output is unchanged: SVG, TikZ and glTF keep the painter's algorithm and their byte-pinned twins, and their colormap tables are only ever extended. The interactive loop is not a library feature (raw mode, signals and the event loop live in the CLI layer; the library exposes frames and encoders, never a tty, and WASM and the C API carry frames and text only). `--follow` polls modification times and does not use inotify or kqueue. The soundtrack is generated, played by an external player and silent unless asked for, in CI and over SSH. See [terminal rendering](./tui.md#design-decisions).

## Suggested sequencing

Open work only; what shipped is in `CHANGELOG.md`.

1. **Format reach ([§1](#_1-format-reach))** — the checks against the vendor tools, as licences or files the tools wrote appear; they are what is left of reader and writer parity.
2. **The OSS-Fuzz submission ([§2](#_2-quality-of-implementation))** — calendar-bound, so it runs alongside everything else.
3. **Primitive constructors ([§3](#_3-operations))** — tier 1, the planar domains and the reference cells have shipped, and most of the test fixtures they replace are retired; what remains is the other tiers (surfaces, solids, lines and points), as tests and notebooks ask for them, since they are prerequisites of `extrude`/`revolve` and of the octree's fixtures (the 2-D `voxelize` they were once listed under has shipped).
4. **Octree leftovers ([§3](#_3-operations))** — `plane=` on `voxelize` with the next ABI bump, and the `check_conformity` probes once 3.2.1 lands. What remains of the volume mesher is 3.1.4.3.
5. **The MMG backend ([§3](#_3-operations))** — Medit `.sol` first, since it needs no link and opens the file route; then `adapt`, `discretize_levelset`, `mesh_domain` and, with ELAS, `move`.
6. **Registration ([§4](#_4-ecosystem-reach))** — calendar-bound, so start the submissions early and let them run alongside everything else; the viewer's look (4.5) and the dataset manager's thumbnails (4.6) need no decision first and can run beside them.
7. **MMG under Emscripten ([§5](#_5-the-full-webassembly-build))** — after the native MMG backend of §3.3, through the full build v17.2.0 shipped.
8. **Mesh generation ([§6](#_6-mesh-generation))** — what the first milestone still leaves (6.1: the model through the pipeline and one Gmsh physical group per face) is small and independent, so it can go first. Refinement (6.2) landed in v17.15.0 with the interpolation-error check (6.11); the stated small-angle bound (6.2.3) remains beside it, and off-centres (6.2.9) were measured and parked: on lattice-seeded faces they change nothing. Size fields (6.3) come next, since every later quality claim rests on them and on refinement, then metrics (6.4), with the reparametrisation of unusable faces (6.4.4) after them. The real-CAD corpus (6.5) and its failure taxonomy (6.5.6) should start early, since they measure every other item and decide which of 6.5.1, 6.5.2 and 6.4.4 is worth landing next; the rest of the interpolation-error check (6.11) lands with 6.3, so sizing is judged by accuracy as well as angles. The volume route through `octree_mesh` (6.7.1) needs only documentation; the tetrahedral backends follow their licence checks, measured on the Thingi10K corpus (6.7.8). Curved meshes (6.6) landed in v17.16.0 with their validity beyond the nodes; placing their interior nodes (6.6.2) is small, and their untangling (6.6.3) follows a design pass. Quads (6.8) and boundary layers (6.9) start with their design passes once 6.2 and 6.3 have landed, and boundary layers after `extrude` (3.1.2). Adaptation on the CAD (6.10) follows MMG (3.3), closest-point projection in the isogeometric layer and, for anisotropic metrics, 6.4.1.
