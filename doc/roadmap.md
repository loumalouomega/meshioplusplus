# meshio++ roadmap

Status at time of writing: **v16.30.0** — 80 core formats plus five Python-only physics-ML ones, forty-seven mesh operations + six data operations, six language surfaces (Python / C / Fortran / Julia / R / WASM), two viewers plus a browser dataset manager, a Blender add-on, a ParaView plugin, an MCP server, a settings-driven pipeline engine, a dataset-manifest layer with a PhysicsNeMo adapter, and a versioned ABI (`MESHIOPLUSPLUS_ABI_VERSION` 22), sanitizer and fuzzing gates, and a format conformance matrix.

This document lists what is *not* built. Nothing here duplicates shipped functionality; where a feature partially exists, the shipped half is named and the gap is stated explicitly. Release history lives in [`CHANGELOG.md`](https://github.com/loumalouomega/meshioplusplus/blob/main/CHANGELOG.md), not here.

Effort key: **S** = days, **M** = a couple of weeks, **L** = a month or more, **XL** = a project in its own right. An item names a **probe** — the failing test that proves the gap — wherever one is cheap.

## How this file works

- **Sections are ordered, and the order is the recommendation.** Each section states what belongs in it; an item that sounds exciting does not move up for that reason. An empty section is removed, not kept as a placeholder.
- **A closed item is removed, not struck through.** Its history is the `CHANGELOG.md` entry and the feature's own `doc/` page; a partly closed item is narrowed to what remains (the `AGENTS.md` change checklist rule).
- **Every level of the outline is numbered**, so a gap can be cited in an issue, a commit or a release note: a group of work is `section.item` (a `###`/`####` heading, or a bold label line), the work under it `section.item.subitem`, and a bullet under that `section.item.subitem.subsub`. Lists that record a decision rather than open work — *Considered, not queued*, a section's *Landing an item* steps and the [non-goals](#non-goals-and-decisions-taken) — stay unnumbered, because a number here means work to do. The numbering follows the sections, so a new section inserted at the top renumbers the rest, as the rule above says, and so does a section removed once its last item closes (Performance, October 2026: what was §4 onward moved up one; and again when reader and writer parity closed, the same month: operations, ecosystem reach and the full WebAssembly build became §3 to §5). The long-run section closed the same month as the last of its spikes landed ([findings](./spikes.md)); being last, it renumbered nothing.
- **Defect-shaped items go in a *Correctness debts* section at the top, regardless of size** — behaviour that loses data, mis-orients cells, does not terminate on valid input or fails silently is not a feature request, even when the fix and the feature are the same work. None is open today, so there is no such section; the first defect found opens one as §1 and renumbers the rest.
- **An item estimated from a doc, a `.d.ts` or a changelog alone says so** ("verify first") and names its probe; the code has repeatedly been more or less capable than its description.
- **[Non-goals](#non-goals-and-decisions-taken) record decisions already taken**, with their reasons, so they are not re-proposed as gaps.

## 1. Format reach

*Admission: a format a simulation or physics-ML workflow actually exchanges; a shipped format's missing half is not a roadmap item, because every registered format reads and writes ([decisions](#non-goals-and-decisions-taken)). "Exchanges" means a file that crosses a tool boundary in a real pipeline (mesher → solver, solver → post-processor, solver → training set), not a format that merely exists. Every item names the consumer on the other side of the file.*

Sizes: **S** ≈ days, **M** ≈ two weeks, **L** ≈ a month or more, including tests, docs page and CLI wiring. They assume a new format reuses the shared components rather than growing its own: the card tokenizer (`detail/keyword_card.hpp`), the [node-ordering registry](./node_ordering.md), the Fortran record reader (`detail/fortran_records.hpp`) and the directory sniffing that sequence globs share.

Link legend: unmarked links were opened or returned by a search while this section was written (September 2026); links marked † are quoted from memory and must be checked before relying on them. Vendor documentation portals move often — when a link is dead, search the document title.

Every format this section queued is now read: the native FEM interchange, solver input and result-file readers of v16.5.0 to v16.12.0 (Tecplot, Femap, MFEM, Patran, Abaqus `.fil`, Radioss, Z88, libMesh, Marc, Ansys `.rst`, LS-DYNA and OP2), DOLFINx's ADIOS2 `.bp` ([`vtx`](./formats/vtx.md)) and Tecplot SZL through TecIO ([`szplt`](./formats/szplt.md)) of v16.13.0, and the [vendor-runtime routes](./vendor_routes.md) for the files only a vendor's software reads (Abaqus `.odb`, Marc `.t16`, Femap `.modfem`, Ansys results beyond the native reader). Since v16.17.0 the shared components are used wherever a format's layout fits them, the input decks are written too (Radioss's starter deck, checked with the OpenRadioss starter, and Marc's), Femap writes a series as one output set per step, and every format read but not written names its reason on the [conformance page](./conformance.md#formats-missing-a-direction), which a test keeps in step with the registry; the missing half of each has since been written, so every registered format reads and writes. What they still lack is a check against a run of the vendor tool, listed under [Awaiting a licensed run](#_1-2-awaiting-a-licensed-run): take each as soon as a licence, or a file the tool wrote, is in hand.

### Considered, not queued

- **Graphics, CAD, VFX or lab-specific rather than simulation interchange:** 3MF, X3D, DXF, Alembic, OpenVDB, Silo, LAS/LAZ, E57, OBJ materials (`.mtl`).
- **Closed FEM databases with no route worth shipping:** Altair `.h3d` (undisclosed format, SDK not redistributable — Altair's own advice for OpenRadioss is ANIM → VTK, see the [OpenRadioss discussion](https://github.com/orgs/OpenRadioss/discussions/552)); HyperMesh `.hm`; Abaqus `.sim`.
- **No native format to implement:** deal.II (reads and writes UCD, VTK, Gmsh, Abaqus, Exodus — all reachable today); MOOSE (Exodus).
- **Nastran OP4 matrices and punch `.pch`:** matrix and card dumps, not mesh/field exchange; pyNastran serves them.
- **Non-MSC Nastran HDF5 dialects:** incompatible schemas; revisit with a file in hand.
- **Partitioning niche:** gmsh `$PartitionedEntities` (Kratos partitions through MDPA).
- **CalculiX `.dat` print files:** `frd.read_dat` stays a Python helper that returns a list of table dictionaries; it is not a `Mesh`, it has no writer, and `.dat` already belongs to Tecplot and Marc ([CalculiX results](./formats/frd.md)).
- **Operators and tooling, not formats** (listed only because they came up in the same review): ICP registration; mesh duals; cylindrical/spherical coordinate transforms; shell completions.

Revisit any of them when a consumer asks with a file in hand — a real deck or result file, the tool version that wrote it, and the tool that needs the converted output.

#### 1.2 Awaiting a licensed run

Checks that need the vendor tool itself, or a file it wrote that no public source has. Each reader works from the vendor's documentation and every public file found (September 2026); what remains is one probe per line.

The [vendor-runtime routes](./vendor_routes.md) of v16.13.0 are tested against stand-ins of the vendor APIs only. Each needs one recorded run, with the vendor version written into its page; what to install for it:

- **1.2.1 Abaqus `.odb`.** Abaqus 2020 or later (its `abaqus python`, whose bundled numpy the script needs; 2023 and before run Python 2.7, 2024 and later Python 3). Run `contrib/abaqus_odb/odb_to_vtu.py` on a job with shells, C3D20R and an assembly-level set, and compare its nodal `U` and centroidal `S` against the same job's `.fil` read natively ([route](./routes/abaqus_odb.md)).
- **1.2.2 Marc `.t16`.** Marc/Mentat 2020 or later with PyPost (`py_post`, run with Mentat's Python). Run `contrib/marc_t16/t16_to_vtu.py` on a job that writes both `.t16` and `.t19`, and compare against the `.t19` read natively; confirm that post file position 0 holds the model ([route](./routes/marc_t16.md)).
- **1.2.3 Ansys results via PyDPF.** A DPF Server (Ansys 2021 R1 or later, or the standalone DPF Server 2024 R2 or later) and `pip install ansys-dpf-core pyvista meshioplusplus[h5py]`. Run `contrib/ansys_dpf/rst_to_vtkhdf.py` on a structural `.rst` and compare against the native `.rst` reader; then on a `/FCOMP,RST,1` file, which the native reader refuses ([route](./routes/ansys_dpf.md)).
- **1.2.4 Femap `.modfem`.** Femap 2301 or later on Windows, and `pip install pywin32`. Run `contrib/femap/export_neutral.py`, check `feFileWriteNeutral`'s argument list against that version's API help, and read the neutral file back ([route](./routes/femap_modfem.md)).
- **1.2.5 Tecplot `.szplt`.** Tecplot 360 2023 or later, and `pip install pytecplot`. Save a data set as `.szplt` and as `.plt` from Tecplot itself and read both (the TecIO-backed reader against the native one); run `contrib/tecplot/szplt_to_plt.py` and the macro `contrib/tecplot/szplt_to_plt.mcr`; and point `MESHIOPLUSPLUS_TECIO_LIBRARY` at Tecplot's own shared `libtecio` for the ctypes reader ([route](./routes/tecplot_szplt.md)). Also open in Tecplot 360 a file meshio++ wrote with single-precision, 16-bit and byte variables and one with partitioned zones; and, with a TecIO newer than 2018.3 (which refuses to write polygon and polyhedral zones in an SZL file), write such a zone, read it back, and check the written face map against Tecplot's reading, which would turn the refusal of those zones into a reader and a writer.

The readers:

- **1.2.6 Tecplot.** A `.plt` written by `preplot` from the ASCII fixtures (`#!TDV112`), read identically to its `.dat`, and the `.plt` meshio++ now writes opened in Tecplot or checked by `preplot`; binary files of versions 100–105 and 109–111, of which no sample was found (the VisIt suite covers 71, 75, 106–108).
- **1.2.7 Femap.** Element (404) and group (408) records written by Femap 10 and by 12 or later (the public 2401 files hold none); the slot layout of the 13-node pyramid (topology 19); a file meshio++ writes, a multi-set series included, imported into Femap.
- **1.2.8 Patran.** A neutral file exported by ANSA or HyperMesh.
- **1.2.9 Abaqus `.fil`.** A binary run with shells and C3D20R, checked against its `.dat` printout (the truss run TenBarArea is checked); a binary file of a single-precision build (4-byte words), of which no layout description or sample was found, which decides whether the reader and the writer take that width; and a file meshio++ writes, opened in Abaqus.
- **1.2.10 Radioss.** Animation files of the layouts before OpenRadioss (magic numbers `0x5426` to `0x542B`): neither OpenRadioss's tools nor its readers document them. The 16-bit encoding of the nodal normals (the writer leaves them zero: `anim_to_vtk` ignores them and the encoding is undocumented), and a run of OpenRadioss's `anim_to_vtk` on a file meshio++ wrote, time-history lists included.
- **1.2.11 Marc.** A run of Marc itself, including on a deck or a `.t19` post file (a remeshing series included) meshio++ writes (`SIZING`'s fields, one type per `ELEMENTS` line, and the shell and plane-strain default types follow Volume C and Mentat's decks); post files before revision 9 (Marc K7 and earlier, Volume D 2000's PLDUMP layout); Volume A's edge and face numbering, to map edge and face sets (kept as `(cell, number)` field data) onto facets, which also decides whether side regions can be written to decks and post files; the binary `.t16`, read or written natively, which needs Volume D's PLDUMP description of it or a sample file (today it is read only through Marc's PyPost, by the [route](./routes/marc_t16.md)).
- **1.2.12 Ansys `.rst`.** A file written with `/FCOMP,RST,1` or higher (zlib records): `detail/zlib_inflate` is ready, the record framing needs a sample. A harmonic (complex) result file, which no public sample or open reader covers (pymapdl-reader takes cyclic mode pairs only and only DPF reads complex sets), so complex results are neither read nor written; and a file meshio++ writes with element rotations and nodal coordinate systems, read by DPF (pymapdl-reader applies the three nodal rotations in the opposite order, so it agrees only on single-axis angles).
- **1.2.13 LS-DYNA.** A family from LS-DYNA with adaptive remeshing (`NADAPT`), the `d3thdt` time-history database, the cubic and bubble solids (21P, 15T, 20T, 40P, 64), airbag particles and rigid roads (read and written from the manual and lasso-python only: the airbag variable names of a real file, and rigid roads with the full rigid-body velocities, `NDIM = 9`, which the writer leaves out), a real `d3part`, thick shells, and the whole reader against LS-PrePost, with the families and `binout` files (links included) meshio++ writes opened there; whether LS-DYNA writes a ten-node solid's extra nodes once or twice.
- **1.2.14 Nastran OP2.** Random element tables, complex SORT2 nodal tables, CBUSH and CGAP forces, CBUSH real stresses, and NX's solid types 300–303 (read from pyNastran's layouts; no sample). Files meshio++ writes, opened in Femap, Patran or an NX/Simcenter post-processor: the writer produces the MSC dialect only, and the element tables it writes beyond pyNastran's reach (the SORT1 PSD, CRM and ATO random tables, the complex layouts pyNastran does not read) follow the reader's layouts.
- **1.2.15 CalculiX `frd`.** `cgx -b` (CalculiX GraphiX) reading a binary file meshio++ writes; `ccx2paraview` parses the ASCII layout only, so no open tool checks the binary variant beyond meshio++'s own reader and the binary files `ccx` wrote.
- **1.2.16 FEBio `.xplt`.** FEBio Studio or `febio4` opening a file meshio++ wrote: the remeshed series (a mesh section per remeshed step), surfaces with per-surface-node variables, and the compressed states.
- **1.2.17 Nastran HDF5.** MSC's own post-processors (Patran, Simcenter) reading a file meshio++ wrote: its tables follow the column sets of the six MSC Nastran 2020 files, but the `CBUSH`, `CGAP`, `CMASS` and `CONM1` element tables and the `MAT5`, `MAT8`, `MAT9`, `PBARL`, `PBEAML` and `PCOMPG` tables have no sample, so they are not written; a file with them would add them.
- **1.2.18 DOLFINx VTX.** ParaView's `ADIOS2VTXReader` (`tools/gen_vtx_reference.py` drives it) and DOLFINx reading a file meshio++ wrote with several cell types or parts (one block per type and part, with `meshio.shared_points`): both read one cell type per file, so this is meshio++'s own extension of the layout; and a `VTXMeshPolicy.reuse` file (ParaView 6.1 aborts on every step after the first of DOLFINx's own).

## 3. Operations

*Admission: a new operation, or a public face for machinery that already exists privately inside one.*

**3.1 Generation.** Almost every operation transforms a mesh you already have. The exceptions all start from something else — `grid` from a lattice (`detail/grid_lattice.hpp`), `voxelize`/`compute_sdf` from a surface's bounding box, `remesh_volume` from a closed surface — and nothing builds a shape from parameters, sweeps one, or fills a skin with an adaptive lattice. Triangulating a domain is not this library's work; it reaches meshio++ only through the optional MMG backend (3.3).

- **3.1.1 Primitive constructors** — parametric generators in `operations/primitives.hpp` beside `grid`. Tier 1, the planar domains and the reference cells have shipped (`rectangle`, `box`, `disk`, `uv_sphere`, `icosa_sphere`, `cylinder`, `reference_triangle`, `ngon`, `annulus`, `lshape`, `plate_with_hole`, `honeycomb` and `reference_cells`, on every surface; see [parametric primitives](./primitives.md)); the catalogue below is what is left. They are dependency-free and remove the fixture-file dependency from tests, docs, notebooks, the browser demo and the MCP server, and `reference_cells` could replace the test-local canonical mesh of the [format conformance matrix](./conformance.md) (whose coordinates are exact in binary and keep a deliberately inexact `0.1` vertex, so the swap needs that vertex kept). **The hand-rolled helpers are mostly retired**: the x-fastest `_quad_grid`, `_hex_grid` and `_tri_grid` of ten Python test files, and `hex_grid`, `quad_grid` and `tri_grid` of nine C++ test files, call `rectangle` and `box`, whose coordinates are bit-identical (`origin + size * i / n` is exactly `i` for a size equal to the count). **What remains is a decision per helper, each recorded here so it is not re-litigated:** `_unit_cube` (three Python copies and `test_voxelize.py`) numbers its corners in VTK order, not `box`'s x-fastest order; `_hex_cube` and `_tet_cube` carry extra `point_data` and `cell_data`, and `np.linspace` differs from `size * i / n` in the last bit above three cells; the i-major helpers of `test_smooth` and `test_openfoam` pin a different numbering; `test_region_analysis.cpp`'s `quad_grid` is asserted against region counts the generators' side regions would change; and the jittered `ft_*` fixtures of `golden_fixtures.hpp` feed pinned digests. The notebook helpers (`hex_grid` in 03 and 09, `hex_block` in 25, `plate` in 09, the squircle `disk` of 27) are left to the next edit of each notebook, since a change re-executes it. The catalogue follows [meshzoo](https://github.com/meshpro/meshzoo)'s where the two overlap, taking names and parameterisations from its README only: check its licence before reading its code, since later releases are not MIT. **S per tier**
  - **3.1.1.1 What every further generator owes.** The contract is shipped (index-computed coordinates, a documented order, a `max_cells` budget, a zero count as an empty mesh, outward surfaces and positive volumes, named side `Region`s); a new generator adds the same surface list: Python and its numpy twin, C (`mio_gen_opts` has room in its reserved tail, so a shape that needs a field grows the struct append-only), Fortran, Julia, R, WASM, both CLIs' `generate` verb, an MCP tool and a pipeline `Generate` shape. **Remaining in the contract itself:** `order=2` serves the serendipity types only; the full-Lagrange types (`quad9`, `hexahedron27`, `wedge18`) and the VTK Lagrange family are not generated.
  - **3.1.1.4 Surfaces**: spheres from the other platonic seeds (`tetra_sphere`, `octa_sphere`, and `cube_sphere` in quads); `geo_sphere` (a UV sphere closed with triangle caps rather than degenerate quads); `torus` (genus one, negative Gaussian curvature on the inner rim and periodic both ways — the [curvature](./curvature.md) and Euler-characteristic probe a sphere cannot give); `moebius` (non-orientable, with `num_twists`: no consistent orientation exists, which probes [`compute_normals`](./normals.md)' `inconsistent_pairs` report and `repair(fix_orientation=True)`); `tube`, `cone` and `capsule` (open and closed surfaces of revolution, with sharp rims for [`feature_edges`](./feature_edges.md)); `box_surface` (today's `cube_quads`, a region per face); and the five platonic solids with one cell per face, the dodecahedron's pentagons as a `polygon` block. **S**
  - **3.1.1.5 Solids**: `ball` (tetrahedra, or hexahedra by a seven-block butterfly so no cell degenerates at the centre); `spherical_shell` and `pipe` (thick shells between two radii in hexahedra, `inner`/`outer` regions, with a radial grading ratio for wall-resolved spacing); `fichera` (the cube minus one octant, the 3-D L-shape and its corner singularity); `solid_torus`. **S**
  - **3.1.1.6 Lines and points**: `line` (a subdivided segment), `circle` (a closed polyline) and `helix` (a spring), as `line` cells for beam and 1-D format fixtures; point clouds on a sphere (a Fibonacci lattice) or in a box (seeded sampling) for the point-cloud formats and [point budgets](./point_budgets.md). Seeded sampling needs its own small generator (splitmix64 or PCG) in both twins: `std::uniform_real_distribution` is implementation-defined, and numpy's `default_rng` has no C++ counterpart. **S**
  - **3.1.1.8 Watch.** Byte identity between the twins holds for `grid` because it is index arithmetic; `std::sin`/`std::cos` are not correctly rounded and differ between glibc, MSVC, Emscripten's libc and numpy's own SIMD kernels. Pin byte identity only for the polynomial generators (`rectangle`, `box`, `reference_triangle`, `lshape`, `honeycomb`, `reference_cells`) and compare the trigonometric ones within a few ulps, or have the Python twin take its angle table from the core. Seams and poles are welded points, never duplicates, or `periodic`, `clean` and the Euler-characteristic checks see a boundary that is not there.
- **Deliberately not**, so not re-proposed: generators driven by a user callback (no callback crosses the flat ABI; numpy users build `Mesh(points, cells)` directly, and [`isosurface`](./isosurface.md) on a `grid` covers implicit shapes); scanned or modelled assets (the bunny, the teapot, the bracket fixture — data rather than parameters, each under its own licence); and CSG combinations (a [non-goal](#non-goals-and-decisions-taken)) — two-body interface and contact fixtures are primitives placed with `transform` and joined with `merge`.
- **3.1.2 `extrude`** — 2-D → 3-D sweep (triangle → wedge, quad → hexahedron) with `nlayers` and per-layer offsets, carrying regions to side and cap regions. The most-requested generation primitive. **M**
- **3.1.3 `revolve`** — `extrude`'s rotational sibling around an axis, sharing its layer machinery; degenerate cells on the axis are the only new work. **M**
- **3.1.4 Octree and quadtree: what is left.** [`octree`](./octree.md) (octrees and quadtrees from a skin with `hanging`, `polyhedra` and `templates` transitions, snapping, curvature / feature / size-field criteria and a choice of plane) and the 2-D [`voxelize`](./voxelize.md#2-d-pixels) have shipped; what remains is below. **S**
  - **3.1.4.1 `plane=` on `voxelize`.** The pixel variant picks the skin's plane automatically; an explicit `plane` option needs a field on `VoxelOptions`, which is a released type, so it waits for the next ABI bump. **S**
  - **3.1.4.2 Probes.** [`check_conformity`](#_3-2-checks-selection-and-measurement) (3.2.1) reporting zero hanging nodes under `"polyhedra"` and `"templates"` and exactly `octree:hanging` under `"hanging"`, once it exists; the tests already check face sharing and volumes with their own oracle.
  - **3.1.4.3 `octree_mesh`: a volume mesher on the octree.** A new operation that meshes the inside of a skin on a balanced linear octree, driven by a size field (curvature, features, thickness, a user array) and a fast winding number: castellated hexahedra with surrogate-boundary regions and the signed distance and closest point at the nodes, conforming graded tetrahedra by isosurface stuffing with sharp features snapped and the mesh fitted and untangled (the default), and all-hexahedra by the octree dual. `octree` itself does not change. The [plan](./octree_mesh_3d_plan.md) gives the phases; this item narrows as they land. **L**

**3.2 Checks, selection and measurement.**

- **3.2.1 `check_conformity`** — hanging nodes, T-junctions and interface facets that only partly overlap, so a user knows which `find_interface` mode to choose. It also gives `refine` and `undo_green`, which discuss conformity only in comments, a checker. A report plus a flagging `point_data` array. **S–M**
- **3.2.2 `find_intersections`** — self-intersection of a surface and mutual interpenetration of two parts, by triangle–triangle tests over the bucket grid. Returns the pairs, the intersection segments as a line mesh and a flagging `cell_data` array, with exact and "possible" hits reported separately because there are no robust predicates; booleans stay a [non-goal](#non-goals-and-decisions-taken). Also the precondition check for `repair`, `shrinkwrap` and `remesh_volume`. Probe: two overlapping spheres. **M**
- **3.2.3 `select`** — write `Region`s (cell, point or side) from a box, plane or sphere, a `cell_data` or quality threshold, a component label, or normal-angle patch growing bounded by `feature_edges`, so boundary-condition and contact patches are reproducible and feed `find_interface`. Reuses `crop(where=)`'s predicate parser, `feature_edges` and `split(by="component")`. **M**
- **3.2.4 `thickness`** — wall thickness and inter-part clearance per facet, from a ray along the inward normal to the opposite surface. Needs a ray–triangle kernel that `find_intersections` also needs: write it once in `detail/`. **M**
- **3.2.5 `mirror`** — reflect across a plane, flipping the winding so the orientation stays valid, optionally welding on the plane: a full model from a half, and the demi-sphere fixture from one hemisphere. **Verify first:** a reflecting `transform` matrix may already flip orientation correctly; probe by mirroring a tetrahedral mesh and asserting positive volumes, and if it does this item shrinks to documentation. **S**

**3.3 Optional MMG backend.** [MMG](https://www.mmgtools.org/) — `mmg2d` (planar triangles), `mmgs` (surface triangles in 3-D) and `mmg3d` (tetrahedra) — adapts an existing simplicial mesh to a size or an anisotropic metric, embeds a level set in it conformally, and moves it in a Lagrangian way; `mmg2d` also triangulates a planar domain from its boundary. Everything here was read in the source of MMG 5.8.0 (October 2024), not taken from its documentation. It is LGPL-3.0, so it follows the KaHIP, ADIOS2 and TecIO pattern exactly: **`MESHIOPLUSPLUS_WITH_MMG`**, off by default, bring-your-own (`find_package(mmg CONFIG)` over the package MMG installs, with its `Mmg::` targets; `mmg_DIR` or `CMAKE_PREFIX_PATH` point at it), never vendored, never downloaded, never probed under Emscripten, linked dynamically only, and absent from the release wheels and the native CLI binaries; the page states the licence's implications for anyone who redistributes a build with it. Without it, every operation below throws `Unsupported` naming the flag, as `partition(method="kahip")` does, and reports it in the configured capabilities. There is no numpy twin — MMG's result cannot be reproduced by a second implementation, the [`remesh_volume`](./remesh_volume.md) precedent — so Python raises `NotImplementedError` naming the flag when the core lacks it.

- **3.3.1 `adapt`** — remesh to a size field or a metric. A tetrahedral mesh goes to `MMG3D_mmg3dlib`, a triangle surface in 3-D to `MMGS_mmgslib`, a planar triangle mesh to `MMG2D_mmg2dlib`. **M**
  - **3.3.1.1 Size and metric.** A constant `hsiz`; a scalar size as one-component `point_data`; or an anisotropic metric as a symmetric tensor `point_data` (six components in 3-D, three in 2-D, in the upper-triangular order MMG expects — verify first against `MMG3D_Set_tensorSol`). The producers are already in the tree: [`hessian`](./hessian.md) (with a small metric-from-Hessian helper — absolute eigenvalues, scaled by a target error and clamped to `hmin`/`hmax`), [`error`](./error.md) for an isotropic size, and [curvature](./curvature.md) for a surface.
  - **3.3.1.2 Parameters.** `hmin`, `hmax`, `hausd` (the Hausdorff distance the boundary may move), `hgrad` and `hgradreq` (gradation), `angle_detection` (ridge angle, or off), `optim`, `noinsert`/`noswap`/`nomove`/`nosurf`, `nreg` (normal regularisation), `opnbdy` (keep internal open surfaces), `mem` and `verbose` (default −1, since MMG prints to stdout), and per-region `hmin`/`hmax`/`hausd` through `Set_localParameter` (`local={"inlet": {"hmax": 0.01}}`).
  - **3.3.1.3 Entities.** Cell and side regions map to MMG references through a reference ↔ name table and come back under their names; `frozen` points and named `required` regions become required vertices, edges, triangles and tetrahedra; [`feature_edges`](./feature_edges.md) become ridges, and their corners MMG corners. `wedge` blocks pass as MMG prisms, which `mmg3d` keeps unchanged (verify first), and boundary quads as MMG quadrilaterals (verify). Hexahedra, pyramids, higher-order cells and ragged blocks are refused with a pointer to [`convert_cells`](./convert_cells.md).
  - **3.3.1.4 What does not survive**, as for `remesh`: point and cell data on the new points are dropped with a warning — compose with [`interpolate`](./interpolate.md) — and `field_data` carries through.
  - **3.3.1.5 Report.** MMG's return code: `MMG5_SUCCESS`; `MMG5_LOWFAILURE`, where MMG returns a valid mesh it could not finish adapting, is a warning in the report, not an error; `MMG5_STRONGFAILURE` throws. Also points and cells in and out, and the quality histogram of the result.
- **3.3.2 `discretize_levelset`** — `MMG3D_mmg3dls`, `MMGS_mmgsls` and `MMG2D_mmg2dls` cut a mesh along the zero (or a chosen) isovalue of a `point_data` field and remesh both sides, so the interface is a conforming side region between an `inside` and an `outside` cell region; several materials through `Set_multiMat`, and small parasitic components removed through `rmc`. Where [`isosurface`](./isosurface.md) extracts a level set and [`crop`](./crop.md) cuts along cells, this embeds it in a mesh fit for a solver. Chained with `compute_sdf` on a `grid` and `convert_cells(simplexify)`, it is the backend's route from a skin to a tetrahedral mesh of its interior. **S–M**
- **3.3.3 `mesh_domain`** — `MMG2D_mmg2dmesh` triangulates a planar domain from its boundary `line` cells, with `hsiz`, `hmax` or a size field, boundary references kept as side regions. How MMG tells holes and subdomains apart is not yet read in its source: verify first, probing with an annulus. This is the only domain mesher meshio++ offers, and only through the backend (the [non-goal](#non-goals-and-decisions-taken) stands for native meshing). MMG has no 3-D counterpart that meshes from a surface; the 3-D routes are 3.3.2, [`remesh_volume`](./remesh_volume.md) and the octree of 3.1.4. **S**
- **3.3.4 `move`** — `MMG3D_mmg3dmov` and `MMG2D_mmg2dmov` move a mesh by a displacement `point_data` vector and remesh as it deforms. They need MMG built with the ELAS linear-elasticity library, so the operation is gated on that capability too, and comes last. **S**
- **3.3.5 Embedding hazards**, read in the 4.8.0 source:
  - **3.3.5.1 Signal handlers.** `MMG3D_mmg3dlib` calls `signal()` for `SIGABRT`, `SIGFPE`, `SIGILL`, `SIGSEGV`, `SIGTERM` and `SIGINT` on every call (`libmmg3d.c`), which replaces Python's Ctrl-C handler and any crash handler of the host. The wrapper saves every handler with `sigaction` before the call and restores it after, on every path including errors, and the page says a call cannot be interrupted. Check the other entry points and libraries for the same.
  - **3.3.5.2 Index width.** `MMG5_int` is `int32_t` unless MMG was configured with `-DMMG5_INT=int64_t`: detect it at configure time, and refuse a mesh beyond its range by name rather than truncate.
  - **3.3.5.3 Threads.** Whether two meshes can be adapted at once in one process is not established; serialise the calls behind one mutex until it is. ParMmg, MMG's MPI layer, falls under the MPI [non-goal](#non-goals-and-decisions-taken).
- **3.3.6 The file route, and Medit's half of it.** MMG's native files are Medit `.mesh` and `.sol`. meshio++'s `medit` reader discards `Corners`, `Ridges` and the `Required*` keywords and has no `.sol` support. Reading and writing `.sol` (and `.solb`) — scalar, vector and symmetric-tensor solutions at vertices and cells, as `point_data` and `cell_data` — and keeping those keywords as regions (shipped; see [Medit](./formats/medit.md)) make the `mmg3d_O3`/`mmgs_O3`/`mmg2d_O3` executables usable through files with no link at all, which also serves anyone driving MMG themselves. Independent of the rest, so it can land first. **S**
- **3.3.7 Surfaces and probes.** `operations/mmg.hpp` in the core; Python; C entry points with append-only, reserved-tail option structs and reports (`mio_adapt_ex`, the `mio_remesh_ex` pattern); Fortran, Julia and R mirrors; both CLIs (`adapt`, `discretize-levelset`, `mesh-2d`); MCP tools that report the capability; an `Adapt` pipeline step; no WASM. A `doc/mmg.md` page with the licence section, and a notebook adapting a `rectangle` to the metric of an analytic field's [`hessian`](./hessian.md). CI: one Linux leg that builds MMG 5.8 from source (cached) and runs with the flag on, beside the KaHIP and ADIOS2 legs; a conda-forge `mmg` package may serve instead †. Probes: a constant `hsiz` gives a mean edge length within a stated tolerance of it; region names and frozen points survive bit for bit; the level set of a sphere's signed distance gives an interface of area ≈ 4πr²; an anisotropic metric along a boundary layer gives elongated triangles aligned with it.

## Non-goals and decisions taken

Recorded so they are not re-proposed as gaps.

- **Every registered format reads and writes, in both engines** — decided in October 2026, when the parity tier closed; it reversed the earlier non-goals that kept result files and the export-only formats read-only. A format reads and writes in the C++ core and in its Python twin, so it reaches every surface (C, Fortran, Julia, R, WASM, both CLIs and the MCP server's format capabilities); a core-only path is unreadable from the surfaces that have no fallback, a Python-only one has no twin to check it against. `read(write(m))` equals `m` within the limits the format itself imposes (single precision, a cell type it has no slot for, a concept it cannot express): a loss that is a fact of the format is stated on its page and in the [conformance](./conformance.md) notes, and one that is only an unwritten feature is a gap that reopens a *Reader and writer parity* section here. A new format or direction lands as `AGENTS.md` says (native writer registered in `registry.cpp`, parameters through `WriteOptions`, the Python twin behind `core_declined`, the arrays a reader returns written back under the same names, a `SPEC` declaration and a *Writing* section). The exemptions are recorded in `tests/python/conformance_spec.py` (`READ_ONLY`, `ENGINE_EXEMPT`, `PARTIAL_ENGINE_EXEMPT`) and checked by `test_conformance.py`:
  - **Pure 2-D drawings.** `svg` and `tikz` draw a mesh rather than store it: their readers parse only the structure meshio++'s own writers emit, return the geometry as planar (`z = 0`) and warn once per read that depth, and whatever else the drawing could not hold, is lost; anything else in the file is a `ReadError` naming the construct, never a guess.
  - **`ansys_rst_cyclic`**, which is not a file but the full rotor a cyclic `.rst` expands to; its write side is `ansys_rst`'s cyclic option. **`step` and `iges`** outside a build with OpenCASCADE: reading a CAD model means a CAD kernel, which the wheels and release binaries carry and a source build finds when it can ([skin to CAD](./cad_fit.md), [STEP](./formats/step.md#reading)); on WASM the lean build is the exempt one, and the [full build](./wasm.md#lean-and-full-builds) carries the kernel.
  - **One engine only, by decision**: GiD (gidpost and its Gauss points are implemented once, in the core), the OpenFOAM case writer and its zone, field and multi-region reading, CGNS's face-based polyhedra (the writer's winding repair is a discrete branch two implementations could resolve differently), the CAD readers, and the `step` writer's merged and fitted faces (`faces="planar"`/`"fitted"`, with `segment`'s primitive method that feeds them: loop walking, vertex snapping and the primitive growth are discrete branches too, so the twin writes `faces="facet"` byte for byte and nothing else); the Python entry points raise naming the missing core rather than guess.
- **What the parity tier left as facts of the format**, each stated on the format's page and in the conformance notes, none an unwritten feature:
  - **`nastran_op2`** writes the MSC dialect only (32-bit little-endian words, SORT1 tables). 64-bit words, big-endian files, NX/Simcenter's interlaced table names and double-precision GRIDs are read and detected, not written: a post-processor reads the MSC dialect with no flags, and whether NX accepts it is a vendor check ([§1.2.14](#_1-2-awaiting-a-licensed-run)). The random PSD, CRM and ATO tables are written as SORT1 magnitudes, as the reader reads them (MSC writes them SORT2, and pyNastran reads only the RMS and NO ones in SORT1); no SORT2 pivot is written. Elements on scalar points (`CELAS3`/`CELAS4`, `CDAMP3`/`CDAMP4`, `CMASS3`/`CMASS4`) and `CBUSH1D` and `CBEND` have no cell type — `Mesh` has no scalar-point entity to hang them on — and are skipped with a warning.
  - **`nastran_h5`** writes a table only where an MSC sample fixes its layout: `CBUSH`, `CGAP`, `CMASS` and `CONM1` elements, and `MAT5`, `MAT8`, `MAT9`, `PBARL`, `PBEAML` and `PCOMPG` values, have no table in the six MSC Nastran 2020 files at hand, so the elements are left out and the values go on the plain cards, each with one warning; the OP2 file holds them.
  - **`lsdyna_d3plot`** leaves the rigid roads' full rigid-body velocities (`NDIM = 9`) out of the state, and writes an airbag variable under a title-case name, since the names of a real file are in no manual available.
  - **`radioss_anim`** writes the nodal normals as zeros: `anim_to_vtk` ignores them and their 16-bit encoding is undocumented.
  - **`abaqus_fil`** writes 8-byte words only, the reader's width; a single-precision build's 4-byte layout has no description or sample.
  - **`ansys_rst`** has no complex (harmonic) results, read or written: no public sample or open reader covers them, and DPF alone reads them. The nodal coordinate systems are written as `ansys:node_angles` and agree with pymapdl-reader only for single-axis angles, since it applies the three turns in the opposite order.
  - **`xplt`** writes a per-surface-node variable as `FMT_NODE` in surface order, where the reader averages the values a node on two surfaces has into one point value, which both surfaces then write.
  - **`marc` and `marc_t19`**: edge and face sets stay `(cell, number)` field data and side regions are dropped, since mapping them to facets needs Volume A's numbering ([§1.2.11](#_1-2-awaiting-a-licensed-run)); the Herrmann, bubble and generalized-plane-strain types come back as the default type of their shape, and a deck holds no data arrays.
  - **`szplt`** does not write polygon and polyhedral zones: TecIO 2018.3, the newest source available, refuses them in an SZL file, so the reader refuses them by name too and the face-based zones stay with the `.plt` and ASCII readers. Partitioned output is for tetrahedron and brick zones of a static file only (TecIO's own limit), and a series is written whole.
  - **`vtx`**: DOLFINx and ParaView read one cell type per file, so a file of several cell types or parts is meshio++'s own extension of the layout.
- **MPI in the library** — none planned ([C++ API](./cpp_api.md)); `partition`'s ghost layers produce the halo an MPI assembly in the owning application needs. ParMmg, MMG's MPI layer, is excluded with it.
- **Solver-coupled physics-ML** — assembled solver residuals, adjoints and Sobolev training, co-simulation, active-learning *labeling*, adaptive remeshing driven by a surrogate, and MPI model-part gathering. Every one needs a live solver (an assembly routine, its tangent, its communicator) and meshio++ has no notion of a discrete system; they belong in the application that owns the solver, the division [Symbolic and physics](physicsnemo/symbolic_and_physics.md) describes.
- **The Python-only layers stay Python** — `pmsh`, `zarr`, `cae` and `usd`, and the physics-ML surface (grids, point budgets, proximity graphs, datasets, training) are export targets and tooling for a training pipeline, registered in Python rather than the shared C++ registry. A core kernel they call (the neighbour search) does not change that; `tessellate` moved to the core ([tessellation](./tessellation.md)) because the native CLI and the flat bindings needed it, and its `Tessellation` helpers stay Python.
- **Polyscope in the release CLI binaries** — excluded deliberately, so `view`/`screenshot` there report the build flag rather than opening a window ([viewer](./viewer.md)).
- **General meshing algorithms as operations** — Delaunay and constrained triangulation or tetrahedralization of a domain, hex-dominant meshing and general hex meshing from a CAD-like boundary, boolean/CSG, boundary-layer inflation, quadrangulation and geodesic distance are each a library in their own right, and the triangulators need robust geometric predicates, which is where dependency-free stops paying (the reason the queued Delaunay item was dropped). The answer is an optional backend (the KaHIP pattern), not a native implementation: domain meshing and adaptation reach meshio++ only through the MMG backend (§3.3). Lattice generation is the exception, and in scope: [`voxelize`](./voxelize.md), the octree of §3.1.4, [`remesh_volume`](./remesh_volume.md)'s isosurface stuffing and the octree volume mesher of §3.1.4.3 (stuffed tetrahedra and the all-hexahedral octree dual, [plan](./octree_mesh_3d_plan.md)) are index arithmetic over a signed distance on a lattice, followed by projection and untangling, with no predicate to make robust.
- **Contact mechanics itself** — penalty or mortar assembly, friction and contact search in time need a live solver. meshio++ detects and exports the interface of one snapshot ([§3](#_3-operations)); the contact algorithm belongs in the application that owns the solver.
- **MMG in the release wheels and the native CLI binaries** — it is LGPL-3.0 and an external install, so it is linked dynamically into builds that opt in and nowhere else; the operations throw by name where it is absent. The WASM half of the old decision is [§5.2.3](#_5-the-full-webassembly-build)'s probe, not this non-goal.
- **KaHIP in the lean WASM build, ADIOS2 and TecIO in either WASM build** — KaHIP ships only in the full artifact (serial kaffpa, built by `build-wasm-deps.sh --full`; a graph partitioner would bloat every consumer's bundle, so the lean pair keeps the SFC method with `"kahip"` throwing by name as the contract); no one has made a wasm build of ADIOS2 (`vtx`); TecIO's redistribution terms keep `szplt` out. Each reports by name in the lean and the full artifact alike ([what stays out](./wasm.md#what-stays-out)).
- **zstd/lz4 codecs in the lean WASM build** — the lean artifact keeps zlib as its only block codec; the full one (v17.2.0) links zstd, lz4 and bzip2. A zstd-compressed VTK XML file is a meshio++ extension VTK itself has no compressor for, so vtk.js does not read it; the second reader of a zstd file is meshio++'s native and Python ones. **Memory mapping and the Kokkos backend under Emscripten** — CMake refuses the Kokkos backend under Emscripten, and there is nothing to map inside MEMFS.
- **Single-file output for DOLFIN, TetGen and EnSight from WASM**, or lifting DOLFIN's simplicial restriction — both are facts of the formats; `writeMesh`'s written-paths return value (v11.2.0) is the fix for the bookkeeping they cause.
- **NURBS patches and trims as a second entity kind inside `Mesh`** — decided with the [isogeometric layer](./iga.md) (v16.43.0, [findings](./spikes.md#the-isogeometric-layer)): a model (`NurbsInfo`, `BrepInfo`) stays a side channel beside the mesh, with its own evaluate, refine and sample operations, because a first-class entity kind needs patches, control nets, weights, knots and trimming curves in `Mesh`, every mesh backend (MESHIO, NATIVE, KRATOS), every binding and the C++ ABI: a major version for a gain the three operations already give. Reopen it when an operation must act on patches and trims as mesh entities (mixed IGA and FEM assembly in one model, for instance, or a patch-aware `partition`), and start from the spike's list of what the side channel cannot do: no `Mesh` operation sees a patch, the model does not travel through the pipeline, and an MFEM model refines every direction alike.
- **Polyhedron blocks as a WASM gap** — `vtu`, `ensight`, `cgns`, `med` and `openfoam` all write them from WASM; a consumer that cannot is constrained by its own data model.
- **Performance work measured or decided against** — recorded when the roadmap's performance section closed (October 2026); a new performance change passes the gates of [landing a performance change](./benchmarks.md#landing-a-performance-change):
  - **The serial phases kept for determinism**: the keep-first weld loop (chains make it order-dependent), the union sweeps of `split` and `compute_normals` (cheap, and their partitions are order-independent anyway), and `remesh`'s energy sweep (every accepted move changes what the next test reads; it has no numpy twin because a near-tie decided differently yields a different clustering).
  - **A facet table cached across pipeline steps** — measured ([benchmarks](./benchmarks.md#pipeline-row-what-a-shared-facet-table-could-save)): in a `Smooth` then `ExtractSurface` chain a cache saves at most one table build, about 3.6% of the chain on SEQ at tier L with the default ten iterations, at most 10% on four OpenMP threads and about 20% with one iteration. `smooth` and `extract_surface` do not share a record structure, so it would also need a refactor, and a cache on the `Mesh` is a Tier A layout change. Reopen it for a workload that chains several facet readers after cheap topology-preserving steps; the `pipeline_smooth_surface` row measures it.
  - **Explicit SIMD intrinsics or `-march` flags** — portability across wheels, WASM and the release binaries is worth more than the scalar kernels cost; revisit only if the harness shows a kernel dominating.
  - **Kokkos device execution** — every `parallel_for` body captures host pointers (`parallel.hpp`); the GPU route is the DLPack/CuPy handoff ([GPU handoff](./gpu.md)).
  - **A BVH in place of the distance query's uniform grid** — `detail/surface_distance.hpp` rejects one because its visit order would make the equidistant-triangle tiebreak observable.
  - **Tuning the pure-Python fallback readers** — the fix is making the C++ path accept the file, not a faster fallback; `_decimate.py`'s heap-based twin is deleted once `decimate` accepts its inputs, not optimised.
  - **Dropping the copy in `transform`** — `transform` copies the connectivity and data it does not change (through `transform_owned_copy`, as 17 operation files copy through `clone_mesh`, `clone_geometry` or `quality_clone_mesh`), and the Python twin copies too; that copy is what makes the result a new mesh that aliases nothing, so removing it is an API change, not an optimisation.
  - **Caching between the browser viewer's applies** — every apply re-reads the staged file and replays the whole pipeline, which is what makes undo exact. Measured with the typed-array channel ([benchmarks](./benchmarks.md#a-typed-array-channel-for-the-browser-viewer)), the read is at most 2 to 25% of an apply that smooths and up to 69% of a quality-only apply on a large surface; a cached mesh or pipeline prefix would hold a second copy of the mesh in the 32-bit heap MEMFS already shares, and make undo depend on invalidation.

- **Terminal rendering stays software, dependency-free and core-only** — no GPU, no windowing stack, no new dependency and no audio library; it is a *preview*, not a replacement for Polyscope or vtk.js, and does not try to match their fidelity, lighting or picking. Python calls the core or raises by name (the [`remesh_volume`](./remesh_volume.md) precedent: a NumPy edge-function rasterizer would be slow and double the surface that has to stay byte-identical). Vector output is unchanged: SVG, TikZ and glTF keep the painter's algorithm and their byte-pinned twins, and their colormap tables are only ever extended. The interactive loop is not a library feature (raw mode, signals and the event loop live in the CLI layer; the library exposes frames and encoders, never a tty, and WASM and the C API carry frames and text only). `--follow` polls modification times and does not use inotify or kqueue. The soundtrack is generated, played by an external player and silent unless asked for, in CI and over SSH. See [terminal rendering](./tui.md#design-decisions).

## Suggested sequencing

Open work only; what shipped is in `CHANGELOG.md`.

1. **Format reach ([§1](#_1-format-reach))** — the checks against the vendor tools, as licences or files the tools wrote appear; they are what is left of reader and writer parity.
2. **The OSS-Fuzz submission ([§2](#_2-quality-of-implementation))** — calendar-bound, so it runs alongside everything else.
3. **Primitive constructors ([§3](#_3-operations))** — tier 1, the planar domains and the reference cells have shipped, and most of the test fixtures they replace are retired; what remains is the other tiers (surfaces, solids, lines and points), as tests and notebooks ask for them, since they are prerequisites of `extrude`/`revolve` and of the octree's fixtures (the 2-D `voxelize` they were once listed under has shipped).
4. **Octree leftovers ([§3](#_3-operations))** — `plane=` on `voxelize` with the next ABI bump, and the `check_conformity` probes once 3.2.1 lands. The volume mesher of 3.1.4.3 runs in its own phases ([plan](./octree_mesh_3d_plan.md)).
5. **The MMG backend ([§3](#_3-operations))** — Medit `.sol` first, since it needs no link and opens the file route; then `adapt`, `discretize_levelset`, `mesh_domain` and, with ELAS, `move`.
6. **Registration ([§4](#_4-ecosystem-reach))** — calendar-bound, so start the submissions early and let them run alongside everything else; the viewer's look (4.5) and the dataset manager's thumbnails (4.6) need no decision first and can run beside them.
7. **MMG under Emscripten ([§5](#_5-the-full-webassembly-build))** — after the native MMG backend of §3.3, through the full build v17.2.0 shipped.
