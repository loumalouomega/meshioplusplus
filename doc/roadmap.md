# meshio++ roadmap

Status at time of writing: **v19.0.0**, ABI 44. What ships is listed where it is documented rather than counted here, where counts went stale: the formats in [supported formats](./formats.md) and the [conformance matrix](./conformance.md), the operations in [architecture](./architecture.md#the-operations-layer), the language surfaces in the [C API](./c_api.md), [Fortran](./fortran.md), [Julia](./julia.md), [R](./r.md), [Octave / MATLAB](./octave.md) and [WebAssembly](./wasm.md) pages.

This document lists what is *not* built. Nothing here duplicates shipped functionality; where a feature partially exists, the shipped half is named and the gap is stated explicitly. Release history lives in [`CHANGELOG.md`](https://github.com/loumalouomega/meshioplusplus/blob/main/CHANGELOG.md), not here.

Effort key: **S** = days, **M** = a couple of weeks, **L** = a month or more, **XL** = a project in its own right. An item names a **probe** — the failing test that proves the gap — wherever one is cheap.

## How this file works

- **Sections are ordered, and the order is the recommendation.** Each section states what belongs in it; an item that sounds exciting does not move up for that reason. An empty section is removed, not kept as a placeholder.
- **A closed item is removed, not struck through.** Its history is the `CHANGELOG.md` entry and the feature's own `doc/` page; a partly closed item is narrowed to what remains (the `AGENTS.md` change checklist rule).
- **Every level of the outline is numbered**, so a gap can be cited in an issue, a commit or a release note: a group of work is `section.item` (a `###`/`####` heading, or a bold label line), the work under it `section.item.subitem`, and a bullet under that `section.item.subitem.subsub`. Lists that record a decision rather than open work — *Considered, not queued*, a section's *Landing an item* steps and the [non-goals](#non-goals-and-decisions-taken) — stay unnumbered, because a number here means work to do. The numbering follows the sections, so a new section inserted at the top renumbers the rest, as the rule above says, and so does a section removed once its last item closes (Performance, October 2026: what was §4 onward moved up one; and again when reader and writer parity closed, the same month: operations, ecosystem reach and the full WebAssembly build became §3 to §5). - **Defect-shaped items go in a *Correctness debts* section at the top, regardless of size** — behaviour that loses data, mis-orients cells, does not terminate on valid input or fails silently is not a feature request, even when the fix and the feature are the same work. ## 1. Format reach {#format-reach}

*Admission: a format a simulation or physics-ML workflow actually exchanges; a shipped format's missing half is not a roadmap item, because every registered format reads and writes ([decisions](#non-goals-and-decisions-taken)). "Exchanges" means a file that crosses a tool boundary in a real pipeline (mesher → solver, solver → post-processor, solver → training set), not a format that merely exists. Every item names the consumer on the other side of the file.*

Sizes: **S** ≈ days, **M** ≈ two weeks, **L** ≈ a month or more, including tests, docs page and CLI wiring. They assume a new format reuses the shared components rather than growing its own: the card tokenizer (`detail/keyword_card.hpp`), the [node-ordering registry](./node_ordering.md), the Fortran record reader (`detail/fortran_records.hpp`) and the directory sniffing that sequence globs share.

Link legend: unmarked links were opened or returned by a search while this section was written (September 2026); links marked † are quoted from memory and must be checked before relying on them. Vendor documentation portals move often — when a link is dead, search the document title.

---

Every format this section queued is now read: the native FEM interchange, solver input and result-file readers of v16.5.0 to v16.12.0 (Tecplot, Femap, MFEM, Patran, Abaqus `.fil`, Radioss, Z88, libMesh, Marc, Ansys `.rst`, LS-DYNA and OP2), DOLFINx's ADIOS2 `.bp` ([`vtx`](./formats/vtx.md)) and Tecplot SZL through TecIO ([`szplt`](./formats/szplt.md)) of v16.13.0, and the [vendor-runtime routes](./vendor_routes.md) for the files only a vendor's software reads (Abaqus `.odb`, Marc `.t16`, Femap `.modfem`, Ansys results beyond the native reader). Since v16.17.0 the shared components are used wherever a format's layout fits them, the input decks are written too (Radioss's starter deck, checked with the OpenRadioss starter, and Marc's), Femap writes a series as one output set per step, and every format read but not written names its reason on the [conformance page](./conformance.md#formats-missing-a-direction), which a test keeps in step with the registry; the missing half of each has since been written, so every registered format reads and writes. What they still lack is a check against a run of the vendor tool, listed under [Awaiting a licensed run](#awaiting-a-licensed-run): take each as soon as a licence, or a file the tool wrote, is in hand.

### Considered, not queued

- **Graphics, CAD, VFX or lab-specific rather than simulation interchange:** X3D, VRML, Alembic, Silo, FBX, COLLADA, AMF, BYU, Rhino `.3dm`, Parasolid, OpenCASCADE `.brep`. DXF, once listed here, was reopened for sketches and outlines measured from a scan and ships as a drawing format ([DXF](./formats/dxf.md)); 3MF, E57, LAS/LAZ, OpenVDB and OBJ materials, listed here until November 2026, were reopened the same way, because the operations that produce or consume them have shipped since (1.4.5 to 1.4.8).
- **Building and city models, and GIS vector layers:** IFC, CityGML and CityJSON, GeoJSON, Shapefile, GeoPackage. Their consumers want semantics (storeys, attributes, layers) a `Mesh` does not carry, and GDAL and IfcOpenShell serve them; [WKT](./formats/wkt.md) stays the one geometry exchange. Revisit with 8.10.2 if georeferenced meshes become a workflow.
- **Medical image volumes:** NIfTI, NRRD and DICOM are voxel images, not meshes; an array from nibabel or SimpleITK reaches [`isosurface`](./isosurface.md) through `grid` today. The surface formats of the same pipelines are 1.4.4.
- **Closed CFD databases:** STAR-CCM+ `.ccm` (libccmio is not redistributable) and `.sim`; FUN3D and FAST grids beyond what [UGRID](./formats/ugrid.md) already reads.
- **Closed FEM databases with no route worth shipping:** Altair `.h3d` (undisclosed format, SDK not redistributable — Altair's own advice for OpenRadioss is ANIM → VTK, see the [OpenRadioss discussion](https://github.com/orgs/OpenRadioss/discussions/552)); HyperMesh `.hm`; Abaqus `.sim`.
- **No native format to implement:** deal.II (reads and writes UCD, VTK, Gmsh, Abaqus, Exodus — all reachable today); MOOSE (Exodus).
- **Nastran OP4 matrices and punch `.pch`:** matrix and card dumps, not mesh/field exchange; pyNastran serves them.
- **Non-MSC Nastran HDF5 dialects:** incompatible schemas; revisit with a file in hand.
- **Partitioning niche:** gmsh `$PartitionedEntities` (Kratos partitions through MDPA).
- **CalculiX `.dat` print files:** `frd.read_dat` stays a Python helper that returns a list of table dictionaries; it is not a `Mesh`, it has no writer, and `.dat` already belongs to Tecplot and Marc ([CalculiX results](./formats/frd.md)).
- **Operators, not formats** (listed only because they came up in the same review): mesh duals other than the tetrahedral median dual (now [`tet_to_poly`](./tet_poly.md)). ICP registration, the cylindrical and spherical transforms and the shell completions, listed here with them, shipped as [`register_rigid`](./registration.md), [`convert_coordinates`](./coordinates.md) and `meshioplusplus completion`.

Revisit any of them when a consumer asks with a file in hand — a real deck or result file, the tool version that wrote it, and the tool that needs the converted output.

### 1.2 Awaiting a licensed run {#awaiting-a-licensed-run}

Checks that need the vendor tool itself, or a file it wrote that no public source has. Each reader works from the vendor's documentation and every public file found (September 2026); what remains is one probe per line.

The [vendor-runtime routes](./vendor_routes.md) of v16.13.0 are tested against stand-ins of the vendor APIs only. Each needs one recorded run, with the vendor version written into its page; what to install for it:

- **1.2.1 Abaqus `.odb`.** Abaqus 2020 or later (its `abaqus python`, whose bundled numpy the script needs; 2023 and before run Python 2.7, 2024 and later Python 3). Run `contrib/abaqus_odb/odb_to_vtu.py` on a job with shells, C3D20R and an assembly-level set, and compare its nodal `U` and centroidal `S` against the same job's `.fil` read natively ([route](./routes/abaqus_odb.md)).
- **1.2.2 Marc `.t16`.** Marc/Mentat 2020 or later with PyPost (`py_post`, run with Mentat's Python). Run `contrib/marc_t16/t16_to_vtu.py` on a job that writes both `.t16` and `.t19`, and compare against the `.t19` read natively; confirm that post file position 0 holds the model ([route](./routes/marc_t16.md)).
- **1.2.3 Ansys results via PyDPF.** A DPF Server (Ansys 2021 R1 or later, or the standalone DPF Server 2024 R2 or later) and `pip install ansys-dpf-core pyvista meshioplusplus[h5py]`. Run `contrib/ansys_dpf/rst_to_vtkhdf.py` on a structural `.rst` and compare against the native `.rst` reader; then on a `/FCOMP,RST,1` file, which the native reader refuses ([route](./routes/ansys_dpf.md)).
- **1.2.4 Femap `.modfem`.** Femap 2301 or later on Windows, and `pip install pywin32`. Run `contrib/femap/export_neutral.py`, check `feFileWriteNeutral`'s argument list against that version's API help, and read the neutral file back ([route](./routes/femap_modfem.md)).
- **1.2.5 Tecplot `.szplt`.** Tecplot 360 2023 or later, and `pip install pytecplot`. Save a data set as `.szplt` and as `.plt` from Tecplot itself and read both (the TecIO-backed reader against the native one); run `contrib/tecplot/szplt_to_plt.py` and the macro `contrib/tecplot/szplt_to_plt.mcr`; and point `MESHIOPLUSPLUS_TECIO_LIBRARY` at Tecplot's own shared `libtecio` for the ctypes reader ([route](./routes/tecplot_szplt.md)). Also open in Tecplot 360 a file meshio++ wrote with single-precision, 16-bit and byte variables and one with partitioned zones; and, with a TecIO newer than 2018.3 (which refuses to write polygon and polyhedral zones in an SZL file), write such a zone, read it back, and check the written face map against Tecplot's reading, which would turn the refusal of those zones into a reader and a writer.

The readers:

- **1.2.6 Tecplot.** A `.plt` written by `preplot` from the ASCII fixtures (`#!TDV112`), read identically to its `.dat`, and the `.plt` meshio++ now writes opened in Tecplot or checked by `preplot`; binary files of versions 100–105 and 109–111, of which no sample was found (the VisIt suite covers 71, 75, 106–108).
- **1.2.7 Femap.** Element (404) and group (408) records written by Femap 10 and by 12 or later (the public 2401 files hold none); the slot layout of the 13-node pyramid (topology 19); a file meshio++ writes, a multi-set series included, imported into Femap.
- **1.2.8 Patran.** A neutral file exported by ANSA or HyperMesh.
- **1.2.9 Abaqus `.fil`.** A binary run with shells and C3D20R, checked against its `.dat` printout (the truss run TenBarArea is checked); a binary file of a single-precision build (4-byte words), of which no layout description or sample was found, which decides whether the reader and the writer take that width; and a file meshio++ writes, opened in Abaqus.
- **1.2.10 Radioss.** Animation files of the layouts before OpenRadioss (magic numbers `0x5426` to `0x542B`): neither OpenRadioss's tools nor its readers document them. The 16-bit encoding of the nodal normals (the writer leaves them zero: `anim_to_vtk` ignores them and the encoding is undocumented), and a run of OpenRadioss's `anim_to_vtk` on a file meshio++ wrote, time-history lists included.
- **1.2.11 Marc.** A run of Marc itself, including on a deck or a `.t19` post file (a remeshing series included) meshio++ writes (`SIZING`'s fields, one type per `ELEMENTS` line, and the shell and plane-strain default types follow Volume C and Mentat's decks); post files before revision 9 (Marc K7 and earlier, Volume D 2000's PLDUMP layout); Volume A's edge and face numbering, to map edge and face sets (kept as `(cell, number)` field data) onto facets, which also decides whether side regions can be written to decks and post files; the binary `.t16`, read or written natively, which needs Volume D's PLDUMP description of it or a sample file (today it is read only through Marc's PyPost, by the [route](./routes/marc_t16.md)).
- **1.2.12 Ansys `.rst`.** A file written with `/FCOMP,RST,1` or higher (zlib records): `detail/zlib_inflate` is ready, the record framing needs a sample. A harmonic (complex) result file, which no public sample or open reader covers (pymapdl-reader takes cyclic mode pairs only and only DPF reads complex sets), so complex results are neither read nor written; and a file meshio++ writes with element rotations and nodal coordinate systems, read by DPF (pymapdl-reader applies the three nodal rotations in the opposite order, so it agrees only on single-axis angles).
- **1.2.13 LS-DYNA.** A family from LS-DYNA with adaptive remeshing (`NADAPT`), the `d3thdt` time-history database, the cubic and bubble solids (21P, 15T, 20T, 40P, 64), airbag particles and rigid roads (read and written from the manual and lasso-python only: the airbag variable names of a real file, and rigid roads with the full rigid-body velocities, `NDIM = 9`, which the writer leaves out), a real `d3part`, thick shells, and the whole reader against LS-PrePost, with the families and `binout` files (links included) meshio++ writes opened there; whether LS-DYNA writes a ten-node solid's extra nodes once or twice.
- **1.2.14 Nastran OP2.** Random element tables, complex SORT2 nodal tables, CBUSH and CGAP forces, CBUSH real stresses, and NX's solid types 300–303 (read from pyNastran's layouts; no sample). Files meshio++ writes, opened in Femap, Patran or an NX/Simcenter post-processor: the writer produces the MSC dialect only, and the element tables it writes beyond pyNastran's reach (the SORT1 PSD, CRM and ATO random tables, the complex layouts pyNastran does not read) follow the reader's layouts.
- **1.2.15 CalculiX `frd`.** `cgx -b` (CalculiX GraphiX) reading a binary file meshio++ writes; `ccx2paraview` parses the ASCII layout only, so no open tool checks the binary variant beyond meshio++'s own reader and the binary files `ccx` wrote.
- **1.2.16 FEBio `.xplt`.** FEBio Studio or `febio4` opening a file meshio++ wrote: the remeshed series (a mesh section per remeshed step), surfaces with per-surface-node variables, and the compressed states.
- **1.2.17 Nastran HDF5.** MSC's own post-processors (Patran, Simcenter) reading a file meshio++ wrote: its tables follow the column sets of the six MSC Nastran 2020 files, but the `CBUSH`, `CGAP`, `CMASS` and `CONM1` element tables and the `MAT5`, `MAT8`, `MAT9`, `PBARL`, `PBEAML` and `PCOMPG` tables have no sample, so they are not written; a file with them would add them.
- **1.2.18 DOLFINx VTX.** ParaView's `ADIOS2VTXReader` (`tools/gen_vtx_reference.py` drives it) and DOLFINx reading a file meshio++ wrote with several cell types or parts (one block per type and part, with `meshio.shared_points`): both read one cell type per file, so this is meshio++'s own extension of the layout; and a `VTXMeshPolicy.reuse` file (ParaView 6.1 aborts on every step after the first of DOLFINx's own).

### 1.3 Depth in formats already read {#format-depth}

Constructs a registered format's reader refuses, skips or flattens, taken from each format's own page (November 2026) and not from files: **verify each first** against a file the named tool wrote, and add the fixture with the fix. These are neither a missing direction nor an unwritten feature of something read (the [parity decision](#non-goals-and-decisions-taken) covers both); they are parts of the format nothing in meshio++ reads yet, so each lands in both engines, with its *Reading* and *Writing* sections and its conformance declaration.

- **1.3.1 CGNS.** A `Structured` zone raises `ReadError`; `BC_t`, `Family_t` and `ZoneGridConnectivity_t` are not read, so a CFD mesh arrives without its boundary conditions or its zone interfaces; `FaceCenter` and `EdgeCenter` solutions and rind layers are skipped; bases after the first are ignored with a warning; side regions are not written; and ADF files and NGON/NFACE polyhedra need the optional cgnslib build ([CGNS](./formats/cgns.md)). Consumers: Fluent, STAR-CCM+, Pointwise, SU2 and every CFD post-processor. Structured zones expand to hexahedra as `vts` does until 7.6 decides otherwise; boundary conditions and families map onto side regions and their names. Probe: the multi-block and boundary-condition files of the CGNS example set. **M–L**
- **1.3.2 Exodus II.** No global variables, no `NSIDED`/`NFACED` polyhedral blocks, no node-set or side-set variables and no assemblies ([Exodus](./formats/exodus.md)). Consumers: MOOSE, Sierra, Cubit and ParaView's IOSS reader; MOOSE postprocessor values are global variables, and its polyhedral output is `NFACED`. Verify first whether the Python reader already holds any of them. **M**
- **1.3.3 EnSight Gold.** Transient and moving geometry, wildcard geometry names, structured `block` parts, measured (particle) and complex variables are not read; the writer writes one part and no transient series ([EnSight](./formats/ensight.md)). Consumers: EnSight and ParaView reading what Fluent, STAR-CCM+, CONVERGE and OpenFOAM's `foamToEnsight` export. Complex variables wait on 7.1. **M**
- **1.3.4 A series writer for every format that reads one.** MED, CGNS, Tecplot, Gmsh, EnSight and UNV read time steps, but `sequence_write_supports_time` does not list them, so a [sequence](./sequences.md) written to them is one file per step or refused. Each has an in-file timeline its writer could fill. Probe: a three-step `write_sequence` to each, read back with its times. **S each**
- **1.3.5 OpenFOAM.** Gzip-compressed case files (`points.gz`, the default of `writeCompression on`), `polyMesh/sets` (topoSet output) and `lagrangian` clouds are not read ([OpenFOAM](./formats/openfoam.md)); the inflate is in the core already (`detail/zlib_inflate`), and a cloud is a vertex block with point data. **S–M**
- **1.3.6 Gmsh.** `$ElementNodeData` (discontinuous fields, what Gmsh's own post-processing and GetDP write), `$InterpolationScheme` and `$GhostElements` are skipped ([Gmsh](./formats/gmsh.md)). Element-node data needs a home first: 7.3. **S–M**
- **1.3.7 The structured VTK family.** [VTKHDF](./formats/vtkhdf.md) refuses `ImageData`, `RectilinearGrid`, `StructuredGrid`, `OverlappingAMR` and `HyperTreeGrid` by name; the parallel index files `.pvts`, `.pvtr` and `.pvti` have no reader beside `pvtu` and `pvtp`; and `vtr`, `vts` and `vti` fail the round-trip [conformance](./conformance.md) check, because a graded or unstructured mesh has no structured form to be written in. The readers follow the expansion `vts` uses today; the round trip is 7.6's. **M**
- **1.3.8 Decomposed files, read whole without MPI.** The OpenFOAM reader reconstructs a `processorN` case and `pvtu` its pieces; the same reassembly for Exodus's Nemesis spread files (`.e.N.P`) and for a CGNS or MED mesh written one file per rank is not there (verify first). Reopened from the MPI [non-goal](#non-goals-and-decisions-taken), which stays as it is for the library: gathering the pieces of a finished run is file reading, and it is what a user of a parallel solver has in hand. Probe: a four-rank Nemesis set from `decomp`, read as one mesh with `partition:part` cell data. **M**
- **1.3.9 Smaller losses, one fix each.** glTF: morph targets for a transient result (its page calls them a plausible follow-up), so a deformation series is one `.glb` a browser plays; STL: the names of several ASCII `solid` sections as regions, and the binary attribute bytes as a colour array where a writer used them; OBJ: the `vn` indices; PLY: list-typed vertex properties in the core, and `int64` kept; Medit: `Normals` and `Tangents` as point data; `mphtxt`, `med` and `frd`: the side regions and cell data their pages list as dropped; LS-DYNA keyword: 20-node hexahedra. Each is the parity decision's "unwritten feature" if the format can hold it: check that first, and state the ones it cannot on the page. **S each**

### 1.4 New formats {#new-formats}

Each names its consumer, as the admission asks. None was estimated from a file: **verify first** with one in hand, and with the licence of whatever reader the layout is taken from.

- **1.4.1 Fluent case and data.** The `.msh` mesh is read ([`ansys`](./formats/ansys.md)), but not a `.cas`/`.dat` pair nor the HDF5 `.cas.h5`/`.dat.h5` (CFF) that Fluent 2020 and later write by default: a Fluent user cannot bring a solution to meshio++ without exporting it first. The legacy case shares the `.msh` section grammar; the CFF layout is undocumented, and VTK's `vtkFLUENTCFFReader` (BSD) and PyFluent's file readers are the open descriptions†. Consumer: Fluent → ParaView, OpenFOAM or a training set. **M** (legacy), **M** (CFF, with HDF5)
- **1.4.2 PLOT3D.** Multi-block structured grids (`.xyz`/`.x`, `.q`, `.f`), ASCII and Fortran-unformatted, single and double precision, with `iblank`: what OVERFLOW, CFL3D and the NASA turbulence-modelling resource exchange. The record reader is `detail/fortran_records.hpp`; blocks expand to hexahedra until 7.6. **S–M**
- **1.4.3 Coastal and ocean meshes.** The [UGRID conventions](https://ugrid-conventions.github.io/ugrid-conventions/) over NetCDF (a `mesh_topology` variable naming node coordinates and face-node connectivity: Delft3D-FM, SCHISM, FVCOM, D-Flow and xugrid write it, and it is unrelated to the AFLR3 [`ugrid`](./formats/ugrid.md) already read); ADCIRC's `fort.14` mesh with `fort.63`/`fort.64` results; TELEMAC's Selafin (`.slf`, Fortran records). Triangles and mixed polygons with nodal fields and a timeline, all of which the model holds. Consumer: a hydrodynamic run → ParaView, QGIS's mesh layer or a surrogate's training set. Needs a format name that does not collide with `ugrid`. **M** for the three
- **1.4.4 Neuroimaging surfaces.** GIFTI (`.gii`, XML with base64 and gzip arrays, which the VTK XML readers already decode) and FreeSurfer's binary surfaces and per-vertex `curv`/`annot` files. Consumer: head models for TMS and EEG simulation (SimNIBS, Brainstorm, MNE), which mesh these surfaces into volumes; [`tetrahedralize`](./tetrahedralize.md) is the next step of that pipeline. Lowest of the four: take it when a user asks. **S–M**
- **1.4.5 3MF.** Reopened from *Considered, not queued*: print preparation is now a meshio++ workflow ([`repair`](./repair.md), [`offset_surface`](./offset_surface.md)'s thicken and hollow, [`remesh`](./remesh.md), the scan-to-part loop), and 3MF is what slicers exchange, with units, several objects and per-triangle colour where STL has none. The core model is a ZIP container of one XML part; the inflate and the XML reader are in the core, a ZIP directory reader and a deflate-store writer are not. Consumer: PrusaSlicer, Cura, Bambu Studio. Core specification only; the materials, slice and beam-lattice extensions stay out. **M**
- **1.4.6 E57 and LAS/LAZ.** Reopened: scan registration, [surface reconstruction](./reconstruct_surface.md), deviation and the fitting operations shipped, and their input today is `pcd`, `ply` or `xyz`, while a terrestrial scanner writes E57 and an airborne one LAS. LAS is a fixed binary record layout (**S**, native); LAZ needs LASzip or laz-perf (Apache-2.0†) and E57 libE57Format (BSL-1.0†), each an optional dependency behind a named refusal, as TecIO is. Read first; writing follows the parity decision. **M**
- **1.4.7 OpenVDB, through NanoVDB.** Reopened: [`compute_sdf`](./sdf.md), [`voxelize`](./voxelize.md) and [`octree`](./octree.md) produce the sparse level sets and fog volumes it stores, and physics-ML pipelines and Blender consume them. NanoVDB is a header-only, dependency-free reader and writer of its own `.nvdb` layout (verify its licence and whether it reads `.vdb` without the OpenVDB library†). A grid is not a `Mesh`: this is an export of `sdf:distance` on a lattice and an import to a `grid`, the shape `zarr` has. **M, design pass first**
- **1.4.8 Materials and textures.** Reopened: [`parameterize`](./parameterize.md) now produces texture coordinates, which gives OBJ's `.mtl` and glTF's textures and materials something to carry (a baked field as an image, a scan's colour). Limited to passing through what one format read to the other and writing a parameterized mesh with one base-colour image; no material model. **S–M**

## 4. Performance {#performance}

*Admission: a slowdown in a path a user hits, measured or verified in the code, with the shape of the fix named. Every item lands through [landing a performance change](./benchmarks.md#landing-a-performance-change): output byte-identical across backends, thread counts and the baseline digests, SEQ not slower, the ABI tier stated. The section closed in October 2026 with its decisions recorded in the [non-goals](#non-goals-and-decisions-taken); the November 2026 audit reopened it with what those decisions do not cover, and re-proposes none of them except the bounding-volume hierarchy for the distance query (then 5.3.2, since landed), whose stated reason the code no longer supported; the review later that month reopened two more with a narrower shape (4.14, 4.15). The impact estimates come from reading the code and from the tier rows of [benchmarks](./benchmarks.md) and the [XL spike](./spikes.md), not from new measurements: each item's first step is the measurement its probe names.*

- **4.1 The harness first.** The items below are only provable where the harness sees them. The pull-request gate on instruction counts landed ([benchmarks](./benchmarks.md#instruction-count-gate)). **S–M**
  - **4.1.2 The missing rows.** Formats: the result-file readers (`lsdyna_d3plot`, `nastran_op2`, `ansys_rst`, `xplt`). Integrations: the WASM ingestion of a JS mesh, the physics-ML Python layers, and the ParaView and Blender converters. An item below whose operation has no row adds one first, as the landing rules require.
  - **4.1.4 `decimate_volume`'s ballooning star.** Its row runs at tier S only ([benchmarks](./benchmarks.md#decimate_volume-and-conservative_interpolate-rows)): the greedy order collapses onto one survivor until its star holds hundreds of tets, and every attempt on it walks the whole star (24,576 tets take 110 s, the 162,000 of tier M over 17 minutes). Bounding the star changes which collapses happen, so it needs a decision on the operation's output first: a valence cap, or a priority that penalises a growing star, measured for quality against today's output. **M**
- **4.2 The wheels' parallel runtimes.** The Linux wheels build the THREADS backend since v19.1 ([installation](./installation.md)), a `std::thread` pool in the core that needs no runtime library. What is left: one manylinux wheel built in CI, measured against the last SEQ wheel on `bench.py --sizes L --formats vtu,xdmf` and `tools/bench_ops.sh`, its numbers recorded in [benchmarks](./benchmarks.md#a-threads-backend-for-the-linux-wheels); and whether delocate bundles Homebrew's libomp into the macOS wheel (`delocate-listdeps`), which [installation](./installation.md) leaves open. **S**
- **4.5 Operation hot spots.** **M**
  - **4.5.2 `optimize_volume`'s worst-cell smoothing.** The [profile](./benchmarks.md#profiling-optimize_volume) at tier S puts 73% of the row's instructions in `optvol_smooth_worst`, which evaluates every tet of a vertex's star (six cross products and a square root each, `optvol_min_dihedral`) at every line-search probe and every central difference, for the least angle; the comparison sorts of the face and edge tables are 7.4% together, the passes that use them (edge removal, multi-face removal, 2-3 flips) 21%. The `acos` that was 31% of the row is now skipped where it cannot give the least angle. What is left is algorithmic: per probe, evaluate only the tets whose angles lie in the active band, with an argument that the others cannot become the least within the step, inside the determinism pins of [optimize_volume](./optimize_volume.md).
- **4.8 HDF5.** The appended rows of a VTKHDF time series are compressed in parallel since 5.8.1 ([benchmarks](./benchmarks.md#appended-rows-deflated-in-parallel)). **M–L**
  - **4.8.2 The library lock around library calls only.** The parallel gzip of the HDF5 helpers, whole datasets and row windows alike, and the VTKHDF reader's mesh assembly run with the lock given up ([benchmarks](./benchmarks.md#compression-outside-the-library-lock)): four gzip VTKHDF writes at once are 2.8x faster, four reads 1.5x. What is left: the writers hold the lock for their whole body (`formats/vtkhdf.cpp`, `formats/xdmf.cpp`), so the arrays they build between library calls (offsets, types, connectivity) are prepared under it. Giving it up around the VTKHDF writer's cell tables (`vtkhdf_collect`) was tried and measured no change on four concurrent writes of a 125,000-hexahedron box (0.63 s either way): the deflate was the bulk of the locked time. Reopen it on a profile that shows the preparation dominating. The lock's invariant, no two threads inside the libraries, is unchanged. **S–M**
- **4.9 WASM: bulk copies of JS arrays.** The bindings convert JS arrays with `emscripten::vecFromJSArray` (34 calls in `bindings/wasm/js_bindings.cpp`), element by element through embind, and copy the result again into the `NDArray`. A `typed_memory_view` over the destination, filled by the typed array's `set` (or `convertJSArrayToNumberVector`), writes straight into it. Verify first against emsdk 6.0.3's `val.h`. Probe: a Node script that writes a 1M-tetrahedron JS mesh with `writeMesh`. **S**
- **4.11 Sequences.** The [sequence driver](./sequences.md) keeps at most one mesh alive, by design. An opt-in read-ahead (`Prefetch: 1`, reading step k+1 while step k computes, with the cost of two meshes stated); fields-only reads for the later steps of the formats with an in-file timeline (XDMF, Exodus, VTKHDF, d3plot), which re-read the geometry at every step today; and no second read of each step in the PhysicsNeMo pairing. **M**

- **4.12 Profile-guided optimisation of what is released.** Link-time optimisation was measured and left opt-in because counts moved both ways ([benchmarks](./benchmarks.md#link-time-optimisation)); a profile was never tried, and it is what tells the compiler which of those ways matters. Train the release CLI binaries and the wheels on the harness's tier M rows (`-fprofile-generate`, then `-fprofile-use`, with and without LTO; `/GENPROFILE` on MSVC), and measure with `tools/bench_instructions.py` and wall time. Output must stay byte-identical (`-ffp-contract=off` holds), so the determinism check is the gate. The default build is untouched: this is a release-pipeline change. **M, measure first**
- **4.13 A 64-bit WebAssembly build.** Several decisions rest on the 32-bit heap: the viewer's applies are not cached because a second copy of the mesh shares 4 GB with MEMFS, and the browser's ceiling is a mesh of a few tens of millions of cells. Memory64 has shipped in Chromium and Firefox; verify first the emsdk pin's support (`-sMEMORY64`), embind's 64-bit `size_t` mapping to `BigInt` (which the typed-array channel must hide), Safari's status and the measured slowdown of 64-bit pointers. If it holds, a third artifact beside lean and full, chosen by the loader, and the [caching decision](#non-goals-and-decisions-taken) can be measured again on it. **M, verify first**
- **4.14 An in-place `transform`.** Reopened from the decision against dropping `transform`'s copy, which stands for `transform` itself: its result aliases nothing, and that is its contract. An explicit second entry point is an addition, not a change: `transform_inplace(mesh, ...)` in C++ and C, `inplace=True` in Python where the points are owned and writable (and a named refusal where they are a borrowed view), and the pipeline using it between steps, where the intermediate mesh is never observed. Measure first on the `pipeline_*` rows and the sequence driver, where a transform per step copies the connectivity it does not touch; if the copy is under a few percent of those rows, record the number and close it. The same question applies to `flip_normals`, `mirror` and the data-only operations. **S–M, measure first**
- **4.15 Vector kernels behind runtime dispatch.** Reopened from the decision against SIMD intrinsics and `-march` flags, whose reason was portability across wheels, WASM and the release binaries, with "revisit only if the harness shows a kernel dominating". Both halves have moved: the per-row profiles now exist ([profiling](./benchmarks.md#profiling-optimize_volume)), and function multi-versioning (`target_clones`, or Highway's dynamic dispatch) compiles the AVX2 and NEON variants into one portable binary, with WASM SIMD as a build flag of the full artifact. Measure first which rows spend their time in loops that vectorise: the float-to-text and text-to-float paths, base64 and byte swapping in the VTK XML and binary readers, the BVH's box tests, the centroid and bounding-box gathers. A kernel qualifies only if its vector form is bit-identical to the scalar one (integer and byte kernels are; floating-point reductions are not, and stay scalar), so the determinism check still holds on every machine. **M, measure first**

## 7. Data model {#data-model}

*Admission: something files hold and users ask for that `Mesh` has no place for, so that every format carrying it drops it, splits it or hides it in a naming convention. Each item changes `NDArray` or `Mesh`, so it reaches every mesh backend (MESHIO, NATIVE, KRATOS), every binding and the [ABI](./abi.md): each starts with a design pass in the manner of the [long-run spikes](./spikes.md), which decided the last two questions of this kind (NURBS as a side channel; the isogeometric layer beside `Mesh`), and the outcome may again be "a convention, documented and tested" rather than a new type. The items are independent; the order is by how many shipped formats lose data for want of each.*

- **7.1 Complex values.** `DType` has the real floats and the integers of 8 to 64 bits. Harmonic, modal and frequency-response results are complex: Ansys `.rst` harmonic sets are neither read nor written, OP2's complex tables and UNV's complex datasets are split into `_real`/`_imag` or magnitude and phase by per-format conventions that do not agree, and EnSight's complex variables are skipped. Design pass: a `complex64`/`complex128` dtype (NumPy, HDF5 compound, Julia and R have native forms; C, Fortran and WASM need a stated layout) against one documented `:re`/`:im` naming convention with helpers to pair and split, applied by every reader. The convention is days and no ABI; the dtype is a Tier A change. Probe: one complex OP2 table and one complex UNV dataset read to arrays of the same shape and naming. **S** (convention) or **L** (dtype), design pass first
- **7.2 Strings and booleans.** No string dtype: Exodus QA and info records, MED and CGNS descriptors and per-entity names live in per-format side structs or are dropped, and `field_data` holds numbers only. No boolean: masks widen to `uint8` and come back as integers. Design pass: whether `field_data` takes UTF-8 strings (a ragged byte array with offsets, which `NDArray` already expresses for polyhedra) and whether a mask is a dtype or a documented `uint8` convention; verify first what Python's `Mesh` already accepts that the core rejects. **M, design pass first**
- **7.3 Integration-point data.** Gauss-point results are the primary output of a structural solver, and they arrive as cell arrays of shape `(cells, points × components)` under each format's own name and point order (d3plot, Abaqus `.fil`, MED's ELGA fields, GiD, `.rst`). No operation knows the array is per integration point: `interpolate`, `data_average` and `tessellate` treat the columns as components, and converting MED to GiD cannot map one rule's order onto the other's. Design pass: a third data location beside `point_data` and `cell_data` (with the rule named per block, sharing 2.4.3's quadrature tables) against a metadata convention on cell data (`meshio:integration_rule`), and the two operations that make it useful: extrapolation to nodes and averaging to cells. Gmsh's `$ElementNodeData` (1.3.6) is the same shape with the nodes as the points. **L, design pass first**
- **7.4 Data on facets and edges.** Side regions hold membership only; a value per boundary face (a heat flux, a pressure load, a wall shear stress, CGNS `FaceCenter` and Exodus side-set variables of 1.3) has no home except a duplicated block of surface cells, and edge data (Nédélec degrees of freedom, a wire's current) none at all. Design pass: values on a side region's `(cell, local facet)` rows, which every backend already stores, against the lower-dimensional blocks used today, stated as the convention. **M–L, design pass first**
- **7.5 Hierarchy.** Regions are flat, with nesting spelt as `/` in the name; assemblies of parts and instances (Abaqus, VTKHDF's `Assembly`, `.vtm`, CGNS families, Exodus assemblies, USD prims) flatten to that on read and cannot be rebuilt on write, and the KRATOS backend drops the nesting. Design pass: whether the `/` convention plus a small tree of names in `field_data` is enough to round-trip the formats named, before any new type. **M, design pass first**
- **7.6 Structured grids that stay structured.** A `vti`, `vtr`, `vts`, CGNS structured zone or PLOT3D block is expanded to explicit hexahedra: eight indices per cell for what three integers describe, and nothing can be written back as structured, which is why `vtr`, `vts` and `vti` fail [conformance](./conformance.md). The physics-ML [grids](./grids.md) are the opposite case, structured in Python with no `Mesh` at all. Design pass: an implicit-connectivity block kind (dimensions, and origin and spacing, axes or points) that `CellView` iterates without materialising, against a `meshio:structured` annotation on an ordinary block that the structured writers honour and operations invalidate. The annotation is the smaller step and closes the conformance failures; the block kind is what 10⁸-cell voxel data needs. **M** (annotation) or **XL** (block kind), design pass first

## 8. Operations {#operations}

*Admission: an operation a mesh workflow reaches for that the core's own kernels nearly give, found by reading each operation's page for what it refuses and by comparing the surface with what users of comparable libraries call. Not the algorithms the [non-goals](#non-goals-and-decisions-taken) leave to backends. Each lands on every surface as `AGENTS.md` says. All but 8.1 were estimated from the `doc/` pages: verify first that no existing operation's option already does it.*

- **8.1 Surface booleans through a backend.** Reopened from the non-goals, which record why a native `mesh_boolean` was not queued: the [spike](./spikes.md#surface-booleans-formerly-roadmap-7-8) was exact in topology and failed on rounding its output and on coplanar contact, the two things a dedicated library spends its complexity on. The same non-goal says the answer to such an algorithm is an optional backend, and the provider registry that makes one cheap arrived after the spike was scoped. [Manifold](https://github.com/elalish/manifold) (Apache-2.0†, C++, guaranteed-manifold output from manifold input, coplanar faces handled by symbolic perturbation, a WebAssembly build of its own) was not measured; OpenCASCADE's mesh-independent booleans are the route for fitted solids and stay there. First step, before any API: build Manifold as a provider behind the spike's harness and run the synthetic and Thingi10K [boolean corpus](./spikes.md#surface-booleans-formerly-roadmap-7-8) through it, on the spike's own criteria (watertight, free of self-intersections by `find_intersections`, the volume identities, the coplanar classes). If it passes: `mesh_boolean(a, b, op)` as a provider-backed operation that refuses by name where the provider is absent, an add-on wheel in the `meshioplusplus-{occt,netgen,mmg}` pattern, cell data carried through Manifold's triangle provenance, and with it the two things parked behind booleans: CSG of the [primitives](./primitives.md#not-generated) and a scan cut by a fitted solid. If it fails, the measured reason joins the spike's and the non-goal stands. **M, measure first**
- **8.2 Smooth subdivision.** [`refine`](./refine.md) splits at midpoints and [`subdivide`](./subdivide.md) is polyhedral; neither moves a point. Loop (triangles) and Catmull–Clark (quads and polygons), with creases on feature edges and boundaries, are the standard way to turn a coarse control mesh into a smooth dense one, and `fit_cad`'s patch network already evaluates Catmull–Clark limits internally. An option of `refine` (`scheme="loop"`) or its own verb; point data interpolated with the same masks. **M**
- **8.3 Ray and nearest-point queries.** The triangle BVH (`detail/tri_bvh`) answers nearest-triangle, winding-number and ray queries for `distance_to_surface`, `thickness`, `octree_mesh` and `boundary_layer`, and none of it is public: a user who wants the first hit of a bundle of rays (a line of sight, a sensor model, a projection along a direction) or the cells containing a set of points builds their own. A `SurfaceQuery` handle that owns the BVH (`nearest`, `ray_first_hit`, `ray_all_hits`, `contains`) and a `locate_points` for volume cells, batched and parallel, with the handle's lifetime stated on each binding. **M**
- **8.4 Mass properties.** [`compute_stats`](./stats.md) and [`measure`](./measure.md) give area, volume and centroid; the inertia tensor about the centroid, the principal axes and moments and the radius of gyration of a closed surface or a volume mesh, per region and with a density field, are one more moment of the integrals already taken (the divergence-theorem form for surfaces, quadrature for cells). **S**
- **8.5 Elevation beyond order 2.** [`convert_cells`](./convert_cells.md)'s elevate refuses the full-Lagrange second-order cells (`quad9`, `hexahedron27`) and every order above 2, while the readers and `tessellate` hold cells to order 10 and `mesh_cad_surface` generates order 3. Elevation from order p to q by interpolating the geometry at the target's nodes (2.4.3's bases), which also gives order reduction other than `linearize`, and with `project_to_cad` a curved mesh of any order from a linear one. **M**
- **8.6 Repeated and mixed green refinement.** [`refine`](./refine.md#what-is-not-implemented) names two limits. A later selective pass refines the green (transitional) cells directly rather than restoring them to their parent first, so repeated passes over one region degrade quality without bound: [`undo_green`](./undo_green.md) exists as a separate operation, and the hierarchy arrays (`refine:cell_id`, `refine:parent_id`, `refine:level`) are what an automatic undo-then-refine needs, which is what an adaptive loop driven by [`error_size`](./error_size.md) calls every iteration. And mixed-type green (a quadrilateral closed into triangles, a hexahedron into pyramids) is not offered, because one input block would emit several output blocks, which the cell maps' *first child within the corresponding output block* contract cannot express: that half needs the map shape decided first, with every binding's. **M** (undo before refine); **M–L, design pass first** (mixed)
- **8.7 Partitioning.** [`partition`](./partition.md) has the space-filling curve natively and KaHIP as an optional backend; METIS and Scotch are reached only as graph files written for an external run. (1) Both as partition providers in the registry's pattern (METIS is Apache-2.0 since 5.1.1†, Scotch CeCILL-C†), since they are what solvers and their users already trust and compare against. (2) Connected parts: KaHIP's `--connected_blocks` is not reachable through the `kaffpa` C interface, as the page records; a native post-pass that reassigns the smaller components of a disconnected part to the neighbour they share most facets with gives the same guarantee for every method, the space-filling curve included, at a stated cost in balance. **S–M**
- **8.8 The isogeometric layer's open list.** [IGA](./iga.md) marks as not yet: Bézier extraction (the operators an IGA code assembles with, and the bridge to the VTK Bézier cells the readers already hold), knot removal, public second derivatives, and closest-point projection onto a patch (which `project_to_cad` does for a B-rep through other code). **M**
- **8.9 Point-cloud conditioning.** Scans arrive with outliers, uneven density and no normals; `point_normals` and `reconstruct_surface` exist, and RANSAC rejects outliers inside the fits, but nothing cleans the cloud itself: statistical and radius outlier removal, voxel-grid and Poisson-disk downsampling as operations on vertex blocks (verify first against [`point_budgets`](./point_budgets.md), which subsamples for training). **S–M**
- **8.10 Units and coordinate systems.**
  - **8.10.1 Units of fields.** A length unit travels in `field_data["meshio:length_unit"]`; a field has none, though MED and CGNS can hold one per array (MED's is read into a side channel) and a conversion between a millimetre-tonne-second deck and an SI post-processor is where results go wrong silently. Design pass: a `meshio:unit:<array>` convention read and written by those formats, and a `convert_units` that scales the mesh and every array with a known dimension, refusing the rest by name. **M, design pass first**
  - **8.10.2 Georeferencing.** A coordinate reference system as metadata (an EPSG code or WKT string in `field_data`) carried by the formats that have one (1.4.3's, LAS, glTF's and 3D Tiles' conventions), and reprojection through PROJ as an optional dependency of `convert_coordinates`; only if 1.4.3 or 1.4.6 lands, since nothing read today is georeferenced. **S–M**

## Non-goals and decisions taken

Recorded so they are not re-proposed as gaps. A decision is reopened when what it rested on has changed, and then it is narrowed here, with the date and the number of the item that took it up; the November 2026 review read each against what has shipped since. It reopened five (surface booleans through a backend, 8.1; decomposed files read without MPI, 1.3.8; the `zarr` and `pmsh` stores in the core, 3.15; an in-place `transform`, 4.14; vector kernels behind runtime dispatch, 4.15) and four formats of *Considered, not queued* (1.4.5 to 1.4.8), and left the rest as they stand: the reasons recorded for the native constrained tetrahedralisation, NURBS as an entity kind in `Mesh`, Kokkos device execution, link-time optimisation by default (though a profile was never tried: 4.12), solver-coupled learning, contact mechanics, the copyleft codes and the CAD modeller have not moved.

- **Every registered format reads and writes, in both engines** — decided in October 2026, when the parity tier closed; it reversed the earlier non-goals that kept result files and the export-only formats read-only. A format reads and writes in the C++ core and in its Python twin, so it reaches every surface (C, Fortran, Julia, R, WASM, both CLIs and the MCP server's format capabilities); a core-only path is unreadable from the surfaces that have no fallback, a Python-only one has no twin to check it against. `read(write(m))` equals `m` within the limits the format itself imposes (single precision, a cell type it has no slot for, a concept it cannot express): a loss that is a fact of the format is stated on its page and in the [conformance](./conformance.md) notes, and one that is only an unwritten feature is a gap that reopens a *Reader and writer parity* section here. A new format or direction lands as `AGENTS.md` says (native writer registered in `registry.cpp`, parameters through `WriteOptions`, the Python twin behind `core_declined`, the arrays a reader returns written back under the same names, a `SPEC` declaration and a *Writing* section). The exemptions are recorded in `tests/python/conformance_spec.py` (`READ_ONLY`, `ENGINE_EXEMPT`, `PARTIAL_ENGINE_EXEMPT`) and checked by `test_conformance.py`:
  - **Pure 2-D drawings.** `svg` and `tikz` draw a mesh rather than store it: their readers parse only the structure meshio++'s own writers emit, return the geometry as planar (`z = 0`) and warn once per read that depth, and whatever else the drawing could not hold, is lost; anything else in the file is a `ReadError` naming the construct, never a guess.
  - **`ansys_rst_cyclic`**, which is not a file but the full rotor a cyclic `.rst` expands to; its write side is `ansys_rst`'s cyclic option. **`step` and `iges`** outside a build with OpenCASCADE: reading a CAD model means a CAD kernel, which the `meshioplusplus-occt` add-on wheel (since v18.0.0) and the release binaries carry and a source build finds when it can ([skin to CAD](./cad_fit.md), [STEP](./formats/step.md#reading)); on WASM the lean build is the exempt one, and the [full build](./wasm.md#lean-and-full-builds) carries the kernel.
  - **One engine only, by decision**: GiD (gidpost and its Gauss points are implemented once, in the core), the OpenFOAM case writer and its zone, field and multi-region reading, CGNS's face-based polyhedra (the writer's winding repair is a discrete branch two implementations could resolve differently), the CAD readers, and the `step` writer's merged and fitted faces (`faces="planar"`/`"fitted"`, with `segment`'s primitive method that feeds them: loop walking, vertex snapping and the primitive growth are discrete branches too, so the twin writes `faces="facet"` byte for byte and nothing else); the Python entry points raise naming the missing core rather than guess.
- **What the parity tier left as facts of the format**, each stated on the format's page and in the conformance notes, none an unwritten feature:
  - **`nastran_op2`** writes the MSC dialect only (32-bit little-endian words, SORT1 tables). 64-bit words, big-endian files, NX/Simcenter's interlaced table names and double-precision GRIDs are read and detected, not written: a post-processor reads the MSC dialect with no flags, and whether NX accepts it is a vendor check ([§1.2.14](#awaiting-a-licensed-run)). The random PSD, CRM and ATO tables are written as SORT1 magnitudes, as the reader reads them (MSC writes them SORT2, and pyNastran reads only the RMS and NO ones in SORT1); no SORT2 pivot is written. Elements on scalar points (`CELAS3`/`CELAS4`, `CDAMP3`/`CDAMP4`, `CMASS3`/`CMASS4`) and `CBUSH1D` and `CBEND` have no cell type — `Mesh` has no scalar-point entity to hang them on — and are skipped with a warning.
  - **`nastran_h5`** writes a table only where an MSC sample fixes its layout: `CBUSH`, `CGAP`, `CMASS` and `CONM1` elements, and `MAT5`, `MAT8`, `MAT9`, `PBARL`, `PBEAML` and `PCOMPG` values, have no table in the six MSC Nastran 2020 files at hand, so the elements are left out and the values go on the plain cards, each with one warning; the OP2 file holds them.
  - **`lsdyna_d3plot`** leaves the rigid roads' full rigid-body velocities (`NDIM = 9`) out of the state, and writes an airbag variable under a title-case name, since the names of a real file are in no manual available.
  - **`radioss_anim`** writes the nodal normals as zeros: `anim_to_vtk` ignores them and their 16-bit encoding is undocumented.
  - **`abaqus_fil`** writes 8-byte words only, the reader's width; a single-precision build's 4-byte layout has no description or sample.
  - **`ansys_rst`** has no complex (harmonic) results, read or written: no public sample or open reader covers them, and DPF alone reads them. The nodal coordinate systems are written as `ansys:node_angles` and agree with pymapdl-reader only for single-axis angles, since it applies the three turns in the opposite order.
  - **`xplt`** writes a per-surface-node variable as `FMT_NODE` in surface order, where the reader averages the values a node on two surfaces has into one point value, which both surfaces then write.
  - **`marc` and `marc_t19`**: edge and face sets stay `(cell, number)` field data and side regions are dropped, since mapping them to facets needs Volume A's numbering ([§1.2.11](#awaiting-a-licensed-run)); the Herrmann, bubble and generalized-plane-strain types come back as the default type of their shape, and a deck holds no data arrays.
  - **`szplt`** does not write polygon and polyhedral zones: TecIO 2018.3, the newest source available, refuses them in an SZL file, so the reader refuses them by name too and the face-based zones stay with the `.plt` and ASCII readers. Partitioned output is for tetrahedron and brick zones of a static file only (TecIO's own limit), and a series is written whole.
  - **`vtx`**: DOLFINx and ParaView read one cell type per file, so a file of several cell types or parts is meshio++'s own extension of the layout.
- **Generators the primitives leave out** — recorded when roadmap §3.1 closed (October 2026), with the [parametric primitives](./primitives.md#not-generated): generators driven by a user callback (no callback crosses the flat ABI; numpy users build `Mesh(points, cells)` directly, and [`isosurface`](./isosurface.md) on a `grid` covers implicit shapes); scanned or modelled assets (the bunny, the teapot, the bracket fixture — data rather than parameters, each under its own licence); and CSG combinations, under the volume-meshing non-goal below (surface booleans were reopened as a spike and kept out on its measurements, [findings](./spikes.md#surface-booleans-formerly-roadmap-7-8)) — two-body interface and contact fixtures are primitives placed with `transform` and joined with `merge`.
- **MPI in the library** — none planned ([C++ API](./cpp_api.md)); `partition`'s ghost layers produce the halo an MPI assembly in the owning application needs. ParMmg, MMG's MPI layer, is excluded with it. Narrowed in November 2026: reading the files a parallel run left, one per rank, into one mesh needs no MPI, as the OpenFOAM and `pvtu` readers show, and is queued for the formats that lack it as 1.3.8.
- **Solver-coupled physics-ML** — assembled solver residuals, adjoints and Sobolev training, co-simulation, active-learning *labeling*, adaptive remeshing driven by a surrogate, and MPI model-part gathering. Every one needs a live solver (an assembly routine, its tangent, its communicator) and meshio++ has no notion of a discrete system; they belong in the application that owns the solver, the division [Symbolic and physics](physicsnemo/symbolic_and_physics.md) describes.
- **The Python-only layers stay Python** — `pmsh`, `zarr`, `cae` and `usd`, and the physics-ML surface (grids, point budgets, proximity graphs, datasets, training) are export targets and tooling for a training pipeline, registered in Python rather than the shared C++ registry. A core kernel they call (the neighbour search) does not change that; `tessellate` moved to the core ([tessellation](./tessellation.md)) because the native CLI and the flat bindings needed it, and its `Tessellation` helpers stay Python. Narrowed in November 2026 for the two stores a dataset is written to: reading `zarr` and `pmsh` in the core, so the browser, the flat bindings and the native CLI open what Python wrote, is queued as 3.15 behind a design pass; `usd`, `cae` and the physics-ML surface stay as decided.
- **Polyscope in the release CLI executables** — excluded deliberately, so `view`/`screenshot` there report the build flag rather than opening a window ([viewer](./viewer.md)): the executable stays free of OpenGL, GLFW and X11. Narrowed in November 2026, once v18.0.0's plugins made it possible: a Polyscope plugin loaded beside the executable is queued as 3.8.2.
- **General volume meshing algorithms as native operations** — constrained tetrahedralization of a domain, hex-dominant meshing and general hex meshing from a CAD-like boundary, boolean/CSG, boundary-layer inflation and quadrangulation are each a library in their own right. (Narrowed in November 2026: geodesic distance, once listed here, is not one, since the heat method needs only the P1 operators and the sparse solver the core has, and shipped as [`geodesic_distance`](./geodesic.md); surface booleans were measured by a spike in November 2026 (exact in topology, but rounding its output to doubles left most curved results self-intersecting and coplanar contact unhandled, so no native operation is queued: [findings](./spikes.md#surface-booleans-formerly-roadmap-7-8), though the backend route this non-goal names was not measured for them and is, since the same month, 8.1); and v18.0.0's provider registry is the optional-backend route below, which external meshers and field-aligned quads now take as installed programs: [`tetrahedralize`](./tetrahedralize.md#external-meshers-tetgen-and-gmsh)'s TetGen and Gmsh and [`remesh_quads`](./remesh_quads.md)'s QuadriFlow and Instant Meshes.) The answer is an optional backend (the KaHIP pattern), not a native implementation: volume domain meshing reaches meshio++ through [`tetrahedralize`](./tetrahedralize.md) (v17.23.0: natively by its octree backend, the skin fitted by isosurface stuffing, and exactly by Netgen, the skin kept) and adaptation through MMG ([MMG backend](./mmg.md)); boundary-layer inflation reopened through a design pass for layers grown from a surface ([`boundary_layer`](./boundary_layer.md), v17.23.0), the volume behind them filled by `tetrahedralize`; and quadrangulation reopened for CAD surfaces only (recombination of `mesh_cad_surface`'s own triangles by a matching, v17.23.0), field-aligned remeshing through installed programs ([`remesh_quads`](./remesh_quads.md)). A native constrained tetrahedralisation stays out: `orient3d` and `insphere` exist and the Delaunay kernel is short (Bowyer 1981, Watson 1981), but boundary recovery with Steiner points is where TetGen and the exact constructions spend their complexity (George, Hecht and Saltel 1991; Si and Gärtner 2005; Shewchuk 2008; Si 2015; Diazzi et al. 2023). Reopen it when a design pass shows a native recovery on the core's predicates within a stated size, measured against `tetrahedralize`'s probes and its Thingi10K sample. Two exceptions are in scope. Surface triangulation of a CAD model is native since v17.13.0 ([`mesh_cad_surface`](./mesh_cad.md)): the robust predicates it needs are Shewchuk's, public domain and a few hundred lines, and a planar constrained Delaunay triangulation per face is small enough to own; this reverses the earlier decision that dropped the queued Delaunay item, for surfaces and the plane only. Lattice generation is the other: [`voxelize`](./voxelize.md), [`octree`](./octree.md), [`remesh_volume`](./remesh_volume.md)'s isosurface stuffing and the octree volume mesher [`octree_mesh`](./octree_mesh.md) (stuffed tetrahedra and the all-hexahedral octree dual, uniform or graded, [plan](./octree_mesh_3d_plan.md)) are index arithmetic over a signed distance on a lattice, followed by projection and untangling, with no predicate to make robust.
- **A declared tolerance deciding degeneracy in `mesh_cad_surface`** — `model_tolerances` widens where uses start, how far corners and uses may lie apart and which trims pair, but whether an edge is degenerate (a pole) stays on the global tolerance: an edge shorter than a generous declared tolerance is real geometry, and collapsing it would change the model rather than accept its gaps ([item 21](./mesh_cad.md#how-it-works)).
- **What mesh generation leaves, by decision** — recorded when roadmap §6 closed (October 2026); [mesh generation](./mesh_cad.md) and its [measured-and-parked notes](./mesh_cad.md#measured-and-parked) hold the numbers:
  - **No small-angle bound stated on a curved face.** Corner lopping's bound (Pav and Walkington 2005) is the plane's; on a curved face `lop_corners` reports the angles it reaches and termination stays `max_points` and the insertion-radius declines. Stating one would need the paper's argument redone in the surface's metric.
  - **A pinched boundary stays declined** by the flattening of 6.4.4: splitting the pinch into one vertex per wedge makes the coarse mesh manifold, but the face's loops pair the pinch's edges otherwise than the wedges do, so each loop would have to be re-stitched through both copies.
  - **Field-aligned quads stay with backends.** Recombination of the mesher's own triangles leaves its worst quads at poles (0.12 on the sphere at `h = 0.1`); field-aligned remeshing is Instant Meshes (BSD-3), QuadriFlow (MIT) or QuadWild (GPL, excluded), each a library of its own. Since v18.0.0 that pattern is the provider registry, and [`remesh_quads`](./remesh_quads.md) runs an installed QuadriFlow or Instant Meshes as a separate process (0.25 to 0.58 on the same sphere, by seed); a linked add-on wheel extracting their solvers stays unqueued until a user needs them in the wheels or the browser. The core's cross field and quad layout (`detail/cross_field`, `detail/quad_layout`) stay `fit_cad`'s.
  - **Curved boundary layers: linearize first.** `boundary_layer` takes linear triangles and quads; a `triangle6` or `quad9` surface is linearized first. Growing curved layers needs a Bernstein bound on a prism's and a hexahedron's Jacobian (the tensor bound `detail/curved_quad` has for quads, raised a dimension) to keep "no cell is written folded" true, and its mid-edge nodes' directions; no model has asked.
  - **Mesh-generation corpora with non-commercial terms stay out.** The Fusion 360 Gallery (Willis et al. 2021) permits use for non-commercial research only and asks its users to indemnify Autodesk, which an MIT project's published measurements cannot accept.
  - **No numpy twin** of `mesh_cad_surface`, `triangulate_polygon_2d` or `tetrahedralize`: a second implementation of the predicates and the triangulation could not stay byte-identical, the precedent of [`remesh_volume`](./remesh_volume.md).
  - **Healing the model.** Sewing gaps, removing sliver faces or rebuilding pcurves changes the CAD model, which is the CAD kernel's work; `mesh_cad_surface` meshes around defects without writing them back. Narrowed in November 2026: the CAD kernel is reachable through the provider registry, so healing at read time, before the B-rep reaches the mesher, is the STEP and IGES readers' `heal` option ([STEP reading](./formats/step.md#reading)); `mesh_cad_surface` itself still never heals.
  - **Code from Triangle, TetGen, Gmsh, CGAL's GPL packages or Blossom V**, under any route other than a separate process: their licences ([THIRD_PARTY_NOTICES](https://github.com/loumalouomega/meshioplusplus/blob/main/THIRD_PARTY_NOTICES.md)). Geogram's constrained tetrahedralisation is in that list too: it creates TetGen's AGPL Delaunay kernel. The separate-process route is `tetrahedralize(backend="tetgen")` and `backend="gmsh"` ([external meshers](./tetrahedralize.md#external-meshers-tetgen-and-gmsh): installed executables behind named tet-mesher providers, never linked), and the rule keeps the gmsh Python API, which runs in-process, out of the interop bridges (3.10).
  - **A native parallel Delaunay kernel** in the style of HXT (Marot, Pellerin and Remacle 2019): it is the fast path of a 3-D mesher the core does not have, and the 2-D triangulation of one face is small enough that faces in parallel already use every thread on a real model.
  - **Advancing-front surface meshing as a second native mesher** (Lo 1985, Peraire et al. 1987, Löhner and Parikh 1988, Schöberl 1997): smoother gradation, but its robustness rests on the front's intersection tests that the Delaunay route avoids, and two native meshers would double what must stay byte-identical. Frontal point placement inside the Delaunay mesher (Rebay 1993, Tristano, Owen and Canann 1998) is the alternative if the varying metric's circumcentres leave triangles poorly aligned on strongly stretched faces.
- **Contact mechanics itself** — penalty or mortar assembly, friction and contact search in time need a live solver. meshio++ detects and exports the interface of one snapshot ([interfaces and contact](./region_adjacency.md)); the contact algorithm belongs in the application that owns the solver.
- **MMG in the base wheel and in the native CLI executables** — it is LGPL-3.0 (GPL-3.0 with the ELAS that `move` needs) and an external install, so the native backend is linked dynamically into builds that opt in, and its operations throw by name where it is absent ([MMG backend](./mmg.md#licence)). v18.0.0 narrowed this for Python: the `meshioplusplus-mmg` add-on wheel ships it, built without ELAS, beside the MIT base wheel ([installation](./installation.md#what-the-pypi-wheels-contain)); the same split for the native CLI, a plugin beside the executable, is queued as 3.8.1. Its WebAssembly half was lifted for the full artifact when roadmap 3.1.8 closed (October 2026): MMG is linked there statically, without ELAS, under the LGPL-3.0 relinking terms the artifact's notices state ([WebAssembly](./wasm.md#mmg-in-the-full-artifact)); the lean artifact keeps none.
- **What the full WebAssembly build leaves, by decision** — recorded when roadmap §5 closed (October 2026); [fit CAD's measured and parked notes](./fit_cad.md#measured-and-parked) hold the numbers and the reopening conditions:
  - **Constraints beyond the coaxial, right-angle and equal-radius ones.** Parallel but offset axes are different surfaces, and a bolt circle or a plane at another angle needs the pattern known to the pass, so `constrain_primitives` stays exact only where it is exact.
  - **G1 at valence 5 and 6 beyond the sweeps' reach.** The refine-before-discard step of the patch network brings the largest G1 angle down on the Catmull-Clark fixtures ([limitations](./fit_cad.md#limitations)); a construction that holds G1 exactly there (Loop and Schaefer's full scheme, or G-splines) is not implemented.
  - **Genus-one-and-more homology cuts.** The layout's pieces are triangle groups, so a cut along both sides of a loop has no representation; that is a change to the layout's partition, not a bounded experiment.
  - **THB stays experimental**, behind its knot-line fallback: a rung whose hierarchical fit misses its target falls back to knot lines, so `"thb"` never leaves as facets a patch `"knots"` fits.
- **KaHIP in the lean WASM build, ADIOS2 and TecIO in either WASM build** — KaHIP ships only in the full artifact (serial kaffpa, built by `build-wasm-deps.sh --full`; a graph partitioner would bloat every consumer's bundle, so the lean pair keeps the SFC method with `"kahip"` throwing by name as the contract); no one has made a wasm build of ADIOS2 (`vtx`); TecIO's redistribution terms keep `szplt` out. Each reports by name in the lean and the full artifact alike ([what stays out](./wasm.md#what-stays-out)).
- **zstd/lz4 codecs in the lean WASM build** — the lean artifact keeps zlib as its only block codec; the full one (v17.2.0) links zstd, lz4 and bzip2. A zstd-compressed VTK XML file is a meshio++ extension VTK itself has no compressor for, so vtk.js does not read it; the second reader of a zstd file is meshio++'s native and Python ones. **Memory mapping and the Kokkos backend under Emscripten** — CMake refuses the Kokkos backend under Emscripten, and there is nothing to map inside MEMFS.
- **Single-file output for DOLFIN, TetGen and EnSight from WASM**, or lifting DOLFIN's simplicial restriction — both are facts of the formats; `writeMesh`'s written-paths return value (v11.2.0) is the fix for the bookkeeping they cause.
- **NURBS patches and trims as a second entity kind inside `Mesh`** — decided with the [isogeometric layer](./iga.md) (v16.43.0, [findings](./spikes.md#the-isogeometric-layer)): a model (`NurbsInfo`, `BrepInfo`) stays a side channel beside the mesh, with its own evaluate, refine and sample operations, because a first-class entity kind needs patches, control nets, weights, knots and trimming curves in `Mesh`, every mesh backend (MESHIO, NATIVE, KRATOS), every binding and the C++ ABI: a major version for a gain the three operations already give. Reopen it when an operation must act on patches and trims as mesh entities (mixed IGA and FEM assembly in one model, for instance, or a patch-aware `partition`), and start from the spike's list of what the side channel cannot do: no `Mesh` operation sees a patch, the model does not travel through the pipeline, and an MFEM model refines every direction alike.
- **Polyhedron blocks as a WASM gap** — `vtu`, `ensight`, `cgns`, `med` and `openfoam` all write them from WASM; a consumer that cannot is constrained by its own data model.
- **Performance work measured or decided against** — recorded when the roadmap's performance section closed (October 2026), and not re-proposed when it reopened as [§4](#performance) (then §5) in November 2026; a new performance change passes the gates of [landing a performance change](./benchmarks.md#landing-a-performance-change):
  - **The serial phases kept for determinism**: the keep-first weld loop (chains make it order-dependent), the union sweeps of `split` and `compute_normals` (cheap, and their partitions are order-independent anyway), and `remesh`'s energy sweep (every accepted move changes what the next test reads; it has no numpy twin because a near-tie decided differently yields a different clustering).
  - **A facet table cached across pipeline steps** — measured ([benchmarks](./benchmarks.md#pipeline-row-what-a-shared-facet-table-could-save)): in a `Smooth` then `ExtractSurface` chain a cache saves at most one table build, about 3.6% of the chain on SEQ at tier L with the default ten iterations, at most 10% on four OpenMP threads and about 20% with one iteration. `smooth` and `extract_surface` do not share a record structure, so it would also need a refactor, and a cache on the `Mesh` is a Tier A layout change. Reopen it for a workload that chains several facet readers after cheap topology-preserving steps; the `pipeline_smooth_surface` row measures it.
  - **Link-time optimisation by default** — measured ([benchmarks](./benchmarks.md#link-time-optimisation)), November 2026: identical output and binaries a third smaller, but the instruction counts move both ways (`read_vtk_ascii` +40%, `gradient` +14%, `decimate` −6%), so it is the opt-in `MESHIOPLUSPLUS_ENABLE_LTO` rather than the default.
  - **Explicit SIMD intrinsics or `-march` flags** — portability across wheels, WASM and the release binaries is worth more than the scalar kernels cost; revisit only if the harness shows a kernel dominating. Narrowed in November 2026: the decision stands for flags and for intrinsics compiled unconditionally; variants selected at run time inside one portable binary, for kernels whose vector form is bit-identical, are to be measured as 4.15.
  - **Kokkos device execution** — every `parallel_for` body captures host pointers (`parallel.hpp`); the GPU route is the DLPack/CuPy handoff ([GPU handoff](./gpu.md)).
  - **An occupancy pyramid over the distance query's bucket grid** (formerly roadmap 5.3.1) — measured in November 2026 and not taken: descending the grid's occupancy at coarser block sizes, best first with Euclidean bounds, was 2 to 3 times faster than the Chebyshev-shell search at tier L, but a bounding-volume hierarchy of the triangles (formerly 5.3.2, which had been decided against because its visit order was thought to make the equidistant-triangle tiebreak observable, a reason the total order on (distance², triangle id) answers) was a further 2 to 4 times faster with its build included, on uniform and graded targets alike, and replaced the grid in ABI 40 ([benchmarks](./benchmarks.md#a-bounding-volume-hierarchy-for-the-distance-query-and-a-grid-for-find_interface)). A cell's bound is the cell's, so a point far from the surface still opens every bucket of a patch around its nearest one; a box is as tight as its triangles.
  - **Tuning the pure-Python fallback readers** — the fix is making the C++ path accept the file, not a faster fallback; `_decimate.py`'s heap-based twin is deleted once `decimate` accepts its inputs, not optimised.
  - **Dropping the copy in `transform`** — `transform` copies the connectivity and data it does not change (through `transform_owned_copy`, as 17 operation files copy through `clone_mesh`, `clone_geometry` or `quality_clone_mesh`), and the Python twin copies too; that copy is what makes the result a new mesh that aliases nothing, so removing it is an API change, not an optimisation. Narrowed in November 2026: that holds for `transform`; a second, explicitly in-place entry point changes no existing contract and is to be measured as 4.14.
  - **Caching between the browser viewer's applies** — every apply re-reads the staged file and replays the whole pipeline, which is what makes undo exact. Measured with the typed-array channel ([benchmarks](./benchmarks.md#a-typed-array-channel-for-the-browser-viewer)), the read is at most 2 to 25% of an apply that smooths and up to 69% of a quality-only apply on a large surface; a cached mesh or pipeline prefix would hold a second copy of the mesh in the 32-bit heap MEMFS already shares, and make undo depend on invalidation. The heap's size is the half of this a 64-bit build would change (4.13); measure again there before reopening.

- **Code from AGPL-3.0 scan tools** — [ScanRuler](https://github.com/CNCKitchen/ScanRuler) and its STEP importer meshStep are AGPL-3.0, which this MIT library cannot take in any form: no copying, porting, translating or paraphrasing of their code, tests, shaders, guides or data. The scan metrology section (then §7, closed November 2026) was listed from their published feature descriptions only; an agent implementing an item of that kind (8.9 is one) works from the literature it cites and from meshio++'s own kernels, does not open their source, and does not use their output files as fixtures. The same rule as for Triangle, TetGen and Gmsh above, without the separate-process exception, since nothing there needs to run them.
- **Booleans of a scan with fitted solids** — subtracting a measured cylinder from a scan, or adding a modelled body to it (roadmap 7.8.7, closed November 2026), waits on surface booleans, which a spike measured and kept out: exact in topology, but rounding its output to doubles left most curved results self-intersecting and coplanar contact unhandled ([findings](./spikes.md#surface-booleans-formerly-roadmap-7-8)). A fitted solid reaches a CAD kernel as STEP ([`write_step_elements`](./formats/step.md#elements)), where the boolean is the kernel's. If a boolean backend passes the spike's criteria (8.1), this is its first use and the entry is removed.
- **An interactive parametric CAD modeller** — a sketch constraint solver, a feature history with rebuilds and rollback, face fingerprints that survive upstream edits, thread and insert catalogues: a CAD application, not a mesh library. meshio++ fits and writes geometry ([`fit_cad`](./fit_cad.md), 7.6.5) and may build a solid from a scripted list of profile features through the CAD provider (7.7.4); editing that solid belongs to the CAD tool that opens the STEP file.
- **Terminal rendering stays software, dependency-free and core-only** — no GPU, no windowing stack, no new dependency and no audio library; it is a *preview*, not a replacement for Polyscope or vtk.js, and does not try to match their fidelity, lighting or picking. Python calls the core or raises by name (the [`remesh_volume`](./remesh_volume.md) precedent: a NumPy edge-function rasterizer would be slow and double the surface that has to stay byte-identical). Vector output is unchanged: SVG, TikZ and glTF keep the painter's algorithm and their byte-pinned twins, and their colormap tables are only ever extended. The interactive loop is not a library feature (raw mode, signals and the event loop live in the CLI layer; the library exposes frames and encoders, never a tty, and WASM and the C API carry frames and text only). `--follow` polls modification times and does not use inotify or kqueue. The soundtrack is generated, played by an external player and silent unless asked for, in CI and over SSH. See [terminal rendering](./tui.md#design-decisions).

## Suggested sequencing

Open work only; what shipped is in `CHANGELOG.md`.

1. **Format reach ([§1](#format-reach))** — the checks against the vendor tools, as licences or files the tools wrote appear; they are what is left of reader and writer parity. Depth before breadth in what is new: CGNS's boundary conditions and structured zones (1.3.1), the series writers (1.3.4) and compressed OpenFOAM cases (1.3.5) reach more users than any format of 1.4, where Fluent's case files (1.4.1) and the coastal trio (1.4.3) come first.
2. **The OSS-Fuzz submission ([§2](#quality-of-implementation)) and registration ([3.1](#ecosystem-reach))** — calendar-bound, so start them early and let them run alongside everything else; the dataset manager's thumbnails (3.6) needs no decision first and can run beside them. Code cleaning (2.4) and Clang-Tidy (2.5) also run alongside everything: take 2.4's items in the order SonarCloud's duplication report gives, and 2.5's stages in order. Of the tooling the November 2026 review added, take first what costs days and guards everything after it: the security policy and dependency updates (2.14), `clang-format` and the documentation checks (2.8, 2.16), coverage on pull requests (2.11), the warning baseline (2.6, whose first stage is a count) and ThreadSanitizer (2.9), which the free-threaded wheel (2.15) waits on; then typed Python (2.7), CodeQL (2.10), the round-trip fuzz target (2.12, after 2.1) and the ABI diff (2.13).
3. **Performance ([§4](#performance))** — the harness first (4.1), since every other item shows its numbers on it; then the wheels' remaining parallel-runtime checks (4.2; the Linux wheels build the THREADS backend since v19.1, so the parallel items reach pip users); then the rest by measured payoff. The four items the review added (4.12 to 4.15) each begin with a measurement that can close them.
4. **Split Python packages on Windows ([3.7](#ecosystem-reach)) and the CLI plugins (3.8)** — the MSVC recipe for the static libraries (3.7.1), then plugins through a shared core DLL (3.7.2); the Linux and macOS plugin archive (3.8.1) needs neither and can go first, the Polyscope plugin (3.8.2) after it.
5. **The embeddable MCP server (3.9)** — its design pass (3.9.1) before any code, since it decides whether the Python server's sandbox and sanitizer move into the core.
6. **Code duplication ([§5](#code-duplication))** — no open item; rerun `tools/dup_report.py` alongside everything, like 2.4, and list what it finds there.
7. **SonarCloud findings ([§6](#sonarcloud-findings))** — the next scan's counts first (6.1), then the coverage gate (6.2); the viewer's rebuild (6.3) goes with the next WebAssembly build.
8. **Operations ([§8](#operations))** — the boolean backend's measurement first (8.1), since it decides a non-goal and two parked features; then the small ones a user notices missing (mass properties 8.4, the public queries 8.3, point-cloud conditioning 8.9), then subdivision and elevation (8.2, 8.5). They need no decision from §7.
9. **Data model ([§7](#data-model))** — design passes only until one says otherwise, and in the order of the section: the complex-value convention (7.1) and the structured annotation (7.6) are the two whose small form is days and closes losses already listed on format pages; integration-point data (7.3) is the one worth a major version if any is. The format items that wait on them say so (1.3.3, 1.3.6, 1.3.7, 1.4.2).
