# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

meshio++ (Python package/import name `meshioplusplus`) is a Python library for reading and writing many mesh file formats used in scientific computing and FEM (Finite Element Method). It provides a unified `Mesh` data structure that all format readers/writers convert to and from.

This branch (`port-to-c++`) adds a **C++ core** (`meshioplusplus._core`, pybind11) built with **scikit-build-core + CMake**, replacing the old setuptools build. Most formats read/write through the C++ core with a pure-Python fallback.

## Keeping docs in sync (required)

**Every time a feature or format is added or changed, update all three of `CLAUDE.md`, `README.md`, and the `doc/` site in the same change.** At minimum: the format table and format-specific notes in [`doc/formats.md`](doc/formats.md) (plus any other relevant `doc/` page), the supported-formats list in `README.md`, and the architecture/"Adding a new format" guidance here. Changes to the shared format registry or the flat-binding surfaces must also be reflected in [`doc/wasm.md`](doc/wasm.md), [`doc/c_api.md`](doc/c_api.md), and [`doc/fortran.md`](doc/fortran.md). A feature is not "done" until CLAUDE.md, README.md, and the docs all reflect it.

**Keep the example notebooks (`example/*.ipynb`) current with new features too.** When a user-facing capability is added (a new operation, a new format, a notable API), demonstrate it in the notebooks (a new/updated cell) and re-execute them with outputs (`PYVISTA_OFF_SCREEN=true jupyter nbconvert --to notebook --execute --inplace example/*.ipynb`) so the committed outputs stay in sync. **Notebook demos must be graphical, not just printed values** — render results with PyVista (off-screen: `pv.OFF_SCREEN=True` + a `pv.Plotter(off_screen=True).screenshot(return_img=True)` embedded via matplotlib, with a matplotlib fallback for head-less GL), coloring the mesh by the relevant data array (quality metric, per-point diff error, ...) so the effect is visually understandable. `example/03_mesh_operations.ipynb` is the reference pattern for the operations.

## Version bumps (required)

**"Bump the version" always means every one of these five, together, to the same value — never just one or two:**

- [`pyproject.toml`](pyproject.toml) — `version`
- [`CMakeLists.txt`](CMakeLists.txt) — `project(... VERSION ...)`
- [`conanfile.py`](conanfile.py) — `version`
- [`ports/meshioplusplus/vcpkg.json`](ports/meshioplusplus/vcpkg.json) — `version`
- [`wasm/package.json`](wasm/package.json) — `version` (npm publish uses this file verbatim; it silently lagged behind at 6.3.0 through two releases before this rule existed — it's the one that's easiest to forget since it lives outside the Python/CMake build)

The CMake `VERSION` feeds `mio_version()`, the C API `.so`'s VERSION/SOVERSION, and the installed package configs, so it isn't optional/cosmetic.

**A dated [`CHANGELOG.md`](CHANGELOG.md) entry is required in the same change as every version bump** — new formats, new operations, notable enhancements *and* breaking changes, not breaking changes only. Mark breaking items explicitly with a **Breaking:** prefix; everything else is assumed additive. (This rule replaced a breaking-changes-only policy under which the file silently fell six releases behind, from v6.6.0 to v7.1.0 — the entries were reconstructed from git history. Treat "bump the five version files" and "add the CHANGELOG entry" as one indivisible step.) A pure patch/bugfix bump can be a single line.

## Commands

**Build/install for development** (native paths on). PEP 668 systems: use the in-repo uv venv (`uv venv --python 3.12 .venv`), then:
```bash
CMAKE_ARGS="-DMESHIOPLUSPLUS_WITH_HDF5=ON -DMESHIOPLUSPLUS_WITH_NETCDF=ON -DMESHIOPLUSPLUS_WITH_ZLIB=ON" \
  uv pip install --python .venv --no-build-isolation -e .
```
Plain environments: `pip install -e ".[all]"`. The optional deps (HDF5, netCDF, zlib) are auto-detected; when absent the C++ paths compile out and Python fallbacks (h5py/netCDF4/stdlib zlib) take over.

**Standalone C++ build**: `build/configure.sh` (Linux/macOS) and `build/configure.bat` (Windows) configure a CMake tree next to themselves (`build/cpp-<type>[-<mesh-backend>]`); flags: `--backend SEQ|STL|OPENMP|TBB`, `--mesh-backend MESHIO|NATIVE|KRATOS` (non-MESHIO implies `-DMESHIOPLUSPLUS_BUILD_PYTHON=OFF`), `--tests`, `--cli` (the native CLI binary, below), `--build`, `--with/-out-hdf5/netcdf/zlib`, `--tbb-dir <path>`. They print the matching `CMAKE_ARGS … pip install` line (MESHIO only).

**Native CLI binary** (`cpp/cli/main.cpp` → `meshioplusplus_cli`, installed executable name `meshioplusplus`): a **Python-free** command-line tool over `meshioplusplus_core_obj` mirroring the Python console script's verbs (convert/info/ascii/binary/compress/decompress/quality/extract-surface/reorder/diff/merge/transform/clean/crop/split/stats, plus the nested `data <verb>` group with the same nine sub-verbs and the same colon rules). Supporting the repeated `--point`/`--cell`/`--field` flags the `data` verbs need required one extension to the hand-rolled parser: `cli_opt_spec` gained nothing, but `cli_parsed` gained a `multi` map recording every occurrence of each value-option, populated **alongside** the existing last-wins `values` map so all 16 pre-existing verbs are behaviourally unchanged; read it with `opt_values(p, name)` and test presence with `has_opt(p, name)`. `MESHIOPLUSPLUS_BUILD_CLI` (OFF by default; `build/configure.sh --cli --build`). Reuses the shared `registry.hpp` for format dispatch (with the `sniff_format` read fallback); ASCII/binary/compress variants call the per-format writer free functions directly (the registry bakes one default per format), and the operation verbs use `operations/*.hpp`. Works under any mesh/parallel backend and optional-dep set. **Documented gaps vs the Python CLI** (same as the C-API/WASM flat surfaces): point/cell **sets** and `convert -s/-d` never reach the C++ core, so `info`/`diff` omit sets and `convert -s/-d` errors; formats whose C++ reader raises (e.g. gmsh `$Entities`, which the Python path handles via fallback) are unreadable here — there is no Python fallback. `--version`'s `MESHIOPLUSPLUS_CLI_VERSION` is fed by CMake `PROJECT_VERSION`. **Prebuilt, statically-linked release binaries** (Linux x86_64, Linux arm64, macOS universal, Windows x86_64) are attached to every `v*` tag's GitHub Release by `cli.yml` (see "CI" below) — built with `MESHIOPLUSPLUS_STATIC_RUNTIME=ON` (hoisted to a top-level option so it applies to both `_core` and `meshioplusplus_cli`: static `libgcc`/`libstdc++` on GNU, static MSVC CRT via `MSVC_RUNTIME_LIBRARY` on Windows) and `WITH_HDF5/NETCDF/ZLIB=OFF` + `PARALLEL_BACKEND=SEQ` for a single dependency-free executable; build from source with `--cli` (optionally without `--without-hdf5` etc.) for the full native format/threading feature set.

**WebAssembly build** (`@meshioplusplus/wasm` npm package): `build/configure-wasm.sh --build` (needs the [Emscripten SDK](https://emscripten.org/docs/getting_started/downloads.html) on `PATH`) configures `build/wasm-<type>` with `-DMESHIOPLUSPLUS_BUILD_PYTHON=OFF -DMESHIOPLUSPLUS_BUILD_WASM=ON -DMESHIOPLUSPLUS_PARALLEL_BACKEND=SEQ -DMESHIOPLUSPLUS_MESH_BACKEND=NATIVE` (the fastest mesh backend; the JS API shape is unchanged and `meshBackend()` reports `"native"`), HDF5/netCDF off, builds `bindings_js/js_bindings.cpp` (embind) against the same `meshioplusplus_core_obj` as `_core`, and copies `meshioplusplus_wasm.{mjs,wasm}` into `wasm/dist/`. Ships 36 formats + XDMF's XML/Binary path — 35 readable, 36 writable (`openfoam` read-only; `svg`/`tikz` write-only), no HDF5/netCDF-backed formats — see `doc/wasm.md`. Smoke test: `node wasm/test/smoke.mjs`. `-fwasm-exceptions` is required (applied `PUBLIC` on `meshioplusplus_core_obj` under `if(EMSCRIPTEN)`) so `ReadError`/`WriteError` surface as catchable JS `Error`s instead of aborting; `log.hpp`'s `std::osyncstream` usage has a `std::mutex`-guarded fallback for standard libraries (Emscripten's non-threaded libc++) that ship `<syncstream>` without actually defining it (`__cpp_lib_syncbuf` unset). `configure-wasm.sh` runs `embuilder build zlib` right after configuring (when zlib is on) to pre-warm Emscripten's zlib port cache single-threaded — `-sUSE_ZLIB=1` makes every translation unit trigger that port's build on first use, and a parallel `-j` build races many `em++` invocations against the same cold-cache lock, aborting with "attempt to lock the cache while a parent process is holding the lock (sanity)". CI (`.github/workflows/wasm.yml`) builds+smoke-tests and publishes to npm (`NPM_TOKEN` secret) only on `v*` tags (mirrors `wheels.yml`'s trigger), plus `workflow_dispatch`.

**C API / Fortran build** (`libmeshioplusplus` + Fortran module, for C/Fortran HPC consumers): `build/configure.sh --c-api` or `--fortran` (implies `--c-api`; both also exist in `configure.bat`, Fortran untested on MSVC) → CMake options `MESHIOPLUSPLUS_BUILD_C_API` / `MESHIOPLUSPLUS_BUILD_FORTRAN` (both OFF by default). `cmake --install <tree> --prefix <p>` installs the shared lib(s), the single pure-C header `bindings_c/include/meshioplusplus/meshioplusplus.h`, a `find_package(meshioplusplus)` config package, a relocatable pkg-config file, and (Fortran) the `.mod` **plus** `bindings_fortran/meshioplusplus.f90` (`.mod` files are compiler-specific; consumers on another compiler recompile the module — the HDF5 approach). Tests: `cpp/tests/test_c_api.cpp` (auto-globbed into the gtest suite when C_API is on) and the `fortran_api` ctest (`bindings_fortran/test/test_fortran_api.f90`). CI-tested consumer examples: `doc/examples/c_api_example.c`, `doc/examples/fortran_example.f90`. See "Version bumps" above — `project()`'s `VERSION` feeds `mio_version()` and the `.so`'s VERSION/SOVERSION here.

**Conan / vcpkg packaging** (self-hosted, in-repo, for the C API): the root `conanfile.py` (Conan 2.x, with `test_package/`) and the `ports/meshioplusplus/` vcpkg overlay port (`vcpkg.json` + `portfile.cmake` + `usage`) both drive the same `-DMESHIOPLUSPLUS_BUILD_C_API=ON -DMESHIOPLUSPLUS_BUILD_PYTHON=OFF` install/`find_package` path (the `meshioplusplus::meshioplusplus` target). Options/features: `with_hdf5`/`with_netcdf`/`with_zlib` (on) and `fortran`/`with_eigen` (off — Eigen is a submodule absent from a source tarball, so the MED transpose uses the fallback loop; the lib is shared-only). Verified locally end-to-end (bootstrapped vcpkg, built `libaec`+`hdf5`+`netcdf-c` against this overlay set). `.github/workflows/packages.yml` validates the Conan recipe (two option legs, each on x86_64 and arm64 — see "CI" below) and the vcpkg manifest (x86_64 only; the overlay-port zip it produces is source, not an arch-specific binary) on every PR, and on `v*` tags pins the tarball SHA512 + builds the vcpkg port end-to-end. Docs: [`doc/c_api.md`](doc/c_api.md#package-managers-conan-vcpkg).

## Architecture

**Core data model** (`src/meshioplusplus/_mesh.py`, pure Python, unchanged):
- `Mesh`: holds `points`, `cells` (list of `CellBlock`), `point_data`, `cell_data`, `field_data`, `point_sets`, `cell_sets`, optionally `gmsh_periodic`/`info`
- `CellBlock`: a cell type string (e.g. `"triangle"`, `"tetra10"`) + numpy node-index array
- `_common.py`: `num_nodes_per_cell`; `topological_dimension` in `_mesh.py`

**C++ core** (`cpp/`, `bindings/`):
- `cpp/include/meshioplusplus/` headers (`ndarray.hpp`, `mesh.hpp`, `mesh_api.hpp`, `cell_type.hpp`, `types.hpp`, `registry.hpp`, `backends/*`, `detail/*`, `formats/*`), `cpp/src/formats/*.cpp`, compiled with `bindings/_core.cpp` into `meshioplusplus._core`.
- **Format dispatch registry** (`registry.hpp` + `cpp/src/registry.cpp`, compiled into `meshioplusplus_core_obj`): the C++-level `format name -> read/write function` tables, `extension -> default format` map, `resolve_format()`, and `registry_compiled_out()` (names the missing optional dep for HDF5/netCDF formats absent from a build; their extensions are mapped unconditionally so errors say "no HDF5 support" instead of "cannot infer format"). Shared by the **flat bindings** — WASM (`bindings_js/js_bindings.cpp`, which no longer carries its own tables) and the C API (`bindings_c/`) — while the pybind11 binding keeps its one-function-per-format surface with dispatch in Python (`_helpers.py`). Parameterized writers get fixed defaults here (documented per entry; matching the Python reference defaults, except xdmf which follows the build: HDF when HDF5 is available, XML otherwise). **A new C++ format must also be registered here** (reader/writer entry + extension default) or the flat bindings won't see it.
- **C API** (`bindings_c/`): `include/meshioplusplus/meshioplusplus.h` (the single installed pure-C99 header; the C++ headers make no ABI promise) + `c_api.cpp`, built into the installable `libmeshioplusplus` shared lib (SOVERSION 0) when `MESHIOPLUSPLUS_BUILD_C_API=ON`. Flat whole-mesh API over the **uniform mesh API only**, so it compiles under all three mesh backends and the gtest C-API suite runs per-backend in CI. Contract: `mio_status` codes + thread-local `mio_last_error()` (no exception crosses the ABI — every extern "C" body runs in `guarded()`/`guarded_ptr()`); setters copy, getters are zero-copy borrows valid until the next mutating call; strings via caller-buffer + required-length return (never `c_str()` of a per-backend-possibly-temporary `Type()`); row-major arrays, 0-based connectivity (int32 widened to int64 on ingest); ragged blocks are reported (`is_ragged`) but their connectivity is inaccessible (v1); side-channel structs (point_sets/cell_sets/MED families) are dropped like WASM. The `mio_cell_type` enum duplicates the cell-type list in the C header and `c_api.cpp` static_asserts every entry against `CellType`, so drift is a compile error.
- **Fortran module** (`bindings_fortran/meshioplusplus.f90`, module `meshioplusplus`, `MESHIOPLUSPLUS_BUILD_FORTRAN=ON` which force-enables the C API): modern OO Fortran 2008 (`type(mio_mesh)` with type-bound procedures, HDF5/PETSc style) over the C API via ISO_C_BINDING; raw `bind(c)` interfaces are private (`c_mio_*`). Conventions: arrays are Fortran-shaped — points `(dim, n)`, conn `(npc, ncells)` — which is the *same memory* as the C row-major shapes (no transpose anywhere); connectivity is 1-based, shifted ±1 inside the copying setters/getters only; `points_ptr` is the zero-copy borrow (no shift needed); every fallible procedure takes optional `stat`/`errmsg`, absent `stat` + failure = print + `error stop` (stdlib pattern); handles freed explicitly (`m%free()`, no finalizer).
- **Mesh backends** (`mesh.hpp` dispatch; mirrors the parallel-backend pattern): `MESHIOPLUSPLUS_MESH_BACKEND` = `MESHIO|NATIVE|KRATOS` selects, at compile time, which structure `meshioplusplus::Mesh` is — exactly one `MESHIOPLUSPLUS_MESH_BACKEND_*` macro is defined. `MESHIO` (default, `backends/meshio_mesh.hpp`) is the meshio-mirroring `Mesh`/`CellBlock` and is **required** when `MESHIOPLUSPLUS_BUILD_PYTHON=ON` (CMake `FATAL_ERROR` otherwise; `np_conversions.hpp` `#error`s too) — PyPI/wheels are unaffected by the other backends. `NATIVE` (`backends/native_mesh.hpp`) is canonical statically-typed storage (Float64 points, Int64 connectivity, `CellType` enum from `cell_type.hpp`, CSR ragged blocks, lazy whole-mesh CSR via `GlobalConnectivity()`); the WASM build uses it. `KRATOS` (`backends/kratos_mesh.hpp`) wraps a Kratos-style `ModelPart` (`backends/model_part.hpp`: Nodes/Elements/Conditions with 1-based Ids, nested SubModelParts sharing root-owned entities, simplified per-entity variables) — ingest stages canonically, `GetModelPart()` materializes lazily (Elements = blocks of max topological dimension, Conditions = lower, names from `backends/kratos_names.hpp` ported from `_mdpa.py`; integer tag cell-data like `gmsh:physical` auto-becomes SubModelParts, toggle `SetBuildSubModelPartsFromTags(false)`), writers serve from staging so round-trips never pay for the ModelPart; after direct ModelPart mutation call `InvalidateBlocks()`. `kratos_bridge.hpp` (header-only, backend-independent) `to_model_part`/`from_model_part` populate/read ANY Kratos-like class — incl. real `Kratos::ModelPart` via a properties-getter — with one O(n) bulk-create pass; CI compile-checks it against real CoSimIO headers (fetched at CI time only — CoSimIO's BSD-4-clause-with-advertising license is never vendored into this MIT repo; `model_part.hpp` is a clean-room implementation). `_core.__mesh_backend__` / JS `meshBackend()` report the active backend. **Adding a backend** = one CMake branch defining `MESHIOPLUSPLUS_MESH_BACKEND_<NAME>` + one `#elif` in `mesh.hpp` + a `backends/<name>_mesh.hpp` implementing the uniform API (`cpp/tests/test_mesh_api.cpp` must pass). CI runs the gtest suite once per backend (`ci.yml` `cpp-tests` matrix).
- **Uniform mesh API rule** (`mesh_api.hpp`): format code (`cpp/src/formats/*`, shared `detail/*` helpers, `bindings_js/`) MUST go through the uniform methods — ingest `AssignPoints`/`AddCellBlock`/`AddPolygonBlock`/`AddPolyhedronBlock`/`AddPointData`/`AddCellData`/`AppendCellData`/`AddFieldData`, accessors `Points()`/`PointDim()`/`Cells(i)`/`CellRange()` (`Mesh::CellView` with `Type()`/`NumCells()`/`NodesPerCell()`/`Conn()`/`IsRagged()`/ragged `Row`/`Face`) and `PointDataNames()`/`PointData(name)`/`CellData(name, block)`/`CellDataNumBlocks`/`FieldData(name)` (+ `Has*`/`Num*`) — and never backend struct members; that's what lets one format compile under all three backends. Hoist `Points()`/`Conn()`/data lookups out of per-element hot loops. The one sanctioned exception is `bindings/np_conversions.hpp` (pinned to MESHIO). NATIVE/KRATOS canonicalize dtypes at ingest *within kind* (floats→Float64, ints→Int64, never int→float — "first integer cell_data is the tag" conventions survive); owning canonical arrays are moved, not copied.
- **Zero-copy at the I/O boundary**: readers return capsule-backed writeable numpy; writers view numpy memory (`bindings/np_conversions.hpp`). The conversion layer carries points/cells/point_data/cell_data/field_data, but **not** `mesh.info`, `cell_sets`, or `point_sets` — formats that need those either defer to Python or carry them out-of-band via a **side-channel struct** the binding `setattr`s onto the Python `Mesh` (e.g. `MedInfo`, `AnsysInfo`/`UnvInfo` for `point_sets`/`cell_sets`, `OpenFoamInfo` for `cell_tags`). **Field-only formats** (`mff`/`dex`/`ip`, the Modulef/FLUX/ANSYS-Fluent field files) carry no geometry: they read/write a geometry-less `Mesh` (no cells, field values in `point_data`; `dex`/`ip` also fill `points` from the file's coordinates, `mff` has none so its `points` has zero columns) — there is no companion-mesh auto-pairing.
- **Ragged cell blocks**: every backend supports optional ragged blocks — 1-level (jagged polygons, `AddPolygonBlock`) and 2-level (list of faces per cell, `AddPolyhedronBlock`) — for types that can't fit a rectangular `NDArray`, read back via `CellView`'s `RowSize`/`Row` and `NumFaces`/`Face`. MESHIO stores them as nested vectors (`CellBlock::mPolygonRows`/`mPolyhedronRows`), NATIVE as CSR offset arrays, KRATOS as staging pass-through (no ModelPart entities). Zero-copy applies only to rectangular blocks; ragged blocks are **copied** across the Python boundary. `py_to_mesh`'s `allow_ragged` flag is **off by default** (so every rectangular-only writer keeps safely rejecting ragged meshes → Python fallback) and only the ragged-aware bindings (MED write) opt in.
- **Operations layer** (`cpp/src/operations/*.cpp` + `cpp/include/meshioplusplus/operations/*.hpp`): computations *on* a mesh (not file formats — deliberately **not** registered in `registry.cpp`). Each operation is uniform-mesh-API-only (compiles under all three backends — the KRATOS `Mesh` is **not** copy-constructible, so never `Mesh out = in;`; clone via the uniform API as `quality_clone_mesh` does), parallelizes its hot loop with `parallel_for`, and is exposed across **every** binding surface (pybind `_core`, C API `mio_*`, Fortran type-bound procedures, WASM embind) plus a CLI verb. `.cpp` anon-namespace helpers are uniquely prefixed (`surface_`/`quality_`/`sniff_`/`reorder_`/`diff_`/`merge_`/`transform_`/`clean_`/`crop_`/`split_`/`stats_`, and for the data bundle `dmanage_`/`davg_`/`calc_`/`dcond_`/`dinfo_` — **distinct per file**, since a shared `data_` prefix across five TUs would collide) because the amalgamation concatenates TUs; `detail/` header inline helpers (`geometry.hpp`, `cell_edges.hpp`, `subset.hpp`, `data_ops.hpp`) are exempt. New `cpp/src/operations/*.cpp` are auto-globbed by CMake and `rglob`ed by the amalgamator — regenerate + commit the single header after any change. The **crop** and **split** operations share `detail/subset.hpp`'s `build_cell_subset` (prune-points-to-kept-cells + remap connectivity/data, `drop_empty_blocks` flag for split's homogeneous pieces); the five **data operations** share `detail/data_ops.hpp`'s `clone_mesh(mesh, filter)` (backend-agnostic geometry copy + per-array keep/rename decision — the workaround for the uniform API having no remove/rename for data arrays), `FiniteStats` (chunked parallel reduction, serial combine, non-finite values excluded and counted) and `cell_measure`. The eleven **mesh** operations (on geometry) and five **data** operations (on data arrays) are listed below.
  - **Surface/skin extraction** (`operations/surface.{hpp,cpp}`, Python `_surface.py`/`_skin.py`): `extract_surface(mesh, record_parent_ids=false)` picks the dimension automatically (3D volume → boundary faces, 2D surface → boundary edges via `detail/cell_edges.hpp`); `extract_skin(mesh, linearize=false)` (declared in `skin.hpp`) is the volume-only special case — **both share the one implementation in `surface.cpp`** (`extract_skin` calls it in force-face mode, byte-identical to the old `skin.cpp` it absorbed). Kratos `SkinDetectionProcess` face-hashing (sorted corner-node key occurring exactly once = boundary); face topology in `detail/cell_faces.hpp` (Python twin in `_skin.py`, must stay in sync; outward winding enforced by a gtest Newell-normal invariant in `test_skin.cpp`), edge topology in `detail/cell_edges.hpp` (twin in `_surface.py`). Supported volume types: tetra(10), hexahedron(20/27), wedge(15), pyramid(13/14). Output blocks in fixed canonical order (triangle, triangle6, quad, quad8, quad9 / line, line3), points compacted ascending original-id (numpy fallback relies on `np.unique` sortedness for identical output — `tests/test_skin.py`/`test_extract_surface.py`), `point_data` subset, other data dropped. Two-phase parallel: keys built in `parallel_for` into disjoint slots, then a **serial** dedup/emit so output is byte-identical across backends and thread counts. `record_parent_ids` attaches Int64 `surface:parent_cell` cell_data (per-output-facet owning input-cell index). **Consumers:** `write_stl`/`write_ply` take a trailing `skin` flag (default **true** — writes the extracted linearized skin, STL triangulating quads; `skin=false` = legacy drop-with-warning; pinned true in `registry.cpp`), and the SVG/TikZ writers project the skin (below).
  - **Mesh quality** (`operations/quality.{hpp,cpp}`, Python `_quality.py`): `compute_quality(mesh)` → `QualityReport` (per-metric summaries + histograms, per-block `cell_data` arrays, inverted/degenerate counts); `attach_quality(mesh)` returns a clone with the metrics as `cell_data` (names `quality:<metric>`). Metrics (triangle/quad/tetra/hex/wedge/pyramid, quadratic variants on corners; NaN where N/A): volume/area, scaled_jacobian, aspect_ratio, skewness, min/max_angle, warpage, min/max_dihedral, inverted, degenerate. Verdict/VTK formulas; ideal element → ideal value (SJ=1, aspect=1, skew=0, tri angles 60°, tetra dihedral ≈70.53°) — pinned by `test_quality.cpp`/`tests/test_quality.py`. Reusable vec3 math in `detail/geometry.hpp`.
  - **Format sniffing** (`operations/sniff.{hpp,cpp}`, Python `_sniff.py`): `sniff_format(path)` returns a format name only on a confident leading-bytes signature match (vtk/vtu/vtp/gmsh/ply/off/xdmf/stl-ascii/abaqus), else `""` (ambiguous magics like generic HDF5 or headerless binary STL are never claimed). Wired as a **read-only** fallback in the read paths (`_helpers._read_file`, C `mio_read`, WASM `read_mesh`) when the extension gives nothing — never on a write path.
  - **Reordering / renumbering** (`operations/reorder.{hpp,cpp}`, Python `_reorder.py`): `reorder(mesh, ReorderMethod::RCM|Morton|Hilbert)` → `ReorderResult{mMesh, mNodePermutation, mCellPermutations}` — a **pure permutation** (no nodes/cells added/removed, geometry + all data preserved) returning the applied node/cell permutations (old→new, Int64). RCM builds the node-adjacency CSR (element cliques — nodes sharing a cell are neighbours), picks a pseudo-peripheral start per connected component (rooted-level-structure heuristic), Cuthill–McKee BFS by increasing degree, then reverses; Morton/Hilbert quantize coords to 21 bits/axis over the bbox and stable-sort along the curve. Element perm orders each block's cells by min new-node index. Applies to points/point_data (scatter by node perm, dtype-preserving byte-row gather via `parallel_for_bw`) + connectivity (Int64, remap+reorder) + cell_data (reorder by per-block cell perm); field_data unchanged; ragged/polyhedron blocks supported. `compute_bandwidth(mesh)` = max over cells of (max−min node index). The BFS/argsort stay serial for cross-backend determinism (surface.cpp's phase-split philosophy). `point_sets`/`cell_sets` are remapped in the Python shim (they never reach the C++ core); `mesh.info`/`gmsh_periodic` are not carried through. The C API uses an opaque `mio_reorder_result` handle (mesh borrow + zero-copy perm getters + `mio_reorder_result_take_mesh` ownership transfer for Fortran); Fortran/WASM expose node perm (Fortran, 1-based) / full node+cell perms (WASM object). CLI verb `reorder … --method rcm|morton|hilbert [--report]`.
  - **Comparison / diff** (`operations/diff.{hpp,cpp}`, Python `_diff.py`): `diff(mesh_a, mesh_b, DiffOptions{atol,rtol,unordered,max_reported})` → `DiffReport` (verdict `Identical`/`EqualWithinTolerance`/`Different`; per-section `ArrayDiff`/`BlockDiff`/`DataDiff` with max abs/rel error, worst flat index, mismatch counts, keys-only-in-one, first-N mismatching cells); `meshes_equal(a,b,atol,rtol)` = `verdict != Different` (ordered). Tolerance rule `abs_err <= atol + rtol*|expected|` (expected from `a`); "identical" is exact equality. **Ordered** path (default) compares points/cells/data index-by-index — the elementwise reduce is chunked and `parallel_for`-parallel, combined serially (deterministic). **Unordered** (`unordered=true`) matches points by proximity via a bucket-grid coordinate hash (no O(N²)); conservative — sets `mCorrespondenceFailed` + verdict `Different` rather than guessing when no one-to-one match exists. Only points/cells/`point_data`/`cell_data`/`field_data` are reachable in C++; **named `point_sets`/`cell_sets` are compared in the Python shim only** (added/removed/changed → a `"sets"` report section, folded into the verdict) — C/Fortran/WASM never see sets. Python `diff` returns a nested dict (with the numpy fallback returning an identically-keyed dict), `meshes_equal` is a boolean; `_format_report` renders the CLI output. C API: `mio_diff`/`mio_meshes_equal` + opaque `mio_diff_result` (verdict/point-summary/per-block getters, `mio_diff_result_free`). Fortran `m%equals`/`m%diff` (verdict 0/1/2). WASM `diff`/`meshesEqual`. CLI verb `diff A B [--atol --rtol --unordered --exact --quiet]` — **exit code is nonzero when meshes differ** (0 for identical or equal-within-tolerance; `--exact` makes only identical pass) for CI/Makefile use.
  - **Merge / weld** (`operations/merge.{hpp,cpp}`, Python `_merge.py`): `merge(vector<const Mesh*>, MergeOptions{weld,atol,source_tag,data_policy,drop_duplicate_cells})` → `MergeResult{mMesh, mPointMaps, mCellMaps}` — combine 2+ meshes into one. **Concatenate** (default, O(N)): prefix-sum point offsets, offset connectivity, merge cell blocks by `Type()` (first-seen order), concat data. **Weld** (`weld=true`): coincident points within `atol` fused via a spatial-hash bucket grid — quantize to `atol`-cells (`parallel_for`), **serial** first-occurrence dedup checking the 27-neighbourhood (keep-first, deterministic), then `parallel_for_bw` gather + connectivity remap (surface.cpp's phase-split philosophy, no O(N²)). `source_tag` (default on) adds Int64 `source_mesh_id` cell_data (originating input per cell). `data_policy` `Intersection` (default; keep keys in all inputs) vs `Fill` (union, NaN→Float64 for missing rows); differing dtypes promote to Float64; 1-D scalar data stays 1-D. `drop_duplicate_cells` (weld-only) drops cells with identical sorted connectivity (keep-first). `field_data` key collisions namespace by source id (`"i:name"`). `mPointMaps`/`mCellMaps` (per-input old→new index, -1 for dropped cells) exist so the **Python shim** can remap+namespace the shim-only `point_sets`/`cell_sets` (never reach C++, like diff); `mesh.info`/`gmsh_periodic` not carried. Ragged/polyhedron blocks supported in C++ (the numpy fallback `_merge_py` is rectangular-only, raising otherwise). C API `mio_merge(meshes, count, weld, atol, source_tag, data_policy/*0=intersection,1=fill*/, drop_duplicate_cells)` → new `mio_mesh*`. Fortran module-level `mio_merge(meshes(:), ...)` → `type(mio_mesh)`. WASM `merge([...], weld, atol, sourceTag, dataPolicy, dropDuplicateCells)`. CLI verb `merge FILE… OUTFILE [--weld --atol --data-policy intersection|fill --drop-duplicate-cells --no-source-tag --quiet]` (last positional = output; prints an in/out/welded summary).
  - **Transform** (`operations/transform.{hpp,cpp}`, Python `_transform.py`): `transform(mesh, AffineTransform{4x4 row-major}, rotate_vector_data=false)` → new `Mesh` — affine transform of point coords (points change; connectivity/`cell_data`/`field_data` carried; `point_data` carried unless `rotate_vector_data` rotates trailing-dim-3 vectors `R·v` / trailing-dim-9 tensors `R·A·Rᵀ`). Builders `transform_translation`/`_scale`/`_units`/`_rotation`(Rodrigues)/`_from_matrix`/`_compose`. Points transformed in `parallel_for_bw` (dtype preserved). Negative-determinant transforms `log::warn` orientation-may-flip. `point_sets`/`cell_sets` pass through unchanged (Python shim). Python API builds the matrix from `translate`/`scale`/`rotate=(axis,deg)`/`matrix`/`scale_units` kwargs (compose order units→scale→rotate→translate). C API `mio_transform(mesh, double[16], rotate_vector_data)` → `mio_mesh*`. Fortran `m%transform(matrix(16), rotate_vector_data=...)`. WASM `transform(mesh, matrix, rotateVectorData)`. CLI `transform IN OUT --translate|--scale|--rotate|--matrix|--scale-units [--rotate-data]` (exactly one source; negatives need `--opt=` form).
  - **Clean** (`operations/clean.{hpp,cpp}`, Python `_clean.py`): `clean(mesh, CleanOptions{weld,atol,remove_orphans,drop_degenerate,drop_duplicate_cells})` → `CleanResult{mMesh, mPointMap, mCellMaps, mPointsWelded, mPointsRemovedOrphan, mCellsDroppedDegenerate, mCellsDroppedDuplicate}` — one-pass weld/prune/de-dup. Order: weld (spatial-hash bucket grid, keep-first, `clean_build_weld_map`, no O(N²)) → drop degenerate (repeated corner node, or |measure|<eps via `detail/geometry`+`cell_faces`) → drop duplicate (sorted-conn key, keep-first per block) → remove orphans (compact). Defaults: no weld, the other three on (matches CLI no-flag default). `point_data` keep-first on weld; sets remapped in the Python shim (dropped entries removed). Ragged/polyhedron supported in C++; numpy fallback rectangular-only (reuses `_merge._weld_map`). C API `mio_clean(mesh, weld, atol, remove_orphans, drop_degenerate, drop_duplicate_cells, &n_welded, &n_orphan, &n_degen, &n_dup)` → `mio_mesh*`. Fortran `m%clean(...)` with optional count out-args. WASM `clean(...)` → `{mesh, pointsWelded, ...}`. CLI `clean IN OUT [--weld --atol --remove-orphans --drop-degenerate --drop-duplicates]` (no step flags = default set).
  - **Crop** (`operations/crop.{hpp,cpp}`, Python `_crop.py`): `crop_bbox(mesh, lo[3], hi[3], CropMode::All|Any, record_ids=false)` and `crop_halfspace(mesh, point[3], normal[3], mode, record_ids)` → `CropResult{mMesh, mPointMap, mCellMaps}` — subset by AABB (`lo≤p≤hi`) or half-space (`(p−point)·normal≥0`). Per-point inside mask in `parallel_for`; keep cell if ALL (default) or ANY node inside; then `detail::build_cell_subset` prunes points + remaps. `record_ids` attaches Int64 `crop:original_point_id` point_data + `crop:original_cell_id` cell_data. Sets remapped in the Python shim. C API `mio_crop_bbox`/`mio_crop_plane(..., mode/*0=all,1=any*/, record_ids)` → `mio_mesh*`. Fortran `m%crop_bbox(lo,hi,mode=...)`/`m%crop_plane(point,normal,mode=...)`. WASM `cropBbox`/`cropPlane`. CLI `crop IN OUT --bbox …|--plane … [--mode all|any --record-ids]` (negatives need `--bbox=` form). Python API `crop(mesh, bbox=…|plane=(pt,nrm), mode, record_ids)`.
  - **Split** (`operations/split.{hpp,cpp}`, Python `_split.py`): `split(mesh, SplitBy::Type|Component|Tag, tag_name="")` → `SplitResult{vector<SplitPiece{mKey, mMesh, mPointMap, mCellMaps}>}` — partition into submeshes. **Type**: one piece per first-seen cell type. **Component**: union-find (`split_uf_*`) over node-sharing cell adjacency, one piece per connected component (keys `"0"`,`"1"`,…). **Tag**: distinct integer values of a named `cell_data` (auto-detect first integer cell_data if empty; keys = value). Each piece pruned via `detail::build_cell_subset(..., drop_empty_blocks=true)`. **File-writing is a caller concern** — the core returns pieces; the CLI/Python expand the `out_{key}.vtu` pattern. Python `split(mesh, by="type"|"region"|"component", tag=None)` → ordered `dict {key: Mesh}`; **`by="region"` uses `cell_sets` when present (Python-only), else the integer tag**. Sets remapped per piece in the shim. C API opaque `mio_split_result` (`mio_split(mesh, by, tag_name)` + `_count`/`_key`/`_mesh`/`_take_mesh`/`_free`). Fortran `m%split(by, tag_name=..., keys=...)` → `type(mio_mesh) array`. WASM `split(mesh, by, tagName)` → array of `{key, mesh}`. CLI `split IN OUT_{key}.EXT --by type|region|component [--tag NAME]`.
  - **Stats** (`operations/stats.{hpp,cpp}`, Python `_stats.py`): `compute_stats(mesh)` → `StatsReport{mNumPoints, mNumCells, mBBoxMin/Max/Extent/Centroid[3], mCellTypeCounts(vector<pair<name,count>>, first-seen), mTotalArea, mSignedVolume, mUnsignedVolume, mNumInverted}` — read-only geometric stats (the geometric complement to the topological `info`). bbox/centroid via chunked `parallel_for` reduction; per-cell area (tri/quad Newell) and 3D signed volume (divergence theorem over `cell_faces`, `parallel_for`); total area = 2D-cell areas + boundary area of 3D cells (via `extract_surface`); inverted = 3D cells with negative signed volume. pybind/Python/WASM return a dict/object incl. `cell_type_counts`; **C/Fortran fill a scalar `mio_stats_report` struct (per-cell-type counts omitted — documented flat-ABI gap)**. C API `mio_stats(mesh, mio_stats_report*)`. Fortran `report = m%stats()` (`type(mio_stats_report)`, `bind(c)`). WASM `stats(mesh)`. CLI `stats IN [--json]` (human table or JSON).
- **Data operations** (`cpp/src/operations/data_*.cpp` + headers, Python `_data_*.py`, docs `doc/data_operations.md` + one page per op): act on `point_data`/`cell_data`/`field_data`, **never** on geometry (points/connectivity/block order come through bit-identical — `cpp/tests/mesh_fixtures.hpp`'s `mt::expect_same_geometry` and `tests/helpers_data.py`'s `assert_same_geometry` assert this per op). Shared vocabulary in `operations/data_common.hpp`: `DataLocation{Point,Cell,Field}`, `NanPolicy{Ignore,Replace,Fail}`, the `*_from_name` string parsers (both CLIs and WASM pass enums as strings), and `data_unknown_key_message` (the standard "no X array named 'y' (available: …)" diagnostic). **Cross-cutting rules:** any op writing `cell_data` emits exactly `NumCellBlocks()` arrays (KRATOS materializes per-entity variables from that list) and any op reading one validates `CellDataNumBlocks(name) == NumCellBlocks()`; components = product of trailing dims, 1-D scalars stay 1-D; **non-finite values are always excluded from every reduction**, with `NanPolicy` deciding only what reaches the output (`data_info` never throws — it counts). `point_sets`/`cell_sets` pass through unchanged in the Python shim and never reach the core. The five operations:
  - **Array management** (`data_manage.{hpp,cpp}`, Python `_data_manage.py`): `data_manage(mesh, DataManageOptions{keep,drop,rename,ignore_missing})` → `DataManageResult{mMesh, mDropped, mRenamed}`, plus the `data_drop`/`data_keep`/`data_rename` convenience wrappers the flat bindings and CLIs use. Phases apply **keep → drop → rename**; `keep` only affects the locations it mentions (so `data_keep(m, Point, {})` drops all point_data but leaves cell/field alone — implemented as the *complement* via `drop`, not a sentinel key). All validation runs against the input before any cloning. Renaming onto an existing name throws unless that target is itself renamed away or dropped in the same pass, which makes a two-name swap legal. Values/dtypes/shapes are byte-identical passthrough. C API exposes the three primitives only (`mio_data_drop`/`_keep`/`_rename`) — the combined `data_manage` is a **documented flat-ABI gap**.
  - **Location averaging** (`data_average.{hpp,cpp}`, Python `_data_average.py`): `point_data_to_cell_data` (each cell = mean over its own nodes; ragged rows use `Row`, polyhedra the *distinct* nodes across faces) and `cell_data_to_point_data` (each point = mean over incident cells, `CellPointWeight::Uniform|Measure`; unavailable measures fall back to weight 1 with one warn per call). Component-wise; output is **always Float64** (a mean is not an integer). A point/cell with no finite contribution yields NaN. **The cell→point accumulation pass is deliberately SERIAL** — it is a scatter and FP addition is not associative, so parallelizing it would make results thread-count-dependent and flake the 4-leg backend matrix; only the final divide is `parallel_for_bw`. Same phase-split philosophy as `surface.cpp`.
  - **Expressions** (`data_calc.{hpp,cpp}`, Python `_data_calc.py`): `data_calc(mesh, expr, DataCalcOptions{location,output,overwrite,dtype})`. Hand-written tokenizer + recursive-descent parser — **no external parser lib, no arbitrary-code path**. Grammar: `+ - * /`, unary minus, parens, numeric literals, array names, and `abs`/`sqrt`/`min`/`max`/`norm`. Identifiers admit `:`/`.` after the first char (load-bearing: `gmsh:physical`), backticks quote names with spaces. Parse builds a **flat `vector<CalcNode>` pool** (shareable read-only across `parallel_for`, no per-node allocation); three passes: width inference + name resolution, operand widening to double once per array (`parallel_for_bw`), then the element loop (`parallel_for`) using stack buffers — `DATA_CALC_MAX_COMPONENTS=16` is what makes the loop allocation-free, `DATA_CALC_MAX_DEPTH=64` guards the parser against stack overflow from hostile input reaching it via the C ABI. Scalars broadcast against wider operands; `norm` is always scalar. Literals go through `std::strtod`, **not** `std::from_chars` (whose float overload is a real Emscripten/libc++ hazard) — matching `dex.cpp`/`wkt.cpp`/`nastran.cpp`. Every error is `std::invalid_argument` prefixed `meshio++: data_calc: ` and carries the character position. Division by zero is IEEE inf/NaN, not an error. Cell location evaluates **once per block**.
  - **Value conditioning** (`data_condition.{hpp,cpp}`, Python `_data_condition.py`): `data_condition(mesh, DataConditionOptions{location,names,mode,scope,lo,hi,nan_policy,nan_replacement,suffix,preserve_dtype})` with `ConditionMode{Clamp,Normalize,Standardize}` and `ConditionScope{Component,Magnitude}` (magnitude rescales whole rows, preserving direction). For `cell_data` the statistics are computed **jointly across all blocks** before one transform is applied to each. Degenerate reductions are handled, not NaN'd: constant array under Normalize → fill `lo` + warn; zero stddev under Standardize → fill 0 + warn. `Clamp` + `preserve_dtype` keeps the input dtype; Normalize/Standardize force Float64. `suffix` writes to a new name instead of in place.
  - **Data summary** (`data_info.{hpp,cpp}`, Python `_data_info.py`): `data_info(mesh)` → `DataInfoReport{mArrays, mNumPointData/CellData/FieldData}` of `DataArrayInfo` (location, name, dtype, shape, blocks, entries, components, values, min/max/mean whole-array *and* per component, NaN/inf/finite counts, `mInconsistentBlocks`), plus `data_array_info(mesh, loc, name)`. Read-only; the data-side complement to the topological `info` and the geometric `compute_stats`. **Never throws on non-finite values** and reports (rather than throws on) a cell_data array whose blocks disagree in component count. C/Fortran use an **opaque `mio_data_info` handle** (`_create`/`_count`/`_name`/`_entry`/`_component`/`_free`) since the report is variable-length — modelled on `mio_split_result`.
- **SVG/TikZ 3D rendering** (`cpp/include/meshioplusplus/detail/projection.hpp`, Python twin `src/meshioplusplus/_projection.py` — arithmetic kept expression-for-expression identical for TikZ byte-parity): non-flat 3D input (any |z| > 1e-14) takes a projected path — skin-extract volume cells (linearized), orthographic camera from `azimuth`/`elevation`/`roll` degrees (defaults 45/atan(1/√2)/0 = classic CAD isometric, `w ∝ (1,1,1)`), painter's-algorithm stable sort on face-centroid depth, then the existing path/`\draw` emission. Flat input keeps the legacy 2D code path physically untouched (byte-identical output). Camera args are appended **after** the existing writer params in the C++ signatures, pybind bindings, and shims — the shims pass positionally, order is load-bearing. `tests/test_tikz.py` asserts C++/Python byte-identity on the 3D path too; the FP-parity rules: cast coordinates to double before arithmetic, left-to-right multiply-adds, `std::stable_sort`/`np.argsort(kind="stable")`.
- **Container convention**: use `std::unordered_map`/`std::unordered_set` for name/id lookup and dedup tables (O(1), order-irrelevant) — the default. Reach for `std::map`/`std::set` **only** when sorted iteration order is itself relied on (see `su2` `tag_counts`, `openfoam` `by_n`, gmsh's `node_data`/`elem_data` staging locals). The mesh data maps' name order **is** observable — it drives Python dict key order and the on-disk field/variable order of writers (VTU, VTK, XDMF, Exodus, Tecplot, HMF, PLY, AVS-UCD, tetgen, h5m) plus "first int field" selectors (medit, ugrid, su2, netgen, avsucd). The uniform API bakes that guarantee in: `PointDataNames()`/`CellDataNames()`/`FieldDataNames()` **always return sorted names** on every backend (the former `detail::sorted_keys` idiom, now behind the accessors; `map_order.hpp` remains for non-Mesh maps and the pybind layer), so output stays byte-identical across backends.
- **C++ naming convention**: Kratos Multiphysics style — classes/structs/enums and methods (member functions) are `PascalCase` (e.g. `Mesh::NumPoints()`, `CellBlock::IsRagged()`); member variables are `m`-prefixed `PascalCase` (e.g. `Mesh::mPoints`, `CellBlock::mData`); reference parameters are `r`-prefixed (`const std::string& rPath`) and pointer parameters `p`-prefixed (`const int* pPerm`) — forwarding references (`F&&`) and rvalue-reference/move parameters are exempt; free functions, local variables, and lambda parameters stay `snake_case` (e.g. `read_vtu`, `parallel_for`, `detail::sorted_keys`). File names stay `snake_case`. Brace style is K&R (opening brace on the same line) at 4-space indentation — codified in the repo-root `.clang-format`, run via `clang-format -i` over `cpp/`, `bindings/`, `bindings_js/` (never `cpp/third_party`). None of this renames the pybind11/embind **string literals** that define the Python/JS-facing API (`.def("...")`, `.attr("...")`, `emscripten::function("...", ...)`) — those stay exactly as they are; only the C++ symbols on the other side of each binding call follow this convention.
- **Optional deps** (`CMakeLists.txt`): `MESHIOPLUSPLUS_WITH_HDF5`/`_NETCDF`/`_ZLIB`/`_EIGEN` options → `MESHIOPLUSPLUS_HAS_*` compile definitions and `_core.__has_hdf5__`/`__has_netcdf__` flags. `#ifdef`-guarded sources become empty TUs (or fall back to a plain loop) when off. Shared HDF5 helpers in `cpp/include/meshioplusplus/detail/hdf5_util.hpp`. **Eigen** is vendored as a git submodule at `cpp/third_party/eigen` (header-only; run `git submodule update --init` for source builds) and used for the MED Fortran↔C transpose (`med.cpp`, guarded by `MESHIOPLUSPLUS_HAS_EIGEN`); when the submodule is absent the code uses a hand-written transpose, so sdists without submodules still build.
- **C++ standard: C++20** (pinned in `CMakeLists.txt` twice: `CMAKE_CXX_STANDARD` + `target_compile_features`). macOS needs deployment target ≥ 13.3 for `std::format` (set in `ci.yml`/`wheels.yml`).
- **Logging** (`cpp/include/meshioplusplus/log.hpp`): `meshioplusplus::log::debug/info/warn/error("fmt {}", …)` — `std::format` (compile-time-checked) + `std::source_location`, thread-safe via `std::osyncstream`, filtered at runtime by the `MESHIOPLUSPLUS_LOG_LEVEL` env var (`debug|info|warn|error|off`, default `warn`). No printf/cerr elsewhere; errors remain exceptions.
- **Parallelism** (`cpp/include/meshioplusplus/parallel.hpp`): `meshioplusplus::parallel_for(n, f, grain=2048, max_threads=0)` with a compile-time backend selected by `MESHIOPLUSPLUS_PARALLEL_BACKEND` = `AUTO|SEQ|STL|OPENMP|TBB`. **Default is `AUTO`**, which prefers **OpenMP** (portable: libgomp on manylinux, MSVC built-in, libomp on macOS; needs no TBB), else the STL(+TBB) probe, else SEQ. `_core.__parallel_backend__` reports the active backend from Python (STL-without-TBB is effectively sequential — that's why AUTO avoids it). Adding a backend (Kokkos, …) = one CMake branch + one `#elif` in `parallel.hpp`. Iterations must be independent; the first exception is captured and rethrown after the join; `n <= grain` runs sequentially. **Two flavors:** `parallel_for` (all cores — for compute-bound loops: zlib/base64 in `detail/vtu_binary.hpp`, ASCII formatting) and **`parallel_for_bw`** (thread-capped, `parallel_bandwidth_threads=4` — for memory-bandwidth-bound loops: byte-swap/transpose/gather, which *regress* past ~4 threads because they saturate memory bandwidth). Use `parallel_for_bw` for byte I/O and index gathers; `parallel_for` only when the per-element work is real compute. The OpenMP backend uses `schedule(dynamic, grain/4)` — on hybrid CPUs (P+E cores) a static split makes E-cores stragglers; the chunk honours explicitly coarse grains (the VTU zlib loop passes `grain=1` so each block dispatches individually — do NOT floor the chunk above the grain). Hoist per-element dtype switches with `detail::dispatch_dtype(dt, []<class T>(){…})` (`value_io.hpp`) before parallelizing. **Binary I/O rule:** never write per-element to a `std::ostream` (byte-at-a-time `os.put`/tiny `os.write` was the pre-optimization VTK/Gmsh bottleneck) — build one pre-sized buffer (fused gather+byteswap where possible) and emit it with a single `os.write`; read binary sections straight into the destination array (or bulk seek+read, never `istreambuf_iterator`). Endianness conversion goes through `detail/byteswap.hpp` (`bswap_copy`/`bswap_inplace`, single-instruction intrinsics) — never a per-byte reversal loop.

**Format registration** (`src/meshioplusplus/_helpers.py`): each format's `__init__.py` calls `register_format(name, extensions, reader, {name: writer})`. `read`/`write` auto-detect from extension. Modules are imported (and thus registered) in `src/meshioplusplus/__init__.py`.

**Format module layout** (the shim pattern, e.g. `src/meshioplusplus/su2/`):
- `__init__.py` — imports `_core`, defines `read`/`write` that **try the C++ function and fall back** to the Python reference on any exception, then `register_format(...)`.
- `_<format>.py` — the pure-Python reference reader/writer.
- Multi-version formats (Gmsh, VTK) dispatch to version submodules.

**Cell type naming**: meshio++ uses its own names (`triangle`, `tetra10`, `hexahedron20`, …). Each format maps between its native names and meshio++'s (e.g. `gmsh/common.py`).

**Tests** (`tests/`): `helpers.py` has `Mesh` fixtures + `write_read()` (the round-trip pattern). Per-format `test_<format>.py` parametrize over meshes. `tests/meshes/` and `tests/input/` hold read-only reference files (Git-LFS). HDF5/netCDF suites use `pytest.importorskip`.

**CLI** (`src/meshioplusplus/_cli/`): `convert`, `info`, `ascii`, `binary`, `compress`, `decompress`, plus the operation verbs `quality`, `extract-surface`, `reorder`, `diff`, `merge`, `transform`, `clean`, `crop`, `split`, `stats`, registered in `_main.py`. **`data` is the repo's first *nested* subcommand** (`_cli/_data.py`, nine sub-verbs: `info`/`rename`/`drop`/`keep`/`to-cell`/`to-point`/`calc`/`clamp`/`normalize`) — it needs no change to `_main.py`'s dispatch because `set_defaults(func=...)` on the *inner* parser overrides the outer one, so the existing `args.func(args)` still reaches the right handler. **Colon rule** (implemented identically in `_cli/_data.py`, `cpp/cli/main.cpp` and `doc/cli.md`, because data names routinely contain colons): `data rename --point OLD:NEW` splits on the **last** colon, `data calc --point "NAME = EXPR"` on the **first** `=`; `drop`/`keep` take comma-separated lists with no location prefix.

**CI** (`.github/workflows/`): `ci.yml` (3-OS Python test matrix — Linux/macOS build native paths, Windows builds them off and uses Python fallbacks — plus a `cpp-tests` matrix running the gtest suite per mesh backend: MESHIO×STL, MESHIO×OPENMP, NATIVE×OPENMP, KRATOS×OPENMP, the non-MESHIO legs with `BUILD_PYTHON=OFF`; every leg also builds with `BUILD_C_API=ON`/`BUILD_FORTRAN=ON` so the C-API gtests and the `fortran_api` ctest run per backend; the NATIVE leg additionally does a `cmake --install` + external-consumer smoke test — gcc via pkg-config, gfortran against the installed `.mod`, and a `find_package` mini-project, compiling `doc/examples/*`; the KRATOS leg also compile-checks `kratos_bridge.hpp` against real CoSimIO headers cloned at CI time), `wheels.yml` (cibuildwheel with native paths off + PyPI trusted publishing on `v*` tags; the Linux matrix legs are `ubuntu-latest` (x86_64) and `ubuntu-24.04-arm` (arm64) — GitHub's free-for-public-repos hosted arm64 runner, native build with no QEMU/binfmt setup, since cibuildwheel's `CIBW_ARCHS` defaults to the runner's own arch and `CIBW_MANYLINUX_AARCH64_IMAGE` was already pinned), `packages.yml` (Conan recipe + vcpkg overlay validation on PRs; full vcpkg port build on `v*` tags; the Conan job's matrix crosses `{fallback, full}` option sets with `{x86_64 (ubuntu-latest), arm64 (ubuntu-24.04-arm)}` via `include` — see the note below), `cli.yml` (builds the standalone native CLI binary on PRs touching `cpp/`/`CMakeLists.txt`; on `v*` tags builds and attaches one statically-linked binary per supported OS/arch — Linux x86_64 and Linux arm64 (`ubuntu-24.04-arm`, native, no emulation) both in the matching `manylinux_2_34` container with gcc-toolset-13 + `MESHIOPLUSPLUS_STATIC_RUNTIME=ON`, verified to have no `libstdc++`/`libgcc_s` dependency; macOS universal (x86_64+arm64 via `CMAKE_OSX_ARCHITECTURES`); Windows x86_64 with the MSVC static CRT (`/MT`) — to the tag's GitHub Release, mirroring `packages.yml`'s release job. All legs build with `MESHIOPLUSPLUS_WITH_HDF5/NETCDF/ZLIB=OFF` and `PARALLEL_BACKEND=SEQ` for a dependency-free single-file binary — same portability trade-off as the manylinux wheel leg; users needing those need `build/configure.sh --cli` from source), `docs.yml` (VitePress → GitHub Pages).

## Adding a new format

1. Create `src/meshioplusplus/<format>/_<format>.py` (Python reference `read`/`write`) and `__init__.py` (shim + `register_format`). `register_format` may also live directly in `_<format>.py` for a Python-only format with no shim to wrap (e.g. `mdpa`, `neuroglancer`, `ansysInp`, `openfoam`).
2. Add the C++ implementation: `cpp/src/formats/<format>.cpp` + `cpp/include/meshioplusplus/formats/<format>.hpp`, bind it in `bindings/_core.cpp`, register it in the shared dispatch registry (`cpp/src/registry.cpp`: reader/writer entry + extension default — that's what makes it reachable from WASM and the C/Fortran API), and switch `__init__.py` to the try-C++/Python-fallback shim. New `.cpp` files are auto-globbed by CMake. The implementation must build/read the mesh **through the uniform mesh API only** (see the "Uniform mesh API rule" above) so it works under every mesh backend. **This step is optional** — a format can stay Python-only indefinitely (precedent: `mdpa`, `neuroglancer`, and the Simvia-contributed `ansysInp`/`openfoam`); don't force a C++ port just to satisfy this checklist.
3. Import the module in `src/meshioplusplus/__init__.py` (both the import tuple and `__all__`).
4. Add `tests/test_<format>.py` using `helpers.write_read()`. Verify a direct C++ roundtrip and cross-compat with the Python reference (if a C++ path exists).
5. **Update `README.md`, `doc/formats.md`, and this file** (see "Keeping docs in sync").

Do not copy test data from GPL sources (e.g. FEconv examples) into this MIT repo — generate reference files via round-trip instead. Code/fixtures from other MIT-licensed forks in the same lineage (e.g. the [meshlane](https://github.com/simvia-tech/meshlane) fork) may be copied directly; credit the source in `CITATION.cff`/`CHANGELOG.md`.

**Note on `ensight`:** EnSight Gold, geometry only (`.case` + `.geo` sibling pair; write logic ported from Kratos's `EnSightOutput`, reader is meshio++-original). ASCII + C-binary both ways; the binary reader auto-detects a foreign byte order from record plausibility. Per the Gold spec connectivity is **positional** (1-based into the part's coordinates) — `given`/`ignore` id arrays are skipped, matching VTK's readers (not Kratos's id-based writing assumption). Node ordering: meshio (VTK) order matches EnSight for every type except `wedge15` ↔ `penta15`, which differ by the involution `{0,2,1,3,5,4, 8,7,6, 11,10,9, 12,14,13}` — do **not** port Kratos's penta15/hexa20 group swaps (those fix Kratos-specific ordering). Multi-part files → concatenated points, one block per part-section, `cell_data["ensight:part"]` when ≥2 parts; the writer emits a single `assign`-id part and drops mesh data (warns). Ragged write raises (v1).

**Note on `vtp`:** VTK XML PolyData; shares the VTU stack — the `<DataArray>` helpers live in `detail/vtk_xml.hpp` (used by `vtu.cpp`/`vtu_read.cpp`/`vtp.cpp`/`vtp_read.cpp`; keep VTU byte-identical when touching it). Surface cells only; cell data follows VTK's canonical Verts→Lines→Polys order (writer reorders blocks into that partition). PolyData has no cell-type array, so 3-/4-noded polygons read back as triangle/quad. The pybind `vtp_write` binding opts into `allow_ragged` (jagged polygons are legal Polys rows).

**Note on `triangle`:** 2D analogue of tetgen (`.node`/`.ele` pairs → `triangle`/`triangle6`, `.poly` PSLG → `line` segments; holes/regions skipped with a warning). Extension dispatch: `.node`/`.ele` stay tetgen-first everywhere; the Python reader dispatcher falls through to triangle when tetgen raises on a 2D file, writes need `file_format="triangle"`; only `.poly` defaults to triangle (also in the C++ registry, so the flat bindings need an explicit format for 2D `.node`/`.ele`). The multi-file buffer guards in `_helpers.py` cover `tetgen`/`triangle`/`ensight`.

**Note on `med`:** the C++ core (built with HDF5) handles the mesh-representation part of MED exactly — points, point/cell tags, families with `GRO` group names, mesh-level metadata (`mesh_name`/`description`/`unit_time`/`unit_coords`/`point_tag_groups`/`cell_tag_groups`, via `MedInfo`), node-orientation permutations, and `POG`/`POG2` ragged polygons — and `meshioplusplus.med.read`/`write` use it by default. It **raises** (→ Python fallback) for the constructs it does not replicate byte-for-byte: `CHA` fields (MED-4.1 bitmask / units / step metadata), the `gmsh:physical`→family bridging, non-default profiles/ELGA, and multi-mesh files (`read_med_multi`/`write_med_multi` are always Python). The C++ MED reader iterates `MAI` cell blocks in HDF5 **creation order** (`group_links_crt`, matching h5py `track_order`) since block order aligns cell_data/cell_sets; the shim reconstructs `point_sets`/`cell_sets` from families via the shared Python helpers. See [`doc/formats/med.md`](doc/formats/med.md#quirks-limitations).
