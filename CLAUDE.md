# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

meshio++ (Python package/import name `meshioplusplus`) is a Python library for reading and writing many mesh file formats used in scientific computing and FEM (Finite Element Method). It provides a unified `Mesh` data structure that all format readers/writers convert to and from.

This branch (`port-to-c++`) adds a **C++ core** (`meshioplusplus._core`, pybind11) built with **scikit-build-core + CMake**, replacing the old setuptools build. Most formats read/write through the C++ core with a pure-Python fallback.

## Keeping docs in sync (required)

**Every time a feature or format is added or changed, update all three of `CLAUDE.md`, `README.md`, and the `doc/` site in the same change.** At minimum: the format table and format-specific notes in [`doc/formats.md`](doc/formats.md) (plus any other relevant `doc/` page), the supported-formats list in `README.md`, and the architecture/"Adding a new format" guidance here. Changes to the shared format registry or the flat-binding surfaces must also be reflected in [`doc/wasm.md`](doc/wasm.md), [`doc/c_api.md`](doc/c_api.md), and [`doc/fortran.md`](doc/fortran.md). A feature is not "done" until CLAUDE.md, README.md, and the docs all reflect it.

**Keep the example notebooks (`example/*.ipynb`) current with new features too.** When a user-facing capability is added (a new operation, a new format, a notable API), demonstrate it in the notebooks (a new/updated cell) and re-execute them with outputs (`PYVISTA_OFF_SCREEN=true jupyter nbconvert --to notebook --execute --inplace example/*.ipynb`) so the committed outputs stay in sync. **Notebook demos must be graphical, not just printed values** — render results with PyVista (off-screen: `pv.OFF_SCREEN=True` + a `pv.Plotter(off_screen=True).screenshot(return_img=True)` embedded via matplotlib, with a matplotlib fallback for head-less GL), coloring the mesh by the relevant data array (quality metric, per-point diff error, ...) so the effect is visually understandable. `example/03_mesh_operations.ipynb` is the reference pattern for the operations.

## Version bumps (required)

**"Bump the version" always means every one of these five, together, to the same value — never just one or two:**

- [`pyproject.toml`](pyproject.toml) — `version`
- [`CMakeLists.txt`](CMakeLists.txt) — `project(... VERSION ...)`
- [`conanfile.py`](conanfile.py) — `version`
- [`ports/meshioplusplus/vcpkg.json`](ports/meshioplusplus/vcpkg.json) — `version`
- [`wasm/package.json`](wasm/package.json) — `version` (npm publish uses this file verbatim; it silently lagged behind at 6.3.0 through two releases before this rule existed — it's the one that's easiest to forget since it lives outside the Python/CMake build)

The CMake `VERSION` feeds `mio_version()`, the C API `.so`'s VERSION/SOVERSION, and the installed package configs, so it isn't optional/cosmetic.

**A dated [`CHANGELOG.md`](CHANGELOG.md) entry is required in the same change as every version bump** — new formats, new operations, notable enhancements *and* breaking changes, not breaking changes only. Mark breaking items explicitly with a **Breaking:** prefix; everything else is assumed additive. (This rule replaced a breaking-changes-only policy under which the file silently fell six releases behind, from v6.6.0 to v7.1.0 — the entries were reconstructed from git history. Treat "bump the five version files" and "add the CHANGELOG entry" as one indivisible step.) A pure patch/bugfix bump can be a single line.

## Commands

**Build/install for development** (native paths on). PEP 668 systems: use the in-repo uv venv (`uv venv --python 3.12 .venv`), then:
```bash
CMAKE_ARGS="-DMESHIOPLUSPLUS_WITH_HDF5=ON -DMESHIOPLUSPLUS_WITH_NETCDF=ON -DMESHIOPLUSPLUS_WITH_ZLIB=ON" \
  uv pip install --python .venv --no-build-isolation -e .
```
Plain environments: `pip install -e ".[all]"`. The optional deps (HDF5, netCDF, zlib) are auto-detected; when absent the C++ paths compile out and Python fallbacks (h5py/netCDF4/stdlib zlib) take over.

**Standalone C++ build**: `build/configure.sh` (Linux/macOS) and `build/configure.bat` (Windows) configure a CMake tree next to themselves (`build/cpp-<type>[-<mesh-backend>]`); flags: `--backend SEQ|STL|OPENMP|TBB`, `--mesh-backend MESHIO|NATIVE|KRATOS` (non-MESHIO implies `-DMESHIOPLUSPLUS_BUILD_PYTHON=OFF`), `--tests`, `--cli` (the native CLI binary, below), `--build`, `--with/-out-hdf5/netcdf/zlib`, `--tbb-dir <path>`. They print the matching `CMAKE_ARGS … pip install` line (MESHIO only).

**Native CLI binary** (`cpp/cli/main.cpp` → `meshioplusplus_cli`, installed executable name `meshioplusplus`): a **Python-free** command-line tool over `meshioplusplus_core_obj` mirroring the Python console script's verbs (convert/info/ascii/binary/compress/decompress/quality/extract-surface/reorder/diff/merge/transform/clean/crop/split/convert-cells/refine/partition/smooth/stats/view/screenshot, plus the nested `data <verb>` group with the same nine sub-verbs and the same colon rules). Supporting the repeated `--point`/`--cell`/`--field` flags the `data` verbs need required one extension to the hand-rolled parser: `cli_opt_spec` gained nothing, but `cli_parsed` gained a `multi` map recording every occurrence of each value-option, populated **alongside** the existing last-wins `values` map so all 16 pre-existing verbs are behaviourally unchanged; read it with `opt_values(p, name)` and test presence with `has_opt(p, name)`. `MESHIOPLUSPLUS_BUILD_CLI` (OFF by default; `build/configure.sh --cli --build`). Reuses the shared `registry.hpp` for format dispatch (with the `sniff_format` read fallback); ASCII/binary/compress variants call the per-format writer free functions directly (the registry bakes one default per format), and the operation verbs use `operations/*.hpp`. Works under any mesh/parallel backend and optional-dep set. **Documented gaps vs the Python CLI** (same as the C-API/WASM flat surfaces): point/cell **sets** and `convert -s/-d` never reach the C++ core, so `info`/`diff` omit sets and `convert -s/-d` errors; formats whose C++ reader raises (e.g. gmsh `$Entities`, which the Python path handles via fallback) are unreadable here — there is no Python fallback; and `view`/`screenshot` exist only in a **Polyscope-enabled** build (`-DMESHIOPLUSPLUS_WITH_POLYSCOPE=ON`, OFF by default and never in the release binaries — see the viewer entry below), otherwise they are listed but throw naming the flag. `--version`'s `MESHIOPLUSPLUS_CLI_VERSION` is fed by CMake `PROJECT_VERSION`. **Prebuilt, statically-linked release binaries** (Linux x86_64, Linux arm64, macOS universal, Windows x86_64) are attached to every `v*` tag's GitHub Release by `cli.yml` (see "CI" below) — built with `MESHIOPLUSPLUS_STATIC_RUNTIME=ON` (hoisted to a top-level option so it applies to both `_core` and `meshioplusplus_cli`: static `libgcc`/`libstdc++` on GNU, static MSVC CRT via `MSVC_RUNTIME_LIBRARY` on Windows) and `WITH_HDF5/NETCDF/ZLIB=OFF` + `PARALLEL_BACKEND=SEQ` for a single dependency-free executable; build from source with `--cli` (optionally without `--without-hdf5` etc.) for the full native format/threading feature set.

**WebAssembly build** (`@meshioplusplus/wasm` npm package): `build/configure-wasm.sh --build` (needs the [Emscripten SDK](https://emscripten.org/docs/getting_started/downloads.html) on `PATH`) configures `build/wasm-<type>` with `-DMESHIOPLUSPLUS_BUILD_PYTHON=OFF -DMESHIOPLUSPLUS_BUILD_WASM=ON -DMESHIOPLUSPLUS_PARALLEL_BACKEND=SEQ -DMESHIOPLUSPLUS_MESH_BACKEND=NATIVE` (the fastest mesh backend; the JS API shape is unchanged and `meshBackend()` reports `"native"`), HDF5/netCDF off, builds `bindings_js/js_bindings.cpp` (embind) against the same `meshioplusplus_core_obj` as `_core`, and copies `meshioplusplus_wasm.{mjs,wasm}` into `wasm/dist/`. Ships 36 formats + XDMF's XML/Binary path — 35 readable, 36 writable (`openfoam` read-only; `svg`/`tikz` write-only), no HDF5/netCDF-backed formats — see `doc/wasm.md`. Smoke test: `node wasm/test/smoke.mjs`. **Three files, not one:** a binding is only reachable from `loadMeshioPlusPlus()` if it is (1) registered in `bindings_js/js_bindings.cpp`, (2) **forwarded** in `wasm/src/index.mjs`'s returned object, and (3) declared in `wasm/index.d.ts`. Step 2 is the one that gets forgotten — it silently shipped every geometry op unreachable until v7.4.0 (and the `data_*` ops until v7.2.1). `smoke.mjs` exercises operations **through the wrapper**, never `Module.*`, precisely so a missing forward fails the build, and its reflection guard is now **exhaustive** over all 39 names rather than the geometry ops only. Note that `bindings_js/` is **outside the amalgamation** (which covers `cpp/include` + `cpp/src`), so a binding-only addition needs no single-header regen — `availableFormats` and `convertSurface` (v7.8.0) were both added that way. `-fwasm-exceptions` is required (applied `PUBLIC` on `meshioplusplus_core_obj` under `if(EMSCRIPTEN)`) so `ReadError`/`WriteError` surface as catchable JS `Error`s instead of aborting; `log.hpp`'s `std::osyncstream` usage has a `std::mutex`-guarded fallback for standard libraries (Emscripten's non-threaded libc++) that ship `<syncstream>` without actually defining it (`__cpp_lib_syncbuf` unset). `configure-wasm.sh` runs `embuilder build zlib` right after configuring (when zlib is on) to pre-warm Emscripten's zlib port cache single-threaded — `-sUSE_ZLIB=1` makes every translation unit trigger that port's build on first use, and a parallel `-j` build races many `em++` invocations against the same cold-cache lock, aborting with "attempt to lock the cache while a parent process is holding the lock (sanity)". CI (`.github/workflows/wasm.yml`) builds+smoke-tests and publishes to npm (`NPM_TOKEN` secret) only on `v*` tags (mirrors `wheels.yml`'s trigger), plus `workflow_dispatch`.

**C API / Fortran build** (`libmeshioplusplus` + Fortran module, for C/Fortran HPC consumers): `build/configure.sh --c-api` or `--fortran` (implies `--c-api`; both also exist in `configure.bat`, Fortran untested on MSVC) → CMake options `MESHIOPLUSPLUS_BUILD_C_API` / `MESHIOPLUSPLUS_BUILD_FORTRAN` (both OFF by default). `cmake --install <tree> --prefix <p>` installs the shared lib(s), the single pure-C header `bindings_c/include/meshioplusplus/meshioplusplus.h`, a `find_package(meshioplusplus)` config package, a relocatable pkg-config file, and (Fortran) the `.mod` **plus** `bindings_fortran/meshioplusplus.f90` (`.mod` files are compiler-specific; consumers on another compiler recompile the module — the HDF5 approach). Tests: `cpp/tests/test_c_api.cpp` (auto-globbed into the gtest suite when C_API is on) and the `fortran_api` ctest (`bindings_fortran/test/test_fortran_api.f90`). CI-tested consumer examples: `doc/examples/c_api_example.c`, `doc/examples/fortran_example.f90`. See "Version bumps" above — `project()`'s `VERSION` feeds `mio_version()` and the `.so`'s VERSION/SOVERSION here.

**Conan / vcpkg packaging** (self-hosted, in-repo, for the C API): the root `conanfile.py` (Conan 2.x, with `test_package/`) and the `ports/meshioplusplus/` vcpkg overlay port (`vcpkg.json` + `portfile.cmake` + `usage`) both drive the same `-DMESHIOPLUSPLUS_BUILD_C_API=ON -DMESHIOPLUSPLUS_BUILD_PYTHON=OFF` install/`find_package` path (the `meshioplusplus::meshioplusplus` target). Options/features: `with_hdf5`/`with_netcdf`/`with_zlib` (on) and `fortran`/`with_eigen`/`with_kahip` (off — Eigen is a submodule absent from a source tarball, so the MED transpose uses the fallback loop; KaHIP is on neither ConanCenter nor the vcpkg registry, so `with_kahip`/the vcpkg `kahip` feature map only the CMake flag and the consumer supplies `KAHIP_ROOT`; the lib is shared-only). The vcpkg `hdf5` feature depends on upstream vcpkg's `hdf5` port with `default-features: false` + explicit `features: ["zlib"]` (meshio++ never uses szip, only plain HDF5 + zlib) — kept for forward compatibility, but currently **ineffective**: a known vcpkg-tool limitation (`default-features: false` isn't honored reliably even for a direct manifest dependency — reproduced locally against a fresh vcpkg checkout; see microsoft/vcpkg#31230/#26664) means `hdf5`'s own default `szip` feature still gets pulled in regardless, which in turn needs `libaec`. The **actual** fix is `ports/libaec/`, a second overlay port (alongside `ports/meshioplusplus/`) that replaces vcpkg registry's `libaec` portfile — otherwise byte-identical — with one sourcing the same `v1.1.7` tag from `Deutsches-Klimarechenzentrum/libaec` on GitHub instead of `gitlab.dkrz.de`: same maintainer/org, same release content (different tarball SHA512 since GitHub and GitLab produce differently-encoded archives for identical source), reachable without the rate-limiting (HTTP 429) that had been intermittently failing the release-tag `vcpkg-build` CI job. Verified locally end-to-end (bootstrapped vcpkg, built `libaec`+`hdf5`+`netcdf-c` against this overlay set). `.github/workflows/packages.yml` validates the Conan recipe (two option legs, each on x86_64 and arm64 — see "CI" below) and the vcpkg manifest (x86_64 only; the overlay-port zip it produces is source, not an arch-specific binary) on every PR, and on `v*` tags pins the tarball SHA512 + builds the vcpkg port end-to-end. Not submitted to Conan Center / the upstream vcpkg registry (documented follow-up) — as a stopgap, `v*` tags attach ready-to-use Linux package artifacts, for both x86_64 and arm64, to the tag's GitHub Release (created if absent, via `softprops/action-gh-release`): a `conan cache save "meshioplusplus/<version>:*"` archive per option leg × arch (supplies just the recipe + one matching prebuilt binary — `conan cache restore <file>` then `conan install --requires=meshioplusplus/<version> --build=missing -o ...`; Conan Center still supplies the transitive hdf5/netcdf/zlib/openssl binaries over the network as normal, and `--build=missing` rebuilds meshioplusplus from the archived recipe if the consumer's profile doesn't match the prebuilt one — verified end-to-end both ways) and a zip of the vcpkg overlay port with the release tarball's SHA512 already pinned in (the in-repo `portfile.cmake` keeps the `SHA512 0` placeholder; only the release asset's copy is patched). Docs: [`doc/c_api.md`](doc/c_api.md#package-managers-conan-vcpkg).

**Run tests:** `pytest tests/` (or `.venv/bin/python -m pytest tests/`).
Single file/test: `pytest tests/test_gmsh.py::test_gmsh22`.

**Coverage** (`MESHIOPLUSPLUS_COVERAGE=ON` → `--coverage -O0 -g -fprofile-update=atomic` on `meshioplusplus_core_obj`, GCC/Clang only; OFF by default so a normal `pip install` never pays for it): the `coverage` job in `ci.yml` measures **both layers in one job** so a single `lcov` capture sees the C++ core exercised by the GoogleTest binary **and** by the pytest suite through the pybind11 shims (measuring only the gtest binary badly under-reports the format code). This relies on pyproject's persistent `build-dir = "build/{wheel_tag}"` (the `.gcno/.gcda` survive the pip build) — don't split C++/Python into separate jobs. The gtest build sets `-DMESHIOPLUSPLUS_BUILD_C_API=ON` so `bindings_c/c_api.cpp` and its `test_c_api.cpp` suite are instrumented too. Uploads go to Codecov under two flags, `python` (`src/meshioplusplus/`) and `cpp` (`cpp/`, `bindings/`, `bindings_c/`), gated on the `CODECOV_TOKEN` secret; `.codecov.yml` owns the (blocking) status thresholds and `pyproject.toml`'s `[tool.coverage.run] relative_files=true` keeps `coverage.xml` paths repo-relative. The non-MESHIO mesh-backend headers (`native_mesh`/`kratos_mesh`/`model_part`/`kratos_names`) are excluded from the denominator (both `lcov --remove` and `.codecov.yml` ignore) because this MESHIO-only job never instantiates them — they are covered by the separate `cpp-tests` backend matrix; `single_include/` (generated) is ignored too. Reproduce locally per the two builds in the job: an instrumented standalone `build-cpp-cov` (`-DMESHIOPLUSPLUS_BUILD_PYTHON=OFF -DCMAKE_BUILD_TYPE=Debug`, ctest) plus an instrumented editable install (`CMAKE_ARGS="-DMESHIOPLUSPLUS_COVERAGE=ON …" SKBUILD_CMAKE_BUILD_TYPE=Debug SKBUILD_EDITABLE_REBUILD=false`, then `pytest --cov meshioplusplus --cov-report xml`), then `lcov --capture --directory build-cpp-cov --directory build`. Locally add `-DMESHIOPLUSPLUS_WITH_NETCDF=OFF` and run `ctest -j1` (see the netCDF/MPI link quirk).

**Lint / format:** `pre-commit run -a` (isort, black, flake8). Or `black --check . && flake8 . && isort --check .`.

**C++ include hygiene** (`tools/include-cleanup.sh` + `.clang-tidy`): IWYU-style check via clang-tidy's `misc-include-cleaner`. `--check` (CI gate, `include-cleanup` job in `ci.yml`) fails on any **unused** include; missing-include suggestions are **advisory only** (the convention that a format's `.cpp` leans on its own format header to pull in the mesh types is kept). `--fix` removes unused includes. Deliberately-kept includes (the HDF5/netCDF format headers in `registry.cpp`, guarded optional-dep includes) carry `// IWYU pragma: keep`. Run the gate where HDF5/netCDF are installed (as CI does) or their format registrations compile out and look spuriously unused. `.clang-format` still owns ordering (`SortIncludes: Never`).

**Single-header amalgamation** (`tools/amalgamate.sh` + `tools/amalgamate/amalgamate.py`): generates the committed, STB-style header-only `single_include/meshioplusplus/meshioplusplus.hpp` (all of `cpp/include` + `cpp/src` + bundled pugixml; declarations always visible, `.cpp` bodies behind `#define MESHIOPLUSPLUS_IMPLEMENTATION`). Backend defaults MESHIO/sequential; HDF5/netCDF/zlib/Eigen stay behind `MESHIOPLUSPLUS_HAS_*`. The generator emits every header once at file scope in dependency order (so no header is trapped inside another's `#ifdef`). `--smoke` regenerates + compiles it (decls-only, impl, two-TU link). The `amalgamation` CI job regenerates, `git diff --exit-code`s (fails if stale — **regenerate and commit after any `cpp/` change**), and smoke-compiles. Anonymous-namespace helpers must stay uniquely named across `cpp/src/*.cpp` (they concatenate into one TU under the impl macro; format-prefixed like `su2_tokens`/`GmshCursor`). Docs: [`doc/single_header.md`](doc/single_header.md).

**CLI usage:**

**Native CLI viewer** (`cpp/cli/view_payload.{hpp,cpp}` + `polyscope_view.{hpp,cpp}`, `MESHIOPLUSPLUS_WITH_POLYSCOPE`, **OFF by default**): Polyscope (MIT) vendored as a git submodule at `cpp/third_party/polyscope` — it is in no package manager and its docs offer only `add_subdirectory`/FetchContent. It has **its own** submodules, so `git submodule update --init --recursive` is required; a plain `--init` leaves an `EXISTS`-guarded no-op (the Eigen pattern) and the viewer is simply absent. **It links to the CLI target ONLY, never to `meshioplusplus_core_obj`** — unlike KaHIP, which is in the core because partitioning is a core operation. Viewing is not, so `_core`/C API/Fortran/WASM cannot acquire an OpenGL dependency through it and "the core is dependency-free" stays literally true. Release binaries are unaffected: the flag defaults off and `cli.yml`'s existing `! ldd | grep libstdc++` assertion is the guard. **The mapping is split at the same seam as Python's**: `view_payload.cpp` is deliberately free of every Polyscope header, so it compiles and is gtested (`test_view_payload.cpp`, 14 cases) in the *default* build with no GL, while `polyscope_view.cpp` is the only TU including Polyscope and the only thing the flag guards. `view_payload.cpp` is the **twin of `_viewer.py`'s `_to_polyscope_payload` — KEEP THEM IN SYNC**; both are needed because Python's must work with no compiled core, so moving the logic would relocate the duplication rather than remove it, and the two test suites assert the same invariants deliberately. Two facts read from the vendored headers rather than the docs: the mixed-cell padding sentinel is **`INVALID_IND_32` (UINT32_MAX)**, not the negative value the Python docs describe (the container is `std::array<uint32_t,8>`); and **`registerTetHexMesh` concatenates tets-then-hexes regardless of input order**, which would silently re-map every per-cell quantity — so the padded array must be built by us in block order, and a test pins that. `view`/`screenshot` exist in every build and throw naming the flag when compiled out (the `partition_kahip_parts` contract). CI: the `cli-polyscope` job in `ci.yml`, never `cli.yml`.

**Interactive viewer** (`src/meshioplusplus/_viewer.py` + `_viewer_browser.py`, web app in `viewer/`, docs [`doc/viewer.md`](doc/viewer.md)): one entry point `view(mesh, backend="auto"|"polyscope"|"browser", kind=, color_by=, name=, show=)` plus `screenshot(mesh, path, ...)` and `has_viewer()`, and CLI verbs `view`/`screenshot`. **Polyscope is a PYTHON-ONLY optional dependency** behind the `[viewer]` extra — lazily imported inside the two functions that need it, never at module scope, and it never reaches the C++/WASM/C/Fortran core; a missing install raises naming `pip install meshioplusplus[viewer]`. The bulk of the module is the **pure** `_to_polyscope_payload(mesh, kind)` (no renderer import, no display, no mutation), which is what makes the routing testable in the default CI matrix with polyscope absent. Routing facts that are contracts, not preferences: polyscope volume meshes hold **only tetrahedra and hexahedra**, so wedge/pyramid/higher-order go through `convert_cells(simplexify)` but hexes deliberately do not; a mesh with both tets and hexes is packed into a negative-padded `mixed_cells` array **here** rather than handed over as separate `tets=`/`hexes=` arguments, because otherwise the row order — and so every per-cell quantity — would depend on polyscope's internal merge order; each structure type has its own `defined_on` vocabulary (surface `vertices`/`faces`, volume `vertices`/`cells`, curve `nodes`/`edges`, point cloud **none at all**); `_init_polyscope` is idempotent because polyscope refuses to re-init with a different backend, so a headless screenshot followed by a window would otherwise raise. Cell data is tied to rendered primitives by the `cell_source` global-cell-index array from `_dimension_rows`, whose counter advances over *skipped* blocks — a gmsh file whose `triangle` block follows a boundary-marker `line` block is what makes that necessary, and the wrong answer still renders. Colours are detected by array **name** (`color`/`rgb`/`*_color`/`*_rgb`), never inferred from a [0,1] range. Every lossy step appends to a `notes` list surfaced as a warning. `_viewer_browser.py` writes **VTP** (not VTU — vtk.js has no unstructured-grid model) into the committed single-file bundle at `src/meshioplusplus/_viewer_assets/viewer.html`; its `_renderable_surface` is the **Python twin of the WASM `convertSurfaceOps([])` binding and the two must stay in step** (pinned by a test, not by coincidence). The offline page has no WASM and so cannot *run* operations: anything it should show is baked in by Python — `build_page(..., quality=True)` attaches metrics **before** the boundary extraction so the existing parent-id gather carries them for free, `stats=True` (default) embeds the volume mesh's geometry, and `color_by` resolves to the viewer's `location:name:component` key and **raises** on an unknown name. All three go through exact-string payload slots that CI greps for.

**Browser viewer** (`viewer/`, Vite + **TypeScript** + `@kitware/vtk.js`): a web app that **CONSUMES the published `@meshioplusplus/wasm` package**, not the core — vtk.js/Vite/Playwright are isolated under `viewer/`'s own `package.json` and never touch the root or `wasm/`. Two builds from one source: `build:web` (the Pages demo, WASM worker + file picker) and `build:embed` (a single self-contained file shipped in the wheel, where the WASM client is **aliased to a stub** — dead-code elimination alone is not enough, since Vite's worker plugin emits `new Worker(new URL(...))` chunks at *transform* time). Deployed by **`docs.yml`** as a second static island at `/viewer/` beside Doxygen's `/api/` — a repo gets one Pages deployment, so a separate workflow would fight it over the `pages` concurrency group. That job must run emsdk + `./build/configure-wasm.sh --build` first, because `wasm/dist/` is gitignored. **npm *copies* a `file:` dependency and a later `npm install` does not refresh the copy**, so `vite.config.mjs` compares both the wrapper's exports and the installed `.wasm` against `wasm/dist/` at `buildStart` and fails with the `rm -rf node_modules/@meshioplusplus` recipe; CI is immune because it builds then runs `npm ci`. Viewer samples and fixtures carry a **Git LFS exemption** (`.gitattributes`) — an LFS-less checkout would otherwise hand the app 130-byte pointer files. Playwright asserts on the documented `window.__viewerState` hook rather than pixels, so it needs no GPU. **Click-to-inspect** uses `vtkCellPicker` (CPU ray/cell, so renderer-independent) on click only — its listener must go on the **container**, not the canvas, because vtk.js takes pointer capture on the container and a canvas-bound `click` never fires at all; provenance comes from the `surface:parent_cell` that `convertSurfaceOps(keepProvenance: true)` retains and `scalars.ts` filters out of the colour-by menu. **The app runs meshio++'s own operations** (quality/clean/smooth/refine/partition/section) through the single `convertSurfaceOps` binding: the panel owns the pipeline as a list, every change re-sends the *whole* list, and the worker replays it against the **original file bytes kept staged in MEMFS** — which is why `apply` deliberately never unlinks, why undo is exact rather than an inverse, and why multi-component data survives (no mesh re-enters JS). **TypeScript conventions**: `as any` is banned in `src/` and CI-grepped; gaps go in `vtk-augmentations.d.ts` (declaration merging, still type-checked) or `vtk-shims.ts` (named `as unknown as` helpers) — the augmentation file must **not** be named `vtk-shims.d.ts`, since TS would resolve it and `vtk-shims.ts` to one module, keep the `.ts`, and silently drop the declarations. `window.__viewerState` is typed in `src/types.ts` so a new field with un-updated tests is a compile error. Two vtk.js findings worth not rediscovering: `setInterpolateScalarsBeforeMapping(true)` renders a range spanning zero **entirely in the warm half** in 32.9.0 (measured: 0 blue px vs 275k red), so it is off; and the coincident-topology polygon offset belongs on the **edge** mapper, because a negative offset moves toward the viewer and putting it on the body hides the wireframe behind its own surface. `vtkClipClosedSurface` is unusable for a coloured cut (its point-data interpolation is commented out upstream), which is why the section goes through meshio++'s `crop_plane` + re-skin instead. Regenerate the wheel asset with `npm run build:embed && cp dist-embed/index.html ../src/meshioplusplus/_viewer_assets/viewer.html`; the CI check on it is **structural (10% size drift), never a `git diff`** — Rollup output is not reproducible across npm patch releases.

## Architecture

**Core data model** (`src/meshioplusplus/_mesh.py`, pure Python, unchanged):
- `Mesh`: holds `points`, `cells` (list of `CellBlock`), `point_data`, `cell_data`, `field_data`, `point_sets`, `cell_sets`, optionally `gmsh_periodic`/`info`
- `CellBlock`: a cell type string (e.g. `"triangle"`, `"tetra10"`) + numpy node-index array
- `_common.py`: `num_nodes_per_cell`; `topological_dimension` in `_mesh.py`

**C++ core** (`cpp/`, `bindings/`):
- `cpp/include/meshioplusplus/` headers (`ndarray.hpp`, `mesh.hpp`, `mesh_api.hpp`, `cell_type.hpp`, `types.hpp`, `registry.hpp`, `backends/*`, `detail/*`, `formats/*`), `cpp/src/formats/*.cpp`, compiled with `bindings/_core.cpp` into `meshioplusplus._core`.
- **Format dispatch registry** (`registry.hpp` + `cpp/src/registry.cpp`, compiled into `meshioplusplus_core_obj`): the C++-level `format name -> read/write function` tables, `extension -> default format` map, `resolve_format()`, and `registry_compiled_out()` (names the missing optional dep for HDF5/netCDF formats absent from a build; their extensions are mapped unconditionally so errors say "no HDF5 support" instead of "cannot infer format"). Shared by the **flat bindings** — WASM (`bindings_js/js_bindings.cpp`, which no longer carries its own tables) and the C API (`bindings_c/`) — while the pybind11 binding keeps its one-function-per-format surface with dispatch in Python (`_helpers.py`). Parameterized writers get fixed defaults here (documented per entry; matching the Python reference defaults, except xdmf which follows the build: HDF when HDF5 is available, XML otherwise). **A new C++ format must also be registered here** (reader/writer entry + extension default) or the flat bindings won't see it.
- **C API** (`bindings_c/`): `include/meshioplusplus/meshioplusplus.h` (the single installed pure-C99 header; the C++ headers make no ABI promise) + `c_api.cpp`, built into the installable `libmeshioplusplus` shared lib (SOVERSION 0) when `MESHIOPLUSPLUS_BUILD_C_API=ON`. Flat whole-mesh API over the **uniform mesh API only**, so it compiles under all three mesh backends and the gtest C-API suite runs per-backend in CI. Contract: `mio_status` codes + thread-local `mio_last_error()` (no exception crosses the ABI — every extern "C" body runs in `guarded()`/`guarded_ptr()`); setters copy, getters are zero-copy borrows valid until the next mutating call; strings via caller-buffer + required-length return (never `c_str()` of a per-backend-possibly-temporary `Type()`); row-major arrays, 0-based connectivity (int32 widened to int64 on ingest); ragged blocks are reported (`is_ragged`) but their connectivity is inaccessible (v1); side-channel structs (point_sets/cell_sets/MED families) are dropped like WASM. The `mio_cell_type` enum duplicates the cell-type list in the C header and `c_api.cpp` static_asserts every entry against `CellType`, so drift is a compile error.
- **Fortran module** (`bindings_fortran/meshioplusplus.f90`, module `meshioplusplus`, `MESHIOPLUSPLUS_BUILD_FORTRAN=ON` which force-enables the C API): modern OO Fortran 2008 (`type(mio_mesh)` with type-bound procedures, HDF5/PETSc style) over the C API via ISO_C_BINDING; raw `bind(c)` interfaces are private (`c_mio_*`). Conventions: arrays are Fortran-shaped — points `(dim, n)`, conn `(npc, ncells)` — which is the *same memory* as the C row-major shapes (no transpose anywhere); connectivity is 1-based, shifted ±1 inside the copying setters/getters only; `points_ptr` is the zero-copy borrow (no shift needed); every fallible procedure takes optional `stat`/`errmsg`, absent `stat` + failure = print + `error stop` (stdlib pattern); handles freed explicitly (`m%free()`, no finalizer).
- **Mesh backends** (`mesh.hpp` dispatch; mirrors the parallel-backend pattern): `MESHIOPLUSPLUS_MESH_BACKEND` = `MESHIO|NATIVE|KRATOS` selects, at compile time, which structure `meshioplusplus::Mesh` is — exactly one `MESHIOPLUSPLUS_MESH_BACKEND_*` macro is defined. `MESHIO` (default, `backends/meshio_mesh.hpp`) is the meshio-mirroring `Mesh`/`CellBlock` and is **required** when `MESHIOPLUSPLUS_BUILD_PYTHON=ON` (CMake `FATAL_ERROR` otherwise; `np_conversions.hpp` `#error`s too) — PyPI/wheels are unaffected by the other backends. `NATIVE` (`backends/native_mesh.hpp`) is canonical statically-typed storage (Float64 points, Int64 connectivity, `CellType` enum from `cell_type.hpp`, CSR ragged blocks, lazy whole-mesh CSR via `GlobalConnectivity()`); the WASM build uses it. `KRATOS` (`backends/kratos_mesh.hpp`) wraps a Kratos-style `ModelPart` (`backends/model_part.hpp`: Nodes/Elements/Conditions with 1-based Ids, nested SubModelParts sharing root-owned entities, simplified per-entity variables) — ingest stages canonically, `GetModelPart()` materializes lazily (Elements = blocks of max topological dimension, Conditions = lower, names from `backends/kratos_names.hpp` ported from `_mdpa.py`; integer tag cell-data like `gmsh:physical` auto-becomes SubModelParts, toggle `SetBuildSubModelPartsFromTags(false)`), writers serve from staging so round-trips never pay for the ModelPart; after direct ModelPart mutation call `InvalidateBlocks()`. `kratos_bridge.hpp` (header-only, backend-independent) `to_model_part`/`from_model_part` populate/read ANY Kratos-like class — incl. real `Kratos::ModelPart` via a properties-getter — with one O(n) bulk-create pass; CI compile-checks it against real CoSimIO headers (fetched at CI time only — CoSimIO's BSD-4-clause-with-advertising license is never vendored into this MIT repo; `model_part.hpp` is a clean-room implementation). `_core.__mesh_backend__` / JS `meshBackend()` report the active backend. **Adding a backend** = one CMake branch defining `MESHIOPLUSPLUS_MESH_BACKEND_<NAME>` + one `#elif` in `mesh.hpp` + a `backends/<name>_mesh.hpp` implementing the uniform API (`cpp/tests/test_mesh_api.cpp` must pass). CI runs the gtest suite once per backend (`ci.yml` `cpp-tests` matrix).
- **Uniform mesh API rule** (`mesh_api.hpp`): format code (`cpp/src/formats/*`, shared `detail/*` helpers, `bindings_js/`) MUST go through the uniform methods — ingest `AssignPoints`/`AddCellBlock`/`AddPolygonBlock`/`AddPolyhedronBlock`/`AddPointData`/`AddCellData`/`AppendCellData`/`AddFieldData`, accessors `Points()`/`PointDim()`/`Cells(i)`/`CellRange()` (`Mesh::CellView` with `Type()`/`NumCells()`/`NodesPerCell()`/`Conn()`/`IsRagged()`/ragged `Row`/`Face`) and `PointDataNames()`/`PointData(name)`/`CellData(name, block)`/`CellDataNumBlocks`/`FieldData(name)` (+ `Has*`/`Num*`) — and never backend struct members; that's what lets one format compile under all three backends. Hoist `Points()`/`Conn()`/data lookups out of per-element hot loops. The one sanctioned exception is `bindings/np_conversions.hpp` (pinned to MESHIO). NATIVE/KRATOS canonicalize dtypes at ingest *within kind* (floats→Float64, ints→Int64, never int→float — "first integer cell_data is the tag" conventions survive); owning canonical arrays are moved, not copied.
- **Zero-copy at the I/O boundary**: readers return capsule-backed writeable numpy; writers view numpy memory (`bindings/np_conversions.hpp`). The conversion layer carries points/cells/point_data/cell_data/field_data, but **not** `mesh.info`, `cell_sets`, or `point_sets` — formats that need those either defer to Python or carry them out-of-band via a **side-channel struct** the binding `setattr`s onto the Python `Mesh` (e.g. `MedInfo`, `AnsysInfo`/`UnvInfo` for `point_sets`/`cell_sets`, `OpenFoamInfo` for `cell_tags`). **Field-only formats** (`mff`/`dex`/`ip`, the Modulef/FLUX/ANSYS-Fluent field files) carry no geometry: they read/write a geometry-less `Mesh` (no cells, field values in `point_data`; `dex`/`ip` also fill `points` from the file's coordinates, `mff` has none so its `points` has zero columns) — there is no companion-mesh auto-pairing.
- **Ragged cell blocks**: every backend supports optional ragged blocks — 1-level (jagged polygons, `AddPolygonBlock`) and 2-level (list of faces per cell, `AddPolyhedronBlock`) — for types that can't fit a rectangular `NDArray`, read back via `CellView`'s `RowSize`/`Row` and `NumFaces`/`Face`. MESHIO stores them as nested vectors (`CellBlock::mPolygonRows`/`mPolyhedronRows`), NATIVE as CSR offset arrays, KRATOS as staging pass-through (no ModelPart entities). Zero-copy applies only to rectangular blocks; ragged blocks are **copied** across the Python boundary. `py_to_mesh`'s `allow_ragged` flag is **off by default** (so every rectangular-only writer keeps safely rejecting ragged meshes → Python fallback) and only the ragged-aware bindings (MED write) opt in.
- **Operations layer** (`cpp/src/operations/*.cpp` + `cpp/include/meshioplusplus/operations/*.hpp`): computations *on* a mesh (not file formats — deliberately **not** registered in `registry.cpp`). Each operation is uniform-mesh-API-only (compiles under all three backends — the KRATOS `Mesh` is **not** copy-constructible, so never `Mesh out = in;`; clone via the uniform API as `quality_clone_mesh` does), parallelizes its hot loop with `parallel_for`, and is exposed across **every** binding surface (pybind `_core`, C API `mio_*`, Fortran type-bound procedures, WASM embind) plus a CLI verb. `.cpp` anon-namespace helpers are uniquely prefixed (`surface_`/`quality_`/`sniff_`/`reorder_`/`diff_`/`merge_`/`transform_`/`clean_`/`crop_`/`split_`/`stats_`/`ccells_`/`refine_`/`partition_`/`smooth_`, and for the data bundle `dmanage_`/`davg_`/`calc_`/`dcond_`/`dinfo_` — **distinct per file**, since a shared `data_` prefix across five TUs would collide) because the amalgamation concatenates TUs; `detail/` header inline helpers (`geometry.hpp`, `cell_edges.hpp`, `cell_subdivision.hpp`, `subset.hpp`, `space_filling.hpp`, `node_adjacency.hpp`, `data_ops.hpp`) are exempt. New `cpp/src/operations/*.cpp` are auto-globbed by CMake and `rglob`ed by the amalgamator — regenerate + commit the single header after any change. The **crop** and **split** operations share `detail/subset.hpp`'s `build_cell_subset` (prune-points-to-kept-cells + remap connectivity/data, `drop_empty_blocks` flag for split's homogeneous pieces); the five **data operations** share `detail/data_ops.hpp`'s `clone_mesh(mesh, filter)` (backend-agnostic geometry copy + per-array keep/rename decision — the workaround for the uniform API having no remove/rename for data arrays), `FiniteStats` (chunked parallel reduction, serial combine, non-finite values excluded and counted) and `cell_measure`. The **convert_cells** (elevate mode) and **refine** operations share `detail/cell_subdivision.hpp`'s `cell_refine_edges`/`cell_refine_quad_faces` — the single owner of "the edges / quad faces of type T, in the order T's higher-order node slots expect" (it delegates the 2D rows to `cell_edges.hpp`, which stays surface-only); two transcriptions of the tetra10/hexahedron20/wedge15 orderings would drift silently, since a mismatch still yields a valid, oriented, volume-conserving mesh — just one with permuted quadratic mid-nodes. The **reorder** and **partition** operations share `detail/space_filling.hpp`'s `sfc_part1by2`/`sfc_morton_key`/`sfc_hilbert_key` (the pure Morton/Skilling-Hilbert key transforms, hoisted verbatim from reorder in v7.6.0 — reorder's output stayed byte-identical); the Mesh-coupled bbox/quantization stays per-operation (reorder quantizes node coordinates, partition cell centroids). The **reorder** and **smooth** operations also share `detail/node_adjacency.hpp`'s `build_node_adjacency` — one CSR node-to-node graph with two neighbour definitions, because the consumers genuinely want different graphs: `NodeAdjacencyKind::Clique` (every pair of nodes co-occurring in a cell — the FEM stiffness sparsity pattern, which is exactly what a bandwidth-reducing renumbering must minimise) for **reorder**, `NodeAdjacencyKind::Edge` (only nodes joined by an actual cell edge, topology from `cell_subdivision.hpp`'s `cell_refine_edges` so the three cannot drift) for **smooth**; `node_edge_topology_known` reports the blocks that contribute no edges so a caller can pin their nodes. The fifteen **mesh** operations (on geometry) and five **data** operations (on data arrays) are listed below.
  - **Surface/skin extraction** (`operations/surface.{hpp,cpp}`, Python `_surface.py`/`_skin.py`): `extract_surface(mesh, record_parent_ids=false)` picks the dimension automatically (3D volume → boundary faces, 2D surface → boundary edges via `detail/cell_edges.hpp`); `extract_skin(mesh, linearize=false)` (declared in `skin.hpp`) is the volume-only special case — **both share the one implementation in `surface.cpp`** (`extract_skin` calls it in force-face mode, byte-identical to the old `skin.cpp` it absorbed). Kratos `SkinDetectionProcess` face-hashing (sorted corner-node key occurring exactly once = boundary); face topology in `detail/cell_faces.hpp` (Python twin in `_skin.py`, must stay in sync; outward winding enforced by a gtest Newell-normal invariant in `test_skin.cpp`), edge topology in `detail/cell_edges.hpp` (twin in `_surface.py`). Supported volume types: tetra(10), hexahedron(20/27), wedge(15/18), pyramid(13/14) — `wedge18` gained its `cell_faces` row in v7.5.0 (refine needed its quad-face centres), which made it newly skinnable. Output blocks in fixed canonical order (triangle, triangle6, quad, quad8, quad9 / line, line3), points compacted ascending original-id (numpy fallback relies on `np.unique` sortedness for identical output — `tests/test_skin.py`/`test_extract_surface.py`), `point_data` subset, other data dropped. Two-phase parallel: keys built in `parallel_for` into disjoint slots, then a **serial** dedup/emit so output is byte-identical across backends and thread counts. `record_parent_ids` attaches Int64 `surface:parent_cell` cell_data (per-output-facet owning input-cell index). **Consumers:** `write_stl`/`write_ply` take a trailing `skin` flag (default **true** — writes the extracted linearized skin, STL triangulating quads; `skin=false` = legacy drop-with-warning; pinned true in `registry.cpp`), and the SVG/TikZ writers project the skin (below).
  - **Mesh quality** (`operations/quality.{hpp,cpp}`, Python `_quality.py`): `compute_quality(mesh)` → `QualityReport` (per-metric summaries + histograms, per-block `cell_data` arrays, inverted/degenerate counts); `attach_quality(mesh)` returns a clone with the metrics as `cell_data` (names `quality:<metric>`). Metrics (triangle/quad/tetra/hex/wedge/pyramid, quadratic variants on corners; NaN where N/A): volume/area, scaled_jacobian, aspect_ratio, skewness, min/max_angle, warpage, min/max_dihedral, inverted, degenerate. Verdict/VTK formulas; ideal element → ideal value (SJ=1, aspect=1, skew=0, tri angles 60°, tetra dihedral ≈70.53°) — pinned by `test_quality.cpp`/`tests/test_quality.py`. Reusable vec3 math in `detail/geometry.hpp`.
  - **Format sniffing** (`operations/sniff.{hpp,cpp}`, Python `_sniff.py`): `sniff_format(path)` returns a format name only on a confident leading-bytes signature match (vtk/vtu/vtp/gmsh/ply/off/xdmf/stl-ascii/abaqus), else `""` (ambiguous magics like generic HDF5 or headerless binary STL are never claimed). Wired as a **read-only** fallback in the read paths (`_helpers._read_file`, C `mio_read`, WASM `read_mesh`) when the extension gives nothing — never on a write path.
  - **Reordering / renumbering** (`operations/reorder.{hpp,cpp}`, Python `_reorder.py`): `reorder(mesh, ReorderMethod::RCM|Morton|Hilbert)` → `ReorderResult{mMesh, mNodePermutation, mCellPermutations}` — a **pure permutation** (no nodes/cells added/removed, geometry + all data preserved) returning the applied node/cell permutations (old→new, Int64). RCM builds the node-adjacency CSR (element cliques — nodes sharing a cell are neighbours), picks a pseudo-peripheral start per connected component (rooted-level-structure heuristic), Cuthill–McKee BFS by increasing degree, then reverses; Morton/Hilbert quantize coords to 21 bits/axis over the bbox and stable-sort along the curve. Element perm orders each block's cells by min new-node index. Applies to points/point_data (scatter by node perm, dtype-preserving byte-row gather via `parallel_for_bw`) + connectivity (Int64, remap+reorder) + cell_data (reorder by per-block cell perm); field_data unchanged; ragged/polyhedron blocks supported. `compute_bandwidth(mesh)` = max over cells of (max−min node index). The BFS/argsort stay serial for cross-backend determinism (surface.cpp's phase-split philosophy). `point_sets`/`cell_sets` are remapped in the Python shim (they never reach the C++ core); `mesh.info`/`gmsh_periodic` are not carried through. The C API uses an opaque `mio_reorder_result` handle (mesh borrow + zero-copy perm getters + `mio_reorder_result_take_mesh` ownership transfer for Fortran); Fortran/WASM expose node perm (Fortran, 1-based) / full node+cell perms (WASM object). CLI verb `reorder … --method rcm|morton|hilbert [--report]`.
  - **Comparison / diff** (`operations/diff.{hpp,cpp}`, Python `_diff.py`): `diff(mesh_a, mesh_b, DiffOptions{atol,rtol,unordered,max_reported})` → `DiffReport` (verdict `Identical`/`EqualWithinTolerance`/`Different`; per-section `ArrayDiff`/`BlockDiff`/`DataDiff` with max abs/rel error, worst flat index, mismatch counts, keys-only-in-one, first-N mismatching cells); `meshes_equal(a,b,atol,rtol)` = `verdict != Different` (ordered). Tolerance rule `abs_err <= atol + rtol*|expected|` (expected from `a`); "identical" is exact equality. **Ordered** path (default) compares points/cells/data index-by-index — the elementwise reduce is chunked and `parallel_for`-parallel, combined serially (deterministic). **Unordered** (`unordered=true`) matches points by proximity via a bucket-grid coordinate hash (no O(N²)); conservative — sets `mCorrespondenceFailed` + verdict `Different` rather than guessing when no one-to-one match exists. Only points/cells/`point_data`/`cell_data`/`field_data` are reachable in C++; **named `point_sets`/`cell_sets` are compared in the Python shim only** (added/removed/changed → a `"sets"` report section, folded into the verdict) — C/Fortran/WASM never see sets. Python `diff` returns a nested dict (with the numpy fallback returning an identically-keyed dict), `meshes_equal` is a boolean; `_format_report` renders the CLI output. C API: `mio_diff`/`mio_meshes_equal` + opaque `mio_diff_result` (verdict/point-summary/per-block getters, `mio_diff_result_free`). Fortran `m%equals`/`m%diff` (verdict 0/1/2). WASM `diff`/`meshesEqual`. CLI verb `diff A B [--atol --rtol --unordered --exact --quiet]` — **exit code is nonzero when meshes differ** (0 for identical or equal-within-tolerance; `--exact` makes only identical pass) for CI/Makefile use.

  - **Smoothing** (`operations/smooth.{hpp,cpp}`, Python `_smooth.py`, docs [`doc/smooth.md`](doc/smooth.md)): `smooth(mesh, SmoothOptions{method, iterations, lambda, mu, fix_boundary, preserve_features, feature_angle, guard_inversion, frozen, move_tolerance})` → `SmoothResult{mMesh, mNumNodesMoved, mMaxDisplacement, mNumSkippedInversion}` — relax point coordinates toward their edge-neighbour centroids, the quality-*improving* companion to `compute_quality`, which measures exactly what this changes. A **pure coordinate move**: connectivity, `cell_data`, `field_data` and `point_data` *values* pass through unchanged, point/cell counts are unchanged, and the points array keeps its input dtype (iteration runs in `double` with a single cast on write-back, so a Float32 mesh does not accumulate one rounding per pass). Both operators are driven by the same displacement `L(i) = mean(x[j] : j adjacent to i) - x[i]`: **Laplacian** (`x <- x + lambda*L(x)`) is strong per pass but unconditionally shrinking, **Taubin** (the default) follows each `+lambda` pass with a larger-magnitude `-mu` pass whose pass band leaves features alone (on a jittered 8x8 quad grid over 40 iterations Laplacian contracts the bbox 57%, Taubin 3.6%). `mLambda` uses a **negative sentinel meaning "this method's own default"** — 0.5 Laplacian, 0.33 Taubin — because the sensible value genuinely differs per method and two separate fields would let a caller set the one the chosen method ignores; Python spells the parameter `lambda_` (trailing underscore, `lambda` being a keyword). The neighbour graph is `node_adjacency.hpp`'s **Edge** kind, *not* reorder's Clique: under the clique a hexahedron corner is pulled by its three face diagonals and its body diagonal as hard as by its real edge neighbours, bevelling cubes toward spheres, whereas the edge graph leaves a structured hex block a fixed point. **Pinned by default**: boundary nodes (`mFixBoundary`, classic once-used-facet test — a face used by exactly one 3D cell, or in a pure surface mesh an edge used by exactly one 2D cell), feature nodes where two incident boundary facet **normals** differ by more than `mFeatureAngleDeg` (default 30, the `vtkFeatureEdges` convention, which is what keeps a cube's edges sharp), the caller's `mFrozen` mask, and the nodes of blocks whose edge topology is unknown (the higher-order family, VTK-Lagrange, `custom`) — an unknown neighbourhood is an undefined target, so the node holds still rather than being guessed at. The **inversion guard** (default on) commits a candidate position only if no incident cell's signed measure changes sign, counting each `(node, pass)` rejection; it is "do no harm", not "preserve the sign", so a cell that arrives already inverted imposes no constraint and a tangle can still be repaired. Measures: face-fan volume (tetra/hexahedron/wedge/pyramid), signed shoelace area (2D cells in a 2D mesh), and normal-flip (2D cells in a 3D mesh) — that last mode is smooth's own, with **no counterpart in `compute_quality`**, which correctly declines to call a triangle floating in 3D "inverted" for want of a global orientation convention; a cell with no signed measure at all (`line`, polyhedron, `custom`) is **skipped, not pinned**, since a missing safety check is not a missing target and pinning there would freeze an entire beam-element curve. Determinism: every pass is **Jacobi** (all new positions computed from the previous pass and committed together, so no node observes a half-updated neighbour), neighbour sums run in ascending node id over the sorted adjacency rows, the boundary set comes from a **serial** dedup over a `parallel_for`-filled disjoint-slot buffer (surface.cpp's phase-split idiom) and the counters fold serially out of per-node slots — byte-identical across the three mesh backends and across 1/2/8 threads on a 52k-node mesh. Throws `std::invalid_argument` on a mis-sized `mFrozen`, `mLambda` outside (0,1), or a Taubin `mMu` not satisfying `mMu < -mLambda < 0` (which would amplify rather than filter); `mMoveTolerance` is **relative to the bbox diagonal** so `mNumNodesMoved` is scale-invariant. The numpy fallback (`_smooth_py`) implements both operators but **deliberately not the guard** — it is a discrete branch on a sign, and near-degenerate cells could land the two implementations on opposite sides and then diverge macroscopically — so it raises `NotImplementedError` when one is requested, and the shim re-raises `ValueError`/`TypeError` from `_core` rather than letting a genuine user error fall through to numpy. The Python shim also resolves `frozen` given as a `point_sets` **name** and copies `point_sets`/`cell_sets` through untouched (nothing is renumbered, so unlike refine/crop/split there is nothing to remap). C API `mio_smooth(mesh, method, iterations, lambda, mu, fix_boundary, preserve_features, feature_angle, guard_inversion, &nodes_moved, &max_displacement, &skipped_inversion)` → a plain `mio_mesh*` with nullable counter out-params (mio_clean's shape, **not** an opaque result handle — there are no index maps to hand back); `frozen` is **not** exposed on the flat ABI, a documented gap like the sets gaps in diff/merge/split. Fortran `m%smooth(method, iterations [, lambda, mu, fix_boundary, preserve_features, feature_angle, guard_inversion, nodes_moved, max_displacement, skipped_inversion])`. WASM `smooth(mesh, method, iterations, lambda, mu, fixBoundary, preserveFeatures, featureAngle, guardInversion)` → `{mesh, numNodesMoved, maxDisplacement, numSkippedInversion}`. CLI verb `smooth IN OUT [--method taubin|laplacian --iterations N --lambda L --mu=M --no-fix-boundary --no-preserve-features --feature-angle A --no-guard-inversion --quiet]` in both CLIs (a negative `--mu` needs the `--mu=` form).

CLI: `info --fast`, `convert --points-only|--arrays`, in both CLIs.
- **Memory-mapped reading** (`cpp/include/meshioplusplus/detail/file_source.hpp`, docs [`doc/mmap.md`](doc/mmap.md)): `FileSource` is RAII whole-file access — POSIX `mmap`+`MADV_SEQUENTIAL`, Windows `MapViewOfFile`, always buffered under Emscripten. `Auto` maps regular files ≥ `mmap_auto_threshold_bytes` (16 MiB; `MESHIOPLUSPLUS_MMAP_THRESHOLD` overrides). Mapping is **advisory** — anything unmappable falls back silently rather than erroring. It is a **memory-footprint** win (one fewer full-file copy, halved peak RSS), not a throughput one; say so rather than overselling. **Lifetime is trivial by construction**: every reader copies into owning storage, so nothing in a returned `Mesh` points into the buffer and `FileSource` is just a function-local — the rule "nothing derived from `View()` may be stored in the mesh" is pinned by a read-then-unlink-then-revalidate test. **A mapped buffer is only NUL-terminated because the kernel zero-fills the final partial page**, which `strtod` (gmsh's `next_double`) relies on; files whose size is an exact page multiple are therefore never mapped, even on an explicit request. Windows needs `WIN32_LEAN_AND_MEAN`+`NOMINMAX` before `<windows.h>` since this header reaches user TUs via the amalgamation. All five whole-file readers are migrated: `gmsh` (which also honours an explicit `ReadOptions::mMmap`), `vtk_read`, `ensight`, `ugrid`'s ASCII branch and `openfoam` — the last gained most, since its `ostringstream`+`.str()` paid for two extra full-file copies. Cursors/parsers that held `const std::string&` now hold `std::string_view`; the ascii OpenFOAM parsers deliberately still take an owned string, because they consume via `istringstream`, which cannot take a view — converting them would only relocate the copy. `ugrid`'s binary branch keeps streaming per-section from an `ifstream` (no whole-file intermediate to map).
- **Compression codecs** (`detail/vtu_binary.hpp`'s `VtkCodec`, docs [`doc/codecs.md`](doc/codecs.md)): zlib (default, always) plus optional **zstd**/**lz4** behind `MESHIOPLUSPLUS_WITH_ZSTD`/`_LZ4` → `MESHIOPLUSPLUS_HAS_*` and `_core.__has_zstd__`/`__has_lz4__`/`__has_zlib__`. Both default **OFF** (unlike HDF5/netCDF/zlib) so a build without them reads and writes exactly what it always did; never probed under Emscripten (no port exists). All codecs share VTU's block framing verbatim (32 KiB blocks) — only the per-block compressor differs, dispatched through `vtk_codec_compress_block`/`_decompress_block`, parallelized with `parallel_for` `grain=1` (**not** `parallel_for_bw`). **`lz4` = real VTK interop** (`vtkLZ4DataCompressor`, LZ4 *raw block* format — the size comes from VTU's header since raw blocks carry none); **`zstd` = documented meshio++ extension** (`vtkZSTDDataCompressor`; VTK ships no ZSTD compressor, so ParaView reports an unknown compressor rather than misreading). The per-codec helpers **always exist and throw at runtime** when compiled out — a link error would break the Python-fallback contract — with messages naming the CMake option, `registry_compiled_out()`-style; availability is checked once at header parse. The pure-Python reference supports both via the `codecs` extra, so the fallback is real; a file needing a codec present in neither is genuinely unreadable (a new failure class, failing by name). `--codec zlib|lz4|zstd` on both CLIs' `compress`, **rejected** for formats with no block codec rather than silently ignored. Conan `with_zstd`/`with_lz4` + vcpkg `zstd`/`lz4`, both off by default.
- **Data operations** (`cpp/src/operations/data_*.cpp` + headers, Python `_data_*.py`, docs `doc/data_operations.md` + one page per op): act on `point_data`/`cell_data`/`field_data`, **never** on geometry (points/connectivity/block order come through bit-identical — `cpp/tests/mesh_fixtures.hpp`'s `mt::expect_same_geometry` and `tests/helpers_data.py`'s `assert_same_geometry` assert this per op). Shared vocabulary in `operations/data_common.hpp`: `DataLocation{Point,Cell,Field}`, `NanPolicy{Ignore,Replace,Fail}`, the `*_from_name` string parsers (both CLIs and WASM pass enums as strings), and `data_unknown_key_message` (the standard "no X array named 'y' (available: …)" diagnostic). **Cross-cutting rules:** any op writing `cell_data` emits exactly `NumCellBlocks()` arrays (KRATOS materializes per-entity variables from that list) and any op reading one validates `CellDataNumBlocks(name) == NumCellBlocks()`; components = product of trailing dims, 1-D scalars stay 1-D; **non-finite values are always excluded from every reduction**, with `NanPolicy` deciding only what reaches the output (`data_info` never throws — it counts). `point_sets`/`cell_sets` pass through unchanged in the Python shim and never reach the core. The five operations:
  - **Array management** (`data_manage.{hpp,cpp}`, Python `_data_manage.py`): `data_manage(mesh, DataManageOptions{keep,drop,rename,ignore_missing})` → `DataManageResult{mMesh, mDropped, mRenamed}`, plus the `data_drop`/`data_keep`/`data_rename` convenience wrappers the flat bindings and CLIs use. Phases apply **keep → drop → rename**; `keep` only affects the locations it mentions (so `data_keep(m, Point, {})` drops all point_data but leaves cell/field alone — implemented as the *complement* via `drop`, not a sentinel key). All validation runs against the input before any cloning. Renaming onto an existing name throws unless that target is itself renamed away or dropped in the same pass, which makes a two-name swap legal. Values/dtypes/shapes are byte-identical passthrough. C API exposes the three primitives only (`mio_data_drop`/`_keep`/`_rename`) — the combined `data_manage` is a **documented flat-ABI gap**.
  - **Location averaging** (`data_average.{hpp,cpp}`, Python `_data_average.py`): `point_data_to_cell_data` (each cell = mean over its own nodes; ragged rows use `Row`, polyhedra the *distinct* nodes across faces) and `cell_data_to_point_data` (each point = mean over incident cells, `CellPointWeight::Uniform|Measure`; unavailable measures fall back to weight 1 with one warn per call). Component-wise; output is **always Float64** (a mean is not an integer). A point/cell with no finite contribution yields NaN. **The cell→point accumulation pass is deliberately SERIAL** — it is a scatter and FP addition is not associative, so parallelizing it would make results thread-count-dependent and flake the 4-leg backend matrix; only the final divide is `parallel_for_bw`. Same phase-split philosophy as `surface.cpp`.
  - **Expressions** (`data_calc.{hpp,cpp}`, Python `_data_calc.py`): `data_calc(mesh, expr, DataCalcOptions{location,output,overwrite,dtype})`. Hand-written tokenizer + recursive-descent parser — **no external parser lib, no arbitrary-code path**. Grammar: `+ - * /`, unary minus, parens, numeric literals, array names, and `abs`/`sqrt`/`min`/`max`/`norm`. Identifiers admit `:`/`.` after the first char (load-bearing: `gmsh:physical`), backticks quote names with spaces. Parse builds a **flat `vector<CalcNode>` pool** (shareable read-only across `parallel_for`, no per-node allocation); three passes: width inference + name resolution, operand widening to double once per array (`parallel_for_bw`), then the element loop (`parallel_for`) using stack buffers — `DATA_CALC_MAX_COMPONENTS=16` is what makes the loop allocation-free, `DATA_CALC_MAX_DEPTH=64` guards the parser against stack overflow from hostile input reaching it via the C ABI. Scalars broadcast against wider operands; `norm` is always scalar. Literals go through `std::strtod`, **not** `std::from_chars` (whose float overload is a real Emscripten/libc++ hazard) — matching `dex.cpp`/`wkt.cpp`/`nastran.cpp`. Every error is `std::invalid_argument` prefixed `meshio++: data_calc: ` and carries the character position. Division by zero is IEEE inf/NaN, not an error. Cell location evaluates **once per block**.
  - **Value conditioning** (`data_condition.{hpp,cpp}`, Python `_data_condition.py`): `data_condition(mesh, DataConditionOptions{location,names,mode,scope,lo,hi,nan_policy,nan_replacement,suffix,preserve_dtype})` with `ConditionMode{Clamp,Normalize,Standardize}` and `ConditionScope{Component,Magnitude}` (magnitude rescales whole rows, preserving direction). For `cell_data` the statistics are computed **jointly across all blocks** before one transform is applied to each. Degenerate reductions are handled, not NaN'd: constant array under Normalize → fill `lo` + warn; zero stddev under Standardize → fill 0 + warn. `Clamp` + `preserve_dtype` keeps the input dtype; Normalize/Standardize force Float64. `suffix` writes to a new name instead of in place.
  - **Data summary** (`data_info.{hpp,cpp}`, Python `_data_info.py`): `data_info(mesh)` → `DataInfoReport{mArrays, mNumPointData/CellData/FieldData}` of `DataArrayInfo` (location, name, dtype, shape, blocks, entries, components, values, min/max/mean whole-array *and* per component, NaN/inf/finite counts, `mInconsistentBlocks`), plus `data_array_info(mesh, loc, name)`. Read-only; the data-side complement to the topological `info` and the geometric `compute_stats`. **Never throws on non-finite values** and reports (rather than throws on) a cell_data array whose blocks disagree in component count. C/Fortran use an **opaque `mio_data_info` handle** (`_create`/`_count`/`_name`/`_entry`/`_component`/`_free`) since the report is variable-length — modelled on `mio_split_result`.
- **SVG/TikZ 3D rendering** (`cpp/include/meshioplusplus/detail/projection.hpp`, Python twin `src/meshioplusplus/_projection.py` — arithmetic kept expression-for-expression identical for TikZ byte-parity): non-flat 3D input (any |z| > 1e-14) takes a projected path — skin-extract volume cells (linearized), orthographic camera from `azimuth`/`elevation`/`roll` degrees (defaults 45/atan(1/√2)/0 = classic CAD isometric, `w ∝ (1,1,1)`), painter's-algorithm stable sort on face-centroid depth, then the existing path/`\draw` emission. Flat input keeps the legacy 2D code path physically untouched (byte-identical output). Camera args are appended **after** the existing writer params in the C++ signatures, pybind bindings, and shims — the shims pass positionally, order is load-bearing. `tests/test_tikz.py` asserts C++/Python byte-identity on the 3D path too; the FP-parity rules: cast coordinates to double before arithmetic, left-to-right multiply-adds, `std::stable_sort`/`np.argsort(kind="stable")`. `ProjectedFace` also carries `mSourceCell` (twin: `_projection.py`'s faces are 3-tuples `(nodes, is_line, source_cell)`) — a **field on the sorted element, not a parallel array**, since `stable_sort` permutes `mFaces` and a side array would have to be permuted in lockstep; it counts block-major over **every** block including skipped ones, matching `surface:parent_cell` so the two indices compose. Three consumers unpack that tuple: `_svg.py`, `_tikz.py` and **`logo/gen_logo_tikz.py`** (which bypasses the writers — re-run it and `git diff --exit-code logo/` after touching projection).
- **SVG/TikZ data-driven coloring** (`detail/face_color.{hpp,cpp}` + Python twin `src/meshioplusplus/_facecolor.py`, over `detail/colormap.hpp` + `_colormap.py`; docs [`doc/formats/svg.md`](doc/formats/svg.md#data-driven-colouring)): `color_by`/`component`/`cmap`/`vmin`/`vmax`/`nan_color`/`colorbar` appended **after the camera args** in `write_svg`/`write_tikz`, the pybind bindings and the shims (which pass **positionally** — order is load-bearing). `color_by` unset ⇒ output byte-identical to before, flat 2D path physically untouched. Name resolves in `point_data` first then `cell_data`; point data = mean of a face's corner values (summed left-to-right then divided once — **never `np.mean`**, whose pairwise summation rounds differently), cell data = its owning cell's value, reached through `surface:parent_cell` when a skin was extracted (the writers request provenance **only** when `color_by` actually names a cell_data array). Multi-component → `component` or magnitude (sequential sum-of-squares + one `sqrt`, never `np.linalg.norm`). Auto range is over the **drawn faces**, not the whole array (differs from ParaView, deliberately: the visible figure then spans the whole colorbar, and the reduction stays serial so there is no parallel-chunk FP-parity question); `FiniteStats` seed-on-first-finite semantics, non-finite excluded and drawn in `nan_color`; `vmin == vmax` ⇒ 0.5, `vmin > vmax` throws. **Colormaps are 256-entry uint8 LUTs, not interpolated control points** — that is what makes byte parity structural rather than argued: the entire FP surface of the color path is `static_cast<int>(t * 255.0 + 0.5)` / `int(t * 255.0 + 0.5)`, provably identical because both truncate and no tie-breaking is involved. **Never "improve" that to `std::lround`/`round()`** — they disagree on the exact ties `t = k/510` produces. Both tables are emitted by `tools/gen_colormaps.py` (matplotlib needed only to regenerate) and pinned against each other by `tests/test_colormap.py` via the `_core.colormap_table` export. The two writers share `color_faces_flat` (the flat path's line/triangle/quad enumeration, one rule for both) and `color_faces_from_projection`; only the format vocabulary (`svg_color_hex` → `#rrggbb`, `tikz_color_rgb` → `{rgb,255:red,R;green,G;blue,B}` — braces mandatory or the commas split the option list) stays per-writer. The SVG colorbar widens **only the viewBox** (scaling factor, stroke width and every mesh coordinate come from the unmodified width) and emits `<rect>`, not `<path>`, so the document `path {…}` rule does not stroke it; TikZ's is a pure append. **Coloring is a documented gap on the flat bindings** — `registry.cpp`'s `(path, mesh)` writer lambdas cannot carry params, so C/Fortran/WASM keep the fixed default styling (do NOT thread it through the registry). CLI: `convert --color-by NAME [--component --cmap --vmin --vmax --nan-color --colorbar]` in **both** CLIs, rejected for non-svg/tikz targets; the native one uses a `write_colored_variant` registry bypass modelled on `write_binary_variant`. `extract_skin`+`extract_surface` gained no public parameter for this — the shared impl was lifted to `detail::surface_extract(mesh, forceFaceMode, linearize, recordParentIds, opName)` (declared in `operations/surface.hpp`), because the two public functions are flat-bound in three places and no binding consumer needs linearize+provenance together; `_skin.py::_extract_skin_py` gained the matching `record_parent_ids`.
- **Doc figures** (`tools/gen_doc_images.py`): regenerates the committed static doc/README figures from `example/example.msh` — coloured SVGs through the writer above (`doc/public/images/color_by_*.svg`) and `screenshot()` PNGs through the Polyscope extra. Canonical static figures may come from this script; it **complements, does not replace**, the PyVista notebook convention above (which still owns the executable, re-executed-with-outputs demos). It crops the bracket to ~1.1k skin facets deliberately: the full 298k-cell mesh yields a 4.5 MB SVG whose elements are sub-pixel. Smoke-tested by `tests/test_gen_doc_images.py`, which redirects the output dirs and never writes into `doc/`.
- **Container convention**: use `std::unordered_map`/`std::unordered_set` for name/id lookup and dedup tables (O(1), order-irrelevant) — the default. Reach for `std::map`/`std::set` **only** when sorted iteration order is itself relied on (see `su2` `tag_counts`, `openfoam` `by_n`, gmsh's `node_data`/`elem_data` staging locals). The mesh data maps' name order **is** observable — it drives Python dict key order and the on-disk field/variable order of writers (VTU, VTK, XDMF, Exodus, Tecplot, HMF, PLY, AVS-UCD, tetgen, h5m) plus "first int field" selectors (medit, ugrid, su2, netgen, avsucd). The uniform API bakes that guarantee in: `PointDataNames()`/`CellDataNames()`/`FieldDataNames()` **always return sorted names** on every backend (the former `detail::sorted_keys` idiom, now behind the accessors; `map_order.hpp` remains for non-Mesh maps and the pybind layer), so output stays byte-identical across backends.
- **C++ naming convention**: Kratos Multiphysics style — classes/structs/enums and methods (member functions) are `PascalCase` (e.g. `Mesh::NumPoints()`, `CellBlock::IsRagged()`); member variables are `m`-prefixed `PascalCase` (e.g. `Mesh::mPoints`, `CellBlock::mData`); reference parameters are `r`-prefixed (`const std::string& rPath`) and pointer parameters `p`-prefixed (`const int* pPerm`) — forwarding references (`F&&`) and rvalue-reference/move parameters are exempt; free functions, local variables, and lambda parameters stay `snake_case` (e.g. `read_vtu`, `parallel_for`, `detail::sorted_keys`). File names stay `snake_case`. Brace style is K&R (opening brace on the same line) at 4-space indentation — codified in the repo-root `.clang-format`, run via `clang-format -i` over `cpp/`, `bindings/`, `bindings_js/` (never `cpp/third_party`). None of this renames the pybind11/embind **string literals** that define the Python/JS-facing API (`.def("...")`, `.attr("...")`, `emscripten::function("...", ...)`) — those stay exactly as they are; only the C++ symbols on the other side of each binding call follow this convention.
- **Optional deps** (`CMakeLists.txt`): `MESHIOPLUSPLUS_WITH_HDF5`/`_NETCDF`/`_ZLIB`/`_ZSTD`/`_LZ4`/`_KAHIP`/`_EIGEN` options → `MESHIOPLUSPLUS_HAS_*` compile definitions and `_core.__has_hdf5__`/`__has_netcdf__`/`__has_kahip__` flags. **KaHIP** (partition's quality backend; MIT like meshio++, so no licence implication; OFF by default) is bring-your-own: located by the repo's first Find module, `cmake/FindKaHIP.cmake` (ported from the Kratos KaHIPApplication, ParHIP section dropped — only the serial `kaffpa` interface is linked, never ParHIP, hence **no MPI**), honouring `KAHIP_ROOT`/`KAHIP_DIR` + pkg-config; `CMAKE_MODULE_PATH` is appended only inside the `WITH_KAHIP AND NOT EMSCRIPTEN` branch. Never vendored, never auto-downloaded, no KaHIP LICENSE copy in-tree (the Kratos reviewer's requirement); CI source-builds v3.25 into a cached prefix (the dedicated `kahip` job). `#ifdef`-guarded sources become empty TUs (or fall back to a plain loop) when off. Shared HDF5 helpers in `cpp/include/meshioplusplus/detail/hdf5_util.hpp`. **Eigen** is vendored as a git submodule at `cpp/third_party/eigen` (header-only; run `git submodule update --init` for source builds) and used for the MED Fortran↔C transpose (`med.cpp`, guarded by `MESHIOPLUSPLUS_HAS_EIGEN`); when the submodule is absent the code uses a hand-written transpose, so sdists without submodules still build.
- **C++ standard: C++20** (pinned in `CMakeLists.txt` twice: `CMAKE_CXX_STANDARD` + `target_compile_features`). macOS needs deployment target ≥ 13.3 for `std::format` (set in `ci.yml`/`wheels.yml`).
- **Logging** (`cpp/include/meshioplusplus/log.hpp`): `meshioplusplus::log::debug/info/warn/error("fmt {}", …)` — `std::format` (compile-time-checked) + `std::source_location`, thread-safe via `std::osyncstream`, filtered at runtime by the `MESHIOPLUSPLUS_LOG_LEVEL` env var (`debug|info|warn|error|off`, default `warn`). No printf/cerr elsewhere; errors remain exceptions.
- **Parallelism** (`cpp/include/meshioplusplus/parallel.hpp`): `meshioplusplus::parallel_for(n, f, grain=2048, max_threads=0)` with a compile-time backend selected by `MESHIOPLUSPLUS_PARALLEL_BACKEND` = `AUTO|SEQ|STL|OPENMP|TBB`. **Default is `AUTO`**, which prefers **OpenMP** (portable: libgomp on manylinux, MSVC built-in, libomp on macOS; needs no TBB), else the STL(+TBB) probe, else SEQ. `_core.__parallel_backend__` reports the active backend from Python (STL-without-TBB is effectively sequential — that's why AUTO avoids it). Adding a backend (Kokkos, …) = one CMake branch + one `#elif` in `parallel.hpp`. Iterations must be independent; the first exception is captured and rethrown after the join; `n <= grain` runs sequentially. **Two flavors:** `parallel_for` (all cores — for compute-bound loops: zlib/base64 in `detail/vtu_binary.hpp`, ASCII formatting) and **`parallel_for_bw`** (thread-capped, `parallel_bandwidth_threads=4` — for memory-bandwidth-bound loops: byte-swap/transpose/gather, which *regress* past ~4 threads because they saturate memory bandwidth). Use `parallel_for_bw` for byte I/O and index gathers; `parallel_for` only when the per-element work is real compute. The OpenMP backend uses `schedule(dynamic, grain/4)` — on hybrid CPUs (P+E cores) a static split makes E-cores stragglers; the chunk honours explicitly coarse grains (the VTU zlib loop passes `grain=1` so each block dispatches individually — do NOT floor the chunk above the grain). Hoist per-element dtype switches with `detail::dispatch_dtype(dt, []<class T>(){…})` (`value_io.hpp`) before parallelizing. **Binary I/O rule:** never write per-element to a `std::ostream` (byte-at-a-time `os.put`/tiny `os.write` was the pre-optimization VTK/Gmsh bottleneck) — build one pre-sized buffer (fused gather+byteswap where possible) and emit it with a single `os.write`; read binary sections straight into the destination array (or bulk seek+read, never `istreambuf_iterator`). Endianness conversion goes through `detail/byteswap.hpp` (`bswap_copy`/`bswap_inplace`, single-instruction intrinsics) — never a per-byte reversal loop.

**Format registration** (`src/meshioplusplus/_helpers.py`): each format's `__init__.py` calls `register_format(name, extensions, reader, {name: writer})`. `read`/`write` auto-detect from extension. Modules are imported (and thus registered) in `src/meshioplusplus/__init__.py`.

**Format module layout** (the shim pattern, e.g. `src/meshioplusplus/su2/`):
- `__init__.py` — imports `_core`, defines `read`/`write` that **try the C++ function and fall back** to the Python reference on any exception, then `register_format(...)`.
- `_<format>.py` — the pure-Python reference reader/writer.
- Multi-version formats (Gmsh, VTK) dispatch to version submodules.

**Cell type naming**: meshio++ uses its own names (`triangle`, `tetra10`, `hexahedron20`, …). Each format maps between its native names and meshio++'s (e.g. `gmsh/common.py`).

**Tests** (`tests/`): `helpers.py` has `Mesh` fixtures + `write_read()` (the round-trip pattern). Per-format `test_<format>.py` parametrize over meshes. `tests/meshes/` and `tests/input/` hold read-only reference files (Git-LFS). HDF5/netCDF suites use `pytest.importorskip`.

**CLI** (`src/meshioplusplus/_cli/`): `convert` (now also `--points-only`/`--arrays a,b`), `info` (now also `--fast`), `ascii`, `binary`, `compress` (now also `--codec zlib|lz4|zstd`, rejected where no block codec exists), `decompress`, plus the operation verbs `quality`, `extract-surface`, `reorder`, `diff`, `merge`, `transform`, `clean`, `crop`, `split`, `convert-cells`, `refine`, `partition`, `smooth`, `stats`, `view`, `screenshot`, registered in `_main.py`. **`data` is the repo's first *nested* subcommand** (`_cli/_data.py`, nine sub-verbs: `info`/`rename`/`drop`/`keep`/`to-cell`/`to-point`/`calc`/`clamp`/`normalize`) — it needs no change to `_main.py`'s dispatch because `set_defaults(func=...)` on the *inner* parser overrides the outer one, so the existing `args.func(args)` still reaches the right handler. **Colon rule** (implemented identically in `_cli/_data.py`, `cpp/cli/main.cpp` and `doc/cli.md`, because data names routinely contain colons): `data rename --point OLD:NEW` splits on the **last** colon, `data calc --point "NAME = EXPR"` on the **first** `=`; `drop`/`keep` take comma-separated lists with no location prefix.

## Adding a new format

1. Create `src/meshioplusplus/<format>/_<format>.py` (Python reference `read`/`write`) and `__init__.py` (shim + `register_format`). `register_format` may also live directly in `_<format>.py` for a Python-only format with no shim to wrap (e.g. `mdpa`, `neuroglancer`, `ansysInp`, `openfoam`).
2. Add the C++ implementation: `cpp/src/formats/<format>.cpp` + `cpp/include/meshioplusplus/formats/<format>.hpp`, bind it in `bindings/_core.cpp`, register it in the shared dispatch registry (`cpp/src/registry.cpp`: reader/writer entry + extension default — that's what makes it reachable from WASM and the C/Fortran API), and switch `__init__.py` to the try-C++/Python-fallback shim. New `.cpp` files are auto-globbed by CMake. The implementation must build/read the mesh **through the uniform mesh API only** (see the "Uniform mesh API rule" above) so it works under every mesh backend. **This step is optional** — a format can stay Python-only indefinitely (precedent: `mdpa`, `neuroglancer`, and the Simvia-contributed `ansysInp`/`openfoam`); don't force a C++ port just to satisfy this checklist.
3. Import the module in `src/meshioplusplus/__init__.py` (both the import tuple and `__all__`).
4. Add `tests/test_<format>.py` using `helpers.write_read()`. Verify a direct C++ roundtrip and cross-compat with the Python reference (if a C++ path exists).
5. **Update `README.md`, `doc/formats.md`, and this file** (see "Keeping docs in sync").

Do not copy test data from GPL sources (e.g. FEconv examples) into this MIT repo — generate reference files via round-trip instead. Code/fixtures from other MIT-licensed forks in the same lineage (e.g. the [meshlane](https://github.com/simvia-tech/meshlane) fork) may be copied directly; credit the source in `CITATION.cff`/`CHANGELOG.md`.

**Note on `ensight`:** EnSight Gold, geometry only (`.case` + `.geo` sibling pair; write logic ported from Kratos's `EnSightOutput`, reader is meshio++-original). ASCII + C-binary both ways; the binary reader auto-detects a foreign byte order from record plausibility. Per the Gold spec connectivity is **positional** (1-based into the part's coordinates) — `given`/`ignore` id arrays are skipped, matching VTK's readers (not Kratos's id-based writing assumption). Node ordering: meshio (VTK) order matches EnSight for every type except `wedge15` ↔ `penta15`, which differ by the involution `{0,2,1,3,5,4, 8,7,6, 11,10,9, 12,14,13}` — do **not** port Kratos's penta15/hexa20 group swaps (those fix Kratos-specific ordering). Multi-part files → concatenated points, one block per part-section, `cell_data["ensight:part"]` when ≥2 parts; the writer emits a single `assign`-id part and drops mesh data (warns). Ragged write raises (v1).

**Note on `vtp`:** VTK XML PolyData; shares the VTU stack — the `<DataArray>` helpers live in `detail/vtk_xml.hpp` (used by `vtu.cpp`/`vtu_read.cpp`/`vtp.cpp`/`vtp_read.cpp`; keep VTU byte-identical when touching it). Surface cells only; cell data follows VTK's canonical Verts→Lines→Polys order (writer reorders blocks into that partition). PolyData has no cell-type array, so 3-/4-noded polygons read back as triangle/quad. The pybind `vtp_write` binding opts into `allow_ragged` (jagged polygons are legal Polys rows).

**Note on `triangle`:** 2D analogue of tetgen (`.node`/`.ele` pairs → `triangle`/`triangle6`, `.poly` PSLG → `line` segments; holes/regions skipped with a warning). Extension dispatch: `.node`/`.ele` stay tetgen-first everywhere; the Python reader dispatcher falls through to triangle when tetgen raises on a 2D file, writes need `file_format="triangle"`; only `.poly` defaults to triangle (also in the C++ registry, so the flat bindings need an explicit format for 2D `.node`/`.ele`). The multi-file buffer guards in `_helpers.py` cover `tetgen`/`triangle`/`ensight`.

**Note on `med`:** the C++ core (built with HDF5) handles the mesh-representation part of MED exactly — points, point/cell tags, families with `GRO` group names, mesh-level metadata (`mesh_name`/`description`/`unit_time`/`unit_coords`/`point_tag_groups`/`cell_tag_groups`, via `MedInfo`), node-orientation permutations, and `POG`/`POG2` ragged polygons — and `meshioplusplus.med.read`/`write` use it by default. It **raises** (→ Python fallback) for the constructs it does not replicate byte-for-byte: `CHA` fields (MED-4.1 bitmask / units / step metadata), the `gmsh:physical`→family bridging, non-default profiles/ELGA, and multi-mesh files (`read_med_multi`/`write_med_multi` are always Python). The C++ MED reader iterates `MAI` cell blocks in HDF5 **creation order** (`group_links_crt`, matching h5py `track_order`) since block order aligns cell_data/cell_sets; the shim reconstructs `point_sets`/`cell_sets` from families via the shared Python helpers. See [`doc/formats/med.md`](doc/formats/med.md#quirks-limitations).
