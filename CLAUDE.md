# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this project is

meshio++ (Python package/import name `meshioplusplus`) is a Python library for reading and writing many mesh file formats used in scientific computing and FEM (Finite Element Method). It provides a unified `Mesh` data structure that all format readers/writers convert to and from.

This branch (`port-to-c++`) adds a **C++ core** (`meshioplusplus._core`, pybind11) built with **scikit-build-core + CMake**, replacing the old setuptools build. Most formats read/write through the C++ core with a pure-Python fallback.

## Keeping docs in sync (required)

**Every time a feature or format is added or changed, update all three of `CLAUDE.md`, `README.md`, and the `doc/` site in the same change.** At minimum: the format table and format-specific notes in [`doc/formats.md`](doc/formats.md) (plus any other relevant `doc/` page), the supported-formats list in `README.md`, and the architecture/"Adding a new format" guidance here. Changes to the shared format registry or the flat-binding surfaces must also be reflected in [`doc/wasm.md`](doc/wasm.md), [`doc/c_api.md`](doc/c_api.md), [`doc/fortran.md`](doc/fortran.md), [`doc/julia.md`](doc/julia.md), and [`doc/r.md`](doc/r.md). A feature is not "done" until CLAUDE.md, README.md, and the docs all reflect it.

**Keep the MCP server in sync with the Python API (required).** Every change to the Python public API surface — a new or changed operation, a changed signature or default, a new report field, a new format-affecting capability — must update the MCP server (`src/python/meshioplusplus/mcp/`: the pure tool in `_tools.py` **and** its typed FastMCP registration in `_server.py`), its tests (`tests/python/test_mcp.py`, including the `_NOT_TOOLS` parity table), and the tool table in [`doc/mcp.md`](doc/mcp.md) **in the same change**. This is enforced, not just requested: the parity-guard test (`test_every_operation_has_a_tool`) fails CI whenever a new `meshioplusplus.__all__` operation is claimed by no tool's `wraps` and has no explicit `_NOT_TOOLS` exemption — add the tool, not the exemption, unless the API is genuinely not path-expressible (the in-memory interop `to_*`/`from_*`, the GPU handoff, the interactive `view`). Like the docs rule above, a feature is not "done" until the MCP surface reflects it.

**Keep the example notebooks (`example/python/*.ipynb`) current with new features too.** When a user-facing capability is added (a new operation, a new format, a notable API), demonstrate it in the notebooks (a new/updated cell) and re-execute them with outputs (`PYVISTA_OFF_SCREEN=true jupyter nbconvert --to notebook --execute --inplace example/python/*.ipynb`) so the committed outputs stay in sync. **Notebook demos must be graphical, not just printed values** — render results with PyVista (off-screen: `pv.OFF_SCREEN=True` + a `pv.Plotter(off_screen=True).screenshot(return_img=True)` embedded via matplotlib, with a matplotlib fallback for head-less GL), coloring the mesh by the relevant data array (quality metric, per-point diff error, ...) so the effect is visually understandable. `example/python/03_mesh_operations.ipynb` is the reference pattern for the operations. Mirror notable additions into the C++ counterpart too (`example/cpp/03_mesh_operations.ipynb`) where practical — see the entry below.

## Version bumps (required)

**"Bump the version" always means every one of these **ten** files, together, to the same value — never just one or two. They are, in order: `pyproject.toml`, `CMakeLists.txt`, `conanfile.py`, `packages/vcpkg/meshioplusplus/vcpkg.json`, `src/wasm/package.json`, `src/viewer/package-lock.json`, `bindings/julia/MeshioPlusPlus/Project.toml`, `bindings/r/meshioplusplus/DESCRIPTION`, plus the two **compile-time version headers** added in v9.6.0 — `src/cpp/include/meshioplusplus/version.hpp` (`MESHIOPLUSPLUS_VERSION_MAJOR/MINOR/PATCH` **and** the `MESHIOPLUSPLUS_VERSION_STRING` literal) and `bindings/c/include/meshioplusplus/meshioplusplus.h` (`MIO_VERSION_MAJOR/MINOR/PATCH`). Those last two are the *only* entries on this list that gate themselves: `CMakeLists.txt` parses both and `FATAL_ERROR`s at configure time if either disagrees with `project(... VERSION ...)`, and a `static_assert` in `bindings/c/c_api.cpp` pins the C macros to the C++ ones — so forgetting them is a build failure rather than a wrong answer. They are hand-written rather than `configure_file`d for the same reason `abi_version.hpp` is: a consumer that never runs CMake (the single-header amalgamation, pkg-config, a hand-written makefile) must still be able to read them:**

- [`pyproject.toml`](pyproject.toml) — `version`
- [`CMakeLists.txt`](CMakeLists.txt) — `project(... VERSION ...)`
- [`conanfile.py`](conanfile.py) — `version`
- [`packages/vcpkg/meshioplusplus/vcpkg.json`](packages/vcpkg/meshioplusplus/vcpkg.json) — `version`
- [`src/wasm/package.json`](src/wasm/package.json) — `version` (npm publish uses this file verbatim; it silently lagged behind at 6.3.0 through two releases before this rule existed — it's the one that's easiest to forget since it lives outside the Python/CMake build)
- [`src/viewer/package-lock.json`](src/viewer/package-lock.json) — the `@meshioplusplus/wasm` `version`. The viewer consumes it as a `file:` dependency, so `npm ci` **hard-fails** the moment the lock disagrees with `src/wasm/package.json` — which breaks the `viewer-web` job in `ci.yml` and the Pages build in `docs.yml`. It was already stale at 7.10.0 against a 7.14.0 package when this entry was first written, so treat it as the sixth version file even though nothing else reads it. **Regenerate it with `npm install` run under npm ≥10** (`lockfileVersion: 3`) — do NOT hand-edit: npm 10 splits a `file:` dependency across *two* entries (a top-level `"../wasm"` entry carrying the real `name`/`version`/`license`/`engines`, and a lightweight `node_modules/@meshioplusplus/wasm` entry that is now just `{"resolved": "../wasm", "link": true}`, no version field at all), and a lockfile edited under the old single-entry shape (or under npm 9, which accepts and re-emits that older shape without complaint) silently passes `npm ci` on an npm 9 machine while still hard-failing on the npm ≥10 CI runners with `Missing: @meshioplusplus/wasm@X from lock file` — bit us exactly once, diagnosed only by reproducing with Node 20/22's bundled npm rather than a possibly-older local one. `npm install` (matching npm version) touches only the `@meshioplusplus/wasm`-related lines; nothing else in the lock shifts.
- [`bindings/julia/MeshioPlusPlus/Project.toml`](bindings/julia/MeshioPlusPlus/Project.toml) — `version` (the Julia package manifest, added in v8.3.0 — Pkg reads it verbatim, and like `src/wasm/package.json` it lives entirely outside the Python/CMake build with nothing in CI cross-checking it, so it is exactly the kind of manifest that silently drifts)
- [`bindings/r/meshioplusplus/DESCRIPTION`](bindings/r/meshioplusplus/DESCRIPTION) — `Version:` (the R package manifest, added in v8.3.0 — `R CMD build`/`install` stamp it into the installed package; same outside-the-build, nothing-cross-checks-it drift risk as the Julia manifest. Note the field is `Version:` with a capital V and a colon, DESCRIPTION's DCF syntax, not TOML)

The CMake `VERSION` feeds `mio_version()`, the C API `.so`'s VERSION/SOVERSION, and the installed package configs, so it isn't optional/cosmetic.

**Two docs also print the version verbatim and are CI-gated**: [`doc/cpp_api.md`](doc/cpp_api.md) and [`README.md`](README.md) each carry a `find_package(meshioplusplus X.Y.Z EXACT CONFIG REQUIRED COMPONENTS CXX)` line, and `ci.yml`'s `cpp-install` job `grep -qF`s both against `pkg-config --modversion` of the freshly installed prefix — so a bump that updates the eight files above but not those two lines turns that job red (deliberately; it is what keeps the documented pin from rotting back into a form that cannot work — see the `EXACT` note in the *Installable C++ API* entry below).

**A dated [`CHANGELOG.md`](CHANGELOG.md) entry is required in the same change as every version bump** — new formats, new operations, notable enhancements *and* breaking changes, not breaking changes only. Mark breaking items explicitly with a **Breaking:** prefix; everything else is assumed additive. (This rule replaced a breaking-changes-only policy under which the file silently fell six releases behind, from v6.6.0 to v7.1.0 — the entries were reconstructed from git history. Treat "bump the eight version files" and "add the CHANGELOG entry" as one indivisible step.) A pure patch/bugfix bump can be a single line.

## Commands

**Build/install for development** (native paths on). PEP 668 systems: use the in-repo uv venv (`uv venv --python 3.12 .venv`), then:
```bash
CMAKE_ARGS="-DMESHIOPLUSPLUS_WITH_HDF5=ON -DMESHIOPLUSPLUS_WITH_NETCDF=ON -DMESHIOPLUSPLUS_WITH_ZLIB=ON" \
  uv pip install --python .venv --no-build-isolation -e .
```
Plain environments: `pip install -e ".[all]"`. The optional deps (HDF5, netCDF, zlib) are auto-detected; when absent the C++ paths compile out and Python fallbacks (h5py/netCDF4/stdlib zlib) take over.

**Standalone C++ build**: `build/configure.sh` (Linux/macOS) and `build/configure.bat` (Windows) configure a CMake tree next to themselves (`build/cpp-<type>[-<mesh-backend>]`); flags: `--backend SEQ|STL|OPENMP|TBB`, `--mesh-backend MESHIO|NATIVE|KRATOS` (non-MESHIO implies `-DMESHIOPLUSPLUS_BUILD_PYTHON=OFF`), `--tests`, `--cli` (the native CLI binary, below), `--c-api`/`--fortran` (the C API entry below), `--install-cpp`/`--cpp-backends <LIST>` (the installable C++ API entry below; the list is comma-or-semicolon separated, and on Windows a multi-entry list must be quoted — cmd splits unquoted batch parameters on both `,` and `;`), `--build`, `--with/-out-hdf5/netcdf/zlib`, `--tbb-dir <path>`. They print the matching `CMAKE_ARGS … pip install` line (MESHIO only) and, when anything installable was enabled, the matching `cmake --install` line.

**Native CLI binary** (`src/cpp/cli/main.cpp` → `meshioplusplus_cli`, installed executable name `meshioplusplus`): a **Python-free** command-line tool over `meshioplusplus_core_obj` mirroring the Python console script's verbs (convert/info/ascii/binary/compress/decompress/quality/extract-surface/reorder/diff/merge/transform/clean/crop/slice/isosurface/split/convert-cells/refine/partition/smooth/interpolate/stats/view/screenshot, plus the nested `data <verb>` group with the same nine *operation* sub-verbs and the same colon rules — `data export` is Python-only, see the gaps below). Supporting the repeated `--point`/`--cell`/`--field` flags the `data` verbs need required one extension to the hand-rolled parser: `cli_opt_spec` gained nothing, but `cli_parsed` gained a `multi` map recording every occurrence of each value-option, populated **alongside** the existing last-wins `values` map so all 16 pre-existing verbs are behaviourally unchanged; read it with `opt_values(p, name)` and test presence with `has_opt(p, name)`. `MESHIOPLUSPLUS_BUILD_CLI` (OFF by default; `build/configure.sh --cli --build`). Reuses the shared `registry.hpp` for format dispatch (with the `sniff_format` read fallback); ASCII/binary/compress variants call the per-format writer free functions directly (the registry bakes one default per format), and the operation verbs use `operations/*.hpp`. Works under any mesh/parallel backend and optional-dep set. **Documented gaps vs the Python CLI**: `convert -s/-d` never reaches the C++ core and errors (named **sets** no longer belong on this list — `info` prints point/cell/side sets and `diff` compares regions, since v8.1.0); formats whose C++ reader raises (e.g. gmsh `$Entities`, which the Python path handles via fallback) are unreadable here — there is no Python fallback; **`data export`** has no counterpart at all (it writes Parquet through pyarrow, a Python library — see the interoperability entry below); and `view`/`screenshot` exist only in a **Polyscope-enabled** build (`-DMESHIOPLUSPLUS_WITH_POLYSCOPE=ON`, OFF by default and never in the release binaries — see the viewer entry below), otherwise they are listed but throw naming the flag. `--version`'s `MESHIOPLUSPLUS_CLI_VERSION` is fed by CMake `PROJECT_VERSION`. **Prebuilt, statically-linked release binaries** (Linux x86_64, Linux arm64, macOS universal, Windows x86_64) are attached to every `v*` tag's GitHub Release by `cli.yml` (see "CI" below) — built with `MESHIOPLUSPLUS_STATIC_RUNTIME=ON` (hoisted to a top-level option so it applies to both `_core` and `meshioplusplus_cli`: static `libgcc`/`libstdc++` on GNU, static MSVC CRT via `MSVC_RUNTIME_LIBRARY` on Windows) and `WITH_HDF5/NETCDF/ZLIB=OFF` + `PARALLEL_BACKEND=SEQ` for a single dependency-free executable; build from source with `--cli` (optionally without `--without-hdf5` etc.) for the full native format/threading feature set.

**WebAssembly build** (`@meshioplusplus/wasm` npm package): `build/configure-wasm.sh --build` (needs the [Emscripten SDK](https://emscripten.org/docs/getting_started/downloads.html) on `PATH`) builds **two artifacts** (v8.8.0) in separate trees, both `-DMESHIOPLUSPLUS_BUILD_PYTHON=OFF -DMESHIOPLUSPLUS_BUILD_WASM=ON -DMESHIOPLUSPLUS_MESH_BACKEND=NATIVE` (the fastest mesh backend; the JS API shape is unchanged and `meshBackend()` reports `"native"`) and HDF5/netCDF **on** (v8.0.0), differing only in the parallel backend: the **sequential** `meshioplusplus_wasm.{mjs,wasm}` (`build/wasm-<type>`, `PARALLEL_BACKEND=SEQ`) and the **threaded** `meshioplusplus_wasm_mt.{mjs,wasm}` (`build/wasm-<type>-mt`, `PARALLEL_BACKEND=OPENMP -DMESHIOPLUSPLUS_WASM_THREADS=ON`). `--seq-only` skips the threaded one; `--build` copies all four files into `src/wasm/dist/`. **Threaded = OpenMP over Wasm threads (pthreads/`SharedArrayBuffer`)**, so it is faster for the mesh operations but only loads where the page is **cross-origin isolated** (COOP `same-origin` + COEP `require-corp`) — it aborts on instantiation otherwise, with no in-artifact fallback, which is why both ship. The loader `loadMeshioPlusPlus(overrides, {variant})` (`src/wasm/src/index.mjs`) **auto-selects** via `globalThis.crossOriginIsolated` (undefined under Node ⇒ threaded, since `worker_threads` always work there; else true ⇒ threaded, false ⇒ sequential); `variant: 'mt'|'seq'` forces one. `MESHIOPLUSPLUS_WASM_THREADS` (CMake, EMSCRIPTEN-only) drives `-fopenmp -pthread` PUBLIC on `meshioplusplus_core_obj`, the `_mt` output name, and `-sPTHREAD_POOL_SIZE=globalThis.navigator?navigator.hardwareConcurrency:8` (`navigator` is Node ≥ 21 only, and the package's floor is Node 18 — the guard + `PTHREAD_POOL_SIZE_STRICT=0` on-demand growth is load-bearing; the whole expression is written without spaces/quotes so it survives CMake → Ninja → em++ as one arg). The `-pthread` flags never leak into the Python/gtest/C-API trees (those configure SEQ/native with the option OFF). A `parallelBackend()` JS/embind binding (`parallel_backend_js` in `js_bindings.cpp`, forwarded in `index.mjs`) reports `"openmp"`/`"seq"` so the smoke test can assert which artifact loaded. The **browser viewer** picks the threaded build wherever it can: the Pages demo vendors `src/viewer/public/coi-serviceworker.js` (a COOP/COEP service worker, injected into the **web** `index.html` only via a `vite.config.mjs` `transformIndexHtml` plugin — the embed single-file build uses no WASM and must never see it) to become cross-origin isolated, and `src/viewer/src/worker/worker.ts` imports both `.wasm` `?url`s and returns the matching one from `locateFile`. `src/wasm/package.json`'s `files` and the viewer's `vite.config.mjs` freshness check both cover both binaries. Builds `bindings/wasm/js_bindings.cpp` (embind) against the same `meshioplusplus_core_obj` as `_core`. Ships **all 41 formats** — 40 readable, 42 writable (`openfoam` read-only; `svg`/`tikz`/`gmsh22` write-only — the last since reading auto-detects a file's own `$MeshFormat` version and needs no separate key), XDMF in all three data formats — so there is no longer a wasm-specific format gap; see `doc/wasm.md`. **Ragged cell blocks** (polygon/polyhedron) cross the JS boundary as flat CSR arrays (v8.7.0) — `{type, data, rowOffsets}` for 1-level (jagged polygon rows) and `{type, data, faceOffsets, cellOffsets}` for 2-level (polyhedron, cell → faces → node ids) — since embind has no efficient representation for a nested array of arrays; `mesh_to_val`/`val_to_mesh` build these from/into the uniform API's `RowSize`/`Row`/`NumFaces`/`Face` and `AddPolygonBlock`/`AddPolyhedronBlock` exactly as every C++ operation already does, so the boundary carries a polyhedron block correctly (round-trips through e.g. `clean`) even though **no C++ format writer accepts one yet** — a pre-existing, documented gap the boundary work does not (and could not) close, distinct from and unblocked by it. Smoke test: `node tests/wasm/smoke.mjs`.
**wasm HDF5/netCDF** (v8.0.0): neither is a system library on this target and CMake never downloads anything, so `build/build-wasm-deps.sh` source-builds **HDF5 1.14.6 + netcdf-c 4.9.3** (pinned + SHA256-checked) into `build/wasm-deps/<pins>/`, and `configure-wasm.sh` passes that prefix as **`CMAKE_FIND_ROOT_PATH`** — the required knob, since the Emscripten toolchain sets `CMAKE_FIND_ROOT_PATH_MODE_*=ONLY` (it `list(APPEND)`s its sysroot, so passing ours adds a second root rather than replacing it) and `CMAKE_PREFIX_PATH`/`HINTS` are therefore ignored. `configure-wasm.sh` builds the prefix automatically when missing; `--without-hdf5` (implies `--without-netcdf`) gives the old small artifact, `--deps-prefix` reuses one, and `--with-hdf5 --without-zlib` is a hard error (every HDF5 writer calls `H5Pset_deflate`). HDF5 **≥1.14 is required, not preferred** — 1.14.0 removed `H5detect`/`H5make_libsettings`, which is what made cross-compiling painful. Both are static, `-Oz`, against Emscripten's zlib port, with everything needing an absent OS service off (HDF5: threadsafe/MPI/plugins/ROS3/direct/mirror/subfiling VFDs; netCDF: DAP/DAP4/byterange/NCZarr/S3/libxml2→bundled ezxml/plugins-`dlopen`/mmap). **`HDF5_BUILD_HL_LIB=ON` is load-bearing** even though meshio++ uses only the core C API: netCDF-4's dimension-scale layer needs `H5DS*`. Three fix-ups, all in the script: `build/patches/hdf5-1.14.6-fe-invalid.patch` guards `feclearexcept(FE_INVALID)` (wasm's `<fenv.h>` defines `FE_ALL_EXCEPT` as 0 and no `FE_INVALID` at all), and the two installed CMake configs are rewritten to replace the imported-target names `ZLIB::ZLIB` / `HDF5::HDF5` / `hdf5::hdf5_hl` with archive paths — no single `find_package` in a consumer defines all of them, and CMake `try_compile` scratch projects (which netcdf-c's configure uses heavily) hard-fail on the dangling name. netCDF's interface is also reordered `hdf5_hl` before `hdf5`, since wasm-ld resolves archives in command-line order. **The rewritten `libz.a` path is not stable across CI runs** — it is Emscripten's zlib *port* archive under `em-config CACHE`, i.e. under `$EMSDK`, and `mymindstorm/setup-emsdk` installs into a fresh directory named after the current job's runner-assigned temp dir on every single run — while `build/wasm-deps/<pins>/` (the `$PREFIX`-rooted HDF5 archive paths) is `actions/cache`d *across* runs at a stable workspace path. A cache hit therefore restores CMake configs whose `libz.a` reference still names a prior run's now-nonexistent `$EMSDK`, and ninja fails with "missing and no known rule to make it" — bit us once a cache had gone a while without a rebuild-forcing change to `build-wasm-deps.sh`/`build/patches/*`, hence looking "fine" in every earlier PR. The fix (also in `build-wasm-deps.sh`) is a small unconditional loop, run after both fix-ups regardless of whether HDF5/netCDF were just built or skipped as "already installed": it re-points any `.../sysroot/lib/wasm32-emscripten/libz.a` suffix in either installed config at the *current* run's `$ZLIB_LIBRARY`, a no-op when the path is already current. **`-sSTACK_SIZE=4MB` + `-sSTACK_OVERFLOW_CHECK=1`** on the wasm target are part of this, not incidental: Emscripten's default 64 KiB stack is overrun by HDF5/netCDF-4 frames, the stack grows **down into the static data segment**, and the corruption is silent — one Exodus write clobbered libc++'s locale facets, after which every `istream >> number` in the module (i.e. every ASCII reader) trapped with "null function or function signature mismatch". `tests/wasm/smoke.mjs` pins this with an OBJ read placed *after* the exodus round-trip. Two documented consequences: writing `.xdmf` now emits an `.h5` companion (registry default follows the build — **two** files out of `FS`, not one), and MED **cannot write named fields** here (the C++ writer defers `CHA` fields to the Python reference writer, and there is no Python in this build) — geometry/tags/families write normally. **Three files, not one:** a binding is only reachable from `loadMeshioPlusPlus()` if it is (1) registered in `bindings/wasm/js_bindings.cpp`, (2) **forwarded** in `src/wasm/src/index.mjs`'s returned object, and (3) declared in `src/wasm/index.d.ts`. Step 2 is the one that gets forgotten — it silently shipped every geometry op unreachable until v7.4.0 (and the `data_*` ops until v7.2.1). `smoke.mjs` exercises operations **through the wrapper**, never `Module.*`, precisely so a missing forward fails the build, and its reflection guard is now **exhaustive** over all 44 names rather than the geometry ops only. Note that `bindings/wasm/` is **outside the amalgamation** (which covers `src/cpp/include` + `src/cpp/src`), so a binding-only addition needs no single-header regen — `availableFormats` and `convertSurface` (v7.8.0) were both added that way. `-fwasm-exceptions` is required (applied `PUBLIC` on `meshioplusplus_core_obj` under `if(EMSCRIPTEN)`) so `ReadError`/`WriteError` surface as catchable JS `Error`s instead of aborting; `log.hpp`'s `std::osyncstream` usage has a `std::mutex`-guarded fallback for standard libraries (Emscripten's non-threaded libc++) that ship `<syncstream>` without actually defining it (`__cpp_lib_syncbuf` unset). `configure-wasm.sh` runs `embuilder build zlib` right after configuring (when zlib is on) to pre-warm Emscripten's zlib port cache single-threaded — `-sUSE_ZLIB=1` makes every translation unit trigger that port's build on first use, and a parallel `-j` build races many `em++` invocations against the same cold-cache lock, aborting with "attempt to lock the cache while a parent process is holding the lock (sanity)". CI (`.github/workflows/wasm.yml`) publishes to npm (`NPM_TOKEN` secret) only on `v*` tags (mirrors `wheels.yml`'s trigger), but since v8.0.0 it also **builds+smoke-tests on PRs** touching the wasm surface or `src/cpp/` — the job was tag-only while this build had no external dependencies, which stopped being tenable once it linked a wasm32 HDF5/netCDF; the dependency prefix is `actions/cache`d (keyed on the emsdk pin + `build-wasm-deps.sh` + `build/patches/`) so the added cost is one short job, and Eigen is checked out by targeted `git submodule update --init src/cpp/third_party/eigen` (never `submodules: true`, which would drag in Polyscope).

**C API / Fortran build** (`libmeshioplusplus` + Fortran module, for C/Fortran HPC consumers): `build/configure.sh --c-api` or `--fortran` (implies `--c-api`; both also exist in `configure.bat`, Fortran untested on MSVC) → CMake options `MESHIOPLUSPLUS_BUILD_C_API` / `MESHIOPLUSPLUS_BUILD_FORTRAN` (both OFF by default). `cmake --install <tree> --prefix <p>` installs the shared lib(s), the single pure-C header `bindings/c/include/meshioplusplus/meshioplusplus.h`, a `find_package(meshioplusplus)` config package, a relocatable pkg-config file, and (Fortran) the `.mod` **plus** `bindings/fortran/meshioplusplus.f90` (`.mod` files are compiler-specific; consumers on another compiler recompile the module — the HDF5 approach). Tests: `tests/cpp/test_c_api.cpp` (auto-globbed into the gtest suite when C_API is on) and the `fortran_api` ctest (`tests/fortran/test_fortran_api.f90`). CI-tested consumer examples: `doc/examples/c_api_example.c`, `doc/examples/fortran_example.f90`. See "Version bumps" above — `project()`'s `VERSION` feeds `mio_version()` and the `.so`'s VERSION/SOVERSION here.

**Write options** (`write_options.hpp` + `src/cpp/src/write_options.cpp`, v9.0.0): `registry_write_ex(path, mesh, format, WriteOptions{mEncoding, mCodec/mCodecSet, mFloatFormat})` is the **single owner** of "write this format with these parameters". The registry stores writers as `(path, mesh)` lambdas with one parameter set baked in per format, so nothing going through `registry_writers()` could select ASCII/binary, a block codec or a float format — the CLI had a private variant table and the flat bindings had nothing at all. That table now lives here and `src/cpp/cli/main.cpp`'s `write_binary_variant` is a thin wrapper over it, so the two cannot drift. **All-defaults dispatches straight through the registry**, so the common path stays byte-identical (and picks up formats with no parameterized entry). An option the format cannot honour is an **error** (`registry_write_supports` reports why), never silently ignored — `--codec zstd` on a Gmsh file is a mistake worth reporting. The C ABI counterpart is `mio_write_ex`/`mio_write_opts` with `mio_read_opts`' exact append-only discipline (a `reserved[5]` int64 tail; `mio_write` is `mio_write_ex(..., <defaults>)` unchanged). Note the CLI keeps passing `--float-format` only to a writer that takes one, because it has always been *ignored* elsewhere and `registry_write_supports` would otherwise turn that into a new error.

**XDMF time series** (`formats/xdmf_time_series.{hpp,cpp}`, v9.0.0, docs [`doc/xdmf_time_series.md`](doc/xdmf_time_series.md)): `XdmfTimeSeriesWriter` (`WritePointsCells`/`WriteData(time, mesh)`/`Finalize`, move-only RAII), the C++ counterpart of the Python-only `TimeSeriesWriter`, in all three data formats. **v9.1.0 added the three things a solver needs.** (1) **`Flush()`** — light data used to be written *only* at `Finalize()`, so a killed/crashed/still-running solve left heavy data and no readable `.xdmf`; it saves to a sibling temp file then `rename`s (a crash mid-flush cannot truncate the previous one) and flushes heavy data first (the `.xdmf` never names a dataset not yet on disk). `SetAutoFlush(true)` is **opt-in**: a flush re-serializes the whole document, so per-step flushing is quadratic in the step count, and for `"XML"` — whose heavy data is *in* the document — in the data volume too. (2) **`XdmfSeriesMode::Append`** (trailing defaulted ctor param) continues an existing collection, resolved structurally the way `read_xdmf` does; the heavy-data counter resumes by **scanning the container** (`h5::open_file_rw` + `H5Lget_name_by_idx`, or probing `<base>N.bin`) rather than trusting the document, because a mis-resumed counter silently overwrites `data0` instead of failing. Appending to a nonexistent path is *not* an error — it is a fresh series, so a restartable solver passes it unconditionally. (3) **`WriteData(time, vector<NamedArray>, vector<NamedArray>)`** — the granularity a solver has once the geometry is fixed, and under the KRATOS backend the difference between re-staging the whole ModelPart every output step and not. It shares the step-grid scaffolding and `xts_add_attribute` with the `Mesh` overload but is deliberately **not** implemented by converting a `Mesh`, which would force Int64 cell data to Float64 and change existing output; it validates row counts (stricter than the `Mesh` path, which cannot get them wrong) and emits in the caller's order rather than sorted. Fortran deliberately has **no** array overload (an array of derived types with interop pointers is a poor Fortran shape, and a Fortran solver already holds an `mio_mesh` to `add_point_data` into) — a named gap in `doc/fortran.md`. **Pimpl is load-bearing, not style**: it keeps pugixml (build-only vendored, PRIVATE include dir) and `hdf5.h` (optional dep) out of an *installed* header. Deliberately **not** in `registry.cpp` — a stateful multi-call object is not a `(path, mesh)` format. The shared payload machinery (`DataItemStore`, `attribute_type`, `pack_mixed_topology`, …) was hoisted into `detail/xdmf_common.hpp` and `write_xdmf` refactored onto it, verified by diffing pre/post output byte-for-byte including the `.h5`. The same work fixed a real reader bug: `read_xdmf` resolved `Domain/Grid[0]` — the *collection* — and threw `unknown section Grid` on any temporal file, so **XDMF time series were unreadable**; it now resolves the collection structurally, honours `ReadOptions::mTimeStep` (the second reader after exodus) and fills `MeshMetadata::mTimeValues`. Bindings: C API `mio_xdmf_series_*`; **Fortran/Julia/R** ride that C API with each language's own handle idiom — Fortran `type(mio_xdmf_series)` (type-bound `create`/`write_points_cells`/`write_data`/`finalize`/`num_steps`/`free`, optional `stat`/`errmsg`, explicit free like `mio_mesh`), Julia `XdmfSeries` (GC finalizer + deterministic `close`, plus a `do`-block form; the exported name is **`finalize!` not `finalize`**, since `Base.finalize` means "run this object's GC finalizer"), R `mio_xdmf_series()` (external pointer with its **own** tag `mio_xdmf_series_handle`, in a new `src/xdmf_series.c`, so a `mio_mesh` and a series can never be passed for one another). The rule all three repeat, and the reason `finalize` exists separately from the free: **a write failure during the implicit finalize cannot be reported** — not from a Fortran `free()`, a Julia `close`, or an R GC finalizer — so an R test must release a series *before* its tempdir is removed or the finalizer silently fails writing into a vanished path (bit the test once). WASM `createXdmfTimeSeriesWriter` — an **opaque integer handle plus free functions, not an embind `class_`**, because this package's contract is that `Mesh`/`NDArray` stay internal and JS only ever sees plain objects, and because a bound *member* function bypasses `with_js_errors` and surfaces a `WriteError` as a message-less `WebAssembly.Exception`; the handle is a **table index, not a pointer**, so a stale handle throws instead of being a use-after-free. Python gets `_core.XdmfTimeSeriesWriter` (context-manager capable) exposed **additionally**, NOT as a shim under `xdmf/time_series.py` — the `.mdpa` rule again: a tested, documented Python API is not silently re-implemented underneath.

**Installable C++ API** (`MESHIOPLUSPLUS_INSTALL_CPP`, OFF by default, docs [`doc/cpp_api.md`](doc/cpp_api.md)): installs the whole `src/cpp/include/meshioplusplus/` header tree plus one real library per mesh backend, exported into the **same** `meshioplusplusTargets` set as the C API, so one `find_package(meshioplusplus CONFIG COMPONENTS CXX|C|Fortran)` serves every surface (`check_required_components` genuinely gates them — a missing component fails at `find_package`, not at the link). This is what makes `kratos_bridge.hpp`/`ModelPart` reachable at all: the C ABI cannot hand out a `Mesh` or a `ModelPart`, which is precisely why an out-of-tree Kratos application could not consume meshio++ before. **All three backends build side by side** (`meshioplusplus::core_meshio`/`::core_native`/`::core_kratos`, `meshioplusplus::core` aliasing the `MESHIOPLUSPLUS_MESH_BACKEND` default; `MESHIOPLUSPLUS_INSTALL_CPP_BACKENDS` trims the set) so one prefix serves consumers that disagree about the backend — each variant is a **full, independent compile** of the core, which is the cost. Three implementation facts worth not rediscovering: (1) the variants compile `MESHIOPLUSPLUS_CORE_SOURCES` **directly**, not through an OBJECT library, because a STATIC library records even PRIVATE deps in `INTERFACE_LINK_LIBRARIES` as `$<LINK_ONLY:>` and `install(EXPORT)` then rejects the unexported object library (the C API dodges this only by always being SHARED); (2) every PUBLIC usage requirement is accumulated into `_mio_core_*` lists and re-applied by `meshioplusplus_configure_core_target()` rather than inherited, since the object library can be neither exported nor PUBLIC-linked — the mesh-backend macro is the one thing deliberately *not* in the shared list, being per-variant; (3) HDF5 is linked through the **`HDF5::HDF5` imported target**, not `${HDF5_C_LIBRARIES}` — the raw variable bakes absolute library paths into `meshioplusplusTargets.cmake` and makes the prefix resolve only on a machine whose HDF5 sits exactly where the build's did (fixed v9.0.0). The price, stated in the generated config's own error message, is that `FindHDF5`/`FindMPI` need the **C language enabled** in the consumer's `project()`, which a CXX-only project otherwise has no reason to do. Symbol visibility: the variants are `CXX_VISIBILITY_PRESET hidden` + `VISIBILITY_INLINES_HIDDEN`, with the public surface annotated `MESHIOPLUSPLUS_API` (`export.hpp`, modelled on the C header's `MIO_API`) — a missing annotation is a **link** error for a shared consumer, never silent, which is what makes the annotation set verifiable; `tests/consumer/` linked against a SHARED build is that check, and the `cpp-install` CI job runs it per backend across a static all-backends leg, a shared MESHIO leg and (v9.1.0) a **shared KRATOS** leg — the configuration a Kratos application actually ships, and the only one where a missing annotation on that backend is a link error. That leg must also pass `-DMESHIOPLUSPLUS_MESH_BACKEND=KRATOS`, or `meshioplusplus::core` is undefined and the default-alias sub-step fails. **`MESHIOPLUSPLUS_NO_STD_SPAN` needs no code and no private build**: `std::span` appears in exactly two lines repo-wide (`native_mesh.hpp`'s include and the inline `ConnSpan()`), so the macro is **ABI-neutral**, and the guard is `#ifndef` — a consumer whose Boost uBLAS collides with `<span>` under MSVC defines it on their own command line against *any* prefix, including one built without it. `tests/consumer/`'s `MESHIOPLUSPLUS_CONSUMER_NO_STD_SPAN` option plus a CI leg makes that a gate rather than a claim. **What to pin** (doc/cpp_api.md, and since v9.4.0 [`doc/abi.md`](doc/abi.md) for the whole contract): `COMPONENTS C` is `SOVERSION 0` + `SameMajorVersion` with append-only option structs, so `find_package(meshioplusplus 9 … C)`; `COMPONENTS CXX` makes **no ABI promise** — `Mesh`/`ModelPart`/`GeometricalEntity` are header-defined and v9.1.0 added a member to the last — so pin either the **full three-component** version `EXACT` (`X.Y.Z EXACT`, never `X.Y EXACT`: under `SameMajorVersion` an `EXACT` request is a full *string* comparison against the installed version, so a `major.minor` request matches nothing at all — both docs shipped exactly that unusable form through v9.1.0) or, more precisely, the exported `MESHIOPLUSPLUS_ABI_VERSION`. **The ABI version is deliberately NOT the release version** (v9.4.0): it moves only when the installed headers stop being compatible with an already-compiled consumer, which two of the three 9.x transitions did and the third — v9.3.0, whose entire installed-header delta was one new `inline constexpr` in `formats/exodus.hpp` — did not. It lives in **one** place, `src/cpp/include/meshioplusplus/abi_version.hpp`, which `CMakeLists.txt` *parses* rather than copying (a second copy would put a wrong `SOVERSION` on a library whose symbols say otherwise), and the C++ variants' `SOVERSION` **is** that number (`libmeshioplusplus_core_kratos.so.3`) while the C and Fortran libraries stay at `SOVERSION 0`. `detail/abi_version_check.hpp` is the `mesh_backend_check.hpp` technique on this second axis — a **separate** symbol, so a right-backend/stale-headers consumer hears about the headers — with the same `gnu::used`-is-load-bearing rule and the same **MSVC + shared DLL gap**; `MESHIOPLUSPLUS_NO_ABI_VERSION_CHECK` opts out, and `MESHIOPLUSPLUS_ABI_VERSION` itself is deliberately not `-D`-overridable (that would be a knob to silence the guard while still miscompiling — hence CI stages a mismatch by patching a *copy* of the installed headers). Two gates keep the integer honest, and neither suffices alone: `tests/cpp/test_abi_layout.cpp` pins `sizeof`/`alignof` per backend (catches layout changes mechanically; the numbers are pinned only on Linux/x86_64/libstdc++, since `sizeof(std::string)` alone differs across standard libraries) and `tools/check-abi-version.sh` (in the `lint` job, which therefore needs `fetch-depth: 0`) fails a build whose installed headers changed while the ABI version did not and `doc/abi_reviews.md` records no additive review — that one catches inline-body/ODR changes, which no tool can infer. **That review lookup is keyed on `(ABI version, release version from CMakeLists.txt)` AND on the row naming every changed header, never on the ABI number alone** — the v9.4.0 shape matched any row whose first column was the current ABI, so the moment one existed (two did) every later header change matched it and the gate exited 0 reporting "records the additive review" about a *different* release, leaving Tier B completely unguarded since the layout snapshot cannot see an inline-body edit; keying on the release alone is also not enough, because a header change that skips the version bump still finds the previous release's row, which is why `doc/abi_reviews.md`'s `headers changed` column is load-bearing and must list every header (paths relative to `src/cpp/include/meshioplusplus/`). `tests/python/test_check_abi_version.py` drives the real script over a throwaway git repo and is the guard that it *fires* — written only after confirming all five of its fix-targeting cases fail against the pre-9.4.1 script, since a gate nobody tests for firing is exactly how the v9.1.0 backend guard shipped inert. **Backend-mismatch guards** (the reason `detail/mesh_backend_check.hpp` and `src/cpp/src/mesh_backend_check.cpp` exist): the macro rides in `INTERFACE_COMPILE_DEFINITIONS` so a CMake consumer cannot disagree by accident, defining two macros is a `#error` in `mesh.hpp`, and defining none while linking a NATIVE/KRATOS build is an undefined reference to `mesh_backend_is_<backend>` — that last case is the dangerous one (`mesh.hpp` silently falls through to MESHIO) and only bites non-CMake consumers, hence `MESHIOPLUSPLUS_NO_BACKEND_LINK_CHECK` to opt out. `meshioplusplus-cxx.pc` is a **second** pkg-config file, never an extension of the C one, whose `Cflags` must stay valid under `gcc -std=c99` (CI compiles `doc/examples/c_api_example.c` that way). Note also that `src/cpp/third_party/{pugixml,eigen}` are **PRIVATE** include dirs (v8.9.0): no installed header references either, and Eigen's is a submodule path that does not exist on a consumer's machine — leaving them PUBLIC broke `find_package` outright and collided with a consumer's own vendored pugixml.

**Conan / vcpkg packaging** (self-hosted, in-repo, for the C API): both live under `packages/` — the root `conanfile.py` (Conan 2.x, with the test package at `packages/conan/`, `test_type = "explicit"` so it only runs via an explicit `--test-folder=packages/conan`, as `packages.yml`'s `conan create` does) and the `packages/vcpkg/meshioplusplus/` vcpkg overlay port (`vcpkg.json` + `portfile.cmake` + `usage`) both drive the same `-DMESHIOPLUSPLUS_BUILD_C_API=ON -DMESHIOPLUSPLUS_BUILD_PYTHON=OFF` install/`find_package` path (the `meshioplusplus::meshioplusplus` target). Options/features: `with_hdf5`/`with_netcdf`/`with_zlib` (on) and `fortran`/`with_eigen`/`with_kahip` (off — Eigen is a submodule absent from a source tarball, so the MED transpose uses the fallback loop; KaHIP is on neither ConanCenter nor the vcpkg registry, so `with_kahip`/the vcpkg `kahip` feature map only the CMake flag and the consumer supplies `KAHIP_ROOT`; the lib is shared-only). The vcpkg `hdf5` feature depends on upstream vcpkg's `hdf5` port with `default-features: false` + explicit `features: ["zlib"]` (meshio++ never uses szip, only plain HDF5 + zlib) — kept for forward compatibility, but currently **ineffective**: a known vcpkg-tool limitation (`default-features: false` isn't honored reliably even for a direct manifest dependency — reproduced locally against a fresh vcpkg checkout; see microsoft/vcpkg#31230/#26664) means `hdf5`'s own default `szip` feature still gets pulled in regardless, which in turn needs `libaec`. The **actual** fix is `packages/vcpkg/libaec/`, a second overlay port (alongside `packages/vcpkg/meshioplusplus/`) that replaces vcpkg registry's `libaec` portfile — otherwise byte-identical — with one sourcing the same `v1.1.7` tag from `Deutsches-Klimarechenzentrum/libaec` on GitHub instead of `gitlab.dkrz.de`: same maintainer/org, same release content (different tarball SHA512 since GitHub and GitLab produce differently-encoded archives for identical source), reachable without the rate-limiting (HTTP 429) that had been intermittently failing the release-tag `vcpkg-build` CI job. Verified locally end-to-end (bootstrapped vcpkg, built `libaec`+`hdf5`+`netcdf-c` against this overlay set). `.github/workflows/packages.yml` validates the Conan recipe (two option legs, each on x86_64 and arm64 — see "CI" below) and the vcpkg manifest (x86_64 only; the overlay-port zip it produces is source, not an arch-specific binary) on every PR, and on `v*` tags pins the tarball SHA512 + builds the vcpkg port end-to-end. Not submitted to Conan Center / the upstream vcpkg registry (documented follow-up) — as a stopgap, `v*` tags attach ready-to-use Linux package artifacts, for both x86_64 and arm64, to the tag's GitHub Release (created if absent, via `softprops/action-gh-release`): a `conan cache save "meshioplusplus/<version>:*"` archive per option leg × arch (supplies just the recipe + one matching prebuilt binary — `conan cache restore <file>` then `conan install --requires=meshioplusplus/<version> --build=missing -o ...`; Conan Center still supplies the transitive hdf5/netcdf/zlib/openssl binaries over the network as normal, and `--build=missing` rebuilds meshioplusplus from the archived recipe if the consumer's profile doesn't match the prebuilt one — verified end-to-end both ways) and a zip of the vcpkg overlay port with the release tarball's SHA512 already pinned in (the in-repo `portfile.cmake` keeps the `SHA512 0` placeholder; only the release asset's copy is patched). Docs: [`doc/c_api.md`](doc/c_api.md#package-managers-conan-vcpkg).

**Native CLI viewer** (`src/cpp/cli/view_payload.{hpp,cpp}` + `polyscope_view.{hpp,cpp}`, `MESHIOPLUSPLUS_WITH_POLYSCOPE`, **OFF by default**): Polyscope (MIT) vendored as a git submodule at `src/cpp/third_party/polyscope` — it is in no package manager and its docs offer only `add_subdirectory`/FetchContent. It has **its own** submodules, so `git submodule update --init --recursive` is required; a plain `--init` leaves an `EXISTS`-guarded no-op (the Eigen pattern) and the viewer is simply absent. **It links to the CLI target ONLY, never to `meshioplusplus_core_obj`** — unlike KaHIP, which is in the core because partitioning is a core operation. Viewing is not, so `_core`/C API/Fortran/WASM cannot acquire an OpenGL dependency through it and "the core is dependency-free" stays literally true. Release binaries are unaffected: the flag defaults off and `cli.yml`'s existing `! ldd | grep libstdc++` assertion is the guard. **The mapping is split at the same seam as Python's**: `view_payload.cpp` is deliberately free of every Polyscope header, so it compiles and is gtested (`test_view_payload.cpp`, 14 cases) in the *default* build with no GL, while `polyscope_view.cpp` is the only TU including Polyscope and the only thing the flag guards. `view_payload.cpp` is the **twin of `_viewer.py`'s `_to_polyscope_payload` — KEEP THEM IN SYNC**; both are needed because Python's must work with no compiled core, so moving the logic would relocate the duplication rather than remove it, and the two test suites assert the same invariants deliberately. Two facts read from the vendored headers rather than the docs: the mixed-cell padding sentinel is **`INVALID_IND_32` (UINT32_MAX)**, not the negative value the Python docs describe (the container is `std::array<uint32_t,8>`); and **`registerTetHexMesh` concatenates tets-then-hexes regardless of input order**, which would silently re-map every per-cell quantity — so the padded array must be built by us in block order, and a test pins that. `view`/`screenshot` exist in every build and throw naming the flag when compiled out (the `partition_kahip_parts` contract). CI: the `cli-polyscope` job in `ci.yml`, never `cli.yml`.

**Interactive viewer** (`src/python/meshioplusplus/_viewer.py` + `_viewer_browser.py`, web app in `src/viewer/`, docs [`doc/viewer.md`](doc/viewer.md)): one entry point `view(mesh, backend="auto"|"polyscope"|"browser", kind=, color_by=, name=, show=)` plus `screenshot(mesh, path, ...)` and `has_viewer()`, and CLI verbs `view`/`screenshot`. **Polyscope is a PYTHON-ONLY optional dependency** behind the `[viewer]` extra — lazily imported inside the two functions that need it, never at module scope, and it never reaches the C++/WASM/C/Fortran core; a missing install raises naming `pip install meshioplusplus[viewer]`. The bulk of the module is the **pure** `_to_polyscope_payload(mesh, kind)` (no renderer import, no display, no mutation), which is what makes the routing testable in the default CI matrix with polyscope absent. Routing facts that are contracts, not preferences: polyscope volume meshes hold **only tetrahedra and hexahedra**, so wedge/pyramid/higher-order go through `convert_cells(simplexify)` but hexes deliberately do not; a mesh with both tets and hexes is packed into a negative-padded `mixed_cells` array **here** rather than handed over as separate `tets=`/`hexes=` arguments, because otherwise the row order — and so every per-cell quantity — would depend on polyscope's internal merge order; each structure type has its own `defined_on` vocabulary (surface `vertices`/`faces`, volume `vertices`/`cells`, curve `nodes`/`edges`, point cloud **none at all**); `_init_polyscope` is idempotent because polyscope refuses to re-init with a different backend, so a headless screenshot followed by a window would otherwise raise. Cell data is tied to rendered primitives by the `cell_source` global-cell-index array from `_dimension_rows`, whose counter advances over *skipped* blocks — a gmsh file whose `triangle` block follows a boundary-marker `line` block is what makes that necessary, and the wrong answer still renders. Colours are detected by array **name** (`color`/`rgb`/`*_color`/`*_rgb`), never inferred from a [0,1] range. Every lossy step appends to a `notes` list surfaced as a warning. `_viewer_browser.py` writes **VTP** (not VTU — vtk.js has no unstructured-grid model) into the committed single-file bundle at `src/python/meshioplusplus/_viewer_assets/viewer.html`; its `_renderable_surface` is the **Python twin of the WASM `convertSurfaceOps([])` binding and the two must stay in step** (pinned by a test, not by coincidence). The offline page has no WASM and so cannot *run* operations: anything it should show is baked in by Python — `build_page(..., quality=True)` attaches metrics **before** the boundary extraction so the existing parent-id gather carries them for free, `stats=True` (default) embeds the volume mesh's geometry, and `color_by` resolves to the viewer's `location:name:component` key and **raises** on an unknown name. All three go through exact-string payload slots that CI greps for.

**Interoperability layer** (`src/python/meshioplusplus/_interop.py`, docs [`doc/interop.md`](doc/interop.md)): converts a `Mesh` to/from the **in-memory** objects of PyVista, trimesh and Apache Arrow/Parquet with no file round-trip. **Python-only, over the numpy the readers already return — it adds no format, touches no binding, and the C++/WASM/C/Fortran core is untouched and stays dependency-free.** Structured exactly like `_viewer.py` and for the same reason: the bulk is a **pure payload layer** (`_to_vtk_payload`/`_to_triangles_payload`/`_to_table_payload` + frozen dataclasses) that imports no third-party library, mutates nothing, and is therefore tested in the **default** CI matrix with none of the optional libs installed; the public `to_*`/`from_*` are thin wrappers importing their target *inside* the function and raising a named `pip install meshioplusplus[...]` error (`_require`), with `has_pyvista`/`has_trimesh`/`has_arrow` (+ `has_open3d`/`has_dolfinx` → `False`, Phase 2) as the predicates. **Reuse, not transcription**: the meshio↔VTK type map/node orderings come from `_vtk_common.py` (`meshio_to_vtk_type`, `meshio_to_vtk_order`, and `vtk_cells_from_data` for the reverse — note its `offsets` are *end* offsets, so `from_pyvista` passes `grid.offset[1:]`), and the global block-major cell index comes from `_regions.block_bases` (the Python owner of `detail/cell_index.hpp`) — nothing re-derives a block offset (the `_dimension_rows` counter bug is the cautionary tale). **The zero-copy contract**: buffers are shared when the target takes the array as-is; every `to_*` takes `zero_copy_only` (`False` → each copy lands in `notes`, surfaced as a warning; `True` → `InteropError` naming the array and reason). It governs arrays that *exist in the Mesh* (points, each data array, single-block connectivity) but **not derived ones** — VTK's `offsets`/`celltypes` have no meshio++ counterpart and a multi-block mesh has no single connectivity array, so making those fatal would reject every mixed-type mesh; they go to the payload's separate `derived` list, which is deliberately **not** warned (it is a data-model difference, not a loss). Copies are forced by int32→int64 connectivity, a `wedge` block (meshio's gmsh-Prism order ≠ VTK's), 2-D point padding, non-contiguity, `bool`→uint8, and any cross-block concatenation. **Lifetime is a hard requirement** — the readers hand back capsule-backed numpy owned by the C++ core — so every wrapper carries a `_meshioplusplus_refs` list of the shared arrays rather than relying on VTK's `_numpy_reference`; pinned by a convert→`del`→`gc.collect()`→re-read test. **PyVista**: `pv.UnstructuredGrid(offsets, conn, celltypes, points)` **does not exist** (only the legacy `(cells, cell_type, points)` layout, which always copies), so the zero-copy route through `vtkCellArray.SetData(numpy_to_vtkIdTypeArray(..., deep=False))` + `grid.SetCells(...)` is **mandatory, not a preference**. Blocks VTK cannot express (`polyhedron`, `custom`, unmapped) are dropped-with-a-note, never an exception. **Regions**: Point/Cell export as int8 `region:<name>` masks **plus** a JSON sidecar (`meshioplusplus:regions` in `grid.field_data` / trimesh's `metadata`) carrying `dim`/`tag`, which a mask cannot — without it a gmsh physical tag would not survive; `Side` regions are dropped by name (no VTK `(cell, facet)` concept). **trimesh** is triangles-only and composes the *existing* ops (`extract_surface` → `convert_cells("linearize")` → `convert_cells("simplexify")`), needs `process=False` (the default merges vertices and silently renumbers), and gets **no second region policy** — it inherits those ops' documented behaviour. **Arrow/Parquet** is a **tabular data export, NOT a mesh format**: deliberately not in `registry.cpp`/`_helpers`, so `convert mesh.vtu out.parquet` does not work; multi-component arrays are `fixed_size_list` (never `_0`/`_1`/`_2` — the flat JS mesh representation taught that); `ChunkedArray.combine_chunks()` **copies even for a single chunk**, so `from_arrow` takes `chunk(0)` (measured, and `_arrow_shares` asserts sharing rather than assuming it). CLI: a tenth `data export IN OUT.parquet [--location point|cell]` sub-verb in `_cli/_data.py`, **Python CLI only** (a documented native-CLI gap). Extras `[pyvista]`/`[trimesh]`/`[arrow]`/`[interop]`, kept **out of `[all]`** (which means "the optional deps the *formats* need" — h5py/netCDF4; `[viewer]`/`[kahip]`/`[codecs]` are the precedent). CI: the `interop` job in `ci.yml` (plain pip + `libgl1` for the VTK wheel's import); the per-backend C++ matrix is untouched. Open3D/DOLFINx are Phase 2 stubs raising `NotImplementedError` — the constraints (Open3D's copying `Vector3dVector` and ~400 MB wheel; DOLFINx's single-cell-type limit, `ufl`/`basix` domain, MPI communicator, VTK→basix node permutation via `cell_perm_gmsh`, and conda/apt-only install) are recorded in `doc/interop.md`.

**GPU handoff** (`src/python/meshioplusplus/_gpu.py`, docs [`doc/gpu.md`](doc/gpu.md)): moves a mesh's arrays to/from device memory through the standard exchange protocols — **DLPack primary** (`to_dlpack` returns a frozen `DevicePayload` of host numpy arrays, each natively speaking `__dlpack__`/`__dlpack_device__`; DLPack was chosen because it is framework-neutral AND covers host arrays (`kDLCPU`), so one export path serves CPU and GPU consumers and the host half is fully CI-testable with no GPU), `__cuda_array_interface__` (CAI) **consumed** on ingest and exposed for free by the CuPy arrays `to_cupy` returns. **Python-only over the numpy the readers already return — the C++/WASM/C/Fortran core is untouched and stays dependency-free.** Same pure-payload split as `_interop.py` (whose `InteropError`/`_copy_note`/`_derived_note`/`_prepare_data_array`/`_emit`/`_importable` it reuses — one data policy, not two): the bulk is `_to_device_payload` (no third-party imports), `to_cupy`/`from_cupy` are thin gated wrappers. **The honesty rule (non-negotiable): a host→device move is always a bus transfer** — the feature removes the file round-trip and every *extra* copy around that one transfer; "zero-copy" is used only for host buffer sharing (`to_dlpack` honors `zero_copy_only` — the existing HOST contract, unmuddied) and on-device adoption; `to_cupy` deliberately takes **no** `zero_copy_only` (a lie on a 100%-copy path) and `from_cupy` performs one deliberate, noted device→host copy per array (its ladder: numpy as-is → `np.from_dlpack` for any `kDLCPU` exporter, no CuPy needed → `.get()` → CuPy CAI/DLPack adoption + one copy back). Payload shape: `cells` = per-block `(type, conn)` (ragged blocks dropped-with-note), **cell_data stays per-block** and `block_bases` (from `_regions.block_bases`, never re-derived) rides along so consumers concatenate block-major themselves; **regions ride as plain `(name, kind, dim, tag, entries)` index arrays, NOT the mask+sidecar convention** — that convention exists only because VTK/trimesh have no structured region slot, and index arrays are lossless here (`Side` `(cell,facet)` pairs survive — the only interop target that keeps them; cell/side entries renumbered at export when a ragged block dropped). Dtypes stay canonical float64/int64; `float32=True`/`int32=True` are explicit noted opt-ins, int32 range-checked (`InteropError`, never wrapped). Optional pinned staging (`pinned=True`, `stream=` for async DMA — staging buffers kept on `payload.refs`, caller must sync); **the C++ half of reading directly into pinned memory landed in v8.5.0**: `meshioplusplus::set_buffer_allocator` (`ndarray.hpp`) installs a process-global `BufferAllocator` (plain C callbacks) consulted at every owning-`NDArray` allocation — each buffer pins the allocator it was born with via its own `shared_ptr`, so uninstalling never orphans live buffers and the numpy capsule handoff needs no change (the buffer's deleter fires inside `~NDArray`); copies allocate through the *current* hook (pinned-ness doesn't propagate), views are unaffected; gtested in `tests/cpp/test_ndarray_allocator.cpp`. The Python/CuPy wiring (`pinned_reads()` context manager + `to_cupy(pinned=True)` fast path — GIL in both callbacks, `Py_IsInitialized()` guard on the free path) is the recorded Phase-2 follow-up (doc/gpu.md). **Packaging finding: there is deliberately NO `[gpu]` pip extra** — CuPy wheels are CUDA-version-specific (`cupy-cuda13x`/`cupy-cuda12x`/`cupy-cuda11x`/ROCm), so a pinned extra would break for most users; `_gpu._require_cupy` raises naming the wheel recipe (deliberately not `_interop._require`, whose `pip install meshioplusplus[...]` phrasing is baked in), and `has_cupy` (importable) is distinct from `has_cuda_device` (a device actually answers — CuPy imports fine with no GPU and fails at first use). **CI has no GPU**: `tests/python/test_gpu.py`'s always-on half (pure payloads + the DLPack host round-trip via `np.from_dlpack`, sharing measured not assumed) runs in the default matrix, the coverage job and the `interop` job; the gated device half (`importorskip("cupy")` + `getDeviceCount() > 0`) is **not covered by public CI** and its CuPy-only lines read as uncovered on the Codecov patch check by design — documented, not excluded.

**MCP server** (`src/python/meshioplusplus/mcp/`, docs [`doc/mcp.md`](doc/mcp.md)): exposes the whole Python surface to AI agents over the Model Context Protocol — 33 tools mirroring the CLI verbs (inspection: `formats`/`sniff`/`info`/`stats`/`quality`/`data_info`/`regions`/`bandwidth`/`data_preview`/`diff`; `convert` with `mode`/`compression` params subsuming the CLI's ascii/binary/compress/decompress verbs via the same writer-kwargs mapping; all 16 path-based mesh operations; `data_manage`/`data_convert`/`data_calc`/`data_condition`; gated `data_export` (`[arrow]`) and `screenshot` (`[viewer]`, returned as MCP image content)) plus two resources (`meshioplusplus://formats`, `://version`). **Stateless and file-path based by design** — input path(s) → public-API call → output path(s) → strict-JSON report; no mesh lives between calls, so arbitrarily large meshes never enter the protocol. Same pure/gated split as `_interop.py` and for the same two reasons: `_tools.py` (ALL behaviour: the `_resolve` sandbox, the `_json_safe` sanitizer — numpy→lists, NaN/Inf→`None` with a `non_finite_replaced` count, arrays >1000 elements → `{"truncated", "preview", ...}` wrappers — and one `tool_*` function per tool) imports nothing beyond meshioplusplus+numpy+stdlib and runs in the default CI matrix on every supported Python, while `_server.py` is the only module importing the `mcp` SDK — whose **own floor is Python ≥3.10** against the package's 3.8, the second reason the split is load-bearing, not stylistic. `_server.py`'s typed wrappers contribute exactly the JSON schemas (from annotations) and tool descriptions (docstrings), never behaviour, and every call is guarded into `{"error", "error_type"}` payloads — a tool never surfaces a traceback. `TOOL_REGISTRY` in `_tools.py` is the single source of truth (ordered name → `{fn, wraps, gated}`): `_server` registers from it and the **parity guard** (`test_mcp.py::test_every_operation_has_a_tool`) asserts every operation in `meshioplusplus.__all__` (minus the formats prefix and the explicit `_NOT_TOOLS` exemptions — in-memory interop/GPU, `view`, classes, plumbing) is claimed by some tool's `wraps`, so API/server drift is a red build (see "Keeping docs in sync"). Path sandbox: default unrestricted, opt-in `--root DIR` / `MESHIOPLUSPLUS_MCP_ROOT` with realpath containment. Entry points: console script `meshioplusplus-mcp` → `meshioplusplus.mcp:main` (deliberately NOT `._server:main`, so a missing extra prints the named `pip install meshioplusplus[mcp]` error instead of an ImportError traceback) and `python -m meshioplusplus.mcp`; stdio transport only. Extra `mcp = ["mcp>=1.2"]`, NOT in `[all]` (the interop precedent). One ergonomic addition over the raw API: `data_calc` accepts the CLI's `"NAME = EXPR"` spelling (split on the FIRST `=`, the documented colon rule). CI: the `mcp` job (below); the default matrix runs the pure half with the SDK absent.

**Browser viewer** (`src/viewer/`, Vite + **TypeScript** + `@kitware/vtk.js`): a web app that **CONSUMES the published `@meshioplusplus/wasm` package**, not the core — vtk.js/Vite/Playwright are isolated under `src/viewer/`'s own `package.json` and never touch the root or `src/wasm/`. Two builds from one source: `build:web` (the Pages demo, WASM worker + file picker) and `build:embed` (a single self-contained file shipped in the wheel, where the WASM client is **aliased to a stub** — dead-code elimination alone is not enough, since Vite's worker plugin emits `new Worker(new URL(...))` chunks at *transform* time). Deployed by **`docs.yml`** as a second static island at `/viewer/` beside Doxygen's `/api/` — a repo gets one Pages deployment, so a separate workflow would fight it over the `pages` concurrency group. That job must run emsdk + `./build/configure-wasm.sh --build` first, because `src/wasm/dist/` is gitignored. **npm *copies* a `file:` dependency and a later `npm install` does not refresh the copy**, so `vite.config.mjs` compares both the wrapper's exports and the installed `.wasm` against `src/wasm/dist/` at `buildStart` and fails with the `rm -rf node_modules/@meshioplusplus` recipe; CI is immune because it builds then runs `npm ci`. Viewer samples and fixtures carry a **Git LFS exemption** (`.gitattributes`) — an LFS-less checkout would otherwise hand the app 130-byte pointer files. Playwright asserts on the documented `window.__viewerState` hook rather than pixels, so it needs no GPU. Its specs live at `tests/viewer/` (unit tests at `tests/viewer/unit/`), not under `src/viewer/`, per the repo-wide test unification — but they still need `src/viewer/`'s own `node_modules` (`@playwright/test`, `esbuild`) to resolve, and Node's ESM resolver only walks up from the *importing file's* location, which `tests/` isn't an ancestor of. `src/viewer/tools/link-test-deps.mjs` (run via `postinstall`) symlinks `tests/viewer/node_modules` to `src/viewer/node_modules` for the Playwright specs' bare `@playwright/test` imports; `test:unit`'s runner (`tests/viewer/unit/build-and-run.mjs`) instead resolves `esbuild` explicitly via `createRequire` rooted at `src/viewer/package.json`, since it only needs one resolved entry point rather than transparent resolution for every spec file. **Click-to-inspect** uses `vtkCellPicker` (CPU ray/cell, so renderer-independent) on click only — its listener must go on the **container**, not the canvas, because vtk.js takes pointer capture on the container and a canvas-bound `click` never fires at all; provenance comes from the `surface:parent_cell` that `convertSurfaceOps(keepProvenance: true)` retains and `scalars.ts` filters out of the colour-by menu. **The app runs meshio++'s own operations** (quality/clean/smooth/refine/partition/section/isosurface) through the single `convertSurfaceOps` binding: the panel owns the pipeline as a list, every change re-sends the *whole* list, and the worker replays it against the **original file bytes kept staged in MEMFS** — which is why `apply` deliberately never unlinks, why undo is exact rather than an inverse, and why multi-component data survives (no mesh re-enters JS). **TypeScript conventions**: `as any` is banned in `src/` and CI-grepped; gaps go in `vtk-augmentations.d.ts` (declaration merging, still type-checked) or `vtk-shims.ts` (named `as unknown as` helpers) — the augmentation file must **not** be named `vtk-shims.d.ts`, since TS would resolve it and `vtk-shims.ts` to one module, keep the `.ts`, and silently drop the declarations. `window.__viewerState` is typed in `src/types.ts` so a new field with un-updated tests is a compile error. Two vtk.js findings worth not rediscovering: `setInterpolateScalarsBeforeMapping(true)` renders a range spanning zero **entirely in the warm half** in 32.9.0 (measured: 0 blue px vs 275k red), so it is off; and the coincident-topology polygon offset belongs on the **edge** mapper, because a negative offset moves toward the viewer and putting it on the body hides the wireframe behind its own surface. `vtkClipClosedSurface` is unusable for a coloured cut (its point-data interpolation is commented out upstream), which is why the section goes through meshio++'s `crop_plane` + re-skin instead. Regenerate the wheel asset with `npm run build:embed && cp dist-embed/index.html ../python/meshioplusplus/_viewer_assets/viewer.html`; the CI check on it is **structural (10% size drift), never a `git diff`** — Rollup output is not reproducible across npm patch releases.

**Julia / R example notebooks** (`example/julia/*.ipynb` / `example/r/*.ipynb`, docs [`example/julia/README.md`](example/julia/README.md) / [`example/r/README.md`](example/r/README.md)): the same three-notebook tour (01 read/visualize, 02 convert/inspect, 03 the full ~20-section operations tour) called through the **`MeshioPlusPlus` Julia package** and **`meshioplusplus` R package** — no Python, no C++ core directly, both riding the installed flat C API exactly as Fortran does. Kernels: [IJulia](https://github.com/JuliaLang/IJulia.jl) (`julia -e 'using Pkg; Pkg.add("IJulia")'`, a standard system-wide install, no `--project` baked in — each notebook's first cell `Pkg.activate`s `bindings/julia/MeshioPlusPlus` itself) and [IRkernel](https://irkernel.github.io/) (installed alongside the R package into a `r-notebooks` env in the **same** gitignored `.micromamba/` root the C++ kernel uses — `micromamba create -n r-notebooks -c conda-forge r-base r-irkernel c-compiler`, the `c-compiler` package being required since conda-forge's `r-base` pulls in no compiler by default). Both consume a **prebuilt** `inst-nohdf5/` C API prefix (gitignored, `-DMESHIOPLUSPLUS_WITH_HDF5=OFF -DMESHIOPLUSPLUS_WITH_NETCDF=OFF`) — HDF5 off is **load-bearing for Julia specifically**: on Debian/Ubuntu a HDF5-enabled build links `libhdf5_openmpi`, which links the system `libcurl`, and an IJulia kernel subprocess's `dlopen` of that library can fail with `libcurl.so.4: version 'CURL_OPENSSL_4' not found` since Julia bundles its own incompatible `libcurl` (a real Debian/Ubuntu + Julia interaction, reproduced by toggling HDF5 on vs. off, not a meshio++ bug — this also means the `julia` CI job in `ci.yml` must build with HDF5 off, not just netCDF off, or it would likely fail the same way on real Ubuntu runners); R has no such conflict but reuses the same prefix so the `02_convert_and_inspect.ipynb` file-size comparisons stay apples-to-apples (XDMF's data format follows the build). Rendering mirrors the C++ notebooks' reasoning (no PyVista) but hits an *additional* constraint the C++ notebooks don't: **the flat C API's `mio_write`/`mio_write` can't carry per-call SVG styling at all** (registry.cpp's `(path, mesh)` lambdas take no parameters, unlike C++'s direct `write_svg(...)` call with explicit `color_by`/`cmap`/etc.), so every render in these two notebook sets is **plain, uncoloured** — quality/field distributions that the C++ notebook shows as a coloured mesh are shown as a histogram/bar chart instead (`mio_notebook.jl`'s `bar_chart`/`histogram_chart`, hand-rolled SVG; `mio_notebook.R`'s `mio_bar_chart`/`mio_histogram`, plain base-R graphics IRkernel captures as inline PNG with no extra package — meshio++'s own colormap tables aren't reachable from the C API either, so neither reuses them). Both reuse `example/cpp/example.vtu` (copied, not re-derived — both are Git-LFS so this is cheap) for the same Gmsh-`$Entities` C++-reader-gap reason the C++ notebooks do. **Two real findings surfaced while writing these** (both already fixed in the bindings and documented in `doc/julia.md`/`doc/r.md`/both `example/*/README.md`): (1) `smooth()`'s `mu` default was wrongly hardcoded `-0.53` in **both** the Julia and R bindings (the real default, per Fortran's `meshioplusplus.f90:1853` and Python's `mp.smooth`, is `-0.34`) — a `-0.53` pass-band reliably *degrades* a tangled mesh instead of recovering it, caught by cross-checking the notebooks' synthetic jittered-hex smoothing demo against the Python bindings (which recovered cleanly) before either Julia or R did; (2) R's data setters (`mio_add_point_data`/`mio_append_cell_data`/`mio_add_field_data`) always write `Float64` regardless of the R vector's storage mode — R has no integer type reaching the C ABI on the *write* side either — so `mio_split(by = "region")` cannot be driven by a tag built fresh in R (only one already present in a read file, or produced by the C++ core itself like `isosurface()`'s `iso:index`); `example/r/03_mesh_operations.ipynb`'s split demo uses `by = "type"` for exactly this reason, and this is now a documented `doc/r.md` gap distinct from the Julia binding, which has no such restriction. Committed **with outputs**; re-execute per each README's kernel-setup + nbconvert recipe.

## Architecture

**Core data model** (`src/python/meshioplusplus/_mesh.py`, pure Python, unchanged):
- `Mesh`: holds `points`, `cells` (list of `CellBlock`), `point_data`, `cell_data`, `field_data`, `point_sets`, `cell_sets`, optionally `gmsh_periodic`/`info`
- `CellBlock`: a cell type string (e.g. `"triangle"`, `"tetra10"`) + numpy node-index array
- `_common.py`: `num_nodes_per_cell`; `topological_dimension` in `_mesh.py`

**C++ core** (`src/cpp/`, `bindings/`):
- `src/cpp/include/meshioplusplus/` headers (`ndarray.hpp`, `mesh.hpp`, `mesh_api.hpp`, `cell_type.hpp`, `types.hpp`, `registry.hpp`, `region.hpp`, `backends/*`, `detail/*`, `formats/*`), `src/cpp/src/formats/*.cpp`, compiled with `bindings/python/_core.cpp` into `meshioplusplus._core`.
- **Format dispatch registry** (`registry.hpp` + `src/cpp/src/registry.cpp`, compiled into `meshioplusplus_core_obj`): the C++-level `format name -> read/write function` tables, `extension -> default format` map, `resolve_format()`, and `registry_compiled_out()` (names the missing optional dep for HDF5/netCDF formats absent from a build; their extensions are mapped unconditionally so errors say "no HDF5 support" instead of "cannot infer format"). Shared by the **flat bindings** — WASM (`bindings/wasm/js_bindings.cpp`, which no longer carries its own tables) and the C API (`bindings/c/`) — while the pybind11 binding keeps its one-function-per-format surface with dispatch in Python (`_helpers.py`). Parameterized writers get fixed defaults here (documented per entry; matching the Python reference defaults, except xdmf which follows the build: HDF when HDF5 is available, XML otherwise). **A new C++ format must also be registered here** (reader/writer entry + extension default) or the flat bindings won't see it.
- **C API** (`bindings/c/`): `include/meshioplusplus/meshioplusplus.h` (the single installed pure-C99 header; the C++ headers make no ABI promise) + `c_api.cpp`, built into the installable `libmeshioplusplus` shared lib (SOVERSION 0) when `MESHIOPLUSPLUS_BUILD_C_API=ON`. Flat whole-mesh API over the **uniform mesh API only**, so it compiles under all three mesh backends and the gtest C-API suite runs per-backend in CI. Contract: `mio_status` codes + thread-local `mio_last_error()` (no exception crosses the ABI — every extern "C" body runs in `guarded()`/`guarded_ptr()`); setters copy, getters are zero-copy borrows valid until the next mutating call; strings via caller-buffer + required-length return (never `c_str()` of a per-backend-possibly-temporary `Type()`); row-major arrays, 0-based connectivity (int32 widened to int64 on ingest); ragged blocks are reported (`is_ragged`) but their connectivity is inaccessible (v1); side-channel structs (point_sets/cell_sets/MED families) are dropped like WASM. The `mio_cell_type` enum duplicates the cell-type list in the C header and `c_api.cpp` static_asserts every entry against `CellType`, so drift is a compile error.
- **Fortran module** (`bindings/fortran/meshioplusplus.f90`, module `meshioplusplus`, `MESHIOPLUSPLUS_BUILD_FORTRAN=ON` which force-enables the C API): modern OO Fortran 2008 (`type(mio_mesh)` with type-bound procedures, HDF5/PETSc style) over the C API via ISO_C_BINDING; raw `bind(c)` interfaces are private (`c_mio_*`). Conventions: arrays are Fortran-shaped — points `(dim, n)`, conn `(npc, ncells)` — which is the *same memory* as the C row-major shapes (no transpose anywhere); connectivity is 1-based, shifted ±1 inside the copying setters/getters only; `points_ptr` is the zero-copy borrow (no shift needed); every fallible procedure takes optional `stat`/`errmsg`, absent `stat` + failure = print + `error stop` (stdlib pattern); handles freed explicitly (`m%free()`, no finalizer).
- **Julia / R bindings** (`bindings/julia/MeshioPlusPlus/`, `bindings/r/meshioplusplus/`, docs [`doc/julia.md`](doc/julia.md) / [`doc/r.md`](doc/r.md)): the fourth and fifth consumers of the **installed** C API, alongside Fortran. **No new C++ and no core change** — both build entirely OUTSIDE the CMake tree and consume `libmeshioplusplus` + the installed `.pc`, so `MESHIOPLUSPLUS_BUILD_C_API=ON` + `cmake --install` is the prerequisite for both (`inst/` is gitignored). Full **Fortran parity**: lifecycle, read/write (+ `ReadOptions`/metadata), all setters/getters, regions, and all ~24 operations including the opaque-result ones. **Both languages are column-major, so Fortran's two rules carry over verbatim and are the load-bearing design facts**: points `(dim, n)` / conn `(npc, ncells)` are the *same memory* as the C row-major shapes (**no transpose anywhere** — the one exception is `transform`'s 4x4 affine matrix, which *is* transposed, being a mathematical object rather than a mesh array), and connectivity is 1-based with the ±1 shift **inside the copying accessors only**. Index maps / permutations follow Fortran's rule to the letter — `+1` with the `-1` "pruned/absent" sentinel becoming **`0`** (`meshioplusplus.f90:2042`) — and `partition_labels` returns part *ids*, deliberately unshifted; region `Side` entries shift the cell column but **not** the facet column. **Ownership rule shared by both**: the opaque results (`split`/`partition`/`reorder`/`refine`/`decimate`/`convert_cells`) are always drained through `_take_mesh`, never `_result_mesh`, so every mesh handed to the user owns its handle and no piece can dangle when the result is freed. **Julia**: `ccall` via a runtime `dlopen`/`dlsym` cache (`ccall((:sym, lib), …)` needs a compile-time-constant library, so the path — `MESHIOPLUSPLUS_LIB` first, then `Libdl.find_library` — cannot be used that way); GC **finalizer** rather than Fortran's explicit `m%free()` (`close` is the deterministic form); genuine zero-copy borrows via `unsafe_wrap`, wrapped in a `MeshBorrow <: AbstractArray` that holds the owning `Mesh` (GC) **and** a mutation-generation snapshot, so using a borrow after a mutating call raises `BorrowError` instead of reading stale memory — the C header's rule 3 enforced, not merely documented; `read`/`write`/`convert`/`merge`/`split`/`diff` are **not exported** (they shadow `Base`), everything else is. **R**: plain `.Call` over R's C API, **not Rcpp** (zero `Imports`, no C++ toolchain in `R CMD check`), external pointer + registered finalizer, and **copy-only** — R vectors are R-managed, so there is no borrow and deliberately **no `_ptr` accessor at all**; the 0-based reader is `mio_connectivity_raw`, named so nobody reads it as a borrow. R has no native int64, so every int64 array (connectivity, region entries, maps, perms) comes back as `double` (exact to 2^53, no `bit64` dependency) with the stored dtype reported in a `"dtype"` attribute. The same limitation runs the other way too: **R's data *setters* always write `Float64`** (`mio_add_point_data`/`mio_append_cell_data`/`mio_add_field_data` hardcode `MIO_FLOAT64` regardless of the R vector's storage mode), so `mio_split(by = "region")`, which needs a genuinely integer cell-data tag, cannot be driven by a tag array built fresh in R — only one already present in a *read* file (a gmsh physical group, an `isosurface()`-produced `iso:index`, …) works; `example/r/03_mesh_operations.ipynb` hit exactly this and uses `by = "type"` instead. **`smooth`'s `mu` default is `-0.34`, not `-0.53`** — both the Julia and R bindings initially hardcoded an invented `-0.53` (never checked against the real default in Fortran's `meshioplusplus.f90:1853` / Python's `mp.smooth`), which is a *much* wider Taubin pass-band and reliably **degrades** quality instead of recovering it (caught by cross-checking a synthetic jittered-hex smoothing demo against the Python bindings while writing `example/julia/03_mesh_operations.ipynb` and `example/r/03_mesh_operations.ipynb` — Python recovered cleanly, Julia/R got worse with the wrong default, both matched Python once fixed). R's `configure` generates `src/Makevars` from `src/Makevars.in` (pkg-config → `MESHIOPLUSPLUS_HOME`) because a committed `Makevars` with a `$(shell …)` earns an `--as-cran` non-portable-flags NOTE — the `sf`/`xml2` pattern. Every export is `mio_`-prefixed to stay clear of base R's `points`/`stats`/`split`/`merge`. **Licence exception**: `bindings/julia/` is **GPL-3.0**, NOT MIT — copyleft, not permission-required: no permission is needed to use/modify/sell it commercially, but *conveying* (distributing) it or a modified version requires doing so under GPL-3.0 too with source available; purely private use carries no obligation. GPL-3.0 is OSI-approved so General-registry registration is possible (a separate follow-up, not done), and there is deliberately no JLL yet; `bindings/r/` stays MIT. Both READMEs and doc pages repeat the *same* C-ABI gap list (sets beyond regions, `frozen` masks, per-cell-type counts, ragged connectivity, combined `data_manage`) plus one **format** gap worth not rediscovering: **gmsh does not round-trip named regions** — the writer emits `$PhysicalNames` but attaches no physical tag to an entity in `$Elements`, so the reader has nothing to rebuild the group from (pre-existing, reproducible from Python; abaqus works and is what both test suites use). CI: the `julia` and `r` jobs in `ci.yml`, both mirroring the `cpp-tests` NATIVE leg's install-then-consume shape, each also asserting that a **missing library fails by name**.
- **Mesh backends** (`mesh.hpp` dispatch; mirrors the parallel-backend pattern): `MESHIOPLUSPLUS_MESH_BACKEND` = `MESHIO|NATIVE|KRATOS` selects, at compile time, which structure `meshioplusplus::Mesh` is — exactly one `MESHIOPLUSPLUS_MESH_BACKEND_*` macro is defined. `MESHIO` (default, `backends/meshio_mesh.hpp`) is the meshio-mirroring `Mesh`/`CellBlock` and is **required** when `MESHIOPLUSPLUS_BUILD_PYTHON=ON` (CMake `FATAL_ERROR` otherwise; `np_conversions.hpp` `#error`s too) — PyPI/wheels are unaffected by the other backends. `NATIVE` (`backends/native_mesh.hpp`) is canonical statically-typed storage (Float64 points, Int64 connectivity, `CellType` enum from `cell_type.hpp`, CSR ragged blocks, lazy whole-mesh CSR via `GlobalConnectivity()`); the WASM build uses it. `KRATOS` (`backends/kratos_mesh.hpp`) wraps a Kratos-style `ModelPart` (`backends/model_part.hpp`: Nodes/Elements/Conditions with 1-based Ids, nested SubModelParts sharing root-owned entities, simplified per-entity variables) — ingest stages canonically, `GetModelPart()` materializes lazily (Elements = blocks of max topological dimension, Conditions = lower, names from `backends/kratos_names.hpp` ported from `_mdpa.py`; integer tag cell-data like `gmsh:physical` auto-becomes SubModelParts, toggle `SetBuildSubModelPartsFromTags(false)`), writers serve from staging so round-trips never pay for the ModelPart; after direct ModelPart mutation call `InvalidateBlocks()` — whose rebuild is **lossless as of v9.0.0**: ragged pass-through blocks are carried through at their original positions (cell_data slices included; they never became entities, so a ModelPart edit cannot have touched them) and SubModelParts are read back as named `Cell`/`Point` regions, where before both were silently dropped. SubModelPart **nesting** survives too as of v9.1.0, flattened into region names with `'/'` (the separator `mdpa.cpp` already emitted): `RestoreRegions` walks recursively and `BuildSubModelPartsFromRegions` splits and walks/creates the chain, adding members to the leaf. `'.'` stays reserved (`FullName()` joins with it) and a name containing one is a warn-and-skip rather than a `std::invalid_argument` escaping the lazy accessor. Only a region's `mDim`/`mTag` still cannot survive (recovered from a staged region of the same name, else -1) -- a SubModelPart stores a name and member ids and nothing else, so `-1` is the truthful answer rather than a gap. **Entity names and properties ids survive as of v9.1.0**: `SetBlockEntityName`/`BlockEntityName` are KRATOS-only extras (NATIVE's `PointsData()`/`ConnSpan()` shape) carrying the Kratos spelling per block through `Materialize()` and back through `CollectEntityBlocks` (whose run key compares *effective* names, so an explicit `Element3D4N` still merges with unnamed entities of the same type), and `Materialize()` now reads each entity's properties id from `gmsh:physical` instead of leaving every entity on 0. `GetModelPart()` also has a **`const` overload** (v9.0.0) so a wrapper taking `const Mesh&` can reach it — materialization stays lazy, so `mpRoot`/`mMaterialized` are `mutable`, the same cache-on-demand pattern the staging accessors already use. **Entity names, Properties and the resolver (v9.1.0):** `GeometricalEntity` carries an optional Kratos name (`Name()`/`HasName()`, empty = derive from the cell type) as an interned `const std::string*` from a root-owned `detail::NamePool` — **not** a `std::string`: one distinct name per *block* but one entity per *cell*, so owning it would add ~320 MB to a 10 M-element ModelPart; `unordered_set` is node-based so the pointers survive rehash and a ModelPart move. New **five-argument** `CreateNew{Element,Condition}` `CellType` overloads carry it on the bulk path (distinct arity — no existing call changes). `ModelPart` also gained a real **Properties store** (`CreateNewProperties`/`GetProperties`/`Properties()`) holding `PropertyValue` key/value pairs from the backend-neutral `properties.hpp` shared with MDPA. meshio++ **cannot** fill a real `Kratos::Properties` itself — that needs `KratosComponents<Variable<T>>::Get`, Kratos's registry, deliberately not linked — so a fourth `to_model_part` overload hands each value to a caller-supplied applier callback. `bridge_traits` gained a **detection-guarded `NameOf`** (`if constexpr (requires { e.Name(); })`) so every existing duck-typed source still compiles and simply reports no name. `kratos_bridge.hpp` (header-only, backend-independent) `to_model_part`/`from_model_part` populate/read ANY Kratos-like class — incl. real `Kratos::ModelPart` via a properties-getter — with one O(n) bulk-create pass; CI compile-checks it against real CoSimIO headers (fetched at CI time only — CoSimIO's BSD-4-clause-with-advertising license is never vendored into this MIT repo; `model_part.hpp` is a clean-room implementation). `_core.__mesh_backend__` / JS `meshBackend()` report the active backend. **Adding a backend** = one CMake branch defining `MESHIOPLUSPLUS_MESH_BACKEND_<NAME>` + one `#elif` in `mesh.hpp` + a `backends/<name>_mesh.hpp` implementing the uniform API (`tests/cpp/test_mesh_api.cpp` must pass). CI runs the gtest suite once per backend (`ci.yml` `cpp-tests` matrix).
- **Uniform mesh API rule** (`mesh_api.hpp`): format code (`src/cpp/src/formats/*`, shared `detail/*` helpers, `bindings/wasm/`) MUST go through the uniform methods — ingest `AssignPoints`/`AddCellBlock`/`AddPolygonBlock`/`AddPolyhedronBlock`/`AddPointData`/`AddCellData`/`AppendCellData`/`AddFieldData`, accessors `Points()`/`PointDim()`/`Cells(i)`/`CellRange()` (`Mesh::CellView` with `Type()`/`NumCells()`/`NodesPerCell()`/`Conn()`/`IsRagged()`/ragged `Row`/`Face`) and `PointDataNames()`/`PointData(name)`/`CellData(name, block)`/`CellDataNumBlocks`/`FieldData(name)` (+ `Has*`/`Num*`) — and never backend struct members; that's what lets one format compile under all three backends. **Property sets** (`properties.hpp`, v9.2.0) are on the same footing -- `AddPropertySet`/`NumPropertySets`/`GetPropertySet`/`HasPropertySet`/`FindPropertySet`, ascending by `mId`; the accessor is `GetPropertySet` and not `PropertySet(i)` precisely because of the `Region(i)` name-hiding trap. They are keyed by **id, not entity index**, so no `region_remap` counterpart exists or is needed, and the operation rule is shape-preserving ops carry them (`clean`/`smooth`/`transform`/`attach_quality`/data ops) while restructuring and multi-input ones do not (`merge` would collide on id, plus crop/split/partition/diff). Hoist `Points()`/`Conn()`/data lookups out of per-element hot loops. The one sanctioned exception is `bindings/python/np_conversions.hpp` (pinned to MESHIO). NATIVE/KRATOS canonicalize dtypes at ingest *within kind* (floats→Float64, ints→Int64, never int→float — "first integer cell_data is the tag" conventions survive); owning canonical arrays are moved, not copied.
- **Zero-copy at the I/O boundary**: readers return capsule-backed writeable numpy; writers view numpy memory (`bindings/python/np_conversions.hpp`). The conversion layer carries points/cells/point_data/cell_data/field_data **and named regions** (`region.hpp` — see the regions entry below and [`doc/regions.md`](doc/regions.md)), but **not** `mesh.info` or `gmsh_periodic`. Regions are the model behind the Python `Mesh`'s `.regions` and behind its `point_sets`/`cell_sets`, which are now compat **views** over them; regions are the one thing here that is *copied* rather than viewed on the write path, because `Region::Canonicalize` sorts entries in place and the numpy buffer is not ours to reorder. Formats that still need other out-of-band data carry it via a **side-channel struct** the binding `setattr`s onto the Python `Mesh` (e.g. `MedInfo` for MED's `CHA`/step metadata, `OpenFoamInfo` for `cell_tags`); `AnsysInfo`/`UnvInfo` remain the Phase-2 candidates to absorb into regions. **Field-only formats** (`mff`/`dex`/`ip`, the Modulef/FLUX/ANSYS-Fluent field files) carry no geometry: they read/write a geometry-less `Mesh` (no cells, field values in `point_data`; `dex`/`ip` also fill `points` from the file's coordinates, `mff` has none so its `points` has zero columns) — there is no companion-mesh auto-pairing.
- **Ragged cell blocks**: every backend supports optional ragged blocks — 1-level (jagged polygons, `AddPolygonBlock`) and 2-level (list of faces per cell, `AddPolyhedronBlock`) — for types that can't fit a rectangular `NDArray`, read back via `CellView`'s `RowSize`/`Row` and `NumFaces`/`Face`. MESHIO stores them as nested vectors (`CellBlock::mPolygonRows`/`mPolyhedronRows`), NATIVE as CSR offset arrays, KRATOS as staging pass-through (no ModelPart entities). Zero-copy applies only to rectangular blocks; ragged blocks are **copied** across the Python boundary. `py_to_mesh`'s `allow_ragged` flag is **off by default** (so every rectangular-only writer keeps safely rejecting ragged meshes → Python fallback) and only the ragged-aware bindings (MED write) opt in.
- **Named regions** (`src/cpp/include/meshioplusplus/region.hpp` + `src/cpp/src/region.cpp`, Python `_regions.py`, docs [`doc/regions.md`](doc/regions.md)): `Region{mName, mKind, mDim, mTag, mEntries}` — the unified model of a *named group of entities*, which every set-capable format spells differently (gmsh physical groups, Exodus blocks/node sets/side sets, Abaqus `*NSET`/`*ELSET`/`*SURFACE`, MED families, UNV groups, Ansys components, OpenFOAM patches, Kratos SubModelParts). Three kinds: `Point` (point indices), `Cell` (**global block-major** cell indices — the same numbering `partition_labels` uses, owned by `detail/cell_index.hpp` so nothing re-derives it) and `Side` (`(global cell, local facet)` pairs, facets numbered per `detail/cell_faces.hpp` / `cell_edges.hpp`) — **`Side` has no `point_sets`/`cell_sets` equivalent at all** and is only reachable through `.regions`. `mDim`/`mTag` (-1 = unspecified/none) exist because a gmsh physical group is per-dimension and carries an integer tag two groups of different dimensions may share. Entries are **canonicalized** (sorted + de-duplicated, lexicographically on the pair for `Side`) by `AddRegion` on every backend, which is what makes region equality exact and output byte-identical across MESHIO/NATIVE/KRATOS and thread counts — and what makes a remapped set come back **sorted** rather than in the permutation's order (a visible v8.1.0 change). Storage is `NDArray` Int64 rather than `std::vector` so the read path adopts the buffer zero-copy; the write path copies once. Uniform-API surface: `AddRegion`/`NumRegions`/`Region(i)`/`RegionNames()` (sorted, de-duplicated)/`HasRegion(name[, kind])`/`FindRegion(name, kind)` — **a member function named `Region` hides the type `meshioplusplus::Region` for the rest of each backend's class body, so every declaration after it must qualify it**. The three backends share `detail::RegionList` (in `region.hpp`) so they cannot drift on ordering/canonicalization; KRATOS additionally materializes Point/Cell regions as **SubModelParts**, running **before** the `SetBuildSubModelPartsFromTags` inference so an explicit region wins the name (the existing `HasSubModelPart` guard already implements that), and skipping `Side` with a warn. **Python compat is deprecation-free**: `mesh.regions` is the storage and `point_sets`/`cell_sets` are `dict`-**subclass** write-through views over it (a `dict` subclass, not a bare `MutableMapping`, because `numpy.testing.assert_equal` and plenty of user code branch on `isinstance(x, dict)`). Two accommodations make that lossless: a `cell_sets` entry that is **not** cell-index data takes a private `_extra_cell_sets` passthrough and comes back verbatim (gmsh's `gmsh:bounding_entities` holds signed entity tags — the predicate is *non-negative integers*, deliberately **not** "in range", since 475/476 populated blocks of `example.msh` carry a negative and an in-range test would instead reject a genuine but sloppy cell set that meshio has always accepted), and a `None` block becomes an empty array (global indices cannot express "absent" separately from "empty"; every consumer already treated them alike, and the Abaqus writer's `len(v[ic])` would have raised on a real `None`). `Mesh.__init__` must add sets through the **views**, not the property setters — the setters replace all regions of their kind and would wipe the `regions=` argument every C++-backed reader passes. Flat surfaces: C API opaque `mio_regions` (`_create`/`_count`/`_name`/`_info`/`_entries`/`_free` + `mio_mesh_add_region`, with `mio_region_kind` static_asserted against `RegionKind`), Fortran `m%regions(keys=, entries=)`/`m%add_region(...)` (point/cell indices 1-based, the side **facet** column deliberately not shifted — `partition_labels`' rule), and WASM where regions ride **on the mesh object** so `readMesh`/`writeMesh`/`convert` carry them with no new callable — hence three places (bind in `js_bindings.cpp`, declare in `index.d.ts`, exercise in `tests/wasm/smoke.mjs`) rather than the usual four, and the exhaustive forward guard stays at its then-current count. **Phase 1 formats: gmsh, abaqus and MED** (full round-trip) **plus exodus read-only** (v8.6.0 — element blocks → `Cell` named from `eb_names`/tagged from `eb_prop1`, node sets → `Point`, side sets → `Side`; its *writer* still emits neither `eb_names` nor side sets, so it is a region **source**, recorded in `test_region_roundtrip.py`'s `READ_ONLY_REGIONS` rather than the round-trip `MATRIX`, which by construction cannot hold a write-incapable format). MED joined Phase 1 in v9.6.0 — see the "Note on `med`" entry below. UNV/Ansys/OpenFOAM/XDMF/VTU — and exodus's writer — remain deferred in the `PHASE_2` table. **Exodus side numbering is not `cell_faces.hpp` numbering**, so its side sets go through `exo_face_index` (the `abq_face_index` twin, with a Python twin in `_exodus.py`); a gtest pins every entry against `cell_faces` *by node set* rather than trusting the transcription, because a wrong entry still yields a valid-looking facet index pointing confidently at the wrong face.
- **Region remapping** (`src/cpp/include/meshioplusplus/detail/region_remap.hpp` + `src/cpp/src/detail/region_remap.cpp`): the single owner of "carry a mesh's regions through an operation", replacing nine near-identical per-operation Python `_remap_sets` implementations. It must be **told** which shape the operation's cell map is in, because they genuinely differ and guessing would silently corrupt regions: `Direct` (`map[c]` is *the* output cell, -1 dropped — crop/split/clean/partition/reorder), `FirstChild` (`map[c]` is the first of a contiguous child run ending at the next non-negative entry — convert_cells' simplexify/refine/decimate; correct for 1:1 maps too, but `Direct` must **not** be replaced by it, since a permutation's map is not monotone) and `Global` (one flat array indexed by input *global* cell — merge, whose maps are per input *mesh*). A `Side` entry survives only if its cell does **and** the facet still exists (same output cell type, facet index in range); under `FirstChild` side regions are dropped by name. A region that loses every entry is still carried as an **empty group** — the name is information, and that is what the shims did. `build_cell_subset` calls it internally, so crop/split/partition agree for free (it is the only place that knows the `drop_empty_blocks` block shift). `merge` uses the per-region `remap_region` instead, because it must rename between remapping and storing (two inputs sharing a region name would otherwise collide on the `(kind, name, dim, tag)` key). Ops that cannot carry regions (`slice`, `isosurface`, `extract_surface`/`extract_skin`) call `warn_regions_dropped` — never silent.
- **Operations layer** (`src/cpp/src/operations/*.cpp` + `src/cpp/include/meshioplusplus/operations/*.hpp`): computations *on* a mesh (not file formats — deliberately **not** registered in `registry.cpp`). Each operation is uniform-mesh-API-only (compiles under all three backends — the KRATOS `Mesh` is **not** copy-constructible, so never `Mesh out = in;`; clone via the uniform API as `quality_clone_mesh` does), parallelizes its hot loop with `parallel_for`, and is exposed across **every** binding surface (pybind `_core`, C API `mio_*`, Fortran type-bound procedures, WASM embind) plus a CLI verb. `.cpp` anon-namespace helpers are uniquely prefixed (`surface_`/`quality_`/`sniff_`/`reorder_`/`diff_`/`merge_`/`transform_`/`clean_`/`crop_`/`split_`/`stats_`/`ccells_`/`refine_`/`partition_`/`smooth_`/`interp_`/`slice_`/`iso_`/`decim_`, and for the data bundle `dmanage_`/`davg_`/`calc_`/`dcond_`/`dinfo_` — **distinct per file**, since a shared `data_` prefix across five TUs would collide) because the amalgamation concatenates TUs; `detail/` header inline helpers (`geometry.hpp`, `cell_edges.hpp`, `cell_subdivision.hpp`, `subset.hpp`, `space_filling.hpp`, `node_adjacency.hpp`, `data_ops.hpp`, `spatial_hash.hpp`, `marching.hpp`, `cell_index.hpp`, `region_remap.hpp`) are exempt. New `src/cpp/src/operations/*.cpp` are auto-globbed by CMake and `rglob`ed by the amalgamator — regenerate + commit the single header after any change. The **crop** and **split** operations share `detail/subset.hpp`'s `build_cell_subset` (prune-points-to-kept-cells + remap connectivity/data, `drop_empty_blocks` flag for split's homogeneous pieces); the five **data operations** share `detail/data_ops.hpp`'s `clone_mesh(mesh, filter)` (backend-agnostic geometry copy + per-array keep/rename decision — the workaround for the uniform API having no remove/rename for data arrays), `FiniteStats` (chunked parallel reduction, serial combine, non-finite values excluded and counted) and `cell_measure`. The **convert_cells** (elevate mode) and **refine** operations share `detail/cell_subdivision.hpp`'s `cell_refine_edges`/`cell_refine_quad_faces` — the single owner of "the edges / quad faces of type T, in the order T's higher-order node slots expect" (it delegates the 2D rows to `cell_edges.hpp`, which stays surface-only); two transcriptions of the tetra10/hexahedron20/wedge15 orderings would drift silently, since a mismatch still yields a valid, oriented, volume-conserving mesh — just one with permuted quadratic mid-nodes. The **reorder** and **partition** operations share `detail/space_filling.hpp`'s `sfc_part1by2`/`sfc_morton_key`/`sfc_hilbert_key` (the pure Morton/Skilling-Hilbert key transforms, hoisted verbatim from reorder in v7.6.0 — reorder's output stayed byte-identical); the Mesh-coupled bbox/quantization stays per-operation (reorder quantizes node coordinates, partition cell centroids). The **reorder** and **smooth** operations also share `detail/node_adjacency.hpp`'s `build_node_adjacency` — one CSR node-to-node graph with two neighbour definitions, because the consumers genuinely want different graphs: `NodeAdjacencyKind::Clique` (every pair of nodes co-occurring in a cell — the FEM stiffness sparsity pattern, which is exactly what a bandwidth-reducing renumbering must minimise) for **reorder**, `NodeAdjacencyKind::Edge` (only nodes joined by an actual cell edge, topology from `cell_subdivision.hpp`'s `cell_refine_edges` so the three cannot drift) for **smooth**; `node_edge_topology_known` reports the blocks that contribute no edges so a caller can pin their nodes. The **merge** and **interpolate** operations share `detail/spatial_hash.hpp`'s `GridKey`/`GridKeyHash`/`grid_quantize`/`SpatialGrid` (the bucket-grid spatial hash, hoisted verbatim from merge's weld in v7.13.0 — merge's output stayed byte-identical; the hash only buckets and the map is never iterated, so it cannot affect output): merge uses the fixed 27-cell `ForEachIn27` scan, interpolate additionally the expanding `ForEachInShell` search (clamped to the occupied-key bbox) and `InsertBox` for simplex bounding boxes. **slice** does **not** use `spatial_hash` — its cut points are shared *by topology* (a crossing on a shared simplexified edge, keyed by the sorted endpoint-id pair), so it dedups by edge key with no coordinate tolerance (surface.cpp/refine.cpp's phase-split idiom). The **slice** and **isosurface** operations share `detail/marching.hpp`'s `marching_prepare`/`marching_cut` (the whole marching-tetrahedra cutter — simplexify, sign-mask case table, watertight edge dedup, winding, degeneracy rule, `point_data` interpolation and `cell_data` replication — hoisted verbatim from slice in v7.15.0, the way `spatial_hash.hpp` was hoisted from merge; slice's output stayed byte-identical and its test suites were not touched). It is **two-phase** because the expensive part (simplexify) must be shared across several isovalues *and* because the caller resolves its scalar against the **simplexified** mesh (`MarchingInput::Simp()`) — which is what lets isosurface contour a `point_data` array that rode through the linearization. The one genuinely parameterized rule is `MarchingOrientation`: `FixedDirection` reproduces slice's `dot(newell, normal) < 0` flip against the user's plane normal verbatim (keeping byte-identity structural rather than argued), while `FieldGradient` orients toward increasing field via a per-simplex reference direction stored **as a field on the face struct, not a parallel array** (the `ProjectedFace::mSourceCell` precedent). The nineteen **mesh** operations (on geometry) and five **data** operations (on data arrays) are listed below.
  - **Surface/skin extraction** (`operations/surface.{hpp,cpp}`, Python `_surface.py`/`_skin.py`): `extract_surface(mesh, record_parent_ids=false)` picks the dimension automatically (3D volume → boundary faces, 2D surface → boundary edges via `detail/cell_edges.hpp`); `extract_skin(mesh, linearize=false)` (declared in `skin.hpp`) is the volume-only special case — **both share the one implementation in `surface.cpp`** (`extract_skin` calls it in force-face mode, byte-identical to the old `skin.cpp` it absorbed). Kratos `SkinDetectionProcess` face-hashing (sorted corner-node key occurring exactly once = boundary); face topology in `detail/cell_faces.hpp` (Python twin in `_skin.py`, must stay in sync; outward winding enforced by a gtest Newell-normal invariant in `test_skin.cpp`), edge topology in `detail/cell_edges.hpp` (twin in `_surface.py`). Supported volume types: tetra(10), hexahedron(20/27), wedge(15/18), pyramid(13/14) — `wedge18` gained its `cell_faces` row in v7.5.0 (refine needed its quad-face centres), which made it newly skinnable. Output blocks in fixed canonical order (triangle, triangle6, quad, quad8, quad9 / line, line3), points compacted ascending original-id (numpy fallback relies on `np.unique` sortedness for identical output — `tests/python/test_skin.py`/`test_extract_surface.py`), `point_data` subset, other data dropped. Two-phase parallel: keys built in `parallel_for` into disjoint slots, then a **serial** dedup/emit so output is byte-identical across backends and thread counts. `record_parent_ids` attaches Int64 `surface:parent_cell` cell_data (per-output-facet owning input-cell index). **Consumers:** `write_stl`/`write_ply` take a trailing `skin` flag (default **true** — writes the extracted linearized skin, STL triangulating quads; `skin=false` = legacy drop-with-warning; pinned true in `registry.cpp`), and the SVG/TikZ writers project the skin (below).
  - **Mesh quality** (`operations/quality.{hpp,cpp}`, Python `_quality.py`): `compute_quality(mesh)` → `QualityReport` (per-metric summaries + histograms, per-block `cell_data` arrays, inverted/degenerate counts); `attach_quality(mesh)` returns a clone with the metrics as `cell_data` (names `quality:<metric>`). Metrics (triangle/quad/tetra/hex/wedge/pyramid, quadratic variants on corners; NaN where N/A): volume/area, scaled_jacobian, aspect_ratio, skewness, min/max_angle, warpage, min/max_dihedral, inverted, degenerate. Verdict/VTK formulas; ideal element → ideal value (SJ=1, aspect=1, skew=0, tri angles 60°, tetra dihedral ≈70.53°) — pinned by `test_quality.cpp`/`tests/python/test_quality.py`. Reusable vec3 math in `detail/geometry.hpp`.
  - **Format sniffing** (`operations/sniff.{hpp,cpp}`, Python `_sniff.py`): `sniff_format(path)` returns a format name only on a confident leading-bytes signature match (vtk/vtu/vtp/gmsh/ply/off/xdmf/stl-ascii/abaqus), else `""` (ambiguous magics like generic HDF5 or headerless binary STL are never claimed). Wired as a **read-only** fallback in the read paths (`_helpers._read_file`, C `mio_read`, WASM `read_mesh`) when the extension gives nothing — never on a write path.
  - **Reordering / renumbering** (`operations/reorder.{hpp,cpp}`, Python `_reorder.py`): `reorder(mesh, ReorderMethod::RCM|Morton|Hilbert)` → `ReorderResult{mMesh, mNodePermutation, mCellPermutations}` — a **pure permutation** (no nodes/cells added/removed, geometry + all data preserved) returning the applied node/cell permutations (old→new, Int64). RCM builds the node-adjacency CSR (element cliques — nodes sharing a cell are neighbours), picks a pseudo-peripheral start per connected component (rooted-level-structure heuristic), Cuthill–McKee BFS by increasing degree, then reverses; Morton/Hilbert quantize coords to 21 bits/axis over the bbox and stable-sort along the curve. Element perm orders each block's cells by min new-node index. Applies to points/point_data (scatter by node perm, dtype-preserving byte-row gather via `parallel_for_bw`) + connectivity (Int64, remap+reorder) + cell_data (reorder by per-block cell perm); field_data unchanged; ragged/polyhedron blocks supported. `compute_bandwidth(mesh)` = max over cells of (max−min node index). The BFS/argsort stay serial for cross-backend determinism (surface.cpp's phase-split philosophy). Named regions (and so `point_sets`/`cell_sets`) are remapped **in the C++ core** via `detail/region_remap.hpp`; the Python shim only remaps when the numpy fallback ran. `mesh.info`/`gmsh_periodic` are not carried through. The C API uses an opaque `mio_reorder_result` handle (mesh borrow + zero-copy perm getters + `mio_reorder_result_take_mesh` ownership transfer for Fortran); Fortran/WASM expose node perm (Fortran, 1-based) / full node+cell perms (WASM object). CLI verb `reorder … --method rcm|morton|hilbert [--report]`.
  - **Comparison / diff** (`operations/diff.{hpp,cpp}`, Python `_diff.py`): `diff(mesh_a, mesh_b, DiffOptions{atol,rtol,unordered,max_reported})` → `DiffReport` (verdict `Identical`/`EqualWithinTolerance`/`Different`; per-section `ArrayDiff`/`BlockDiff`/`DataDiff` with max abs/rel error, worst flat index, mismatch counts, keys-only-in-one, first-N mismatching cells); `meshes_equal(a,b,atol,rtol)` = `verdict != Different` (ordered). Tolerance rule `abs_err <= atol + rtol*|expected|` (expected from `a`); "identical" is exact equality. **Ordered** path (default) compares points/cells/data index-by-index — the elementwise reduce is chunked and `parallel_for`-parallel, combined serially (deterministic). **Unordered** (`unordered=true`) matches points by proximity via a bucket-grid coordinate hash (no O(N²)); conservative — sets `mCorrespondenceFailed` + verdict `Different` rather than guessing when no one-to-one match exists. Only points/cells/`point_data`/`cell_data`/`field_data` are reachable in C++; **named `point_sets`/`cell_sets` are compared in the Python shim only** (added/removed/changed → a `"sets"` report section, folded into the verdict) — C/Fortran/WASM never see sets. Python `diff` returns a nested dict (with the numpy fallback returning an identically-keyed dict), `meshes_equal` is a boolean; `_format_report` renders the CLI output. C API: `mio_diff`/`mio_meshes_equal` + opaque `mio_diff_result` (verdict/point-summary/per-block getters, `mio_diff_result_free`). Fortran `m%equals`/`m%diff` (verdict 0/1/2). WASM `diff`/`meshesEqual`. CLI verb `diff A B [--atol --rtol --unordered --exact --quiet]` — **exit code is nonzero when meshes differ** (0 for identical or equal-within-tolerance; `--exact` makes only identical pass) for CI/Makefile use.
  - **Merge / weld** (`operations/merge.{hpp,cpp}`, Python `_merge.py`): `merge(vector<const Mesh*>, MergeOptions{weld,atol,source_tag,data_policy,drop_duplicate_cells})` → `MergeResult{mMesh, mPointMaps, mCellMaps}` — combine 2+ meshes into one. **Concatenate** (default, O(N)): prefix-sum point offsets, offset connectivity, merge cell blocks by `Type()` (first-seen order), concat data. **Weld** (`weld=true`): coincident points within `atol` fused via a spatial-hash bucket grid — quantize to `atol`-cells (`parallel_for`), **serial** first-occurrence dedup checking the 27-neighbourhood (keep-first, deterministic), then `parallel_for_bw` gather + connectivity remap (surface.cpp's phase-split philosophy, no O(N²)). `source_tag` (default on) adds Int64 `source_mesh_id` cell_data (originating input per cell). `data_policy` `Intersection` (default; keep keys in all inputs) vs `Fill` (union, NaN→Float64 for missing rows); differing dtypes promote to Float64; 1-D scalar data stays 1-D. `drop_duplicate_cells` (weld-only) drops cells with identical sorted connectivity (keep-first). `field_data` key collisions namespace by source id (`"i:name"`). `mPointMaps`/`mCellMaps` (per-input old→new index, -1 for dropped cells) exist so the **Python shim** can remap+namespace the shim-only `point_sets`/`cell_sets` (never reach C++, like diff); `mesh.info`/`gmsh_periodic` not carried. Ragged/polyhedron blocks supported in C++ (the numpy fallback `_merge_py` is rectangular-only, raising otherwise). C API `mio_merge(meshes, count, weld, atol, source_tag, data_policy/*0=intersection,1=fill*/, drop_duplicate_cells)` → new `mio_mesh*`. Fortran module-level `mio_merge(meshes(:), ...)` → `type(mio_mesh)`. WASM `merge([...], weld, atol, sourceTag, dataPolicy, dropDuplicateCells)`. CLI verb `merge FILE… OUTFILE [--weld --atol --data-policy intersection|fill --drop-duplicate-cells --no-source-tag --quiet]` (last positional = output; prints an in/out/welded summary).
  - **Transform** (`operations/transform.{hpp,cpp}`, Python `_transform.py`): `transform(mesh, AffineTransform{4x4 row-major}, rotate_vector_data=false)` → new `Mesh` — affine transform of point coords (points change; connectivity/`cell_data`/`field_data` carried; `point_data` carried unless `rotate_vector_data` rotates trailing-dim-3 vectors `R·v` / trailing-dim-9 tensors `R·A·Rᵀ`). Builders `transform_translation`/`_scale`/`_units`/`_rotation`(Rodrigues)/`_from_matrix`/`_compose`. Points transformed in `parallel_for_bw` (dtype preserved). Negative-determinant transforms `log::warn` orientation-may-flip. `point_sets`/`cell_sets` pass through unchanged (Python shim). Python API builds the matrix from `translate`/`scale`/`rotate=(axis,deg)`/`matrix`/`scale_units` kwargs (compose order units→scale→rotate→translate). C API `mio_transform(mesh, double[16], rotate_vector_data)` → `mio_mesh*`. Fortran `m%transform(matrix(16), rotate_vector_data=...)`. WASM `transform(mesh, matrix, rotateVectorData)`. CLI `transform IN OUT --translate|--scale|--rotate|--matrix|--scale-units [--rotate-data]` (exactly one source; negatives need `--opt=` form).
  - **Clean** (`operations/clean.{hpp,cpp}`, Python `_clean.py`): `clean(mesh, CleanOptions{weld,atol,remove_orphans,drop_degenerate,drop_duplicate_cells})` → `CleanResult{mMesh, mPointMap, mCellMaps, mPointsWelded, mPointsRemovedOrphan, mCellsDroppedDegenerate, mCellsDroppedDuplicate}` — one-pass weld/prune/de-dup. Order: weld (spatial-hash bucket grid, keep-first, `clean_build_weld_map`, no O(N²)) → drop degenerate (repeated corner node, or |measure|<eps via `detail/geometry`+`cell_faces`) → drop duplicate (sorted-conn key, keep-first per block) → remove orphans (compact). Defaults: no weld, the other three on (matches CLI no-flag default). `point_data` keep-first on weld; regions (and so sets) remapped in the C++ core via `detail/region_remap.hpp` (dropped entries removed). Ragged/polyhedron supported in C++; numpy fallback rectangular-only (reuses `_merge._weld_map`). C API `mio_clean(mesh, weld, atol, remove_orphans, drop_degenerate, drop_duplicate_cells, &n_welded, &n_orphan, &n_degen, &n_dup)` → `mio_mesh*`. Fortran `m%clean(...)` with optional count out-args. WASM `clean(...)` → `{mesh, pointsWelded, ...}`. CLI `clean IN OUT [--weld --atol --remove-orphans --drop-degenerate --drop-duplicates]` (no step flags = default set).
  - **Crop** (`operations/crop.{hpp,cpp}`, Python `_crop.py`): `crop_bbox(mesh, lo[3], hi[3], CropMode::All|Any, record_ids=false)` and `crop_halfspace(mesh, point[3], normal[3], mode, record_ids)` → `CropResult{mMesh, mPointMap, mCellMaps}` — subset by AABB (`lo≤p≤hi`) or half-space (`(p−point)·normal≥0`). Per-point inside mask in `parallel_for`; keep cell if ALL (default) or ANY node inside (phase-split since v8.5.0: parallel per-cell flag pass, serial ascending compaction); then `detail::build_cell_subset` prunes points + remaps (its remap/gather/map loops `parallel_for_bw` since v8.5.0). `record_ids` attaches Int64 `crop:original_point_id` point_data + `crop:original_cell_id` cell_data. Regions (and so sets) remapped in the C++ core via `detail/region_remap.hpp`. C API `mio_crop_bbox`/`mio_crop_plane(..., mode/*0=all,1=any*/, record_ids)` → `mio_mesh*`. Fortran `m%crop_bbox(lo,hi,mode=...)`/`m%crop_plane(point,normal,mode=...)`. WASM `cropBbox`/`cropPlane`. CLI `crop IN OUT --bbox …|--plane … [--mode all|any --record-ids]` (negatives need `--bbox=` form). Python API `crop(mesh, bbox=…|plane=(pt,nrm), mode, record_ids)`.
  - **Split** (`operations/split.{hpp,cpp}`, Python `_split.py`): `split(mesh, SplitBy::Type|Component|Tag|Region, tag_name="")` → `SplitResult{vector<SplitPiece{mKey, mMesh, mPointMap, mCellMaps}>}` — partition into submeshes. **Type**: one piece per first-seen cell type. **Component**: union-find (`split_uf_*`) over node-sharing cell adjacency, one piece per connected component (keys `"0"`,`"1"`,…). **Tag**: distinct integer values of a named `cell_data` (auto-detect first integer cell_data if empty; keys = value). **Region** (v8.7.0, string `"regions"` — plural, deliberately distinct from the pre-existing singular `"region"`, which stays an untouched alias for `Tag`): one piece per named `RegionKind::Cell` region (`rMesh.RegionNames()` filtered to Cell, entries resolved through `detail::block_bases`/`global_to_block_row` — never re-derived), key = region name. **The one criterion that is not a partition** — regions may overlap, so a cell can land in zero, one, or several pieces, each region processed independently; Point/Side regions produce no piece at all (split's contract is whole submeshes, and there is no sound default for "these facets alone"). Each piece pruned via `detail::build_cell_subset(..., drop_empty_blocks=true)`, which **already remaps every region onto every piece** (via `detail::remap_regions`) regardless of criterion, so `Region` needed no extra plumbing there. **File-writing is a caller concern** — the core returns pieces; the CLI/Python expand the `out_{key}.vtu` pattern. Python `split(mesh, by="type"|"region"|"regions"|"component", tag=None)` → ordered `dict {key: Mesh}`; **`by="region"` keeps its exact pre-8.7.0 behaviour untouched** (`cell_sets` when present, Python-only, else the integer tag) — `by="regions"` is the new, additive, cross-binding-capable criterion, with a pure-Python `_groups_by_region` fallback mirroring the C++ one when `_core` is unavailable. Since `split_by_from_name` is the single free-string dispatch point every binding already goes through (C API/Fortran/Julia/R/WASM's `by` parameter), adding `Region` there was the *entire* cross-binding cost — no per-binding plumbing was needed, unlike a genuinely new field. Sets remapped per piece in the shim (for the legacy `by="region"` Python path only; the C++ `"regions"` path carries regions itself). C API opaque `mio_split_result` (`mio_split(mesh, by, tag_name)` + `_count`/`_key`/`_mesh`/`_take_mesh`/`_free`). Fortran `m%split(by, tag_name=..., keys=...)` → `type(mio_mesh) array`. WASM `split(mesh, by, tagName)` → array of `{key, mesh}`. CLI `split IN OUT_{key}.EXT --by type|region|regions|component [--tag NAME]`. A companion **`regions` CLI verb** (v8.7.0, both CLIs, `_cli/_regions.py` / `cmd_regions` in `main.cpp`) lists a mesh's regions (name/kind/dim/tag/entry count, optionally `--json`) by going through `read_metadata`/`registry_read_metadata` rather than a full read — the direct consumer of the `MeshMetadata::mRegions` work above.
  - **Stats** (`operations/stats.{hpp,cpp}`, Python `_stats.py`): `compute_stats(mesh)` → `StatsReport{mNumPoints, mNumCells, mBBoxMin/Max/Extent/Centroid[3], mCellTypeCounts(vector<pair<name,count>>, first-seen), mTotalArea, mSignedVolume, mUnsignedVolume, mNumInverted}` — read-only geometric stats (the geometric complement to the topological `info`). bbox/centroid via chunked `parallel_for` reduction; per-cell area (tri/quad Newell) and 3D signed volume (divergence theorem over `cell_faces`, `parallel_for`); total area = 2D-cell areas + boundary area of 3D cells (via `extract_surface`); inverted = 3D cells with negative signed volume. pybind/Python/WASM return a dict/object incl. `cell_type_counts`; **C/Fortran fill a scalar `mio_stats_report` struct (per-cell-type counts omitted — documented flat-ABI gap)**. C API `mio_stats(mesh, mio_stats_report*)`. Fortran `report = m%stats()` (`type(mio_stats_report)`, `bind(c)`). WASM `stats(mesh)`. CLI `stats IN [--json]` (human table or JSON).
  - **Cell conversion** (`operations/convert_cells.{hpp,cpp}`, Python `_convert_cells.py`): `convert_cells(mesh, ConvertCellsOptions{mode, record_parent_ids})` → `ConvertCellsResult{mMesh, mPointMap, mCellMaps}` — converts the *element representation*, not the format. Three modes. **Linearize**: every higher-order cell → its linear base via the new `ccells_linear_base` table (line3→line, tetra10→tetra, hexahedron20/24/27/64→hexahedron, ...); corner nodes always lead the meshio/VTK orderings so it is "keep the leading N columns", never a permutation; then points orphaned by the drop are pruned with surface.cpp's `used`/`remap` + byte-`memcpy` pattern (**`detail::build_cell_subset` is NOT reusable** — it is a pure row/point selector that preserves each block's type and node count). **Simplexify**: fixed templates — quad→2 triangle, polygon(n)→(n−2)-triangle fan (both the jagged *and* the rectangular uniform-n-gon storage shape), pyramid→2 tetra, wedge→3 tetra, hexahedron→6 tetra (canonical Freudenthal fan around the main diagonal 0–6, so it conforms across a shared face only when neighbours agree on the diagonal — fixed, not per-cell, for determinism); higher-order input is linearized first (which also prunes what the decomposition would orphan); points untouched, each parent's `cell_data` row replicated to its children; a polyhedron block raises. **Elevate**: linear → serendipity quadratic (triangle→triangle6, hexahedron→hexahedron20, ...), one new node per unique edge at the midpoint with `point_data` = endpoint mean; the full-Lagrange targets needing face/body centres (quad9, hexahedron27) raise by name — an explicit v1 non-goal. Edge orderings come from the shared `detail/cell_subdivision.hpp` (`cell_refine_edges`) because the order is a contract with each quadratic type's node layout (tetra10 nodes 4–9 = edges 01,12,02,03,13,23) and **refine needs the identical order**; `ccells_elevate_table` now only pairs each source type with its target and corner count. **Every mode preserves block structure 1:1** (output has exactly `NumCellBlocks()` blocks in input order) which is what keeps the one-array-per-block `cell_data` invariant trivially correct. All three are **idempotent on cells they do not apply to**, so they are safe on a mixed-order mesh. Determinism: templates are fixed, and the elevate mid-edge numbering comes from a **serial** dedup pass over a `parallel_for`-filled disjoint-slot buffer (surface.cpp's phase-split idiom), never a concurrent hash insert. `record_parent_ids` attaches Int64 `convert:parent_cell` cell_data (per-output-cell source index *within its own block*). Regions (and so sets) are remapped in the C++ core via `detail/region_remap.hpp`'s `FirstChild` map shape — under simplexify a cell region **expands to the parent's children** (contiguous, derived from `mCellMaps`' first-child indices); side regions are dropped by name, since a child cell's facets have no correspondence with the parent's. C API uses an opaque `mio_convert_cells_result` (`_mesh`/`_take_mesh`/zero-copy `_point_map`/`_num_cell_maps`/`_cell_map`/`_free`, modelled on `mio_split_result`). Fortran `m%convert_cells(mode [, record_parent_ids, point_map])`. WASM `convertCells(mesh, mode, recordParentIds)`. CLI verb `convert-cells IN OUT --mode linearize|simplexify|elevate [--record-parent-ids]` — deliberately distinct from the format-conversion `convert` verb.
  - **Refinement** (`operations/refine.{hpp,cpp}` + `detail/refine_templates.{hpp,cpp}`, Python `_refine.py` + `_refine_templates.py`, docs [`doc/refine.md`](doc/refine.md)): `refine(mesh, RefineOptions{levels, record_parent_ids, cells, region, predicate_array/op/value, closure, record_levels})` → `RefineResult{mMesh, mPointMap, mCellMaps}` — subdivide cells into congruent children of the **same** type, the resolution-*increasing* counterpart to convert_cells. With no selector every cell is refined (**uniform**, byte-identical to pre-v9.5.0); with one, only those cells are, and the hanging nodes that leaves are closed up so the output is still conforming (**selective/adaptive**). Fixed full-split templates: line→2, triangle→4 (1-to-4), quad→4 (+face centre), tetra→8, wedge→8, hexahedron→8; local new-node ids coincide with each type's full-Lagrange layout (line3/triangle6/quad9/tetra10/wedge18/hexahedron27), which is what makes the tables readable against the reference elements. Tetra's interior diagonal is the fixed opposite-edge pair 4–9 (ring 6→7→8→5) — for **determinism only**, since it is strictly interior and so, unlike convert_cells' hex-simplexify diagonal 0–6, never affects conformity. A wedge refines as triangle-4-split × 2 levels and its mid-level triangle's edge midpoints **are** its 3 quad-face centres, hence no body node. **The whole operation is driven by one set — which EDGES carry a node — and everything else is DERIVED from it**: an edge node iff the edge is split, a quad-face centre iff **all four** of that face's edges are, a hex body node iff **all twelve** are. Two cells sharing an entity read the same edges, so they cannot disagree — conformity is structural rather than sampled — and with every edge split the rules collapse into the uniform templates, which is what makes uniform output byte-identical. One `RefineNodeKey = array<int64,4>` map serves both entity kinds, edges keyed `{-1,-1,a,b}` and faces `sort{p,q,r,s}`, so the key spaces cannot collide by construction (surface.cpp's padding trick) and the arity is recoverable from the key. Phase-split determinism: `parallel_for` key fill into disjoint slots → **serial** first-seen dedup numbering ENTITIES (point ids are handed out in that same first-seen order once phase 4 decides which entities earn one) → `parallel_for_bw` coordinate/connectivity/data passes; body centres are numbered after the deduped range. **`detail/refine_templates.hpp` owns the (type, split-edge mask) tables.** Each type's **admissible** masks are closed under intersection and contain the full mask — a Moore family — so `refine_promote_mask` (the smallest admissible superset) is a **monotone idempotent closure operator** and the mesh-wide fixed point it drives is unique and independent of traversal order: determinism follows from the algebra, not from a convention. `RefineClosure::RedGreen` (default) promotes to that superset; `Propagate` promotes any non-empty mask straight to full, which is always conforming for every cell type but **converges to uniform refinement of the whole edge-connected component** — the always-works baseline and the test oracle, not an adaptivity mode. **`Balanced` is the third and the only one whose cost is bounded by the selection**: it does not close at all, splitting a cell fully or not at all and merely enforcing 2:1 balance (a cell is drawn in iff some cell sharing a **NODE** with it would end up more than one level above it). Node adjacency is load-bearing, not stylistic -- across a hanging interface the coarse cell spans a whole edge while the fine cell has half of it, so they are *different* entities and an edge-keyed rule is blind to exactly the coarse/fine adjacency 2:1 balance polices (it was written edge-keyed first and the invariant test then read a max level gap of 0, i.e. it silently saw no adjacency at all). On a mesh of uniform level nothing propagates: one cell of a 4x4x4 hex block costs 64->71 cells, against 125 RedGreen and 512 Propagate, and balancing only bites from the second pass onwards. The price is that the output is **1-irregular and NOT conforming** -- every constrained node is reported in the Int64 `refine:hanging` `point_data` array (`kRefineHangingName`, attached only when there are any, so the conforming closures are unaffected), and the rule generating it is stated over *entities* ("a new node whose entity some emitted cell touches without referencing it") rather than per closure, which is what makes it cover quad-face centres as well as edge midpoints -- the test oracle initially missed exactly those. Admissible sets: all masks for line/triangle; the two **opposite** edge pairs for quad (a quadrangulation of an n-gon satisfies `4Q = B + 2I`, so an odd boundary count is impossible and one or three split edges have NO all-quad subdivision at any number of interior nodes — promoting to the opposite pair is the finest type-preserving answer and confines a refined quad to one grid row); unions of the three parallel edge classes for hexahedron (one dual sheet); triangle-edges / verticals / both for wedge; and for tetra any mask up to two edges plus the four face-triples (three edges at a common vertex are excluded **deliberately** — they would put the ambiguous two-edge case on all three incident faces). The 27 tetra entries are **generated** from six orbit representatives by the 12 **even** permutations of its corners (even ⇒ orientation-preserving ⇒ children inherit positive winding), never transcribed; the promotion table is built by brute force straight from the definition. **Green children always have the parent's cell type**, which is what keeps output blocks 1:1 with input blocks and therefore leaves `mCellMaps`/`FirstChild`/`refine:parent_cell`/`cell_data` slicing and every binding's map shape untouched — mixed-type green (quad→triangles) is a documented non-goal for exactly that reason. A cell with two *adjacent* split edges on one face leaves a quad remnant needing a diagonal, and the neighbour across that face must agree: the template stores **both** variants plus two local corner ids, and the emitter picks by **global node id** (diagonal from the smaller-id surviving corner), never by local numbering. Per-cell child counts vary, so `mCellMaps` comes from a **serial ascending prefix sum** (still monotone, still contiguous, every entry non-negative — an untouched cell is a run of length 1) and `cell_data` is a `parent_of_child` **gather** rather than an `i/nchildren` divide. New-node coordinates and `point_data` are the **mean of the entity's corners** (order-independent, so neighbours agree bit-for-bit with no tie-break); dtype is preserved. `levels` loops `refine_once` borrow-then-move (KRATOS `Mesh` is not copy-constructible) and composes maps **before** the move, with level k>1 seeded by the children of level k−1's fully split cells; `record_parent_ids` names the **original** ancestor. **`refine:level`** (opt-in `mRecordLevels`, `kRefineLevelName`) records each cell's depth: +1 per full split, a green child **inherits** its parent's level (a closure is not a refinement). The name is **reserved** — an input already carrying it is *updated* rather than replicated whatever the flag says, so successive passes accumulate; that is the one observable behaviour change in v9.5.0. Green cells are **not undone** before a later refinement, so repeated selective passes degrade quality (documented; `refine:level` + `mCellMaps` is the hierarchy a future green-undo needs). Selection is resolved once against the **input** mesh: `mCells` are global block-major indices (via `detail/cell_index.hpp`, bounds-checked), `mRegion` resolves Cell→its cells / Point→every cell with ANY node in it / Side→**error** (a facet is not a cell), and the predicate is a scalar `cell_data` threshold whose **non-finite values never match** — `compute_quality` reports NaN where a metric does not apply, so rejecting the array would break `quality:*` predicates, the headline use case. Setting two selectors is an error, not a precedence rule. Volume is exact for line/triangle/quad/tetra always but for wedge/hexahedron **only when the parent is affine** — a general trilinear hex's children do not sum to the parent (geometry, not a bug), so conservation tests must use an affine fixture. Higher-order cells, **pyramid** (6-pyramid+4-tetra breaks the same-type and 1:1-block invariants) and ragged blocks **raise by name**. Output is byte-identical across the three mesh backends, thread counts, and the C++/numpy boundary (`test_cpp_matches_python_selective`); the numpy twin's tables are checked against the C++ ones through `_core.refine_mask_table`, not transcribed. Conformity is pinned by three oracles in `test_refine.cpp`, none redundant: facet counting, **no output node at another cell's edge midpoint** (the one that actually finds a hanging node — facet counting cannot, since a hanging node leaves 1 big + 2 small facets all at count 1), and boundary-area preservation; `TheConformityOraclesActuallyFire` proves they are not inert. `test_refine_templates.cpp` asserts the algebra directly (Moore family, closure operator, tiling, orientation, that a template only references nodes its own mask creates). C API opaque `mio_refine_result` plus **`mio_refine_ex` + `mio_refine_opts`** (`mio_read_opts`' append-only `reserved` discipline, `sizeof` static_asserted at 112 and mirrored in Fortran/Julia, whose load-time layout guard caught a wrong constant during development); `mio_refine` unchanged and delegating. Fortran `m%refine(levels [, record_parent_ids, point_map, cells, region, where_array, where_op, where_value, closure, record_levels])` (new optionals appended **after** `errmsg` so no positional call shifts). Julia/R keyword args, `cells` 1-based on both. WASM `refine(mesh, levels, recordParentIds, options)` + the `convertSurfaceOps` `{op:'refine', ...}` branch — where the comparison key is **`compare`, not `op`**, since `op` is the step's own discriminant.   - **Decimation** (`operations/decimate.{hpp,cpp}`, Python `_decimate.py`, docs [`doc/decimate.md`](doc/decimate.md)): `decimate(mesh, DecimateOptions{mTargetRatio, mTargetFaces, mMaxError, mPlacement, mPreserveBoundary, mPreserveFeatures, mFeatureAngleDeg, mFrozen})` → `DecimateResult{mMesh, mPointMap, mCellMaps, mFacesRemoved, mPointsRemoved, mCollapsesRejected, mMaxErrorApplied}` — reduce a **surface** mesh's face count by greedy quadric-error-metric (Garland–Heckbert) edge collapse, the resolution-*reducing* inverse of `refine`. **Surface-only by name**: a 3D/polyhedron block throws pointing at `extract_surface` (QEM decimation of a *volume* mesh is a different, much harder problem — deliberately not silently skinned), higher-order 2D throws naming `linearize`, ragged and `line`/`vertex` blocks throw too; `quad`/rectangular-`polygon` blocks are triangulated first via `convert_cells(Simplexify, record_parent_ids)` (marching_prepare's hold-by-value pattern; `convert:parent_cell` is consumed for `mCellMaps` — input-block-indexed, input cell → first surviving triangle, −1 if none — and never forwarded), so **output is all-triangle with block structure 1:1** (possibly 0-row blocks). Exactly one stopping criterion must be set: `mTargetRatio` (fraction of triangulated faces to KEEP, target = `int64(ratio*F + 0.5)` truncation — never `llround`, whose tie rule the numpy twin couldn't match), `mTargetFaces` (a collapse removes 1–2 faces, so the result lands within one collapse), or `mMaxError` (pop-time `err > e` break — valid even on a stale entry since the heap min bounds all). Per-vertex 4×4 quadrics (10-double symmetric, **area-weighted** so the result is independent of how a planar quad was fanned) accumulate **in ascending incident-face index** (the FP-order pin; the numpy twin's `np.add.at` scatter reproduces it exactly); placement `Optimal` = cofactor 3×3 solve with a documented ill-conditioning fallback to midpoint (`|det| <= 1e-12·max|A_ij|³`, scale-invariant — note an exactly planar patch is singular *by construction*, so flat geometry runs on midpoints; expected, not a bug) / `Midpoint` / `Endpoint` (lower error, tie → lower id). **Pinning mirrors smooth's vocabulary**: boundary vertices (once-used-edge test) and feature vertices (pairwise incident-face-normal cos test over *all* faces, not just boundary facets — creases of a closed surface are interior; default 30°) never move and are never removed; pinned–pinned edges never enter the queue (which is what preserves an open patch's outline exactly), a collapse toward a pinned vertex keeps its position, and `mFrozen` unions in. **Guards reject (counted), never abort**: the link condition (`|ring(a)∩ring(b)| == |shared faces|`; >2 shared = non-manifold, never collapsible; two boundary vertices joined by an interior edge = pinch), and a normal-flip sweep (`n_before·n_after <= 0` on every surviving incident face — smooth's "do no harm": an already-degenerate face imposes no constraint; a zero-area survivor yields dot = 0 and is caught by the same test). **The greedy loop is SERIAL** (QEM is inherently sequential) on a `priority_queue` with the total order `(error, lower id, higher id, versions)` and lazy deletion via per-vertex version counters; setup (planes, quadrics, edge keys, seeding scores) is `parallel_for` into disjoint slots with serial dedup/pushes. Float `point_data` blends endpoints at the clamped edge-projection parameter `t` (exact for Midpoint/Endpoint, an approximation for Optimal; accumulated in Float64 working copies per commit, one cast back at the end); **integer `point_data` keeps the survivor's row** (a blended material id is meaningless); cell rows/`field_data` carry through; emission = surface.cpp's used/remap compaction; `mPointMap` maps every input point to its **survivor's** output index (−1 only if the survivor itself became unreferenced). Queue exhaustion before the target (heavy pinning) is a `log::warn` + normal return, never a throw. **Byte-identical across the three backends, thread counts, and the C++/numpy boundary** (`tests/python/test_decimate.py::test_cpp_matches_python`): `_decimate_py` is a full parity twin — vectorized numpy setup, pure-Python `heapq` greedy loop on the same tuples, every branch-feeding expression transcribed token for token (pinned comments on both sides; no FMA contraction across the pinned expressions, slice/interpolate's standing assumption). The shim resolves `frozen` as ids or a `point_sets` name, remaps `point_sets` through `mPointMap` (survivors dedup via `np.unique`) and `cell_sets` through `mCellMaps` (−1 drops), and supports `return_report` (smooth's shape). C API opaque `mio_decimate_result` (`_mesh`/`_take_mesh`/zero-copy `_point_map`/`_num_cell_maps`/`_cell_map`/counter getters `_faces_removed`/`_points_removed`/`_collapses_rejected`/`_max_error_applied`/`_free`, modelled on `mio_refine_result`; `frozen` is a documented flat-ABI gap like smooth's). Fortran `m%decimate(ratio|target_faces|max_error [, placement, preserve_boundary, preserve_features, feature_angle, counter out-args, point_map])`. WASM `decimate(mesh, ratio, targetFaces, maxError, placement, preserveBoundary, preserveFeatures, featureAngle)` → `{mesh, facesRemoved, pointsRemoved, collapsesRejected, maxErrorApplied}` **plus a `convertSurfaceOps` pipeline op** (`{op:"decimate", ...}`, defaulting to `ratio: 0.5` when no criterion is given, so the browser viewer's worker can chain it; the viewer UI chip itself is a follow-up).   - **Partitioning** (`operations/partition.{hpp,cpp}`, Python `_partition.py`, docs [`doc/partition.md`](doc/partition.md)): `partition(mesh, PartitionOptions{nparts, method, imbalance, mode, seed, record_ids, ghost_layers, weights_key})` → `PartitionResult{vector<PartitionPiece{mPartId, mMesh, mPointMap, mCellMaps}>}` and `partition_labels(...)` → block-aligned Int64 arrays (`partition:part` contract) — decompose into **exactly nparts balanced pieces**, the count-driven complement to `split`. Methods (`PartitionMethod{SFC, KaHIP, Auto}`, `partition_method_from_name`): **SFC** (always available) = Hilbert keys of the cell centroids via `detail/space_filling.hpp` + reorder's quantization idiom, serial `stable_sort` (index tie-break), then a serial cut — unweighted `part = (rank*nparts)/n` (sizes ≤1 apart, the test pin), weighted (`mWeightsKey` = scalar numeric cell_data) `part = min(nparts-1, floor((S_r + w_r/2)*nparts/W))` on the prefix sum (monotone → contiguous; a part can be empty when one weight exceeds W/nparts) — **byte-identical across backends, thread counts, and the C++/numpy-fallback boundary** (`test_cpp_matches_python` pins identical labels; the numpy Hilbert is a lane-exact vectorized Skilling port, and its centroid/prefix sums replicate C++'s sequential accumulation order — never `np.mean`/`np.cumsum`, whose pairwise summation would drift a ulp and flip a quantization bin). **KaHIP** (optional, `MESHIOPLUSPLUS_HAS_KAHIP`; ported from the Kratos KaHIPApplication, KratosMultiphysics/Kratos#14453) = shared-facet dual graph (cells=vertices; facet-key idiom re-implemented locally with `partition_` prefixes — surface.cpp's anon-namespace machinery stays untouched; faces via `cell_faces.hpp` (3D) / edges via `cell_edges.hpp` (2D) at the mesh's max dimension, everything else — ragged/polyhedron/lower-dim — becomes isolated vertices) → CSR (each undirected edge twice, deduped, sorted) → `kaffpa` with `imbalance` (validated in (0,1)), `mode` (`Fast/Eco/Strong`, default **Eco** — the Kratos benchmarks showed eco/strong carry the edge-cut wins), fixed `seed`; the CSR is built in the **installed lib's** index width via runtime `kahip_sizeof_idx()` (int64 buffers `reinterpret_cast` for a `-D64BITMODE=On` lib; never trust the compile-time `kahip_idx` typedef), with named overflow errors; weights scale to int vwgt (sum ≈ 2^30, floor 1); n/nparts/part stay `int`. The compiled-out `partition_kahip_parts` **always exists and throws naming `-DMESHIOPLUSPLUS_WITH_KAHIP=ON`** (vtk_codec pattern — never a silent SFC downgrade); `Auto` = KaHIP if built else SFC (`partition_has_kahip()`, `_core.__has_kahip__`). Pieces via `detail::build_cell_subset(..., drop_empty_blocks=false)` — **deliberately unlike split**: every piece keeps the input block structure 1:1 so `mCellMaps` index by input block and concatenation reproduces the mesh (partition of unity, `ghost_layers=0`); `record_ids` attaches `partition:original_point_id`/`_cell_id`; **`mGhostLayers > 0`** (v9.0.0, was a throwing stub) grows each piece by that many **shared-node** BFS layers of other parts' cells — the halo an MPI decomposition needs — tagged Int64 `partition:ghost` (0 = owned, L = reached at layer L), emitted for *every* block so the array stays block-aligned. Shared-node rather than shared-facet adjacency is the conservative choice (it is what a node-based assembly needs, and the same neighbour definition the KaHIP dual graph falls back on). The pieces then **overlap**, so partition-of-unity holds only at 0; a `stamp[cell] == part` array keeps the BFS one-visit-per-cell-per-part instead of needing a per-part bitmap. **`partition_labels` REJECTS a nonzero value** rather than ignoring it — a flat per-cell label array is the *ownership* map and a cell can be a ghost of several parts at once — and the numpy fallback raises `NotImplementedError` rather than silently returning unghosted pieces. KaHIP tests assert balance/coverage/fixed-seed only, never exact labels (assignment varies by KaHIP version). C API opaque `mio_partition_result` (`_num_pieces`/`_part_id`/`_mesh`/`_take_mesh`/zero-copy per-piece `_point_map`/`_num_cell_maps`/`_cell_map`/`_free`, modelled on `mio_refine_result`) + `mio_partition_labels` (caller buffer, block-major flat, size validated). Fortran `m%partition(nparts [, method, imbalance, mode, seed, record_ids, ghost_layers, weights_key])` → allocatable mesh array + `m%partition_labels(...)` (flat Int64; values are part ids, **no** 1-based shift).   - **Smoothing** (`operations/smooth.{hpp,cpp}`, Python `_smooth.py`, docs [`doc/smooth.md`](doc/smooth.md)): `smooth(mesh, SmoothOptions{method, iterations, lambda, mu, fix_boundary, preserve_features, feature_angle, guard_inversion, frozen, move_tolerance})` → `SmoothResult{mMesh, mNumNodesMoved, mMaxDisplacement, mNumSkippedInversion}` — relax point coordinates toward their edge-neighbour centroids, the quality-*improving* companion to `compute_quality`, which measures exactly what this changes. A **pure coordinate move**: connectivity, `cell_data`, `field_data` and `point_data` *values* pass through unchanged, point/cell counts are unchanged, and the points array keeps its input dtype (iteration runs in `double` with a single cast on write-back, so a Float32 mesh does not accumulate one rounding per pass). Both operators are driven by the same displacement `L(i) = mean(x[j] : j adjacent to i) - x[i]`: **Laplacian** (`x <- x + lambda*L(x)`) is strong per pass but unconditionally shrinking, **Taubin** (the default) follows each `+lambda` pass with a larger-magnitude `-mu` pass whose pass band leaves features alone (on a jittered 8x8 quad grid over 40 iterations Laplacian contracts the bbox 57%, Taubin 3.6%). `mLambda` uses a **negative sentinel meaning "this method's own default"** — 0.5 Laplacian, 0.33 Taubin — because the sensible value genuinely differs per method and two separate fields would let a caller set the one the chosen method ignores; Python spells the parameter `lambda_` (trailing underscore, `lambda` being a keyword). The neighbour graph is `node_adjacency.hpp`'s **Edge** kind, *not* reorder's Clique: under the clique a hexahedron corner is pulled by its three face diagonals and its body diagonal as hard as by its real edge neighbours, bevelling cubes toward spheres, whereas the edge graph leaves a structured hex block a fixed point. **Pinned by default**: boundary nodes (`mFixBoundary`, classic once-used-facet test — a face used by exactly one 3D cell, or in a pure surface mesh an edge used by exactly one 2D cell), feature nodes where two incident boundary facet **normals** differ by more than `mFeatureAngleDeg` (default 30, the `vtkFeatureEdges` convention, which is what keeps a cube's edges sharp), the caller's `mFrozen` mask, and the nodes of blocks whose edge topology is unknown (the higher-order family, VTK-Lagrange, `custom`) — an unknown neighbourhood is an undefined target, so the node holds still rather than being guessed at. The **inversion guard** (default on) commits a candidate position only if no incident cell's signed measure changes sign, counting each `(node, pass)` rejection; it is "do no harm", not "preserve the sign", so a cell that arrives already inverted imposes no constraint and a tangle can still be repaired. Measures: face-fan volume (tetra/hexahedron/wedge/pyramid), signed shoelace area (2D cells in a 2D mesh), and normal-flip (2D cells in a 3D mesh) — that last mode is smooth's own, with **no counterpart in `compute_quality`**, which correctly declines to call a triangle floating in 3D "inverted" for want of a global orientation convention; a cell with no signed measure at all (`line`, polyhedron, `custom`) is **skipped, not pinned**, since a missing safety check is not a missing target and pinning there would freeze an entire beam-element curve. Determinism: every pass is **Jacobi** (all new positions computed from the previous pass and committed together, so no node observes a half-updated neighbour), neighbour sums run in ascending node id over the sorted adjacency rows, the boundary set comes from a **serial** dedup over a `parallel_for`-filled disjoint-slot buffer (surface.cpp's phase-split idiom) and the counters fold serially out of per-node slots — byte-identical across the three mesh backends and across 1/2/8 threads on a 52k-node mesh. Throws `std::invalid_argument` on a mis-sized `mFrozen`, `mLambda` outside (0,1), or a Taubin `mMu` not satisfying `mMu < -mLambda < 0` (which would amplify rather than filter); `mMoveTolerance` is **relative to the bbox diagonal** so `mNumNodesMoved` is scale-invariant. The numpy fallback (`_smooth_py`) implements both operators but **deliberately not the guard** — it is a discrete branch on a sign, and near-degenerate cells could land the two implementations on opposite sides and then diverge macroscopically — so it raises `NotImplementedError` when one is requested, and the shim re-raises `ValueError`/`TypeError` from `_core` rather than letting a genuine user error fall through to numpy. The Python shim also resolves `frozen` given as a `point_sets` **name** and copies `point_sets`/`cell_sets` through untouched (nothing is renumbered, so unlike refine/crop/split there is nothing to remap). C API `mio_smooth(mesh, method, iterations, lambda, mu, fix_boundary, preserve_features, feature_angle, guard_inversion, &nodes_moved, &max_displacement, &skipped_inversion)` → a plain `mio_mesh*` with nullable counter out-params (mio_clean's shape, **not** an opaque result handle — there are no index maps to hand back); `frozen` is **not** exposed on the flat ABI, a documented gap like the sets gaps in diff/merge/split. Fortran `m%smooth(method, iterations [, lambda, mu, fix_boundary, preserve_features, feature_angle, guard_inversion, nodes_moved, max_displacement, skipped_inversion])`. WASM `smooth(mesh, method, iterations, lambda, mu, fixBoundary, preserveFeatures, featureAngle, guardInversion)` → `{mesh, numNodesMoved, maxDisplacement, numSkippedInversion}`. CLI verb `smooth IN OUT [--method taubin|laplacian --iterations N --lambda L --mu=M --no-fix-boundary --no-preserve-features --feature-angle A --no-guard-inversion --quiet]` in both CLIs (a negative `--mu` needs the `--mu=` form).
  - **Interpolation / field transfer** (`operations/interpolate.{hpp,cpp}`, Python `_interpolate.py`, docs [`doc/interpolate.md`](doc/interpolate.md)): `interpolate(source, target, InterpolateOptions{mMethod, mArrays, mExtrapolate, mDefaultValue, mOnConflict})` → a plain new `Mesh` (no maps/counters — transform's shape, not an opaque handle) that is a **copy of the target** (geometry, connectivity, own data preserved exactly, via `detail::clone_mesh`) with the requested SOURCE arrays sampled onto it — the repo's first cross-mesh data-transfer op (diff compares, merge concatenates; neither resamples). Source point_data is sampled at target POINTS, source cell_data at target CELL CENTROIDS and **always by nearest source-cell centroid regardless of method** (no meaningful barycentric interpolant of a piecewise-constant field); cross-location transfer is out of scope — compose with `data to-cell`/`to-point`. `mArrays` empty = all source point_data (sorted names); cell_data only when named; a name in neither location throws listing what exists. Methods (`InterpolateMethod{Nearest, Barycentric}`, `interpolate_method_from_name`): **Nearest** = nearest source point via the shared `detail/spatial_hash.hpp` bucket grid with an expanding Chebyshev-shell search — stop once `((r-1)*cell)² > best_d2`, shells clamped to the occupied-key bbox so far-outside queries stay O(bbox surface) — tie-break smallest d² then lowest source index; values are **raw byte row copies** (dtype-preserving, int64 > 2^53 safe). **Barycentric** = `convert_cells(Simplexify)` on the source first (points untouched for linear sources; point_data rides through the higher-order linearization's row subset, so the op samples the **simplexified mesh's own arrays**), then only the max-topological-dimension simplices (tetra if any, else triangle — evaluated **in the xy-plane**, a documented planar assumption; curved 3D surfaces should use Nearest) are `InsertBox`ed into a grid by quantized bbox; containment = single-cell `Find` (floor quantization is monotone, so a containing simplex's bbox always covers the query's cell) then **first containing simplex in ascending block-then-cell index**, weights = sub-simplex volume ratios via `detail/geometry.hpp`'s `triple_product` with tolerance `>= -1e-12` (dimensionless ⇒ scale-invariant); output always Float64, accumulated corner-by-corner in connectivity order. Outside the domain → `mDefaultValue` (one `log::warn` with the count) unless `mExtrapolate` → nearest-point fallback (from the simplexified mesh). `mOnConflict` `Error` (default, throws) / `Overwrite` / `Suffix` (fixed `name + "_interp"`, throws if that is taken too).   - **Slicing / cross-sections** (`operations/slice.{hpp,cpp}`, Python `_slice.py`, docs [`doc/slice.md`](doc/slice.md)): `slice(mesh, SliceOptions{mOrigin[3], mNormal[3], mRecordParentIds})` → a plain new `Mesh` (transform's shape, no maps/handle) that is the planar cross-section — the actual **intersection** of the mesh with a plane, one topological dimension below the cut cells (3D volume → `triangle`/`quad` surface; 2D surface → `line` mesh). **Distinct from `crop` (plane mode)**, which keeps whole cells on one side; slice computes the intersection and lowers the dimension. **Robust construction (marching tetrahedra):** the input is `convert_cells(Simplexify)`ed first (recordParentIds on) so every 3D cell is a tetra / 2D cell a triangle — each cell's cross-section is then a convex, unambiguously-ordered primitive (no angular sort, no non-convex-hex ambiguity); a hex/wedge section is thus the union of its simplices' sections (correctly located, just triangulated). Signed distance `d_i = dot(x_i − origin, normal)`; an edge crosses iff its endpoints straddle zero, crossing param `t = d_lo/(d_lo − d_hi)` from the **sorted** endpoint pair, so both simplices agree bit-for-bit; `point_data` interpolated at the same `t` (Float64 out). **Degeneracy rule (uniform, documented, tested):** `d_i >= 0` is the positive side (a node on the plane is "above"), making the 4-bit (tetra) / 3-bit (triangle) sign mask **total**, so a plane grazing a shared face is emitted by exactly one incident simplex — **no double-emit** (`test_slice.py::test_grazing…`); any primitive whose crossings collapse (area/length < a bbox-relative tol) is dropped. **Winding:** a fixed marching case table (keyed by the sign mask) gives each section polygon's crossing-edge ring, then a runtime Newell-normal flip orients every face toward the `+normal` side (globally consistent, pinned by `test_slice.cpp`'s Newell invariant). **Watertight:** cut points are shared *by topology* — keyed by the sorted simplexified-node-id edge pair and deduped in a **serial** first-seen sweep over a fixed (block, cell, ring-edge) traversal (surface.cpp/refine.cpp's phase-split idiom; the signed-distance and coordinate/point_data passes are `parallel_for`/`parallel_for_bw`), so shared edges yield one node (grazing configs may leave coincident-but-distinct nodes — the documented exception). Section points are all new: each section cell inherits its parent's `cell_data` (replicated like simplexify, `convert:parent_cell` excluded); `mRecordParentIds` attaches Int64 `slice:parent_cell` (global block-major input cell, composed through `convert:parent_cell` + original block bases). `point_sets`/`cell_sets`, `mesh.info`, `gmsh_periodic` **not** carried. Output is **byte-identical across the three backends, thread counts, and the C++/numpy boundary** (`tests/python/test_slice.py::test_cpp_matches_python`; the numpy `_slice_py` reuses `_convert_cells._simplexify_py` and replicates the traversal/lerp/Newell/tol arithmetic). C API `mio_slice(mesh, origin[3], normal[3], record_parent_ids)` → `mio_mesh*`. Fortran type-bound `m%slice(origin, normal [, record_parent_ids])`. WASM `slice(mesh, origin, normal, recordParentIds)`. CLI verb `slice IN OUT --origin x,y,z --normal x,y,z [--record-parent-ids]` in both CLIs (negatives need the `--normal=`/`--origin=` form). The **browser viewer's** section feature routes through this (see the viewer entry). `slice` shadows the Python builtin **as a module attribute only** (`meshioplusplus.slice`); the builtin is never rebound inside `_slice.py`.

The **data-driven sibling of `slice`**: slice cuts where `dot(x − origin, normal) = 0`, isosurface where `f(x) − isovalue = 0`, **through the same `detail/marching.hpp` cutter** — so the watertightness, winding, degeneracy and determinism guarantees are literally the same code, and this file owns only what is field-specific. **The field must be `point_data`**: `cell_data` is piecewise constant, so there is no crossing to locate and no level set to draw — naming one throws by name and points at `cell_data_to_point_data` (CLI `data to-point`), while an unknown name goes through `data_unknown_key_message`. Multi-component arrays reduce via `mComponent` or the row magnitude, using `iso_scalarize` — deliberately the same arithmetic as `face_color.cpp`'s file-private `fc_scalarize` (sum-of-squares left to right, one `sqrt`) so the numpy twin rounds alike. **Several isovalues land in ONE mesh**: sorted ascending with exact duplicates dropped (a repeat would emit the same contour twice), cut against **one** `marching_prepare` (the simplexify is paid for once), then concatenated by `iso_concat_contours` with the section blocks **merged by cell type** in the cutter's canonical triangle/quad/line order — so a single-isovalue call has exactly slice's block structure. Two tags per contour cell: Float64 **`iso:value`** (the level) and Int64 **`iso:index`** (its ordinal) — both, because `split(SplitBy::Tag)` only accepts an *integer* array, which makes `split(SplitBy::Tag, "iso:index")` — CLI `split --by region --tag iso:index` — the one-mesh-per-contour recipe and `iso:value` the thing you colour by. **The contoured field reads back as EXACTLY the isovalue**: every array is interpolated at the crossing `t`, but the contoured one is *overwritten* during the concat pass (interpolation only reaches the isovalue to within round-off, and the value is known analytically); the exception is a magnitude reduction, where `|lerp(v)| != lerp(|v|)` **mathematically**, so nothing exact exists to write and that case stays interpolated. Degeneracy is inherited: a node exactly at the isovalue counts positive, so a **plateau** at the isovalue emits its boundary once, not twice. Faces are wound toward **increasing field** (`MarchingOrientation::FieldGradient`). An isovalue outside the range is an empty contour, not an error; all outside returns the first cut's (zero-row `point_data`) mesh, matching slice's empty shape. `mRecordParentIds` attaches Int64 `iso:parent_cell`; each contour cell inherits its parent's `cell_data`; `point_sets`/`cell_sets`, `mesh.info`, `gmsh_periodic` **not** carried. Output is **byte-identical across the three backends, thread counts, and the C++/numpy boundary** (`tests/python/test_isosurface.py::test_cpp_matches_python`). C API `mio_isosurface(mesh, array_name, const double* isovalues, int n_isovalues, int component /*negative = magnitude*/, int record_parent_ids)` → `mio_mesh*`. Fortran type-bound `m%isosurface(array, isovalues(:) [, component, record_parent_ids])`. WASM `isosurface(mesh, array, isovalues, component, recordParentIds)` (accepts a scalar or an array). CLI verb `isosurface IN OUT --array NAME --values v1,v2 [--component I] [--record-parent-ids]` in both CLIs (negatives need the `--values=` form). The **browser viewer's** isosurface chip routes through this (see the viewer entry).

- **Memory-mapped reading** (`src/cpp/include/meshioplusplus/detail/file_source.hpp`, docs [`doc/mmap.md`](doc/mmap.md)): `FileSource` is RAII whole-file access — POSIX `mmap`+`MADV_SEQUENTIAL`, Windows `MapViewOfFile`, always buffered under Emscripten. `Auto` maps regular files ≥ `mmap_auto_threshold_bytes` (16 MiB; `MESHIOPLUSPLUS_MMAP_THRESHOLD` overrides). Mapping is **advisory** — anything unmappable falls back silently rather than erroring. It is a **memory-footprint** win (one fewer full-file copy, halved peak RSS), not a throughput one; say so rather than overselling. **Lifetime is trivial by construction**: every reader copies into owning storage, so nothing in a returned `Mesh` points into the buffer and `FileSource` is just a function-local — the rule "nothing derived from `View()` may be stored in the mesh" is pinned by a read-then-unlink-then-revalidate test. **A mapped buffer is only NUL-terminated because the kernel zero-fills the final partial page**, which `strtod` (gmsh's `next_double`) relies on; files whose size is an exact page multiple are therefore never mapped, even on an explicit request. Windows needs `WIN32_LEAN_AND_MEAN`+`NOMINMAX` before `<windows.h>` since this header reaches user TUs via the amalgamation. All five whole-file readers are migrated: `gmsh` (which also honours an explicit `ReadOptions::mMmap`), `vtk_read`, `ensight`, `ugrid`'s ASCII branch and `openfoam` — the last gained most, since its `ostringstream`+`.str()` paid for two extra full-file copies. Cursors/parsers that held `const std::string&` now hold `std::string_view`; the ascii OpenFOAM parsers deliberately still take an owned string, because they consume via `istringstream`, which cannot take a view — converting them would only relocate the copy. `ugrid`'s binary branch keeps streaming per-section from an `ifstream` (no whole-file intermediate to map).

- **Data operations** (`src/cpp/src/operations/data_*.cpp` + headers, Python `_data_*.py`, docs `doc/data_operations.md` + one page per op): act on `point_data`/`cell_data`/`field_data`, **never** on geometry (points/connectivity/block order come through bit-identical — `tests/cpp/mesh_fixtures.hpp`'s `mt::expect_same_geometry` and `tests/python/helpers_data.py`'s `assert_same_geometry` assert this per op). The five operations:
  - **Array management** (`data_manage.{hpp,cpp}`, Python `_data_manage.py`): `data_manage(mesh, DataManageOptions{keep,drop,rename,ignore_missing})` → `DataManageResult{mMesh, mDropped, mRenamed}`, plus the `data_drop`/`data_keep`/`data_rename` convenience wrappers the flat bindings and CLIs use. Phases apply **keep → drop → rename**; `keep` only affects the locations it mentions (so `data_keep(m, Point, {})` drops all point_data but leaves cell/field alone — implemented as the *complement* via `drop`, not a sentinel key). All validation runs against the input before any cloning. Renaming onto an existing name throws unless that target is itself renamed away or dropped in the same pass, which makes a two-name swap legal. Values/dtypes/shapes are byte-identical passthrough. C API exposes the three primitives only (`mio_data_drop`/`_keep`/`_rename`) — the combined `data_manage` is a **documented flat-ABI gap**.
  - **Location averaging** (`data_average.{hpp,cpp}`, Python `_data_average.py`): `point_data_to_cell_data` (each cell = mean over its own nodes; ragged rows use `Row`, polyhedra the *distinct* nodes across faces) and `cell_data_to_point_data` (each point = mean over incident cells, `CellPointWeight::Uniform|Measure`; unavailable measures fall back to weight 1 with one warn per call). Component-wise; output is **always Float64** (a mean is not an integer). A point/cell with no finite contribution yields NaN. **The cell→point accumulation pass is deliberately SERIAL** — it is a scatter and FP addition is not associative, so parallelizing it would make results thread-count-dependent and flake the 4-leg backend matrix; only the final divide is `parallel_for_bw`. Same phase-split philosophy as `surface.cpp`.
  - **Expressions** (`data_calc.{hpp,cpp}`, Python `_data_calc.py`): `data_calc(mesh, expr, DataCalcOptions{location,output,overwrite,dtype})`. Hand-written tokenizer + recursive-descent parser — **no external parser lib, no arbitrary-code path**. Grammar: `+ - * /`, unary minus, parens, numeric literals, array names, and `abs`/`sqrt`/`min`/`max`/`norm`. Identifiers admit `:`/`.` after the first char (load-bearing: `gmsh:physical`), backticks quote names with spaces. Parse builds a **flat `vector<CalcNode>` pool** (shareable read-only across `parallel_for`, no per-node allocation); three passes: width inference + name resolution, operand widening to double once per array (`parallel_for_bw`), then the element loop (`parallel_for`) using stack buffers — `DATA_CALC_MAX_COMPONENTS=16` is what makes the loop allocation-free, `DATA_CALC_MAX_DEPTH=64` guards the parser against stack overflow from hostile input reaching it via the C ABI. Scalars broadcast against wider operands; `norm` is always scalar. Literals go through `std::strtod`, **not** `std::from_chars` (whose float overload is a real Emscripten/libc++ hazard) — matching `dex.cpp`/`wkt.cpp`/`nastran.cpp`. Every error is `std::invalid_argument` prefixed `meshio++: data_calc: ` and carries the character position. Division by zero is IEEE inf/NaN, not an error. Cell location evaluates **once per block**.
  - **Value conditioning** (`data_condition.{hpp,cpp}`, Python `_data_condition.py`): `data_condition(mesh, DataConditionOptions{location,names,mode,scope,lo,hi,nan_policy,nan_replacement,suffix,preserve_dtype})` with `ConditionMode{Clamp,Normalize,Standardize}` and `ConditionScope{Component,Magnitude}` (magnitude rescales whole rows, preserving direction). For `cell_data` the statistics are computed **jointly across all blocks** before one transform is applied to each. Degenerate reductions are handled, not NaN'd: constant array under Normalize → fill `lo` + warn; zero stddev under Standardize → fill 0 + warn. `Clamp` + `preserve_dtype` keeps the input dtype; Normalize/Standardize force Float64. `suffix` writes to a new name instead of in place.
  - **Data summary** (`data_info.{hpp,cpp}`, Python `_data_info.py`): `data_info(mesh)` → `DataInfoReport{mArrays, mNumPointData/CellData/FieldData}` of `DataArrayInfo` (location, name, dtype, shape, blocks, entries, components, values, min/max/mean whole-array *and* per component, NaN/inf/finite counts, `mInconsistentBlocks`), plus `data_array_info(mesh, loc, name)`. Read-only; the data-side complement to the topological `info` and the geometric `compute_stats`. **Never throws on non-finite values** and reports (rather than throws on) a cell_data array whose blocks disagree in component count. C/Fortran use an **opaque `mio_data_info` handle** (`_create`/`_count`/`_name`/`_entry`/`_component`/`_free`) since the report is variable-length — modelled on `mio_split_result`.

The SVG colorbar widens **only the viewBox** (scaling factor, stroke width and every mesh coordinate come from the unmodified width) and emits `<rect>`, not `<path>`, so the document `path {…}` rule does not stroke it; TikZ's is a pure append. **Coloring is a documented gap on the flat bindings** — `registry.cpp`'s `(path, mesh)` writer lambdas cannot carry params, so C/Fortran/WASM keep the fixed default styling (do NOT thread it through the registry). CLI: `convert --color-by NAME [--component --cmap --vmin --vmax --nan-color --colorbar]` in **both** CLIs, rejected for non-svg/tikz targets; the native one uses a `write_colored_variant` registry bypass modelled on `write_binary_variant`. `extract_skin`+`extract_surface` gained no public parameter for this — the shared impl was lifted to `detail::surface_extract(mesh, forceFaceMode, linearize, recordParentIds, opName)` (declared in `operations/surface.hpp`), because the two public functions are flat-bound in three places and no binding consumer needs linearize+provenance together; `_skin.py::_extract_skin_py` gained the matching `record_parent_ids`.
- **Doc figures** (`tools/gen_doc_images.py`): regenerates the committed static doc/README figures from `example/example.msh` — coloured SVGs through the writer above (`doc/public/images/color_by_*.svg`) and `screenshot()` PNGs through the Polyscope extra. Canonical static figures may come from this script; it **complements, does not replace**, the PyVista notebook convention above (which still owns the executable, re-executed-with-outputs demos). It crops the bracket to ~1.1k skin facets deliberately: the full 298k-cell mesh yields a 4.5 MB SVG whose elements are sub-pixel. Smoke-tested by `tests/python/test_gen_doc_images.py`, which redirects the output dirs and never writes into `doc/`.
- **Container convention**: use `std::unordered_map`/`std::unordered_set` for name/id lookup and dedup tables (O(1), order-irrelevant) — the default. Reach for `std::map`/`std::set` **only** when sorted iteration order is itself relied on (see `su2` `tag_counts`, `openfoam` `by_n`, gmsh's `node_data`/`elem_data` staging locals). The mesh data maps' name order **is** observable — it drives Python dict key order and the on-disk field/variable order of writers (VTU, VTK, XDMF, Exodus, Tecplot, HMF, PLY, AVS-UCD, tetgen, h5m) plus "first int field" selectors (medit, ugrid, su2, netgen, avsucd). The uniform API bakes that guarantee in: `PointDataNames()`/`CellDataNames()`/`FieldDataNames()` **always return sorted names** on every backend — memoized since v9.0.0 rather than re-sorted per call, which carries one **discipline**: the MESHIO backend's three data maps are public struct members and `bindings/python/np_conversions.hpp` inserts into them directly (the one sanctioned uniform-API exception), so anything bypassing `AddPointData`/`AddCellData`/`AppendCellData`/`AddFieldData` **must** call `Mesh::InvalidateNameCaches()` or the cache goes stale and silently reorders on-disk fields; `detail::NamedItems` (NATIVE/KRATOS) is sound by construction because all mutation is encapsulated (the former `detail::sorted_keys` idiom, now behind the accessors; `map_order.hpp` remains for non-Mesh maps and the pybind layer), so output stays byte-identical across backends.
- **C++ naming convention**: Kratos Multiphysics style — classes/structs/enums and methods (member functions) are `PascalCase` (e.g. `Mesh::NumPoints()`, `CellBlock::IsRagged()`); member variables are `m`-prefixed `PascalCase` (e.g. `Mesh::mPoints`, `CellBlock::mData`); reference parameters are `r`-prefixed (`const std::string& rPath`) and pointer parameters `p`-prefixed (`const int* pPerm`) — forwarding references (`F&&`) and rvalue-reference/move parameters are exempt; free functions, local variables, and lambda parameters stay `snake_case` (e.g. `read_vtu`, `parallel_for`, `detail::sorted_keys`). File names stay `snake_case`. Brace style is K&R (opening brace on the same line) at 4-space indentation — codified in the repo-root `.clang-format`, run via `clang-format -i` over `src/cpp/`, `bindings/`, `bindings/wasm/` (never `src/cpp/third_party`). None of this renames the pybind11/embind **string literals** that define the Python/JS-facing API (`.def("...")`, `.attr("...")`, `emscripten::function("...", ...)`) — those stay exactly as they are; only the C++ symbols on the other side of each binding call follow this convention.
- **Optional deps** (`CMakeLists.txt`): `MESHIOPLUSPLUS_WITH_HDF5`/`_NETCDF`/`_ZLIB`/`_ZSTD`/`_LZ4`/`_KAHIP`/`_EIGEN` options → `MESHIOPLUSPLUS_HAS_*` compile definitions and `_core.__has_hdf5__`/`__has_netcdf__`/`__has_kahip__` flags. **KaHIP** (partition's quality backend; MIT like meshio++, so no licence implication; OFF by default) is bring-your-own: located by the repo's first Find module, `cmake/FindKaHIP.cmake` (ported from the Kratos KaHIPApplication, ParHIP section dropped — only the serial `kaffpa` interface is linked, never ParHIP, hence **no MPI**), honouring `KAHIP_ROOT`/`KAHIP_DIR` + pkg-config; `CMAKE_MODULE_PATH` is appended only inside the `WITH_KAHIP AND NOT EMSCRIPTEN` branch. Never vendored, never auto-downloaded, no KaHIP LICENSE copy in-tree (the Kratos reviewer's requirement); CI source-builds v3.25 into a cached prefix (the dedicated `kahip` job). `#ifdef`-guarded sources become empty TUs (or fall back to a plain loop) when off. Shared HDF5 helpers in `src/cpp/include/meshioplusplus/detail/hdf5_util.hpp`. **Eigen** is vendored as a git submodule at `src/cpp/third_party/eigen` (header-only; run `git submodule update --init` for source builds) and used for the MED Fortran↔C transpose (`med.cpp`, guarded by `MESHIOPLUSPLUS_HAS_EIGEN`); when the submodule is absent the code uses a hand-written transpose, so sdists without submodules still build.
- **C++ standard: C++20** (pinned in `CMakeLists.txt` twice: `CMAKE_CXX_STANDARD` + `target_compile_features`). macOS needs deployment target ≥ 13.3 for `std::format` (set in `ci.yml`/`wheels.yml`).
- **Logging** (`src/cpp/include/meshioplusplus/log.hpp`): `meshioplusplus::log::debug/info/warn/error("fmt {}", …)` — `std::format` (compile-time-checked) + `std::source_location`, thread-safe via `std::osyncstream`, filtered at runtime by the `MESHIOPLUSPLUS_LOG_LEVEL` env var (`debug|info|warn|error|off`, default `warn`). No printf/cerr elsewhere; errors remain exceptions.
- **Parallelism** (`src/cpp/include/meshioplusplus/parallel.hpp`): `meshioplusplus::parallel_for(n, f, grain=2048, max_threads=0)` with a compile-time backend selected by `MESHIOPLUSPLUS_PARALLEL_BACKEND` = `AUTO|SEQ|STL|OPENMP|TBB|KOKKOS`. **Default is `AUTO`**, which prefers **OpenMP** (portable: libgomp on manylinux, MSVC built-in, libomp on macOS; needs no TBB), else the STL(+TBB) probe, else SEQ. `_core.__parallel_backend__` reports the active backend from Python (STL-without-TBB is effectively sequential — that's why AUTO avoids it). **KOKKOS** (v8.5.0) is bring-your-own like KaHIP — never picked by AUTO, located via `find_package(Kokkos CONFIG)` (`Kokkos_DIR`), not under Emscripten, CI-covered by the dedicated `kokkos` job (cached source build of the pinned 4.5.01 **with `-DCMAKE_POSITION_INDEPENDENT_CODE=ON`** — required because the job also builds `MESHIOPLUSPLUS_BUILD_C_API=ON`, and linking Kokkos's non-PIC static archives into the shared `libmeshioplusplus.so` fails with `relocation R_X86_64_TPOFF32 ... can not be used when making a shared object`, bit the job once, fixed by rebuilding with PIC and bumping the `actions/cache` key — full ctest + a 2-thread-pool rerun) — and runs on `Kokkos::DefaultHostExecutionSpace` **deliberately**: every loop body captures host pointers and some call host-only libraries (zlib), so device dispatch is not meaningful; GPU data movement is the DLPack/CuPy handoff's job. It lazy-initializes Kokkos only if the embedding app hasn't (then finalizes via `std::atexit`), honours `parallel_for_bw`'s 4-thread cap by range-partitioning into ≤ max_threads chunks (Kokkos has no per-call cap), and needs plain `[&]` lambdas only (host space ⇒ no `KOKKOS_LAMBDA`); `Kokkos::is_finalized()` is version-guarded (`KOKKOS_VERSION >= 30700`). Adding a backend (HPX, …) = one CMake branch + one `#elif` in `parallel.hpp` (+ the guarded include block + `parallel_backend_name()`). Iterations must be independent; the first exception is captured and rethrown after the join; `n <= grain` runs sequentially. **Two flavors:** `parallel_for` (all cores — for compute-bound loops: zlib/base64 in `detail/vtu_binary.hpp`, ASCII formatting) and **`parallel_for_bw`** (thread-capped, `parallel_bandwidth_threads=4` — for memory-bandwidth-bound loops: byte-swap/transpose/gather, which *regress* past ~4 threads because they saturate memory bandwidth). Use `parallel_for_bw` for byte I/O and index gathers; `parallel_for` only when the per-element work is real compute. The OpenMP backend uses `schedule(dynamic, grain/4)` — on hybrid CPUs (P+E cores) a static split makes E-cores stragglers; the chunk honours explicitly coarse grains (the VTU zlib loop passes `grain=1` so each block dispatches individually — do NOT floor the chunk above the grain). Hoist per-element dtype switches with `detail::dispatch_dtype(dt, []<class T>(){…})` (`value_io.hpp`) before parallelizing. **Binary I/O rule:** never write per-element to a `std::ostream` (byte-at-a-time `os.put`/tiny `os.write` was the pre-optimization VTK/Gmsh bottleneck) — build one pre-sized buffer (fused gather+byteswap where possible) and emit it with a single `os.write`; read binary sections straight into the destination array (or bulk seek+read, never `istreambuf_iterator`). Endianness conversion goes through `detail/byteswap.hpp` (`bswap_copy`/`bswap_inplace`, single-instruction intrinsics) — never a per-byte reversal loop.

**Format registration** (`src/python/meshioplusplus/_helpers.py`): each format's `__init__.py` calls `register_format(name, extensions, reader, {name: writer})`. `read`/`write` auto-detect from extension. Modules are imported (and thus registered) in `src/python/meshioplusplus/__init__.py`.

**Format module layout** (the shim pattern, e.g. `src/python/meshioplusplus/su2/`):
- `__init__.py` — imports `_core`, defines `read`/`write` that **try the C++ function and fall back** to the Python reference on any exception, then `register_format(...)`.
- `_<format>.py` — the pure-Python reference reader/writer.
- Multi-version formats (Gmsh, VTK) dispatch to version submodules.

**Cell type naming**: meshio++ uses its own names (`triangle`, `tetra10`, `hexahedron20`, …). Each format maps between its native names and meshio++'s (e.g. `gmsh/common.py`).

**Tests** (`tests/python/`): `helpers.py` has `Mesh` fixtures + `write_read()` (the round-trip pattern). Per-format `test_<format>.py` parametrize over meshes. `tests/python/meshes/` and `tests/python/input/` hold read-only reference files (Git-LFS). HDF5/netCDF suites use `pytest.importorskip`.

## Adding a new format

1. Create `src/python/meshioplusplus/<format>/_<format>.py` (Python reference `read`/`write`) and `__init__.py` (shim + `register_format`). `register_format` may also live directly in `_<format>.py` for a Python-only format with no shim to wrap (e.g. `neuroglancer`, `ansysInp`, `openfoam`); move it into `__init__.py` if a shim is added later (`mdpa` did in v8.8.0).
2. Add the C++ implementation: `src/cpp/src/formats/<format>.cpp` + `src/cpp/include/meshioplusplus/formats/<format>.hpp`, bind it in `bindings/python/_core.cpp`, register it in the shared dispatch registry (`src/cpp/src/registry.cpp`: reader/writer entry + extension default — that's what makes it reachable from WASM and the C/Fortran API), and switch `__init__.py` to the try-C++/Python-fallback shim. New `.cpp` files are auto-globbed by CMake. The implementation must build/read the mesh **through the uniform mesh API only** (see the "Uniform mesh API rule" above) so it works under every mesh backend. **This step is optional** — a format can stay Python-only indefinitely (precedent: `neuroglancer` and the Simvia-contributed `ansysInp`/`openfoam`); don't force a C++ port just to satisfy this checklist.
3. Import the module in `src/python/meshioplusplus/__init__.py` (both the import tuple and `__all__`).
4. Add `tests/python/test_<format>.py` using `helpers.write_read()`. Verify a direct C++ roundtrip and cross-compat with the Python reference (if a C++ path exists).
5. **Update `README.md`, `doc/formats.md`, and this file** (see "Keeping docs in sync").

Do not copy test data from GPL sources (e.g. FEconv examples) into this MIT repo — generate reference files via round-trip instead. Code/fixtures from other MIT-licensed forks in the same lineage (e.g. the [meshlane](https://github.com/simvia-tech/meshlane) fork) may be copied directly; credit the source in `CITATION.cff`/`CHANGELOG.md`.

**Note on `gmsh`:** `write_gmsh22` (2.2, attaches each element's physical tag directly in `$Elements`) fully round-trips named `Cell` region **membership**; the registry-default `write_gmsh41` (4.1, needs `$Entities` to link elements to physical tags, which the writer never emits) keeps only the group **name**. Both were always reachable from Python (`gmsh22_write`/`gmsh41_write`, `register_format`'s `"gmsh22"`/`"gmsh"` writer keys) but only `"gmsh"` → `write_gmsh41` was ever registered in the **shared** dispatch tables (`registry.cpp`), so WASM/C API/Fortran had no way to select the round-trip-capable writer at all. v8.7.0 adds a **`"gmsh22"` write-only key** to `registry_writers()` (no matching reader key — reading auto-detects the file's own `$MeshFormat` version and needs no separate entry); `write_gmsh22` already synthesized `gmsh:physical` from `Cell` regions when the mesh carried none of its own (`gmsh_tags_from_regions`), so no core logic changed, only its reachability. `availableFormats().writers` now includes `"gmsh22"` (write-only, like `"svg"`); `--output-format gmsh22` / `writeMesh(path, mesh, "gmsh22")` selects it on every surface `resolve_format`/`registry_writers()` reaches.

**Note on `ensight`:** EnSight Gold, geometry only (`.case` + `.geo` sibling pair; write logic ported from Kratos's `EnSightOutput`, reader is meshio++-original). ASCII + C-binary both ways; the binary reader auto-detects a foreign byte order from record plausibility. Per the Gold spec connectivity is **positional** (1-based into the part's coordinates) — `given`/`ignore` id arrays are skipped, matching VTK's readers (not Kratos's id-based writing assumption). Node ordering: meshio (VTK) order matches EnSight for every type except `wedge15` ↔ `penta15`, which differ by the involution `{0,2,1,3,5,4, 8,7,6, 11,10,9, 12,14,13}` — do **not** port Kratos's penta15/hexa20 group swaps (those fix Kratos-specific ordering). Multi-part files → concatenated points, one block per part-section, `cell_data["ensight:part"]` when ≥2 parts; the writer emits a single `assign`-id part and drops mesh data (warns). Ragged write raises (v1).

**Note on `vtp`:** VTK XML PolyData; shares the VTU stack — the `<DataArray>` helpers live in `detail/vtk_xml.hpp` (used by `vtu.cpp`/`vtu_read.cpp`/`vtp.cpp`/`vtp_read.cpp`; keep VTU byte-identical when touching it). Surface cells only; cell data follows VTK's canonical Verts→Lines→Polys order (writer reorders blocks into that partition). PolyData has no cell-type array, so 3-/4-noded polygons read back as triangle/quad. The pybind `vtp_write` binding opts into `allow_ragged` (jagged polygons are legal Polys rows).

**Note on `triangle`:** 2D analogue of tetgen (`.node`/`.ele` pairs → `triangle`/`triangle6`, `.poly` PSLG → `line` segments; holes/regions skipped with a warning). Extension dispatch: `.node`/`.ele` stay tetgen-first everywhere; the Python reader dispatcher falls through to triangle when tetgen raises on a 2D file, writes need `file_format="triangle"`; only `.poly` defaults to triangle (also in the C++ registry, so the flat bindings need an explicit format for 2D `.node`/`.ele`). The multi-file buffer guards in `_helpers.py` cover `tetgen`/`triangle`/`ensight`.

**Note on `exodus`:** the C++ reader used to `throw ReadError("Exodus: <key> handled by Python fallback")` on `qa_records`, `info_records`, `ns_names` and `node_ns*`. Since **every** file SEACAS/Cubit/Sierra writes carries `qa_records`, that made the format unreadable wherever there is no Python to defer to — i.e. all of WASM — while being invisible from Python, where the shim's blanket `except Exception: pass` silently swapped in the fallback. All four are now handled (v8.6.0). `qa_records`/`info_records` are strings and `NDArray` has **no string dtype**, so they cannot ride on the mesh: they travel in an `ExodusInfo` side-channel struct (`MedInfo`/`OpenFoamInfo`'s pattern) that the pybind binding `setattr`s as `mesh.info`, preserving the Python reference's output byte-for-byte; the flat bindings construct one and drop it, exactly as `registry.cpp` already does for `MedInfo` — a documented gap, not a silent loss. The **fixture is hand-authored** (`tests/python/exodus_fixture.py`, built at test time with `netCDF4` rather than committed as LFS) because meshio++'s own writer emits no `qa_records`, no `eb_names` and no side sets, so a round-trip test could not have caught any of this — the general lesson being that a format's own writer is not a sufficient test oracle for that format's reader. **v9.3.0 is the same lesson again, from the other end of the string.** A netCDF text attribute carries an explicit length, and NetCDF.jl (what PeriLab and other Julia solvers write Exodus with) counts the C string's terminating NUL as part of it, so a `SPHERE` block's `elem_type` arrives as 7 characters and matched no key in the C++ type table — `Exodus: unknown element type SPHERE`, with the NUL **invisible in the message** because `std::runtime_error::what()` is a `const char*` that stops at it, which is what made the diagnosis non-obvious. `netCDF4` strips the NUL on the way in, so the Python twin was fine and the shim's fallback hid it everywhere except WASM (VSCode-MDPA-Preview#63). Both readers now trim trailing NUL/space padding (`read_att_text` / `_elem_type`); `SPHERE → vertex` was already in both type tables and did not change. The real file is committed at `tests/python/meshes/exodus/DCBmodel_PD_solid.e` (Git-LFS, **BSD-3-Clause** from PeriLab — permissive, but its notice + licence text must travel with it, hence the `.license` sidecar and `LICENSE.BSD-3-Clause` beside it; credited in `CITATION.cff`), with `test_the_reference_file_still_carries_a_nul_terminated_elem_type` asserting the *encoding* by raw bytes — without it, a re-fetch from an upstream that switched netCDF writers would leave the whole regression suite passing while testing nothing. Note `wasm.yml` checks out **without** `lfs: true` (only `ci.yml` sets it), so `tests/wasm/smoke.mjs` must keep writing its own Exodus file rather than reaching for that fixture. A synthetic fixture cannot get the property naturally: `netCDF4` strips the NUL whatever spelling you pass, so `write_sphere_fixture` **patches the classic-format bytes**: an attribute is `[nc_type][nelems][value padded to 4]`, and `len("SPHERE") % 4 != 0` means 6 and 7 characters pad to the same size, so bumping the recorded count rewrites four bytes in place and shifts no offset; the gtest twin builds its file through the netCDF C API, where the length is just a parameter. The same release added **per-element attributes** (`attrib{k}`/`attrib_name{k}` — where a `SPHERE`'s radius, a beam's cross-section or a shell's thickness lives) in both directions as `cell_data` under `kExodusAttributePrefix` (`"exodus:attr:"`, twinned as `_exodus.ATTRIBUTE_PREFIX`). The prefix is load-bearing at **both** ends: on read it separates an attribute from a same-named `name_elem_var` element variable (constant-in-time vs per-step, different concepts), and on write it is the only signal marking which `cell_data` belongs in `attrib{k}` — do not "simplify" it into writing every cell_data as an attribute. Values are always Float64 and a block the file omits reads as **NaN**, which is not padding but the round-trip signal: the writer skips an all-non-finite block, so a mixed file comes back byte-equal instead of gaining NaN attributes. Ordinary cell_data is still dropped on write (neither writer emits `vals_elem_var`) — pre-existing, and the reason the prefix has to be explicit.

**Note on `mdpa`:** Kratos MDPA gained a C++ reader/writer (v9.0.0, `src/cpp/src/formats/mdpa.cpp`, registered in `registry.cpp`), which is what makes it reachable from WASM/C API/Fortran/Julia/R/native CLI — but **the Python `mdpa.read` deliberately stays on the pure-Python reference**, unlike every other shim in the repo. That is not an oversight: `_mdpa.py` returns a *non-standard* `Mesh` whose `cell_data` is nested **by cell type** (`{cell_type: {var: array}}`, not the repo-wide `{var: [array_per_block]}`) and which carries `mesh.misc_data` (SubModelPart hierarchy, original Kratos entity ids, `Tables`/`Properties`/`Mesh`-block content) and `mesh.geometries_block` — attributes the C++ `Mesh` cannot hold and which ~24 tests in `tests/python/test_mdpa.py` assert. A C++-first read shim would silently change all of that, so `read` is Python-only and `write` is the C++/fallback shim, gated on the mesh carrying no MDPA extras (`misc_data`/`geometries_block`/`field_data`). The C++ reader maps Nodes/Elements/Conditions (+ property ids as `gmsh:physical`), `ModelPartData` (numeric only), `NodalData`/`ElementalData`/`ConditionalData` and SubModelParts → `Point`/`Cell` **regions** (nested parts flattened to a `parent/child` name), and **throws `ReadError` naming the construct** for everything it cannot represent, so the Python fallback stays correct rather than lossy. **v9.1.0 shortened that list and made the rest optional:** a non-empty `Properties` body is now *parsed* (unconditionally -- a pure de-throwing, so no read that used to succeed changed) into the `MdpaInfo` side channel, and `ReadOptions::mLenient` downgrades the remainder (`Table`/`Geometries`/`Mesh`/`Constraints`, non-empty `SubModelPartData`/`Tables`, a non-numeric `ModelPartData` value) to a warn-and-skip recorded in `MdpaInfo::mSkippedConstructs`. Node ids that are not `1..n`, a malformed row and an unknown entity name still throw **even under `mLenient`** -- skipping those returns a quietly *wrong* mesh, not merely an incomplete one, which is the line that flag must not cross. **`MdpaInfo`** (the `MedInfo`/`ExodusInfo` pattern -- `read_mdpa(path, info)` / `write_mdpa(path, mesh, info)`, both additive overloads) exists because `NDArray` has ten numeric dtypes and no string one, so `CONSTITUTIVE_LAW LinearElastic3DLaw` has no `field_data` representation at all; it carries the `Properties` bodies as `PropertyValue` key/value pairs from the new backend-neutral `properties.hpp` (shared with `ModelPart`, so there is one representation) -- typed where numeric, **verbatim text otherwise, which is what makes an unrecognized value lossless** -- plus the per-block Kratos entity names, without which a round trip renames every `SmallDisplacementElement3D4N` to `Element3D4N`. The reader's block-splitting key gained the entity name, so two adjacent same-type differently-named blocks stay separate. **v9.2.0 moved the `Properties` bodies onto the `Mesh`** (the uniform-API property sets above), because the `MdpaInfo` side channel was unreachable from `registry_read` -- `ReadFn`/`ReadExFn`/`WriteFn` have no info slot -- so every registry-based consumer, i.e. all of them, got ids and no material data, and a registry-driven `mdpa`->`mdpa` write emitted empty blocks. `read_mdpa` now stores them on the mesh unconditionally, `KratosMesh::Materialize` fills `ModelPart::Properties` with **real values** instead of id-only sets (which is what makes `to_model_part`'s applier transfer anything), and the writer emits the mesh's sets plus an empty block per referenced-but-uncovered id. `MdpaInfo` is retained and still **wins** when supplied: it preserves the blocks' *file order*, which the mesh channel deliberately does not (it canonicalizes to ascending id), and it carries `mEntityNames`/`mSkippedConstructs`. A mesh with no property sets writes byte-identical output (pinned by a test). The **writer** now declares every properties id its rows reference instead of one hard-coded `Properties 0` (the rows always wrote their `gmsh:physical` value, so a tagged mesh referenced undeclared properties, which Kratos's own `ModelPartIO` rejects); output stays byte-identical whenever every id is 0, i.e. for every mesh with no `gmsh:physical`. Entity names resolve through **`backends/kratos_names.hpp`**'s `cell_type_from_kratos_name_or_suffix` (never re-transcribe those tables) -- exact lookup then longest resolving suffix, which is what makes real decks' `SmallDisplacementElement3D4N` work. Since v9.1.0 that helper is the **single owner** of the rule and `ModelPart::CreateNewElement` goes through it too, so the two cannot disagree; before that, `CreateNewElement("SmallDisplacementElement3D4N", ...)` threw, which is what essentially every real Kratos application calls. the hexahedron20/27 Kratos↔VTK permutation is applied on read and undone on write (scatter `out[table[i]] = in[i]` reading, gather `out[j] = in[table[j]]` writing — the argsort pair the Python reference builds).

**Note on `med`:** the C++ core (built with HDF5) handles the mesh-representation part of MED exactly — points, point/cell tags, families with `GRO` group names, mesh-level metadata (`mesh_name`/`description`/`unit_time`/`unit_coords`/`point_tag_groups`/`cell_tag_groups`, via `MedInfo`), node-orientation permutations, and `POG`/`POG2` ragged polygons — and `meshioplusplus.med.read`/`write` use it by default. **v9.6.0 promoted MED into the named-regions Phase 1 list** (see the "Named regions" entry above and [`doc/formats/med.md`](doc/formats/med.md#named-regions)): `med_attach_point_regions`/`med_attach_cell_regions` (`formats/med.cpp`) derive one `Region` per group *name* from the same family tables `MedInfo` already carries, alongside — not instead of — `point_tags`/`cell_tags`, so this needed no `MedInfo` schema change and no binding change at all (`py_regions_to_mesh`/`regions_to_py` in `np_conversions.hpp` already carry `.regions` for every format, MED included). On write, `med_point_regions_to_tags`/`med_cell_regions_to_tags` synthesize families from `Point`/`Cell` regions — one family per unique combination of region names, node ids positive from `+1`/element ids negative from `-1`, a C++ port of `_ensure_med_families`'s algorithm matched step for step so the two produce byte-identical `FAS`/`FAM` output — but **only when the mesh carries no native `point_tags`/`cell_tags` of its own** (native data always wins, so a MED→MED round trip is unaffected). This closes a real pre-v9.6.0 bug: a regions-only mesh (e.g. read from Abaqus, no native MED tags) written through the C++ path used to produce a file with **no** `FAS` groups at all, because nothing about the write ever raised to trigger the Python `_ensure_med_families` bridging — `registry.cpp`'s MED writer entry, which supplies an empty `MedInfo`, now closes that gap for free. `Side` regions have no MED equivalent and are dropped with a `log::warn`. The same release added the optional **`NUM`** global node/element numbering Salome/Code_Aster/Kratos write, carried as `point_data`/`cell_data["med:num"]` (the `gmsh:physical`-style `<format>:<thing>` convention, chosen over `MedInfo` specifically because the flat bindings can see it; cell `NUM` only when *every* block has it, else dropped with a warning rather than fabricated), and an **`INFOS_GENERALES` version check** — `MAJ > 4` raises a named `ReadError`, twinned identically in the C++ reader and `_med.py` so a file rejected by one is rejected by the other rather than silently misread by whichever path runs second. `line4`/`SE4` was also added to the type table (no permutation, 1-D). The Python shim's `read()` no longer re-derives `point_sets`/`cell_sets` from the returned tags after a successful C++ read — `mesh_to_py` already attached the equivalent regions, and re-assigning through the property setters would only discard the `dim`/`tag` `mesh_to_py` set. Since v8.7.0 it also handles **`CHA` fields (point_data/cell_data) for the single-timestep common case**: `write_cha_nodal_field`/`write_cha_cell_field` (`formats/med.cpp`) write one `NOE` (nodal) or one-or-more `MAI.<type>` (per contributing cell block) support subgroup per field, fixed `ndt=1/nor=-1/pdt=0.0`, blank `UNI`/`UNT`/`NOM`, and **no MED-4.1 optimization bitmask** (`LEN`/`LGC`/`LNA`/`LAA` — our own reader never reads it, so its absence costs nothing for a meshio++ round-trip, only for interop with tools like Salome/MEDCoupling that use it) — a deliberate, documented scope cut, not an oversight. `read_cha_fields` is the mirror: it accepts only that exact shape and **declines (throws, deferring the whole file to Python) rather than silently drop information** whenever a field's `UNI`/`UNT` is non-empty or a timestep's `NDT`/`NOR`/`PDT` isn't the write-side default — reading a hand-edited or Python-written file with real units/step metadata and silently reporting `ndt=1` would be a wrong answer, not merely an incomplete one. The **enhanced-feature guard lives in the Python shim (`med/__init__.py`), not the C++ core**: `med:field_units`/`med:step_meta` are Python-only dict-valued `field_data` conventions, and `med_write`'s pybind wrapper always uses `lenient_field_data=true` (silently dropping any non-numeric `field_data` entry before it ever reaches the C++ `Mesh`) precisely *because* of conventions like this — a C++-side `HasFieldData("med:field_units")` check is structurally dead code under every binding, since none of them can construct a dict-valued field_data entry in the first place. The shim also defers when any array name uses the `"Name[idx] - pdt"` multi-timestep encoding `_parse_med_field_name` recognizes (`_names_encode_a_timestep`), which the C++ writer has no notion of and would otherwise write as unrelated separate fields instead of grouping them. It still **raises** (→ Python fallback) for what remains out of scope: those three enhanced-field cases, the `gmsh:physical`→family bridging, non-default profiles/ELGA (ELNO/ELGA is structurally unreachable regardless — the uniform mesh API's `cell_data` is always `(n,)`/`(n,k)`, never a 3-D per-node-within-cell shape), and multi-mesh files (`read_med_multi`/`write_med_multi` are always Python). The C++ MED reader iterates `MAI` cell blocks in HDF5 **creation order** (`group_links_crt`, matching h5py `track_order`) since block order aligns cell_data/cell_sets — note this means a multi-block mesh's block order does **not** necessarily survive a MED round-trip (blocks come back in whatever order the file's own `MAI` group lists them), so field values must always be looked up by **cell type**, never a fixed block index, both in the writer (`meshio_to_med()` per block) and any test of it; the pure-Python fallback reader still reconstructs `point_sets`/`cell_sets` from families via `_families_to_point_sets`/`_families_to_cell_sets` (the C++-path shim does not, per the regions paragraph above). See [`doc/formats/med.md`](doc/formats/med.md#quirks-limitations).
