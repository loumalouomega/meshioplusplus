# Changelog

This document records every released version of meshio++ — new formats, new operations,
notable enhancements, and breaking changes. Breaking changes are called out explicitly as
**Breaking:**; everything else is additive unless stated otherwise.

**Keep this file current: add an entry in the same change as every version bump.** See the
"Version bumps" section of `AGENTS.md`.

## Unreleased

- **Added:** OpenUSD face `GeomSubset`s are read as cell regions and a surface mesh's cell regions are written as `GeomSubset`s (roadmap 2.3.9.9).


- **Added:** `registry_write_ex` writes a gzipped OpenFOAM case when the codec is `zlib` (and plain when it is `none`), so the C API and every binding reach `writeCompression on` output (roadmap 2.3.5.3).


- **Added:** Gmsh `$GhostElements` is read as `cell_data["partition:ghost"]` (4.x ASCII, both engines; roadmap 2.3.6.2).


- **Added:** `.pvts`, `.pvtr` and `.pvti` readers (Python): the parallel indexes of structured pieces, each placed by its `Extent` in `WholeExtent` so shared planes are one layer of points, one `piece_<i>` region per piece (roadmap 2.3.7.3; the C++ reader remains).


The first steps of the [freeform fit CAD plan](doc/fit_cad_freeform_plan.md). Everything is off by default, so no default output changes: the `fit_cad` golden digests are as they were.

- **OpenFOAM lagrangian clouds** (roadmap 2.3.5.2, [OpenFOAM](doc/formats/openfoam.md#lagrangian-clouds)): `openfoam.read(case, cloud="name")` (C++ `read_openfoam_cloud`) reads a cloud's particles as `vertex` cells with their ASCII per-particle fields as `point_data`; barycentric-only clouds are refused. Core only.
- **MED series writer** (roadmap 2.3.4.1, [MED](doc/formats/med.md#writing-a-series), [sequences](doc/sequences.md)): `meshioplusplus.med.SeriesWriter` and the C++ `MedSeriesWriter` write the mesh with the first step and one more step group per field for each later step, so a sequence can be written to `.med`. Both engines.
- **Tecplot series writer** (roadmap 2.3.4.3, [Tecplot](doc/formats/tecplot.md#writing-a-series), [sequences](doc/sequences.md)): `meshioplusplus.tecplot.SeriesWriter` and the C++ `TecplotSeriesWriter` write a transient ASCII file, each step's zones with `STRANDID = 1` and its `SOLUTIONTIME`, so a sequence can be written to `.dat`/`.tec`. Both engines; `.plt` is refused.
- **CGNS series writer** (roadmap 2.3.4.2, [CGNS](doc/formats/cgns.md#writing-a-series), [sequences](doc/sequences.md)): `meshioplusplus.cgns.SeriesWriter` and the C++ `CgnsSeriesWriter` write one `FlowSolution_t` per step with `BaseIterativeData_t`/`ZoneIterativeData_t`, so a sequence can be written to `.cgns`; a step carries point data or cell data, not both. Both engines.
- **CGNS structured zones, interfaces, rind, several zones and bases** (roadmap 2.3.1.2 to 2.3.1.5, [CGNS](doc/formats/cgns.md#structured-zones-interfaces-and-bases)): a `Structured` zone is read as its lattice (the shared `detail::lattice_cells` / `_grid.lattice_cells`), `GridConnectivity1to1_t` as `cgns:interface:<name>` point regions, `Rind_t` planes of a solution are stripped, the solutions, regions, BCs and field data of every zone are read (arrays joined over the zones with `NaN` where a zone lacks one), and `cgns.read(..., base=)` chooses a base (C++ `read_cgns_base`). Both engines.
- **Gmsh element-node data and kept sections** (roadmap 2.3.6, [Gmsh](doc/formats/gmsh.md#element-node-data-and-kept-sections)): `$ElementNodeData` is read and written as `cell_data["gmsh:element_node:<name>"]` with its component count in `field_data`, in 2.2, 4.0 and 4.1, ASCII and binary, by both engines; `$GhostElements`, `$InterpolationScheme`, `$PartitionedEntities` and `$Parametrizations` of an ASCII file are kept verbatim in `field_data["gmsh:section:<Name>"]` and written back.
- **EnSight series writer** (roadmap 2.3.3.4 and 2.3.4.5, [EnSight](doc/formats/ensight.md#writing-a-series), [sequences](doc/sequences.md)): `meshioplusplus.ensight.SeriesWriter` and the C++ `EnsightSeriesWriter` write a transient case, the geometry once, one numbered variable file per step and a `TIME` section in the case file, so a sequence can be written to `.case`, in both engines.
- **Gmsh series writer** (roadmap 2.3.4.4, [Gmsh](doc/formats/gmsh.md#writing-a-series), [sequences](doc/sequences.md)): `meshioplusplus.gmsh.SeriesWriter` and the C++ `GmshSeriesWriter` write the mesh with the first step and each later step's `$NodeData` and `$ElementData` sections (2.2 or 4.1, ASCII or binary) into one file, the step's time and position in the sections' tags, so a sequence can be written to `.msh`. A plain write is unchanged.
- **UNV series writer** (roadmap 2.3.4.6, [UNV](doc/formats/unv.md#writing-a-series), [sequences](doc/sequences.md)): `meshioplusplus.unv.SeriesWriter` and the C++ `UnvSeriesWriter` write the mesh with the first step and each later step's results datasets into one file, so a sequence can be written to `.unv`; both engines write the same bytes. A pure ABI addition (a new class in an existing header, in the unreleased ABI 46).
- **VTKHDF `ImageData`** (roadmap 2.3.7.1, [VTKHDF](doc/formats/vtkhdf.md)): a static `ImageData` file is read as its lattice (points, hexahedra, quads or lines, point and cell data) by both engines. `ensight`'s structured-block lattice cells moved to `_grid.lattice_cells`, shared with it.
- **CGNS boundary conditions** (roadmap 2.3.1.1, [CGNS](doc/formats/cgns.md)): `ZoneBC_t/BC_t` nodes of a single-zone file are read as regions named after the BC or its `FamilyName`, with the BC type in `field_data["cgns:bc_type:<region>"]`, in both engines. They are written back as `ZoneSubRegion_t`, not yet as `BC_t`.
- **OpenFOAM sets** (roadmap 2.3.5.1, [OpenFOAM](doc/formats/openfoam.md)): `polyMesh/sets/` (`cellSet`, `faceSet`, `pointSet`) is read into regions named `set:<name>` and written back from them, in the core.
- **Exodus II** (roadmap 2.3.2.1 to 2.3.2.3 and 2.3.2.5, [Exodus](doc/formats/exodus.md)): global variables are read into and written from `field_data["exodus:global:<name>"]` in both engines; node and side set variables (`exodus:nset:`/`exodus:sset:`), `NSIDED` polygon blocks and `NFACED` polyhedron blocks are read and written by both engines (an `NFACED` block used to be dropped silently); `mesh.info` is written back as `info_records`.
- **EnSight Gold depth** (roadmap 2.3.3.1 to 2.3.3.3, [EnSight](doc/formats/ensight.md)): a mesh whose cells carry `ensight:part` is written as one part per value (geometry and variable files, ASCII and binary); a wildcard `model:` line resolves at the selected `time_step`, and `change_coords_only` reads the connectivity from the first file and the coordinates from the step's; `block`, `block uniform` and `block rectilinear` parts (with `iblanked`, kept as `point_data["ensight:iblank"]`) are expanded to points and a lattice of hexahedra, quads or lines. All in both engines.
- **STL solids** (roadmap 2.3.9.2, [STL](doc/formats/stl.md)): several `solid` records of an ASCII file are read as cell regions named after them, and an ASCII mesh with two or more cell regions is written as that many solids, in both engines.
- **PLY** (roadmap 2.3.9.4, [PLY](doc/formats/ply.md)): a list-typed vertex property is refused by name in both engines (the Python twin raised a bare `KeyError`, against what the page said), and a point index above 2³¹ − 1 is refused on write instead of wrapping to int32.
- **Medit normals** (roadmap 2.3.9.5, [Medit](doc/formats/medit.md)): ASCII `Normals` and `NormalAtVertices` are read into `point_data["medit:normal"]` (`NaN` where a vertex has none) and written back, in both engines; the binary `.meshb` path still skips them.
- **OBJ normal indices** (roadmap 2.3.9.3, [OBJ](doc/formats/obj.md)): the per-corner `vn` index of `f v//vn` and `f v/vt/vn` is read, and a point whose corners name different normals is split on the distinct `(vt, vn)` pairs, with `obj:parent_point`, in both engines. Before, the index was dropped and normals that were not one per vertex were scrambled.
- **STL attribute word** (roadmap 2.3.9.2, [STL](doc/formats/stl.md)): the two attribute bytes of a binary facet are read into `cell_data["stl:attribute"]` (`uint16`) when any is non-zero and written back, in both engines. ASCII `solid` names stay open.
- **Add-on wheels carry their licence texts** (roadmap 4.8.1.1, [binary licences](LICENSE-BINARIES.md)): `meshioplusplus-mmg` ships `COPYING.LESSER` (LGPL-3.0) and `COPYING` (GPL-3.0), `meshioplusplus-netgen` ships `COPYING.LESSER` (LGPL-2.1), and both ship `LICENSE` and a `RELINKING.md` naming the pinned source, the build recipe and how to replace the shared library, through `license-files`. The wheel smoke tests check they are installed.
- **Ansys `.rst`**: a record flagged both bit-sparse and windowed-sparse is refused by name in both engines ([Ansys `.rst`](doc/formats/ansys_rst.md#not-read)); it was decoded silently as bit-sparse, with wrong values.
- **`fit_cad` validation report** ([fit CAD](doc/fit_cad.md#validation-report)): `validation_report` measures the built solid against the skin in its NURBS form, the same way for both backends: each face sampled inside its trims (CAD to mesh), the skin's vertices and facet centres projected onto the faces (mesh to CAD), as maxima and 95th and 99th percentiles, the facet-normal deviation at the foot points, and, with OpenCASCADE and a STEP file, the file read back, checked, tested for closed shells and its volume compared; per face as the new `fit_cad:face_deviation` field data. `validation_acceptance` holds every adaptive, network and general freeform face to the sampled distance and a 30-degree normal test before accepting it. Python, both CLIs (`--validation-report`, `--validation-acceptance`), the pipeline (`ValidationReport`, `ValidationAcceptance`), the MCP tool, C (`mio_fit_cad4`, `mio_fit_cad_report_ex4`; `mio_fit_cad_opts_ex2` keeps its size), Fortran, Julia, R, Octave and WASM.
- **`fit_cad` fit schedule and objective** ([fit CAD](doc/fit_cad.md#the-fit-s-schedule-and-objective)): `freeform_fit_schedule="continuation"` starts the adaptive and general freeform faces' B-spline fit smooth and lowers the thin-plate weight as parameter correction stalls, places new knots at the residual-weighted median of a span's bad samples and removes the knots the target does not need; `freeform_objective` picks point distance only (`"pdm"`), a tangent-distance step (`"tdm"`) or a curvature-based squared-distance step (`"sdm"`, after Wang, Pottmann and Liu 2006, extended to surfaces) first in every iteration. Both default to the fit as before; every binding, both CLIs (`--freeform-fit-schedule`, `--freeform-objective`), the pipeline (`FreeformFitSchedule`, `FreeformObjective`) and MCP. `FitCadOptions` 288 -> 296 bytes under the same ABI 46.
- **`fit_cad` kinematic surfaces** ([fit CAD](doc/fit_cad.md#kinematic-surfaces)): `kinematic_surfaces` first tries every patch no primitive explains as a surface of linear extrusion (new `fit_cad:type` 11), of revolution (12) or a helical surface (8), the sweep of a fitted cubic B-spline profile, on both backends; a band closed round is cut into two discs. The extrusion and the revolution are exact: the native STEP writer writes `SURFACE_OF_LINEAR_EXTRUSION` and `SURFACE_OF_REVOLUTION`, the NURBS B-rep (and Kratos CAD JSON) of a revolution is the exact rational patch (`brep_nurbs_face` kind 12), and OpenCASCADE builds `Geom_SurfaceOfLinearExtrusion` and the rational B-spline of the surface of revolution. The lobed prism and the wavy wall of the KPI set lose every facet on both backends; the native helical sweep falls from 0.60 to 0.25 of its area facets. Off by default; the report gains `num_extrusion`, `num_revolution` and `num_kinematic_helical` (C: `mio_fit_cad_opts_ex2.kinematic_surfaces` and `mio_fit_cad_report_ex4`'s new counts, both structs keeping their sizes), every binding, both CLIs (`--kinematic-surfaces`), the pipeline (`KinematicSurfaces`), MCP and the KPI harness. The validation report samples a face with more knot spans than its grid at one node per span (a thread's many turns). `FitCadOptions` 296 -> 304 bytes under the same ABI 46.
- **`fit_cad` coupled G1 solve** ([fit CAD](doc/fit_cad.md#the-coupled-g1-solve)): `freeform_g1_solve="coupled"` fits each patch network region as one least-squares system per step, every interior pole and every free pole of the shared edge curves unknown (the patches' boundary rows mapped linearly onto their curves' poles, so G0 stays exact), the G1 rows aiming both sides at the plane between them, the sweeps polishing after; a region keeps it unless it covers less or leaves a larger angle. The hood's largest G1 angle falls from 2.87 to 0.28 degrees, the monkey saddle's from 1.18 to 0.37 and the cube cages' away from their extraordinary vertices to within 1 degree; a region whose sweeps already meet the target skips it. Through OpenCASCADE the wavy wall of `wavy_capped` loses three patches to facets (0.0047 to 0.047 of its area). Outside the legacy mode the report now splits the largest angle into `max_g1_angle_away_deg` and `max_g1_angle_at_ev_deg` (tensor-product patches cannot be G1 at a vertex of valence other than four) and counts `num_coupled_regions`; every binding, both CLIs (`--freeform-g1-solve`), the pipeline (`FreeformG1Solve`), MCP and the KPI harness. `FitCadOptions` keeps 304 bytes (the new member in its tail padding); C: `mio_fit_cad_opts_ex2.freeform_g1_solve` and three `mio_fit_cad_report_ex4` fields from the reserved tails.
- **`fit_cad` KPI harness** ([benchmarks](doc/benchmarks.md#fit-cad-freeform-kpis)): `meshioplusplus_fit_cad_kpi` (built with the tests) runs the golden, freeform and new kinematic fixtures (an extruded lobe, a revolved wave, a helical sweep) in every freeform mode with both backends, and `tools/fit_cad_kpi.py` writes `benchmark/fit_cad_kpi.csv`, regenerates the KPI tables and compares two runs.
- **Shared utilities**: `GeometryUtils::PointInPolygon2D` (the even-odd test `surface_validate` kept privately), `detail::surface_normal_deviation_deg`, and `detail/brep_deviation`.
- **ABI:** `MESHIOPLUSPLUS_ABI_VERSION` 45 -> 46 (Tier A): `FitCadOptions` takes `mValidationReport` and `mValidationAcceptance` in its tail padding (still 288 bytes), `FitCadResult` appends the validation report, and `CadKernelProvider` appends `mCheckStep` (160 -> 192 bytes) returning the new `CadStepCheck`.

## v20.1.0 (2026-11-11)

A minor release: `adapt_volume`, a native, MIT-licensed, dependency-free tetrahedral remesher that coarsens and improves a tetrahedral mesh towards a graded size field under a Hausdorff bound, and an opt-in `octree_mesh` post-stage that runs it. Everything is additive and `octree_mesh`'s output is unchanged unless `post_adapt` is set. **C++ ABI 45** ([ABI](doc/abi.md)): `OctreeMeshOptions` and `OctreeMeshResult` grew, so C++ consumers recompile against the new headers; the C option structs keep their size (the new fields take their reserved tails), so the C, Fortran, Julia, R, Octave, WASM and Python callers are unaffected.

- **`adapt_volume`: isotropic, size-field-driven tetrahedral remeshing** ([adapt_volume](doc/adapt_volume.md)): collapses, splits, swaps and smooths a valid tetrahedral mesh (typically `octree_mesh`'s graded output) towards a graded size field, keeping the boundary within a Hausdorff bound of the input's, its corners, ridges and patches, the materials and regions and the side tags. Every edit is guarded by the link condition, exact `orient3d`, a quality floor, a normal bound and a two-sided sampled Hausdorff envelope, and the output is byte-identical across thread counts. `boundary_sizing="geometry"` sizes the boundary by curvature, as MMG does, so flat and gently curved boundaries coarsen too. Native, MIT, no new dependency, implemented from the published papers (Dapogny, Dobrzynski and Frey 2014; Klingner and Shewchuk 2007; Freitag and Ollivier-Gooch 1997; Hu et al. 2020; Jiang et al. 2022). Every surface: Python, both CLIs (`adapt-volume`), the `AdaptVolume` pipeline step, C (`mio_adapt_volume`), Fortran, Julia, R, Octave/MATLAB, WASM (`adaptVolume`) and MCP. `tools/adapt_volume_bench.py` measures it against `octree_mesh` and, where found, `mmg3d`; the example `71_adapt_volume.ipynb` walks through it. **ABI 45.**
- **`octree_mesh(post_adapt=True)`**: the tetrahedral output through `adapt_volume` as an opt-in post-stage (`adapt_*` passthroughs, an `adapt` stage in the timings, an `adapt` report); off by default, so no existing output changes. `OctreeMeshOptions` grows 376 -> 576 bytes (**ABI 45**); `mio_octree_mesh_opts` takes `post_adapt` and `adapt` from its reserved tail.
- **Shared kernels**: `optimize_volume`'s flips, edge and multi-face removal, guarded ODT and worst-cell smoothing move verbatim to the core-private `detail/tet_flips` (its golden and `bench_ops --hash` digests unchanged; its tier S row counts 2.6% fewer instructions, re-recorded in `benchmark/instructions_S.csv`); `detail/fem_kernels.hpp` gains `tet_min_dihedral`, `tet_dihedral_range`, `tet_mean_ratio` and `tet_amips`; `detail/size_field_utils` and `detail/tet_remesh` are new.
- **Fuzzing**: a new operation target, `adapt_volume`, whose first campaign found a flat tetrahedron the shared interior smoothing could invert (now repaired by exact orientation) and tangled input (now refused by name); both replay under `tests/fuzz/regressions/op_adapt_volume/`.

## v20.0.0 (2026-11-10)

A major release: the ParaView plugin grows from a reader and a writer into a full integration (a payload layer, polyhedra, time steps, array selection, named regions, the writer's inputs and options, the Pipeline filter and 29 dedicated filters, and a self-contained bundle per ParaView Python), and a linear `wedge` is no longer written to VTK inside out. Scan metrology and reverse engineering land in the roadmap's section 7: measuring and alignment, deviation analysis, chained sections, curves and DXF, scan editing, profile solids, the closed CAD loop, workflow prompts and a measuring mode in the browser viewer. The roadmap's code-duplication and SonarCloud passes close, and they change installed C++ headers. **Breaking:** files meshio++ wrote before this release carry inverted linear wedges (`flip_normals` or a rewrite repairs them), and C++ callers of the headers changed by the duplication pass must adapt (see the entries below). **ABI 44 (Tier A and B):** rebuild native consumers.

- **Fix: VTU files of cells only, and base64 headers encoded with their data** ([#229](https://github.com/loumalouomega/meshioplusplus/issues/229), [VTU](doc/formats/vtu.md#quirks-limitations)): a file whose pieces declare `NumberOfPoints="0"` and have no `<Points>` (the boundary groups GiD writes beside its main VTK export) reads to its cells and cell data with an empty `(0, 3)` `points` in both engines; the Python reader raised a bare `ReadError` and the C++ one returned no points array. An inline `format="binary"` array reads whether its header and data were base64-encoded as one stream (GiD) or apart (VTK): both engines misread a compressed array written as one stream, and the C++ reader an uncompressed one written in VTK's two chunks. The Python reader's inline arrays now go through the appended decoder, which already took both. The report's `Incorrect padding` came from 10.21.1; appended data has read either layout since v16.6.0.
- **Fix: a cgnslib build reads every CGNS zone** (roadmap 2.3.1.1, [CGNS](doc/formats/cgns.md#quirks-limitations)): `read_cgns_mll`, which `read_cgns` tries first when built with `MESHIOPLUSPLUS_WITH_CGNSLIB`, read the first zone of a multi-zone file and dropped the rest with a warning, while the default HDF5 reader concatenated them all. It now reads every zone the same way, in zone-name order, with the same multi-zone rules (solutions, regions and field data are read for a single-zone file only), and `read_cgns_mll_metadata` sums every zone. Zones with different coordinate counts are padded with zeros in all three readers, where the HDF5 reader copied them misaligned.
- **Compressed OpenFOAM cases** (roadmap 2.3.5.1, [OpenFOAM](doc/formats/openfoam.md#compressed-cases)): both readers take a case run with `writeCompression on` (`points.gz`, `faces.gz`, gzipped field files), and `meshioplusplus.openfoam.write(..., compression="gzip")` (C++: `OpenFoamWriteOptions::mCompress`, ABI 44) writes one; writing either form removes the other. The gzip writer libMesh used is now the shared, core-private `detail::gzip_compress`.
- **Fix: the source distribution is 12.6 MB again**: the v19.0.0 sdist exceeded PyPI's 100 MB per-file limit, so its upload failed. Examples, docs, benchmarks and test data are left out of it.
- **CI: the ParaView jobs run on `ubuntu-24.04`** and install the GL libraries Kitware's `pvpython` links (`libglapi-mesa`, `libopengl0`); the plugin probes name the file format they write and read, because a bare `.msh` is Fluent's on some builds and Gmsh's on others, and the Julia silhouette and segmentation tests no longer use a mesh after closing it.
- **ParaView plugin: a self-contained bundle per ParaView Python** (roadmap 6.11, [ParaView plugin](doc/paraview_plugin.md#the-self-contained-bundle)): `src/paraview/build_bundle.py` zips the plugin beside a `site-packages` folder with meshio++, its add-ons and `rich` unpacked (numpy left to ParaView), which the plugin puts on `sys.path`; a release attaches one per platform and Python 3.10–3.13 (`wheels.yml`'s `paraview_bundle`), and CI's `paraview-bundle` job loads one in Kitware's ParaView 5.13 and 6.0 Linux binaries without pip.
- **ParaView plugin: dedicated filters** (roadmap 6.9, [ParaView plugin](doc/paraview_plugin.md#dedicated-filters)): 23 filters under *Filters → meshio++*, one per pipeline step ParaView has no equivalent for (`remesh`, `remesh_volume`, `tetrahedralize`, `octree_mesh`, `boundary_layer`, `optimize_volume`, `decimate_volume`, `refine`, `agglomerate`, `tet_to_poly`, `poly_to_tet`, the adaptation chain, `repair`, `find_intersections`, `thickness`, `check_conformity`, `select`, `region_adjacency`, `find_interface`, `reorder`), generated from the step spec with a typed property per key and an ExtraKeys JSON; and Partition (with ghost layers), Conservative Interpolate, Shrinkwrap, Undo Green (two inputs), Match Periodic Nodes and Contact Pairs over their functions. `tools/gen_pipeline_table.py` also writes `_pipeline_table.KEY_DEFAULTS`, each step's typed keys with their kinds and defaults. `tests/python/test_paraview_plugin_algorithms.py` runs the plugin's algorithms on the PyPI `vtk` wheel.
- **Fixed-order high cells written to VTK** (roadmap 6.3.2, [VTU](doc/formats/vtu.md#cell-types), [cell types](doc/cell_types.md#higher-order-fixed-types)): `triangle10` … `triangle66`, `quad16` … `quad121`, `tetra20` … `tetra286`, `line5` … `line11`, and `wedge40` … `wedge550` and `hexahedron64` … `hexahedron1000` to order 9, which the VTU, legacy VTK, VTKHDF and VTX writers raised on (both engines), are written as VTK Lagrange cells with their Gmsh node order permuted into VTK's, and so reach ParaView through the plugin. The order is generated (`_lagrange.gmsh_lattice`, `gmsh_to_vtk_order`, and their C++ twins in the private `formats/lagrange_common.hpp`; the writers share the private `detail/vtk_write_cell.hpp`) and held to Gmsh 4.15's own node lists by digest (`tools/gen_gmsh_node_order_digests.py`) and to VTK's measure of each written cell. A higher-order hexahedron of this kind also sets VTU 2.2, VTK 9.1's edge order, which the version checks of both engines tested by type name.
- **ParaView plugin: the meshio++ Pipeline filter** (roadmap 6.8, [ParaView plugin](doc/paraview_plugin.md#the-meshio-pipeline-filter)): one filter applies the settings pipeline's `Operations` list (JSON, edited in a multi-line field) to its input through `apply_operations`, so every pipeline operation is reachable in ParaView; the report is the output's `meshioplusplus:report` field array.
- **ParaView plugin: the writer's inputs and options** (roadmap 6.7, [ParaView plugin](doc/paraview_plugin.md#writer-properties)): the writer takes any dataset (through `vtkAppendFilter`) and composite ones, whose leaves are merged with `merge` and become cell regions named after their blocks; and gains **FileFormat**, **Encoding**, **Codec** and **FloatFormat** (the settings pipeline's `Output` mapping over `mcp._tools._variant_kwargs`) and **Provenance**, on by default, which names ParaView and its version as the source.
- **ParaView plugin: named regions** (roadmap 6.6, [ParaView plugin](doc/paraview_plugin.md#named-regions)): point and cell regions cross as `region:<name>` masks with the `meshioplusplus:regions` sidecar, side regions as the VTU convention's `region:side:<name>` field arrays, and the writer rebuilds all of them (and the field arrays of a meshio++ VTU ParaView read itself); the reader dropped every region before. **RegionsAsBlocks** outputs a `vtkPartitionedDataSetCollection` with a `vtkDataAssembly`, one block per region, from `split(by="regions")` and `facet_nodes`. `_to_vtk_payload` takes `carry_sides` for a caller that carries side regions itself.
- **ParaView plugin: read options and add-on status** (roadmap 6.5, [ParaView plugin](doc/paraview_plugin.md#reader-properties)): point and cell array checkboxes filled from `read_metadata` and passed as `arrays=`, **PointsOnly**, **Piece**, **Ghosts**, the STEP and IGES **Deflection** and **AngularDeflection**, and an information-only **AddOns** list (`occt`, `netgen`, `mmg`), as the Blender import's toggles do.
- **ParaView plugin: time steps in and out** (roadmap 6.4, [ParaView plugin](doc/paraview_plugin.md#time-steps)): the reader publishes the steps of a multi-step file (`read_metadata`'s `time_values`) or of a file series (a repeatable `FileName`, timed as `TimeSeries` times one) and reads the step at the time ParaView asks for; the plan is cached per file identity and a **Refresh** button drops it. The writer's **WriteTimeSteps** writes every step of its input, into one file for a series format and one file per step otherwise. ParaView saw one step of every file before.
- **ParaView plugin: Lagrange and Bézier degrees and weights** (roadmap 6.3.1, [ParaView plugin](doc/paraview_plugin.md#what-crosses-into-paraview)): a `HigherOrderDegrees` cell array and a `RationalWeights` point array are set as VTK's active attributes of those names, where its Lagrange and Bézier cells read them; the plugin passed them as plain arrays, which VTK does not consult.
- **Polyhedra reach ParaView and PyVista** (roadmap 6.2, [ParaView plugin](doc/paraview_plugin.md#what-crosses-into-paraview), [interop](doc/interop.md)): the VTK payload no longer drops `polyhedron<n>` blocks.
